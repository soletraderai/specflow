Specflow v2

Global plugin, local memory, adaptive output.

A production-grade product workflow plugin. Installed once globally; behaves like a different plugin in every repo it touches.

Vision & problem

Specflow is installed once globally and behaves like a different plugin in every repo it touches. Each project accumulates its own constitution, profiles, agents, decisions, and task history — and uses that memory to make every subsequent piece of work smarter than the last.

The problem v1 had

v1 is a templated workflow plugin: it scaffolds folders, drives interviews, and produces PRDs / tasks / tests. It doesn't remember anything. There's no per-project memory loop, no visibility into which agents a project has access to, no way to refresh an aged installation without nuking customisation, and no orchestration layer between "task created" and "test written." A project that ran specflow six months ago is no smarter today than the day it started.

What v2 adds

Per-repo adaptivity

Plugin is global; every project's state, memory, and behavior lives in that repo and stays in that repo.

Self-learning memory

Every completed task feeds a decision log + task history that future tasks read from.

Agent visibility

Browsable, indexed per-repo agent registry — standards always present, specialists matched to the stack.

Refreshable

A project can be brought up-to-date with the current plugin without losing customisation (specflow:upgrade).

Self-documenting

A complete worked example ships with the plugin so users see the full shape before committing.

Environment-aware

Specflow inventories what's available (CLIs, MCPs, plugins, agents) and feeds that knowledge to skills so outputs match what the system can actually do.

Architecture & layout

One global plugin, per-repo state. Code lives in ~/.claude/plugins/specflow/; everything else lives inside each project at docs/specflow/, committed.

Core principles

Four non-negotiable principles loaded into the system prompt of every specflow skill. Rules of rules — they govern how the AI behaves on every piece of work, distinct from the project rules registry which governs what the AI accepts in a particular codebase.

Principle 1

Think before coding

Don't assume. Don't hide confusion. Surface tradeoffs. State assumptions explicitly. Present multiple interpretations when ambiguity exists. Push back when a simpler approach exists. Stop when confused — name what's unclear.

Principle 2

Simplicity first

Minimum code that solves the problem. Nothing speculative. No features beyond what was asked. No abstractions for single-use code. No flexibility or configurability that wasn't requested. No error handling for impossible scenarios.

Two AI-specific traps:

  • Explicit beats clever — a one-liner that takes 30 seconds to understand is worse than three explicit lines. The training data rewards "elegant" dense abstractions; resist the bias.
  • Local reasoning beats cross-file elegance — if understanding a single file requires holding three others in your head, the abstraction is wrong. AI can hold many files in context simultaneously; humans can't. Optimise for the human reader.
Principle 3

Surgical changes

Touch only what you must. Don't improve adjacent code, comments, or formatting. Don't refactor what isn't broken. Match existing style. Every changed line must trace directly to the user's request.

Quality nuance: if you spot something wrong outside the work item's scope, do not fix it inline. Auto-create a misc-task capturing the observation and the why, so quality concerns don't fall through cracks while the change set stays clean.

Principle 4

Goal-driven execution

Every skill that produces output declares verify steps inline (1. Step → verify: check). Loop until verified. Strong success criteria let the LLM iterate independently; weak ones force constant clarification.

Verification is not a terminal phase. It runs after every step, not at the end. Every skill SKILL.md has a binary eval: field describing the success check. No skill ships without one.

Agent ecosystem

Specflow ships two categories of standard agents, copied into every new project at setup. Plus specialised agents matched to the project's stack.

Lifecycle agents — standard/lifecycle/

Cover the plan / challenge / confirm moments of any non-trivial work item. Set kept deliberately small — additions only when a clearly distinct lifecycle moment emerges that none of the three covers.

Orchestrator

Coordinates multi-agent workflows; holds the plan; delegates to specialists. Writes the closing decision entry in every multi-agent debate manifest.

Lifecycle moment: plan + final-call

Devil's Advocate

Challenges decisions in-flight — surfaces blind spots in PRDs, scope ambiguity in tasks, architectural gotchas during development.

Lifecycle moment: challenge

Verifier

Confirms work meets the bar at the end of any task. Reads the original requirement and the produced output; verifies they match.

Lifecycle moment: confirm

Principle reviewers — standard/principles/

Fire as parallel reviewers in the multi-agent debate manifest. One reviewer per core principle. Set scales 1:1 with CORE_PRINCIPLES.md — adding a fifth principle requires adding a fifth reviewer.

Simplicity Reviewer

Enforces Simplicity First including the AI-specific sub-tests (explicit beats clever, local reasoning beats cross-file elegance). Asks "is there a simpler way?" first at every gate.

Common findings: premature abstraction, speculative configurability, defensive error handling, clever-over-explicit code.

Surgical Reviewer

Enforces Surgical Changes; flags adjacent-fix creep, missed misc-task creation when out-of-scope rule violations were spotted, and lines touched that don't trace to the work item.

Common findings: "while I was here" edits, style normalisation creep, refactor smuggling.

Think-Before-Coding Reviewer

Enforces Think Before Coding; flags hidden assumptions, missing tradeoff articulation, premature commitment to one approach when alternatives weren't articulated.

Particularly load-bearing at Gates 1 (grill), 2 (PRD), 4 (plan).

Goal-Driven Reviewer

Enforces Goal-Driven Execution; verifies inline verify-steps are present, that they're binary (pass/fail not "looks fine"), and that the skill's eval: field actually exercises the produced output.

Particularly load-bearing at Gates 3 (tasks), 5 (code), 6 (tests).

Specialised agents — specialised/

Drawn from installed marketplaces (whobson, agent-teams, codex, etc.) and matched to the project's stack at setup or via specflow:agent. React project → frontend-developer; Postgres-heavy → database-architect; security-sensitive → security-auditor. Snapshotted into the repo so they're reviewable and don't drift when upstream changes.

End-to-end workflow

The intended lifecycle of a feature, from blank slate to verified delivery.

1

specflow:setup — once per project

Creates docs/specflow/admin/, runs profile interview, seeds rules registry, inventories environment (Playwright hard-required, Codex optional). Hard-checks fail loud; soft requirements log and degrade gracefully.

2

specflow:prime — context priming

Primes the conversation with the relevant codebase context for the upcoming feature. Reads environment.json so primed context can include relevant agent prompts when downstream skills will hand off.

3

specflow:prd — multi-phase PRD creation

User-facing entry point. Five phases: A writes the interview's preamble (original request + codebase context), then articulates a Goal — Outcome / Audience / Success-looks-like / Driving value / Out-of-scope-at-goal-level — and gets the user's explicit confirmation before grilling starts (the precedent everything downstream anchors to); B invokes /grill as a sub-skill which interrogates one question at a time, grounding every recommended answer in the confirmed goal, re-evaluating after each answer, appending rounds to NNN-{slug}-interview.md; C synthesises the PRD body from goal + resolved assumptions into NNN-{slug}-prd.md (Vision section traces directly to the goal); D auto-renders NNN-{slug}-prd.html with a header link to the interview; E fires Gate 2 multi-agent debate manifest into features/NNN-{slug}/debate-log/prd-gate2/ with the goal as primary review lens.

4

specflow:task — task generation + Gate 3

Generates NNN-{slug}-tasks.md with coverage matrix (every PRD requirement → tasks satisfying it) and 2-sentence intent summaries in chat. Gate 3 multi-agent debate manifest fires into features/NNN-{slug}/debate-log/tasks-gate3/; override capture writes to task-history.json for Phase 3 self-learning.

5

specflow:design — optional alignment mockups

Codebase-truth HTML/CSS mockups of current and proposed states (features/NNN-{slug}/design/NNN-{slug}-current.html and NNN-{slug}-proposed.html). Playwright visual diff loop iterates the mockup against the live app. Optional Codex adversarial review at the end of the loop.

6

specflow:linear — task export with bidirectional sync

Exports tasks (or misc-tasks) to Linear. Misc-tasks target the 000-misc-tasks project, auto-created if missing. The Export Map in the source file gets Linear IDs and URLs.

7

specflow:develop — implementation orchestration Phase 2

Lane-based execution: Green (verifiable + low blast + non-confidential) batched and AFK-eligible; Yellow (one axis weak) HITL; Red (high blast or confidential) human-led. Plan emission anchors to PRD requirement. Gates 4 (plan vs PRD anchor) and 5 (code vs plan, cross-provider Codex review) fire as multi-agent debate manifests into features/NNN-{slug}/debate-log/develop-gate{4,5}/.

8

specflow:test — verification cadence

Every PRD acceptance criterion has a test case. Testing is a cadence, not a terminal phase — Playwright loops on every UI change. Verifier confirms the work meets the bar.

9

specflow:complete — retro & memory Phase 3

Captures task outcome (AI assistance level, what worked, what didn't, blast-radius outcome). Writes to task-history.json; significant patterns append to decision-log.md. The compounding loop closes here.

Cross-feature workflows

  • specflow:misc — single-task workflow for bugs and small fixes that don't warrant a PRD. Auto-created on out-of-scope rule violations (Surgical Changes — don't fix inline).
  • specflow:upgrade — refresh an aged installation without losing customisation. Driven by MIGRATIONS.md.
  • specflow:doctor — validate the install (folders, schemas, agent index integrity, environment).
  • specflow:budget — subscription consumption + per-skill context-window cost. Early-warning signal for orchestrator pattern violations.
  • panic & confidence-check — trust-ladder primitives (rewind in-flight changes; declare uncertainty in plain language before risky actions).

Adversarial review chain

Every artefact specflow produces — brief, PRD, tasks, plan, code, tests — runs through an adversarial gate. Six gates phased across Phase 1-3. Each gate uses the multi-agent debate manifest: N reviewers fire findings in parallel; AI responds; reviewers sharpen or accept; Orchestrator writes the closing decision entry.

The six gates

Gate 1 · Phase 1

/grill — AI interrogates the human

This is the alignment review; no separate reviewer needed. Output: rounds appended to NNN-{slug}-interview.md.

Gate 2 · Phase 1

PRD vs brief — auto-fires on specflow:prd

Reviewers compare PRD content against grilling Q&A: did the PRD lose anything, add unstated scope, or paper over an unresolved question? They read the Interview section first.

Gate 3 · Phase 1

Tasks vs PRD — auto-fires on specflow:task

Is every PRD requirement covered? Does any task introduce scope not in the PRD? Are assumptions and acceptance criteria explicit?

Gate 4 · Phase 2

Plan vs tasks + PRD anchor — inside specflow:develop

Does the plan match the task scope? Does it anchor back to the PRD requirement?

Gate 5 · Phase 2

Code vs plan — cross-provider Codex review

Catches what same-provider review misses (Codex finds blind spots; Devil's Advocate runs as backup). Findings Codex catches and the writer missed get promoted to new entries in admin/rules/guidelines.md.

Gate 6 · Phase 3

Tests vs requirements — adversarial coverage review

Coverage review on the test suite for the work item.

The multi-agent debate manifest

Replaces the prior single-reviewer 3-iteration loop with a parallel-reviewer extension of the same shape. Artefacts live inside the feature folder under features/NNN-{slug}/debate-log/{gate}/:

  • manifest.md — collated, human-readable debate transcript (findings + responses + closing).
  • findings/round-{1,2,3}/{reviewer-name}.json — minimal finding files. Severity + evidence + proposed change. Internal reasoning stays in the reviewer's forked context and dies with it.
  • raw/{reviewer-name}.txt (optional) — full reasoning trace, retained only for Phase 3 self-learning archival.

Why feature-scoped paths: when a downstream agent works on the same feature (e.g. specflow:develop after specflow:task), it reads every prior gate's manifest from the same feature folder. No cross-folder chase. The feature folder is a complete record of how the feature was built. Cross-feature gates (misc-task review, /optimize runs) keep the legacy admin/debate-log/ location.

Round structure

  1. Round 1 — Parallel finding fire. Each reviewer runs in a forked sub-agent context. Reads the artefact via command substitution (zero token cost). Writes a minimal finding JSON. Returns one line (the path) to the Orchestrator.
  2. Round 2 — AI responds. Reads every finding via command substitution. For each: accept (will revise) or push back with evidence (code structure, PRD requirement, rule registry entry, decision-log precedent).
  3. Round 3 — Reviewers sharpen or accept. Each reviewer reads the AI's response, writes accept or sharpen. If sharpened, AI revises one more time.
  4. Closer — Orchestrator collates. Reads every round's structured findings, writes the closing decision entry: accepted findings (revised + where), rejected findings (with reasoning), escalated findings (where convergence failed in 3 rounds, surfaced for human decision), sign-off.
Why the manifest beats single-reviewer debate
More eyes catch more failure modes (each principle reviewer is sharp on one concern instead of fuzzy on many). The manifest is queryable — Phase 3 self-learning reads it for patterns: which reviewers' findings are accepted most often (well-calibrated) vs always rejected (over-aggressive prompt to retune). Orchestrator's closing entry replaces "whoever spoke last wins" with an explicit, traceable decision step.

Cost discipline

Round 1 is parallel — N reviewers fire at once, each in its own forked context. Reviewers use cheap models (Haiku for routing, Sonnet for the actual review) except where Codex is available for high-stakes gates (5, 6). 3-round cap retained — more rounds = diminishing returns and drift from original intent.

Per-gate budget target: Orchestrator parent context grows by ≤2K tokens per gate regardless of how many reviewers fire.

Orchestrator pattern

The operational pattern any specflow skill that orchestrates other skills MUST follow. Without this discipline, multi-skill chains leak context: a 5-step orchestration accumulates ~51K tokens by step 5 (raw tool responses, intermediate scrapes, sub-agent reasoning all visible in the parent context). With the pattern, the same chain runs at ~5-8K — roughly 85% reduction.

The three primitives

1. Forked sub-agent contexts

Every sub-skill invocation runs in its own forked context. Tool responses, intermediate reasoning, and raw data stay in the fork. Only the structured result returns to the parent.

2. File handoff between steps

Sub-skills write distilled extraction files to admin/scratch/{orchestration-id}/. A 50KB scrape becomes a 200-token JSON of the fields the next step actually uses.

3. Command substitution

Inject file content via !{cat path/to/file.json}. Substitution happens before the LLM sees the prompt — zero token cost, no tool call cost, no model decision about whether to read.

Calibration anchor

If you're orchestrating ≥3 sub-skills and the parent context is over 15K tokens after step 3, you're leaking. Audit:

  1. Are sub-skills forking? If they're inheriting the parent context, fix that first.
  2. Are tool responses landing in the parent? If yes, the sub-skill isn't returning a structured result — it's returning raw data.
  3. Are scratch files being read with Read tool calls instead of command substitution? Read tool calls accumulate in conversation history.

specflow:budget exposes per-skill token consumption — use it to spot which steps are leaking before the bill arrives.

Skill contracts

Every skill's SKILL.md frontmatter declares requires: and produces: as file-path lists — the lightweight contract orchestrators use to validate handoff between skills:

---
name: specflow:prd
description: Generate a PRD for a feature.
status: v2-enhancement
phase: 1
requires:
  - docs/specflow/admin/profiles.json
  - docs/specflow/admin/CONTEXT.md
produces:
  - docs/specflow/features/{NNN-slug}/NNN-{slug}-interview.md
  - docs/specflow/features/{NNN-slug}/NNN-{slug}-prd.md
  - docs/specflow/features/{NNN-slug}/NNN-{slug}-prd.html
  - docs/specflow/features/{NNN-slug}/debate-log/prd-gate2/manifest.md
eval: interview signed off; PRD body has no orphan requirements; HTML renders with working interview link; Gate 2 manifest closes.
---

File-level contracts are enough for Phase 1's mostly-linear chains. Phase 2 (when specflow:develop orchestrates dynamic compositions) may extend to declared output schemas — but only when there's a concrete second consumer demanding the validation. (Simplicity First.)

Concept · PRD interview file

Every feature folder has a sibling NNN-{slug}-interview.md capturing the chronological audit trail of how the PRD was built — original request, codebase context, grilling Q&A with each answer's reasoning, resolved assumptions, and explicit "topics not discussed". Becomes primary context for downstream reviewers (the multi-agent debate manifest) and for humans returning to a PRD months later asking "why did we decide that?"

Why this exists

  • The PRD body says what was decided. The interview captures how the decision was reached and why each answer became a requirement.
  • Reviewers don't need to reverse-engineer decisions from the PRD body. They read the interview, see the reasoning, and challenge the reasoning directly.
  • Found in real use to be the single highest-leverage addition to the PRD format: review quality jumped because reviewers had transparency into why, not just what.
  • Splitting it out (separate file, not a section in the PRD) keeps the PRD body focused on "what we're building" and the interview focused on "how we got here." Two artefacts, two purposes, both committed.
  • Markdown only — no HTML render. The PRD's HTML render header links to it so reviewers can open both side-by-side.

File structure

# PRD interview — features/NNN-{slug}

## Original request
> [verbatim user ask provided when invoking specflow:prd, in a blockquote]

## Codebase context (pre-grilling)
[What specflow saw before asking anything — files inspected,
 conventions detected, prior PRDs touching adjacent surfaces,
 constraints from CONTEXT.md / rules / decision-log.]

## Goal (confirmed before grilling)
[The AI's articulated understanding of what the user is trying to
 achieve, confirmed by the user before any grilling begins. This is
 the precedent every downstream artefact anchors to.]

- **Outcome:** [what changes for the user / system when this is done]
- **Audience:** [who benefits, by canonical profile name from profiles.json]
- **Success looks like:** [the observable, ideally testable, definition
  of done at the goal level]
- **Driving value:** [why this is worth doing — the pain it removes]

How it's written

  • Phase A of specflow:prd writes the preamble (original request + codebase context), then articulates a goal grounded in that context, gets the user's explicit confirmation, and writes the Goal section. Grilling does NOT start until the goal is confirmed — this is the precedent every downstream artefact anchors to.
  • Phase B — /grill appends each round to the rounds section as the conversation happens, re-evaluating what to ask next after each answer. Every recommended-answer reasoning chain grounds itself in the confirmed goal where applicable.
  • Phase B closes when the user signs off on alignment; the sign-off line is appended.
  • Re-running /grill directly on an existing interview file appends new rounds without overwriting prior ones. The goal section is not re-edited by /grill — only specflow:scope-change updates it (a goal change IS a scope change by definition).

Concept · Rules registry

Every project has a small, slim, live registry of rules the AI must respect. Detection of violations triggers automatic misc-task creation (the AI captures the observation and why, doesn't fix inline — Surgical Changes). The registry self-evolves in Phase 3.

Two tiers + glossary

File What lives here Examples
non-negotiable.md Hard rules. Always-on. Loaded into every skill's system prompt. No hardcoded values; no comments without WHY; never bypass auth; protected paths require Red lane.
guidelines.md Soft rules / project taste. Adaptive. Loaded on-demand for matching paths. Prefer composition over inheritance; tests sit in __tests__ next to source.
glossary.md Every rule listed with one-line description and the why. Self-documenting. Reviewable in PRs as the rule set evolves.

Self-evolution (Phase 3)

  • Three independent occurrences of the same pattern → suggestion in monthly /insights report.
  • Promotion to guideline — human reviews, accepts, entry lands in guidelines.md with frontmatter + body + glossary line.
  • Three guideline-flagged violations of the same shape → suggested promotion to non-negotiable. Human signs off.

Concept · Environment inventory

Specflow knows what tools (CLIs, MCPs, plugins, agents) are available in the user's environment, exposes only the relevant slice to each skill, and can degrade or escalate based on what's present. Better outputs without bloating the context window.

What gets inventoried

  • CLIs — Playwright (required), Codex (optional, enables adversarial review), git, gh, Linear CLI, others as detected.
  • MCPs — every MCP server installed in the user's Claude Code config (Linear, Drive, Gmail, custom).
  • Plugins — every plugin under ~/.claude/plugins/ with version.
  • Agents — every agent exposed by installed plugins, indexed by name + source plugin.

Hard vs soft requirements

  • Hard — missing breaks setup. Currently: Playwright CLI.
  • Soft — missing changes behaviour, doesn't block. Currently: Codex CLI (adversarial review degrades to skipped); specific MCPs (Linear export disabled if missing).

The hard/soft distinction is encoded in environment.json so skills decide whether to fail loud or degrade quietly.

Phasing roadmap

Three phases. The throughline: survive Tuesday before optimising the quarter. Recovery primitives, alignment gates, and the rules substrate ship in Phase 1 — before anything compounds on top of them.

Phase 1 — Foundation
Ship the substrate every later phase depends on. Folders, examples, specflow:upgrade, specflow:design, the rules registry, the four behavioral principles, the adversarial review chain (Gates 1-3), trust-ladder primitives, PRD HTML rendering, the Interview section, multi-agent debate manifest with principle reviewers, simplify autoresearch loop as discipline-installer, SKILLS.md glossary discipline.
Phase 2 — Development
specflow:develop with green/yellow/red lane execution. Agent indexing, agent teams, specialised agent matching, Gates 4 + 5 of the adversarial chain. This is where specflow gains its hands.
Phase 3 — Memory
Self-learning loop closes. task-history.json + decision-log.md populated throughout the lifecycle. specflow:complete retro at task completion. Similarity search wired into specflow:task + specflow:misc. /optimize across the verifiable-skill set. Rules registry self-evolution. Gate 6 of the adversarial chain. Compounding signals captured (no dashboard — five numbers per PRD logged to metrics.md: override rate, green-lane percentage, escaped-bug rate, cycle time, adversarial flag rate).
