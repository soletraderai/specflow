# Saraev perspective — position paper

## TL;DR

Stop polishing prompts by hand. Stop drawing org charts of fake CEOs and CMOs. Stop pretending one-shot evaluation tells you anything about a noisy stochastic skill. The dominant fact about specflow's situation is that intelligence is now improving intelligence, and the only durable assets are (1) a CLAUDE.md that compresses your workspace and logs your failures, (2) skills wrapped in a measured autoresearch loop so they get better while you sleep, and (3) a multi-provider posture so an Anthropic outage doesn't zero your day. Everything else — the agent org charts, the elaborate planning theatre, the human review on every artifact, the framework worship — is friction that multiplies your error rate. Reliability is multiplicative: 0.9³ = 0.73. Every node you add without measurement is a tax. The bet for this quarter is to ship a `/optimize` meta-skill that autoresearches every other skill in specflow against binary evals, and to give every user a CLAUDE.md template with a Lab Notes section. That is how specflow stops being a static plugin and starts being a compounding asset.

## What Saraev gets right

Three things the other camps either miss or fudge.

**One — measurement is the only thing that compounds.** Pocock's grilling skill, Medin's PIV loop, Karpathy's spec-as-code framing — they are all reasonable opinions. But none of them has a number attached. Saraev runs a diagram skill from 32/40 to 39/40 on $10. Saraev takes a website from 1100ms to 67ms across 67 tests. Saraev predicts what Toby Lütke proved on Shopify Liquid: 53% faster parse+render, 61% fewer object allocations, all from an autoresearch agent left running. The other camps argue about *which* skill prompt is best. Saraev argues about *how to know*. Once you have a metric, a mutator, and a judge, you stop arguing — you let the loop tell you. For a docs creator and a small dev team, this is not an academic preference. It is the difference between your skills decaying as Opus 5 lands and your skills compounding into Opus 5.

**Two — CLAUDE.md is not a prompt dump, it is four files in one.** Knowledge compression. Preferences. Capability declarations. A running log of failures. Pocock treats CLAUDE.md as a style guide. Medin treats it as scaffolding for path-scoped rules. Both miss the most leveraged line you can ever put in a CLAUDE.md, which is: "When you have made a mistake, update this file with a running log of things not to do next time." That single line creates a Lab Notes section automatically. Pair it with `/insights` running sub-agents over your full session history and you have a self-curating knowledge base. The 45x compression ratio Saraev demos on App.jsx (1100 tokens → 22 tokens) is not a parlor trick — it is what makes the difference between a 100k smart-zone session and a 200k dumb-zone session.

**Three — the harness is the product, but not in the way Medin thinks.** Medin wants you to build elaborate Archon DAGs with `depends_on:` and `trigger_rule:` and `interactive: true` gates everywhere. That is not a harness, that is a workflow engine. The actual harness is Claude Code itself plus a thin layer of skills, sub-agents, and a CLAUDE.md. Anthropic's "Effective Harnesses for Long-Running Agents" post (Nov 26 2025) was the inflection. The harness is the system prompt, the tools, the hooks, the parameters. specflow should be a layer of skills and a CLAUDE.md template, not a YAML-driven workflow engine that competes with the host.

## 3-5 highest-leverage items

Ranked, blunt.

**1. Ship `/optimize` — a meta-skill that autoresearches every other skill in the plugin.** Three ingredients: a metric, a mutator, an assessor. Binary evals only — none of this Likert-scale theatre that lets the judge drift. ~2 cents per generation × ~10 per cycle × ~50 cycles ≈ $10 to lift one skill from 80% to 97.5%. specflow has, what, 15-20 skills? Two hundred dollars to optimize the entire catalog and the optimization log becomes a durable asset that Opus 5 inherits. This is the single highest-ROI feature you can ship this quarter. Karpathy's autoresearch repo is the template — `program.md`, append-only TSV ledger, branch-per-run, simplicity criterion baked in, "NEVER STOP" autonomy norm bounded by read-only eval files. Steal it.

**2. Ship a CLAUDE.md template with Lab Notes baked in.** Two files. Global (`~/.claude/CLAUDE.md`) for high-level reasoning, identity, capability declarations — what the agent CAN do that it would otherwise forget. Local (`./CLAUDE.md`) for project-specific knowledge compression and the failure log. The template includes the Lab Notes prompt verbatim and a post-task reflection: "How could you have arrived at these conclusions and done everything I asked faster?" The docs creator gets one for their workspace, the dev team gets one per repo. This is the cheapest possible win on goal #3 (fewer errors). It costs nothing and compounds forever.

**3. Make every skill declare its capabilities and write paths.** Agents have no agency by default — they will tell you a build takes 3 months because they think *you* are building it. specflow skills must include a CAN/CANNOT block (Karpathy's `program.md` framing — bullet lists beat policy paragraphs every time) and an explicit "writes outputs to `active/<skill-name>/...`" line. This unblocks the new-to-AI dev team from the constant "Claude says it can't" wall. It also keeps the workspace organized so `active/` is the only thing you ever clean up.

**4. Mirror CLAUDE.md → AGENTS.md → GEMINI.md and ship a Codex composition path.** 70/30 Claude/Codex via the `openai/codex-plugin-cc` plugin or Codex MCP. Anthropic outages have already happened (Dec 17 2025 Opus 4.5 degradation). A 100% Claude team has zero output during incidents. The mirror file is cheap insurance. Bonus: cross-provider adversarial review (Codex reviews Claude's PR, Claude reviews Codex's) is the strongest quality lever specflow can ship — different models have different blind spots, and findings Codex catches that Claude missed get promoted into CLAUDE.md as new rules. That is how specflow self-heals.

**5. Two parallelization patterns, no more.** Fan-out/fan-in (cheap Sonnet/Haiku researchers, Opus synthesizer) for research. Developer + fresh-context QA loop for implementation. That's it. No CEO sub-agents. No CMO sub-agents. No Paperclip / CompanyHelm / OpenGoat / GASTown / SwarmClaude org charts. They are anthropomorphic theater. Reliability is multiplicative: 0.9³ = 0.73, 0.9⁵ = 0.59. Every fake role you add to your org chart is another 0.9 multiplier. Skills should be by *function*, not by *role*.

## What Saraev rejects

**One — heavyweight workflow engines (Archon, BMAD, Spec Kit, GSD).** These force teams to change how they work, add YAML you have to maintain, multiply nodes you have to debug, and become the framework people over-rely on. Cole Medin's own `depends_on:` / `trigger_rule:` / `loop:` DSL is exactly the kind of complexity that compounds error rates. The harness is not a DAG. The harness is a CLAUDE.md plus a handful of skills.

**Two — agent org charts.** Paperclip, CompanyHelm, OpenGoat, GASTown, SwarmClaude — all of them are dressing up function-by-function skills as fake humans. A "CMO sub-agent" and a "marketing-copy skill" are the same markdown file with worse vibes. Worse, the org-chart framing makes you build five agents where two would do, and each extra agent is another multiplicative reliability hit.

**Three — over-specified evaluation rubrics.** Likert scales compound variability at every step. Ten narrow eval rules let the model parrot the criteria back like a student who got 100% on a test without understanding the material. Binary yes/no evals or nothing.

**Four — single-shot evaluation of skill prompts.** Skills are 70% useful / 30% garbage. One happy run is meaningless. Distributional thinking or you are kidding yourself.

**Five — naked public agent endpoints, agent-touched credit cards, AI-suggested package names without an audit, Supabase RLS off-by-default.** The Mol Bot breach already happened. The `~/.claude/` JSONL plaintext leak is real (you can grep your axolotl password right out of it). Typosquat malware exfiltrating `~/.claude/` is real. Five low-hanging-fruit security fixes, all in CLAUDE.md, before specflow ships anything client-facing.

## Disagreements with other camps

**Pocock — "I much prefer my AI to behave like the guy from Memento"** (KP-102). On the surface, agree. Saraev also clears context aggressively and writes durable artifacts. But Pocock then turns around and rejects the "spec-only edits, regenerate code" workflow as "vibe coding by another name" (KP-101) and refuses to review auto-written PRDs (KP-20). That is incoherent. If you trust LLM summarization enough to skip reviewing a PRD, you should trust it enough to evolve specs. The actual answer is neither: spec rot is a real problem, but the fix is *measurement*, not *more human review*. Wrap your spec-to-code pipeline in autoresearch with a "PR matches PRD" binary eval and a "tests pass" binary eval and let the loop tell you which specs survive contact with code.

**Pocock — "if you try to automate the QA, automate the research, you end up with apps that lack taste and are bad"** (KP-85). Wrong framing. Taste is not magic. Taste is a metric you have not bothered to define. If you can articulate what good looks like in binary terms — "is this copy on-brand? yes/no" — you can autoresearch it. Saraev did exactly this with the diagram skill (legible text, pastel palette, linear flow, no ordinals — four binary checks, $10, 32/40 to 39/40). The "human taste re-entry point" line is comfortable but it is also how you justify never measuring anything. Measure first. Then decide what humans add.

**Medin — "every bug is also a system bug"** (KP-24). Agree completely. The fix is `/insights` plus Lab Notes. But Medin's PIV loop with explicit human-approval gates on every PRD and plan.md (KP-13, KP-39) is the wrong direction. Human gates are a tax you pay because you do not have measurement. They cost wall-clock time, they reintroduce the very inconsistency they were meant to prevent (humans review differently on Tuesday than Friday), and they cap throughput at human attention. The right design: gates only where the metric is missing, and a relentless effort to define metrics so gates can be removed.

**Medin — Dark Factory experiment** (KP-113). Cole frames it as aspirational and contradicts his own hybrid thesis. Saraev's read: Dark Factory is correct *for verifiable domains* (tests, lints, perf) and a disaster *for unverifiable ones*. The line is not "autonomy good vs autonomy bad." The line is "do you have a fixed metric and a read-only eval surface." Karpathy's autoresearch repo gets this right with `train.py` editable and `prepare.py` read-only. specflow should ship that exact pattern: read-only eval files per skill, the optimizer can mutate the SKILL.md, and the metric is the only judge.

**Karpathy — "specs are the new code"** (KP-17, KP-99). Closest to Saraev's worldview, but Karpathy under-weights the harness and over-weights the language. Specs in markdown are wonderful, but if your harness will execute `rm -rf` from a Twitter thread (real Codex incident), your spec discipline does not save you. The harness is where reliability lives. Claude Code is the best harness, full stop. Diversify to Codex/Gemini for review and outage insurance, but do not pick an alternate daily driver because of philosophy.

**Karpathy autoresearch — NEVER STOP norm** (KP-21, KP-50). Right for the bounded case. Wrong if you let it leak into pipeline loops. Saraev's resolution: NEVER STOP is safe iff (a) read-only eval surface, (b) fixed scalar metric, (c) git-as-checkpoint so any wrong turn can be reset. Without all three, you need human gates. With all three, gates are friction.

## The one bet

**Ship `/optimize` this quarter.** A meta-skill that walks every SKILL.md in specflow, defines binary evals (or asks the user to author them), runs ~50 mutation cycles per skill against an automated judge (Sonnet vision for visual outputs, Sonnet text for prose), keeps the winner via git-as-experiment-log, and accumulates an `optimization-log.md` per skill. ~$10 per skill, ~$200 for the catalog, every dollar buys you compounding quality that Opus 5 will inherit for free.

Why this beats every other bet on the table:
- It is the only roadmap item that compounds across model upgrades. Pocock's grill skill is good today and will be good with Opus 5; it does not get *better* with Opus 5. An autoresearch-optimized skill does.
- It encodes the entire Saraev worldview (metric + mutator + judge, binary evals, distributional thinking, optimization log as durable asset, harness as product) in one shippable artifact.
- It is genuinely cheap. A docs creator and a five-person dev team can run it overnight with no infra beyond GitHub Actions cron.
- It directly hits all three north-star goals: productivity (skills get faster + more reliable without human effort), better product in shorter time (skills go from 80% to 97.5% on a measurable rubric), fewer errors (the optimization log is a permanent record of failure modes the next model inherits).

Everything else — the parallelization patterns, the CLAUDE.md template, the Codex composition path, the security checklist — falls out of this bet for free, because `/optimize` requires CLAUDE.md to declare metrics, requires CAN/CANNOT framing in skills, and requires read-only eval surfaces. Build the loop. The rest follows.
