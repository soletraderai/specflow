# PRD interview — features/003-complete-skill

## Original request

> Write the spec for `specflow:complete`, the Phase 3 retro skill. The skill captures task outcome at completion and feeds the self-learning loop into `admin/task-history.json` and (for significant patterns) `admin/decision-log.md`. Manually invoked via `/specflow:complete {task-id}` or auto-fired by `specflow:develop` Phase F when a task closes; the architectural shape is locked in by `docs/PRD.md` Phase 3 + Appendix I; this PRD synthesises the implementation contract at the SKILL.md level.

Frontmatter shape is correct; the stub's behaviour section names the retro questions but does not yet have the operational prompt body.
- **Phase 2 `specflow:develop` already populates the same schema.** `skills/develop/SKILL.md` Phase F.5 (lines 546-563) writes the six development-time fields (`lane_assigned`, `ai_assistance_level`, `elapsed_minutes`, `what_worked`, `what_didnt_work`, `blast_radius_outcome`) to `admin/task-history.json` on Verifier pass. `specflow:complete` is the retro layer that runs *after* Phase F — its job is the captured-at-completion fields the development-time write does not own (regressions caught, escaped issues, AI assistance review-after-the-fact, hours estimated vs actual). The Phase 2 `specflow:develop` write extends with: `feature`, `lane_assigned`, `ai_assistance_level`, `elapsed_minutes`, `what_worked`, `what_didnt_work`, `blast_radius_outcome`. Phase 3 retro adds: `regressions_caught`, `escaped_issues`, retro-side `actual_hours`, `prd_anchor`. **Field-name divergence** between Appendix I3 (`whatWorked` camelCase) and the develop skill's snake_case (`what_worked`) is a real schema gap — surfaced as a grilling round.
- **`decision-log.md` schema and prior entries.** `examples/docs/specflow/admin/decision-log.md` shows six prior entries (composition over inheritance, tests in `__tests__/`, Slack removal, specflow adoption, Playwright pin) with the standard six-field shape (Title / Date / Context / Decision / Rationale / Related). The "significant pattern → elevate to decision-log" mechanic this skill ships needs a definition of "significant" that matches the existing entries' calibre — none of those entries is small ("the date format works fine") and none requires more than 6-8 lines of context to be readable a year later.
- **`specflow:linear` is a soft dependency.** `skills/linear/SKILL.md` (v1-shipped) handles Linear MCP integration. PRD Open question 4 (line 562) names "Linear webhook polling" as the deferred-but-considered automation surface. v1 of `specflow:complete` defers webhook-driven auto-fire; auto-invocation comes from `specflow:develop` Phase F (per Phase F.5's task-history.json write — `specflow:complete` runs as the retro layer after Phase F closes the per-task work).
- **Standard agents already operational.** Phase 1 + Phase 2's principle reviewers and lifecycle agents are copied to `admin/agents/standard/` at setup. `specflow:complete` does NOT run a debate manifest — Phase 3 retro skills do not gate at adversarial review (the only "gate" the retro skill enforces is the schema-parse check + the binary "all required fields present"). This is consistent with `specflow:decision` and `specflow:misc` — small Phase 3 skills with binary `eval:` fields and no manifest.
- **Worked examples 001-design-skill + 002-develop-skill.** Calibration anchors for what a healthy interview + PRD + Gate 2 manifest looks like — neither rubber-stamping nor bikeshedding. 002 hit two `block` findings and one push-back; this dogfood pass aims to surface a similar realistic shape on a Phase 3 surface (smaller skill, smaller surface area, but the lenses still need to bite).
- **Idempotency convention.** Phase 1 skills (`specflow:test` with append-only execution log, `specflow:misc` with append-only entries) are the precedent: re-runs of the same skill on the same artefact append rather than overwrite, preserving the audit trail. `specflow:complete` re-runs against the same task-id needs the same discipline — the question is whether to append a fresh entry, replace in place, or refuse the second invocation; surfaced as a grilling round.

## Goal (confirmed before grilling)

- **Outcome:** `specflow:complete` closes the loop between work-done and project-memory. Every closed task leaves a structured trace in `admin/task-history.json` so future tasks read the lessons; significant patterns elevate to `admin/decision-log.md` for the human-readable narrative. The skill turns task outcomes into structured project memory — without it, the self-learning loop has no input data and Phase 3's compounding signals never accumulate.
- **Audience:** Power Users (frontend / backend engineers with specflow installed) running `/specflow:complete` manually at the end of a task they led. Secondary: Developer / API Consumer profiles whose green-lane batches close via `specflow:develop` Phase F auto-firing the retro inline. Tertiary: future-readers (the same engineer six months later, a teammate onboarding to the codebase, an `/insights` (monthly) cadence reading the corpus for patterns) who consume `task-history.json` and `decision-log.md` without ever invoking the skill themselves.
- **Success looks like:** invoking `/specflow:complete {task-id}` (or auto-firing from `specflow:develop` Phase F) on a task whose acceptance criteria passed Verifier produces (a) a structured entry appended to `admin/task-history.json` with all required retro fields populated and parsing against the schema, (b) when the retro identifies a significant pattern, a corresponding entry appended to `admin/decision-log.md` in the canonical six-field shape, (c) a chat-line summary citing the new entry's id and any decision-log entry's title, (d) zero silent failures (refused invocation on incomplete acceptance, schema-gap, or duplicate task-id surfaces explicitly to the user with a structured reason). Every artefact lives at `admin/` so the corpus stays per-repo and committed.
- **Driving value:** removes the failure mode where closed tasks leave no trace and the lessons evaporate; removes the failure mode where significant decisions made during execution are remembered inconsistently across team members because the source was a chat thread that aged out; removes the failure mode where `/insights` (monthly) and `specflow:task` similarity-search have no corpus to read because nothing wrote to it. Structured retro at completion + significant-pattern elevation are the two surfaces the self-learning loop depends on for input data.
- **Out of scope at the goal level:** (1) Linear webhook auto-fire — deferred per `docs/PRD.md` Appendix I8 ("Manual first"); v1 ships manual + Phase F auto-invocation only, webhook polling is a v2 concern; (2) cross-feature retro rollups (e.g. "summarise the last quarter's task outcomes") — that's `/insights` (monthly) Phase 3 scope item 10, a separate skill; (3) similarity-search on the corpus during retro capture — that's `specflow:task` and `specflow:misc` Phase 3 scope item 5 (consumers, not the producer); (4) auto-promotion of patterns to the rules registry — that's Phase 3 scope item 8 (observation → guideline → non-negotiable) driven by `/insights`, not by `specflow:complete`; the retro skill writes only to `task-history.json` + `decision-log.md`, never to `admin/rules/`; (5) editing or removing existing entries — append-only by design; corrections land as new entries that link back, mirroring the `decision-log.md` convention.

User confirmed: 2026-05-06.

## Rounds

### Round 1 — Auto-fire trigger semantics: when does Phase F of `specflow:develop` invoke `specflow:complete`?

- **Q:** `specflow:develop` Phase F.5 already writes the six development-time fields to `task-history.json` on Verifier pass. The PRD Phase 3 scope item 2 names `specflow:complete` as the retro skill that captures outcome at completion. When does Phase F auto-fire `specflow:complete` — once per task as Verifier passes (so the retro fields land on the same entry the development-time fields just wrote), once per feature when the whole batch is closed (so the retro is feature-level not task-level), or never (Phase F writes development-time fields and `/specflow:complete` is always manual)?
- **AI's recommended answer:** Auto-fire once per task at the boundary between Phase F's task-history write (F.5) and the cleanup step (F.6), AFTER Verifier passes (or option-4 accept-and-ship is elected) AND AFTER the per-task PR opens. The retro skill reads the task-history entry the development-time write just produced, asks the retro questions inline (5 questions: hours estimated vs actual, regressions caught during implementation, escaped issues found post-Verifier, AI assistance review-after-the-fact (`full | partial | none`), what's worth elevating to `decision-log.md`), and writes the retro fields to the same entry. Manual `/specflow:complete {task-id}` is the alternate path — used when the user closed the task outside `specflow:develop` (e.g. red-lane human-led task that didn't run the full skill flow, or a misc-task that closes). Phase F auto-fire is the default path; manual invocation is the escape hatch. — *Reasoning: the goal's Outcome calls out that "every closed task leaves a structured trace" — pairing the retro with the moment Verifier passes is the strongest binding of work-completion to memory-capture. Once-per-task matches the development-time write's granularity; once-per-feature would lose per-task signal that the corpus needs for similarity-search. Manual + auto-fire both routes is the same dual-mode pattern `specflow:misc` uses (interactive + auto), which is the locked-in Phase 1 convention.*
- **User's answer:** confirmed, with one edit — Phase F auto-fire on Green-lane batched tasks should fire once per task at the per-task Verifier-pass boundary, NOT batched at the PR-merge boundary. Reason: the per-task signal is the signal `/insights` reads later; batching the retro across a 3-task green batch would collapse three distinct retros into one and lose pattern-detection granularity. Per-task even in batched flows.
- **Resolved:** Phase F auto-fires `specflow:complete` once per task after Verifier passes (or option-4 accept-and-ship is elected) AND after the per-task PR opens, before Phase F.6 scratch-cleanup; Green-lane batched flow fires per-task not per-batch; manual `/specflow:complete {task-id}` is the alternate escape-hatch path for tasks closed outside `specflow:develop`. — flows into §Requirements R1, R2; AC AC-1, AC-2.

### Round 2 — `task-history.json` schema additions: what new fields does the retro add, and how do they reconcile with the existing schema?

- **Q:** Appendix I3 documents the schema with camelCase field names (`whatWorked`, `whatDidntWork`, `aiAssistance`); `specflow:develop` Phase F.5 writes snake_case fields (`what_worked`, `what_didnt_work`, `ai_assistance_level`). Which casing wins for `specflow:complete`'s retro fields, and what new fields does the retro add on top of the development-time write?
- **AI's recommended answer:** Snake_case wins — the Phase 2 `specflow:develop` schema is the authoritative shape going forward, and the Appendix I3 example (which is illustrative, not normative) gets a one-line revision in this PRD's "Schema dependency" note saying so. Retro adds three new fields beyond the development-time set: (1) `actual_hours` — user-reported hours-elapsed retrospective (the development-time `elapsed_minutes` is wall-clock from the orchestration; `actual_hours` is the user's honest "this took me X hours including thinking/blocked/context-switch time"); (2) `regressions_caught` — count + brief description of regressions caught during implementation (machine-check fail, gate failure, Verifier reject — anything caught before ship); (3) `escaped_issues` — count + brief description of issues found AFTER ship (production incident, code review catch, follow-up bug). The retro's `what_worked` / `what_didnt_work` REPLACE the development-time write's same fields — the retro is the source of truth for those fields because it runs after the task closes; the development-time write is the placeholder. AI assistance level is also re-asked at retro (could change from `partial` to `full` or vice versa as the user reflects). — *Reasoning: the goal's Driving value names "lessons evaporate" as the failure mode being removed — the three retro-only fields (`actual_hours`, `regressions_caught`, `escaped_issues`) are the lesson-bearing fields the development-time write cannot produce because Phase F runs at completion-of-implementation, not after-ship. Field-name reconciliation: snake_case is the working convention in `specflow:develop`'s shipped schema; Appendix I3's camelCase is example-not-spec. Pick one, lock it in.*
- **User's answer:** confirmed, with one edit — `escaped_issues` should be capturable both at completion (count: 0 known so far) AND amendable later when one is found. Append-only retro means the original entry stays, but a follow-up `/specflow:complete --amend {task-id} --escaped-issue "{description}"` mode appends a corrigendum-style addendum to the entry. Treating escaped issues as "fixed at retro time" loses the post-ship signal `/insights` reads later.
- **Resolved:** retro fields = snake_case; new fields beyond Phase F's development-time set are `actual_hours`, `regressions_caught`, `escaped_issues`; retro `what_worked` + `what_didnt_work` + `ai_assistance_level` REPLACE the Phase F write's placeholder values; amend mode (`/specflow:complete --amend {task-id} --escaped-issue "{desc}"`) appends an addendum to an existing entry rather than creating a new entry; field-name reconciliation note in the PRD acknowledges Appendix I3 example uses camelCase but snake_case is the working convention. — flows into §Requirements R3, R4, R5; AC AC-3, AC-4, AC-5.

### Round 3 — What counts as a "significant pattern" worth elevating to `decision-log.md`?

- **Q:** The skill writes to `task-history.json` always; to `decision-log.md` only "for significant patterns." The stub SKILL.md doesn't define "significant." `decision-log.md`'s prior entries are big-deal architectural / workflow decisions (composition vs inheritance, Slack removal, specflow adoption). What rule decides which retros elevate?
- **AI's recommended answer:** A retro elevates to `decision-log.md` when AT LEAST ONE of three conditions fires: (a) the retro records a `what_didnt_work` field naming a pattern the user explicitly thinks future tasks should know about (user-flagged via the retro question "Anything from this task that should land in `decision-log.md` for future readers? Y/N + description if Y"); (b) the retro's `escaped_issues` field is non-empty AND the issue's blast-radius is medium or high (escaped issues at low blast are noise; medium+ are signal worth a decision-log entry capturing the lesson); (c) the retro records a `blast_radius_outcome` value that diverges materially from the task's lane assignment's blast-radius axis (e.g. lane was Green / blast=low, but the actual outcome touched 12 files because of an unstated dependency — the divergence is itself a learnable pattern). Conditions are OR'd; any one fires the elevation. The decision-log entry is composed by the skill from the retro fields (Title = task title prefixed with `Retro:`; Context = the task's PRD anchor; Decision = "{user-stated lesson} — pattern surfaced via specflow:complete"; Rationale = the retro field that fired the elevation; Related = the task-history entry id + PRD path). User reviews the composed entry before write — explicit confirm step, not silent. — *Reasoning: the goal's Out-of-scope-at-goal-level rules out auto-promotion to the rules registry but explicitly keeps `decision-log.md` elevation in scope. The three-condition rule binds elevation to observable retro-field shapes (no judgement-call "is this important?"); the user-confirm step prevents the corpus from filling with low-signal entries. The three condition shapes match the three failure modes the goal's Driving value names (lessons evaporate / decisions inconsistent / no corpus to read).*
- **User's answer:** edit — drop condition (c). Lane-vs-outcome divergence is a real signal but it's a `/insights` (monthly) pattern, not a per-task decision-log entry. A single divergent task isn't a decision; it's a data-point. The monthly insights cadence reads the corpus for patterns and proposes the elevation when divergences cluster. Per-task elevation should only fire on (a) explicit user flag or (b) post-ship escaped-issue at medium+ blast. Two conditions, OR'd.
- **Resolved:** decision-log elevation fires when EITHER (a) the user explicitly flags the retro for elevation via the "should this land in `decision-log.md`?" question with a Y answer and description, OR (b) the `escaped_issues` field captures a post-ship issue with blast_radius medium or high; conditions are OR'd; user reviews the composed entry before write; lane-vs-outcome divergence is `/insights`-cadence territory, not per-task. — flows into §Requirements R6, R7; AC AC-6, AC-7.

- **AI's recommended answer:** Entirely absent from v1. No webhook polling, no webhook listener, no `config.json.complete.webhook` knob. The two trigger paths are: (1) `specflow:develop` Phase F auto-fire (in-process; no webhook involved), (2) manual `/specflow:complete {task-id}` (CLI). Adding an opt-in webhook in v1 would be speculative configurability per the Simplicity First sub-clause — the consumer ask isn't documented yet, and the in-process auto-fire from `specflow:develop` covers the auto-fire need without webhook plumbing. v2 lands webhook polling when a real consumer surfaces (e.g. tasks closed in Linear UI without going through `specflow:develop` because the task was a non-specflow workflow). The v2 enhancement PRD will add the polling shape; v1 stays clean. — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly defers webhook auto-fire; honouring the deferral means not shipping the knob even with `enabled: false` default — the knob's existence implies the feature exists, which it doesn't. Simplicity First: don't introduce config knobs without a concrete second consumer demanding them. The two trigger paths shipped (auto from develop + manual CLI) are the documented consumer asks.*
- **User's answer:** confirmed.
- **Resolved:** v1 ships zero webhook integration; two trigger paths only — `specflow:develop` Phase F auto-fire + manual `/specflow:complete {task-id}`; no `config.json.complete.webhook*` knobs; v2 enhancement PRD lands webhook polling when a documented consumer surfaces. — flows into §Requirements R8; AC AC-8.

### Round 5 — Idempotency: what happens when `/specflow:complete` runs twice on the same task-id?

- **Q:** `specflow:misc` is append-only; `specflow:test`'s execution log is append-only; `specflow:decision` is append-only. What happens when `/specflow:complete {task-id}` runs twice on the same task-id — append a fresh entry (corpus has two entries for the same task), replace in place (loses the audit trail), or refuse the second invocation (forces user to use `--amend` for follow-up captures)?
- **AI's recommended answer:** Refuse the second invocation in plain mode; require explicit `--amend` flag for follow-up captures. Rationale: a task closing once is the canonical event; a second `/specflow:complete` without `--amend` is either user error (forgot it already ran) or an attempt to overwrite the audit trail (which append-only forbids). Refusing the plain-mode second invocation surfaces the situation to the user; `--amend` is the explicit path for follow-up captures (e.g. an escaped issue surfaces a week later — `/specflow:complete --amend {task-id} --escaped-issue "{desc}"`). The amend path appends an addendum block to the existing entry's `addenda` array (new field on the schema), preserving the original retro and adding the post-hoc signal. Plain-mode refusal returns a structured chat line: *"Task `{task-id}` already has a retro entry (created `{date}`). Use `--amend` to append addenda; manual edit of `task-history.json` is forbidden."* — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly forbids editing/removing existing entries (append-only by design). The refuse-then-amend pattern is the strongest expression of that non-goal: plain-mode refusal makes the convention loud, the `--amend` path provides the legitimate escape hatch, and the addenda array preserves the original entry intact. Matches the `decision-log.md` convention (superseding decisions get a new entry that links back, never edit-in-place).*
- **User's answer:** confirmed.
- **Resolved:** plain-mode `/specflow:complete {task-id}` on a task with existing retro entry refuses with a structured chat line; `--amend` flag is the explicit path for follow-up captures (escaped issues, retroactive notes); amend appends to an `addenda` array on the existing entry rather than creating a new entry or editing fields in place; manual edits to `task-history.json` outside the skill are forbidden by convention (not enforceable, but documented). — flows into §Requirements R9, R10; AC AC-9, AC-10.

### Round 6 — Failure modes: what happens when acceptance criteria didn't fully pass (Verifier rejected, option-4 accept-and-ship)?

- **Q:** The stub's `eval:` says "entry has all required fields ... and parses against the schema." What about tasks that closed via Verifier rejection + option-4 accept-and-ship (per `specflow:develop` Phase F.3) — does the retro fire normally, fire with a forced `accepted_with_failure: true` flag, or refuse on the basis that acceptance criteria didn't fully pass?
- **AI's recommended answer:** Fire normally, with a forced `accepted_with_failure: true` flag on the retro entry AND a forced "this should be elevated to `decision-log.md`" prompt (the user can still answer N, but the prompt fires unconditionally for accept-and-ship tasks because the option-4 path already wrote a decision-log entry per Phase F.3 — the retro entry needs to point at it). The retro skill reads the task-history entry the Phase F.3 option-4 path wrote, detects the accept-and-ship marker, and surfaces the existing decision-log entry's title to the user with a confirm-or-edit prompt. Refusing the retro on accept-and-ship would lose the lesson the option-4 path was specifically designed to capture; firing without the flag would lose the audit trail that the task shipped with a failed AC. — *Reasoning: the goal's Outcome names "every closed task leaves a structured trace" — accept-and-ship tasks DID close (the user explicitly elected to ship), so they need a retro. The flag distinguishes accept-and-ship retros from clean-pass retros so `/insights` can pattern-match on the calibre of failure that ships. The decision-log link prevents duplicate entries — Phase F.3 already wrote one; the retro points at it.*
- **User's answer:** confirmed.
- **Resolved:** retros fire normally on accept-and-ship tasks with a forced `accepted_with_failure: true` flag; the elevation prompt fires unconditionally for these tasks (user can still answer N); the existing Phase F.3 decision-log entry's title is surfaced for confirmation/edit (not duplicated). Tasks that closed via clean Verifier pass have `accepted_with_failure: false` (default); tasks that didn't close at all (Verifier rejected, no option elected, run abandoned) have no retro entry by virtue of not having a closed task to retro on. — flows into §Requirements R11, R12; AC AC-11, AC-12.

### Round 7 — Interaction with `specflow:scope-change`: if scope changed mid-task, what does the retro entry capture?

- **Q:** `specflow:scope-change` (Phase 3 sister skill) captures mid-development scope changes — updates the PRD, regenerates affected tasks, writes a `decision-log.md` entry. When a task ran through a scope-change mid-execution, does the retro entry record the original task definition (pre-scope-change) or the final task definition (post-scope-change), and does it cite the scope-change decision-log entry?
- **AI's recommended answer:** The retro entry records the FINAL task definition (post-scope-change) — that's the work that actually happened — and adds a `scope_change_log` field listing every `decision-log.md` entry whose `Related` field references the task-id. The skill reads `decision-log.md`, finds entries whose Related field cites the task, and lists their dates + titles in the retro entry's `scope_change_log`. The retro questions are asked against the final task definition (what worked / didn't on the work-as-shipped, not on the work-as-originally-planned). This makes the retro entry coherent (it describes one piece of work, not two) while preserving the audit trail through the cited decision-log entries. — *Reasoning: the goal's Outcome names "structured trace" — recording the final definition matches the work-that-shipped reality; recording the original would be a fiction. Citing the scope-change entries keeps the audit trail intact. Single source of truth (the retro is one entry, with a list of related decisions).*
- **User's answer:** confirmed.
- **Resolved:** retro records the final post-scope-change task definition; `scope_change_log` field lists every `decision-log.md` entry whose Related field references the task-id (skill reads `decision-log.md` to compute this); retro questions are asked against the final definition; per-task retro stays one entry regardless of how many scope-changes the task underwent. — flows into §Requirements R13; AC AC-13.
