# PRD interview — features/004-decision-skill

## Original request

> Write the spec for `specflow:decision`, the Phase 3 lightweight skill users invoke to manually log a decision out-of-band — when something noteworthy happens that isn't tied to a closing task. Complement to `specflow:complete` (which captures task-completion retros). The skill produces a single new entry in `admin/decision-log.md` matching the format the file already uses. Architectural shape is locked in by `docs/PRD.md` Phase 3 scope item 3 + Appendix I5; this PRD synthesises the implementation contract at the SKILL.md level.

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `docs/PRD.md` § "Phase 3 — Memory and self-learning" scope item 3 (line 216) and Appendix I5 (line 546-549) document `specflow:decision` end-to-end: lightweight skill, captures title / context / decision / rationale / date / related, appends to `admin/decision-log.md`. Re-litigating those decisions is out of scope per `v2/docs/SESSION-HANDOFF.md` § "Architectural decisions — locked in".
- **Stub SKILL.md exists.** `skills/decision/SKILL.md` is description-level with the v2 contract: `requires: []`, `produces: [docs/specflow/admin/decision-log.md]`, `eval` field names the six required entry fields (title, context, decision, rationale, date, related files/tasks). Frontmatter shape is correct; the stub does not yet have the operational prompt body.
- **Sister Phase 3 skill `specflow:complete` is the closest neighbour.** `skills/complete/SKILL.md` writes to BOTH `admin/task-history.json` AND `admin/decision-log.md` (when the retro surfaces a significant pattern). `specflow:decision` is the out-of-band counterpart — same target file, no task scope, no retro questions about elapsed-vs-estimate or what-worked. The two skills must not collide on the same surface (see Round 4 below).
- **Existing `decision-log.md` already populated with the format the skill must respect.** `admin/decision-log.md` ships in the worked example with five entries (composition-over-inheritance, tests-in-`__tests__`, Slack-removed, specflow-adoption, Playwright-pin). Schema per the file's preamble: **Title** (declarative `## H2`), **Date** (`YYYY-MM-DD`), **Context**, **Decision**, **Rationale**, **Related** — fields rendered as bold-prefixed paragraphs separated by blank lines, entries separated by `---`. The preamble also declares: "entries do not get edited after the fact — superseding decisions get a new entry that links back."
- **No existing schema validator for the file.** The format is enforced by convention, not by a parser. The skill is the first programmatic writer; it has to respect the format precisely or future entries drift.
- **Phase 1 reference for "lightweight interactive skill" pattern.** `skills/misc/SKILL.md` is the closest precedent — a single-task interactive flow with two invocation modes (interactive + auto-from-another-skill). `specflow:decision` is simpler (no auto mode, no rolling-file allocation) but should match the conversational shape: prompt-per-field, verify before writing, idempotent on re-run.
- **Calibration anchor for sibling Phase 3 skill PRDs.** `features/003-complete-skill/` exists as a debate-log placeholder only — the `specflow:complete` PRD has not been drafted yet. So this PRD has no Phase 3 prior art to mirror; it draws shape from `002-develop-skill` (Phase 2 dogfood) and `001-design-skill` (Phase 1 calibration anchor) for interview/PRD/manifest format only — not for content.
- **Locked-in convention for cross-skill ordering.** Per `v2/docs/SESSION-HANDOFF.md` Phase 3 priority order, `specflow:complete` ships before `specflow:decision`. This PRD assumes `specflow:complete`'s decision-log writer behaviour as fixed (it writes when retros surface significant patterns) and frames `specflow:decision` as the out-of-band complement, not as competition.
- **Worked example: 002-develop-skill.** Calibration anchor for what a Phase 2/3 dogfood interview + PRD + Gate 2 manifest looks like — neither rubber-stamping nor bikeshedding. This dogfood pass aims for the same authenticity at smaller scope.

## Goal (confirmed before grilling)

- **Outcome:** users log decisions the moment they make them, not at task close. Out-of-band decisions don't fall through cracks; the `decision-log.md` accumulates project context as a human-readable narrative paired with the structured task-history that `specflow:complete` writes.
- **Audience:** Power Users (engineers running specflow in their repos) who hit a decision-worthy moment mid-flow — picking between two libraries, reversing a previous architectural choice, sunsetting a tool, ratifying a convention — and want to capture it without leaving the conversation. Secondary: future readers (the same engineers months later, or a new teammate reading the project's decision history).
- **Success looks like:** invoking `/specflow:decision` (or `specflow:decision "title"`) walks the user through the six required fields with sensible inferences where possible (date auto-populated, related files/tasks proposed from recent context), writes a single new entry to `admin/decision-log.md` matching the file's existing format byte-for-byte, and returns one chat line confirming the entry's title and the file path. Re-running the skill on a duplicate title surfaces the existing entry and asks the user how to proceed (supersede, edit-in-place, abort) rather than silently appending a second entry with the same title.
- **Driving value:** removes the failure mode where decisions made between tasks go uncaptured because no skill is firing (`specflow:complete` only fires at task close; `specflow:scope-change` only fires when intent changes mid-development). The decision log is the project's narrative memory; `task-history.json` is the structured ledger. Both are needed — the skill that fills the narrative side at human-decision moments is `specflow:decision`. Removes the secondary failure mode where engineers DO write decisions but drift from the file's schema (manual markdown edits accumulate inconsistencies; a skill keeps the format consistent so Phase 3 self-learning can read the file for patterns).
- **Out of scope at the goal level:** (1) capturing decisions tied to specific tasks — those go through `specflow:complete`'s significant-pattern path, never duplicated here; (2) editing or rewriting prior entries — the file's preamble declares entries are append-only with superseding entries linking back, and the skill respects that (no in-place edits); (3) Linear / external-system sync — `specflow:decision` writes the markdown file, full stop; if a project wants Linear cross-links, that's a `specflow:linear` enhancement, not this skill's surface; (4) auto-detecting decision-worthy moments without user invocation — the skill is user-invoked, not ambient; auto-detection is `/insights` (Phase 3 monthly cadence); (5) Phase 3 self-learning consumption — this skill produces the entries; consumption (pattern mining, rule-promotion suggestions) is `/insights` and `/prune`.

User confirmed: 2026-05-06.

## Rounds

### Round 1 — Invocation modes: interactive only, or also command-line args?

- **Q:** The stub SKILL.md frontmatter lists trigger `/specflow:decision`. The goal's Success-looks-like names two invocation modes — `/specflow:decision` (single-shot interactive) and `specflow:decision "title"` (command-line title arg). Are there other invocation shapes worth supporting in v1 (e.g. `--all-fields-as-args`, `--from-clipboard`, `--scratch-file`)? And what's the conversational flow when the title is supplied vs. omitted?
- **AI's recommended answer:** Two invocation modes for v1, no more. (a) `/specflow:decision` — fully interactive, six prompts in sequence (title → context → decision → rationale → related; date is auto-populated from today). (b) `specflow:decision {title-as-string}` — title pre-filled from the argument, remaining five prompts run interactively. No `--all-fields-as-args` flag in v1: a six-field shell command is harder to compose than a six-prompt conversation, and no documented consumer is asking for it. No `--from-clipboard` or `--scratch-file` in v1: speculative configurability per Simplicity First, and the interactive prompt already accepts multi-line paste for any field. The conversational flow when title is supplied: skip the title prompt, immediately ask for context. When title is omitted: ask for title first. Date prompt is always skipped (auto-populated). Related-files-or-tasks prompt accepts a comma-separated or newline-separated list and validates each entry exists on disk (file paths) or resolves in `admin/task-history.json` (task IDs); unresolvable entries surface a soft warning ("path `foo.ts` not found — keep anyway, edit, or drop?") but never block — the user may legitimately reference a path they're about to create. — *Reasoning: the goal's Driving value field calls out that the skill must be one command in the user's mid-flow moment, so optimising for terseness (one-string title arg) is correct, but adding more flags increases the surface area beyond what the goal's two-use-cases-named justify. The unresolvable-entry soft-warning shape matches the Phase 1 `specflow:misc --auto` precedent of "validate but don't block on disposable references."*
- **User's answer:** confirmed.
- **Resolved:** two invocation modes for v1 — `/specflow:decision` (full interactive) and `specflow:decision {title}` (title pre-filled, remaining fields interactive); date always auto-populated from today; related-files-or-tasks validation produces a soft warning on unresolvable entries (no block); no other flags in v1. — flows into §Requirements R1, R2, R3; AC AC-1, AC-2.

### Round 2 — Schema fidelity: does the skill literally match the existing file's format byte-for-byte?

- **Q:** The goal's Success-looks-like demands "writes a single new entry to `admin/decision-log.md` matching the file's existing format byte-for-byte." Reading the existing file (`plugins/specflow/examples/docs/specflow/admin/decision-log.md`), the schema is: H2 title, blank line, `**Date:**` paragraph, `**Context:**` paragraph, `**Decision:**` paragraph, `**Rationale:**` paragraph, `**Related:**` paragraph, blank line, `---`, blank line. Every existing entry follows this exact shape. Does the skill literally reproduce this byte-for-byte, including trailing blank lines and the separator? And what if a future user has hand-edited the file into a slightly different shape (e.g. added a `**Tags:**` field) — does the skill respect that drift or normalise back?
- **AI's recommended answer:** Yes — byte-for-byte match against the documented schema (H2 title; blank line; five bold-prefixed paragraphs in fixed order Date → Context → Decision → Rationale → Related; blank line; `---`; blank line before next entry). This is the format the worked example file ships with and the format the file's preamble describes. The skill writes new entries in this shape and does NOT normalise prior entries — those are append-only by the file's own preamble rule, so any hand-edited drift in older entries stays. **Hand-drift handling:** before writing, the skill reads the last entry in the file and verifies the schema match. If the last entry has unexpected fields (e.g. a `**Tags:**` line), the skill surfaces a one-line warning to the user — *"Last entry contains a non-standard `**Tags:**` field. Continuing with the standard schema; your entry will not include this field unless you add it manually. To extend the schema project-wide, propose an enhancement PRD."* — and continues. The skill never fails on schema drift; it warns and proceeds with the documented schema. This protects future Phase 3 `/insights` consumers (which expect a consistent schema) without preventing the user from making the entry. — *Reasoning: the goal's Driving value field names "the skill keeps the format consistent so Phase 3 self-learning can read the file for patterns" — that requires the skill itself to write the canonical schema, not mimic drift. But blocking on drift would defeat the goal's "users log decisions the moment they make them" — the skill must ALWAYS proceed. Warn-and-proceed is the calibration; matches the Phase 1 `specflow:misc` validation pattern.*
- **User's answer:** edit — the warning text should also include the path of the offending entry (line number or title), so the user can decide whether to clean it up. Otherwise the warning is too vague to act on.
- **Resolved:** skill writes new entries byte-for-byte against the canonical schema (H2 title; blank line; five bold-prefixed paragraphs in fixed order Date → Context → Decision → Rationale → Related; blank line; `---`; blank line); skill does NOT normalise prior entries; on schema drift in the LAST existing entry, warn with title + line number of the drifting entry, then proceed with canonical schema; never blocks. — flows into §Requirements R4, R5; AC AC-3, AC-4.

### Round 3 — Idempotency on duplicate titles: append, supersede, or refuse?

- **Q:** The file's preamble declares entries are append-only and superseding decisions get a new entry that links back. The goal's Success-looks-like says re-running on a duplicate title surfaces the existing entry and asks the user how to proceed (supersede / edit-in-place / abort). What does each option actually produce — and is "edit-in-place" compatible with the file's append-only rule?
- **AI's recommended answer:** Three options on duplicate-title detection, with one rejected as incompatible: (1) **Supersede** — write a new entry with the same title (or a slightly amended title like *"X (revised)"*) whose `**Related:**` field links back to the original entry's title. The original entry stays untouched. This is the file's documented pattern. (2) **Abort** — the user realises the duplicate is intentional (they were going to log the same decision again) or they'd rather merge mentally. Skill exits without writing; no scratch file leaked. (3) **Edit-in-place** — REJECTED. Editing a prior entry violates the file's append-only preamble rule, which exists for audit reasons (decision history is inviolate). Instead, when the user asks for "edit-in-place" the skill explains the rule and offers the supersede path: *"Existing entries are append-only by file preamble. Supersede instead? The new entry can link back to the original."* If the user genuinely wants to edit (e.g. fixing a typo in a prior entry), they edit the file by hand — the skill is not a markdown editor. Default option on duplicate detection: prompt the user to pick supersede or abort; never auto-supersede. **Title-match is exact-match, case-insensitive, after trimming surrounding whitespace** — fuzzy matching would over-fire on legitimately-different titles that share a keyword. — *Reasoning: the goal's Out-of-scope-at-goal-level forbids editing prior entries; the file's preamble forbids it too. So the option-set is constrained to two real options + one explicit rejection. Exact-match-after-trim is the minimum sufficient check; fuzzy matching would add complexity without a documented use case.*
- **User's answer:** confirmed.
- **Resolved:** duplicate-title detection uses exact-match (case-insensitive, whitespace-trimmed); options are supersede (writes new entry with `**Related:**` linking the original) or abort (exits without writing); edit-in-place is explicitly rejected and the skill explains the file's append-only rule when asked; never auto-supersedes. — flows into §Requirements R6; AC AC-5.

### Round 4 — Boundary with `specflow:complete`: when both could fire on the same surface, which wins?

- **Q:** `specflow:complete` writes to `admin/decision-log.md` when a task retro surfaces a significant pattern. `specflow:decision` writes to the same file out-of-band. If a user just closed a task via `specflow:complete` (which appended a decision-log entry) and then immediately invokes `/specflow:decision` for what feels like a related decision, do we have two skills writing to the same file with overlapping intent? What's the boundary, and is there a check that prevents accidental double-writes?
- **AI's recommended answer:** The boundary is intent-source: `specflow:complete` writes a decision-log entry only when the task's retro surfaces a project-level pattern (the entry is task-derived). `specflow:decision` writes when the user invokes it, regardless of whether a task closed recently (the entry is user-driven, out-of-band). Both writes can legitimately coexist — they capture different semantics. The skill DOES NOT pre-empt or coordinate with `specflow:complete`; that would couple two Phase 3 skills unnecessarily. Two safety nets handle the overlap risk: (a) the duplicate-title check from Round 3 catches accidental re-entry of the same titled decision; (b) when `specflow:decision` is invoked within a short window after `specflow:complete` (heuristic: same parent conversation, OR a `task-history.json` entry was written within the last hour), the skill surfaces a soft prompt — *"You closed a task recently (T{N} — `{title}`). If this decision is task-related, consider running `specflow:complete` instead, which will link the decision to the task. Continue with out-of-band entry, or abort?"* — and proceeds only on explicit confirm. The prompt is non-blocking informational only; the user owns the decision. — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly excludes "capturing decisions tied to specific tasks" — `specflow:complete` owns that lane. The soft prompt makes the boundary visible at the user's mid-flow moment without forcing a coordination layer. The "same parent conversation" heuristic is implementation-flexible; the "within last hour by mtime on `task-history.json`" check is the structured fallback when conversation state isn't accessible.*
- **User's answer:** edit — drop the conversation-state heuristic; the mtime-on-`task-history.json` check is sufficient and doesn't depend on harness behaviour we don't control. The soft prompt should fire when the most-recent `task-history.json` entry has a `completedAt` (or equivalent timestamp) within the last 60 minutes.
- **Resolved:** boundary is intent-source — `specflow:complete` writes task-derived decision entries, `specflow:decision` writes user-driven out-of-band entries; both can coexist on the same file; safety net is the duplicate-title check (Round 3) plus a soft prompt when the most-recent `task-history.json` entry's `completedAt` is within the last 60 minutes; the prompt is informational only and the user can confirm-and-proceed. — flows into §Requirements R7; AC AC-6.

### Round 5 — Failure modes: missing decision-log.md, malformed file, write failure — refuse or recover?

- **Q:** The stub SKILL.md says the file is "created if missing," and the eval names six required fields on the new entry. What's the behaviour when (a) `admin/decision-log.md` does not exist, (b) the file exists but is malformed (e.g. truncated mid-entry, missing the `---` separator at the end), (c) the write fails (disk full, permission denied)? Refuse the run, recover and proceed, or surface the failure?
- **AI's recommended answer:** Three distinct paths. **(a) File missing:** skill creates `admin/decision-log.md` with the standard preamble (the same preamble the worked example file uses — file purpose statement + format-per-entry list) followed by `---` and the new entry. This is the documented "created if missing" behaviour from the stub. **(b) File exists but malformed:** skill performs a minimal parse before writing — read the file, verify it ends with either a complete entry (last `---` followed by an entry that has all five bold-prefixed fields) OR the preamble alone (no entries yet). If the parse detects a truncation (e.g. entry started but never closed), the skill refuses to write and surfaces the failure: *"`admin/decision-log.md` appears truncated — the last entry is incomplete. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` (Phase 1) to validate, or fix the file by hand and re-run."* The skill never auto-repairs a malformed file. **(c) Write failure:** skill catches the write error, leaves any prepared content in `admin/scratch/decision-{timestamp}.md` for recovery, and surfaces the failure: *"Could not write `admin/decision-log.md`: {error}. Your draft is preserved at `admin/scratch/decision-{timestamp}.md` — copy it into the file by hand once the underlying issue is resolved."* The scratch path is also returned to the user in chat so they can see it without opening the folder. — *Reasoning: the goal's Driving value names "the decision log is the project's narrative memory" — corrupting that file silently is the worst possible outcome. Refuse-on-malformed and preserve-on-write-failure are the calibration. Auto-creating on missing is documented behaviour; auto-repairing on malformed is not, and would require schema judgement the skill doesn't have. Scratch-file recovery matches the Phase 1 `panic` precedent of "snapshot before mutating."*
- **User's answer:** confirmed.
- **Resolved:** file-missing → skill creates with standard preamble + new entry; file-malformed (truncated last entry, missing trailing separator) → skill refuses to write and surfaces a clear error pointing at `specflow:doctor` and manual repair; write-failure → skill preserves the draft to `admin/scratch/decision-{timestamp}.md` and surfaces the path. Skill never auto-repairs a malformed file. — flows into §Requirements R8, R9; AC AC-7, AC-8.

### Round 6 — Verify-step discipline: how does the skill confirm the entry landed correctly?

- **Q:** Goal-Driven Execution requires inline verify steps ("loop until verified" / "every skill that produces output declares verify steps inline"). What does verification look like for a single-entry append? Re-read the file and check the new entry exists? Parse the new entry's six fields back? Diff against a pre-write snapshot?
- **AI's recommended answer:** Two-stage verification, both binary. **Stage 1 (post-write read-back):** after the write succeeds, the skill re-reads the file's last entry and confirms (i) the H2 title matches the user's input verbatim, (ii) all five bold-prefixed fields are present in the documented order, (iii) the date matches today's `YYYY-MM-DD`, (iv) the entry is preceded by a `---` separator (or by the file's preamble if this was the first entry). Any failure aborts the run with an error pointing at the scratch file and the file path. **Stage 2 (chat confirmation):** the skill returns one line to the user: *"Logged decision `{title}` to `docs/specflow/admin/decision-log.md`. Date: {YYYY-MM-DD}. Related: {comma-separated list or "none"}."* The chat line is the user's verification surface — they see what the file now says without opening it. No diff-against-snapshot in v1 (overengineered for an append-only flow); the read-back is the binary check. — *Reasoning: the goal's Success-looks-like names "returns one chat line confirming the entry's title and the file path" as the surface — the chat line IS the verification surface, plus the post-write read-back is the binary check. Two stages because (a) the read-back catches mechanical write failures the OS didn't report (e.g. encoding mangling), and (b) the chat line catches user-intent mismatches (the user sees the title they entered echoed back; if it's wrong, they invoke supersede).*
- **User's answer:** confirmed.
- **Resolved:** two-stage verification — (1) post-write read-back confirms title verbatim, five fields present in order, today's date, separator preceding; (2) chat confirmation echoes title + file path + date + related list; failures abort with scratch-file path; no diff-against-snapshot in v1. — flows into §Requirements R10; AC AC-9.
