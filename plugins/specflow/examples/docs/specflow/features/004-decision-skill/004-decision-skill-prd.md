# specflow:decision — out-of-band decision capture

## Vision

`specflow:decision` is the lightweight skill users invoke when they hit a decision-worthy moment mid-flow — picking between two libraries, reversing a previous architectural choice, sunsetting a tool, ratifying a convention — and want to capture it without leaving the conversation. Users log decisions the moment they make them, not at task close. Out-of-band decisions don't fall through cracks; the `decision-log.md` accumulates project context as a human-readable narrative paired with the structured task-history that `specflow:complete` writes. The skill walks the user through the six required fields with sensible inferences (date auto-populated, related files/tasks proposed from recent context), writes a single new entry to `admin/decision-log.md` matching the file's existing format byte-for-byte, and returns one chat line confirming the entry's title and the file path. Re-running on a duplicate title surfaces the existing entry and asks the user to supersede or abort — never silently appending.

## Problem

Phase 3 of specflow closes the self-learning loop: every completed task feeds memory; every new task reads from it. `specflow:complete` captures task-completion retros into `task-history.json` (structured) and `decision-log.md` (narrative, when retros surface significant patterns). But task-derived decisions are not the only decisions a project accumulates. A team picks Postgres triggers over application-layer audit at a whiteboard moment. A tool gets sunsetted in a Slack thread (or what used to be a Slack thread, before this very project log captured the sunset). A convention crystallises through three engineers nodding at the same code review comment. None of those moments fire `specflow:complete`; none fire `specflow:scope-change` (which only fires when intent changes mid-development). Without a dedicated skill the moments stay un-captured — the engineer means to write the entry later, doesn't, and the project's narrative memory is the worse for it. Worse still, when engineers DO write entries by hand, they drift from the file's schema: missing fields, inconsistent date formats, free-text where structured paragraphs belong. Phase 3 self-learning consumers (`/insights`, `/prune`) read the file for patterns; schema drift sabotages that read.

The fix is a skill that runs in seconds, fires at the user's decision moment, and writes the canonical schema. Two invocation modes: `/specflow:decision` (full interactive) and `specflow:decision {title}` (title pre-filled). Six required fields. Date auto-populated. Related files/tasks soft-validated against the project's actual files and `task-history.json`. Duplicate-title detection with supersede / abort options (no silent append, no in-place edit per the file's append-only preamble). Schema-drift detection on the prior entry warns but never blocks. Failure modes (missing file, malformed file, write error) each have an explicit path. Verification is a post-write read-back plus a chat-line echo. Seven requirements; nine acceptance criteria; the smallest skill specflow ships and a worked example of how the lightweight orchestrator pattern scales down.

## Goals

- Two invocation modes — `/specflow:decision` (fully interactive, six prompts) and `specflow:decision {title}` (title pre-filled from arg, remaining five fields interactive). No additional flags in v1.
- Date is always auto-populated from today; never prompted.
- Six required fields per entry (title, date, context, decision, rationale, related), written byte-for-byte against the canonical schema documented in `admin/decision-log.md`'s preamble: H2 title; blank line; five bold-prefixed paragraphs in fixed order Date → Context → Decision → Rationale → Related; blank line; `---`; blank line.
- Related files/tasks are soft-validated — file-path entries checked against disk, task-ID entries resolved against `admin/task-history.json`; unresolvable entries surface a one-line warning naming the unresolvable reference but never block.
- Duplicate-title detection is exact-match (case-insensitive, whitespace-trimmed) — on match, the skill surfaces the existing entry and asks the user to pick supersede (writes new entry whose `**Related:**` field links the original by title) or abort. Edit-in-place is explicitly rejected; the skill explains the file's append-only preamble rule when asked.
- Boundary with `specflow:complete` is preserved by intent-source: `specflow:complete` writes task-derived entries; `specflow:decision` writes user-driven out-of-band entries. Both can coexist on the same file. A soft prompt fires when `admin/task-history.json` was last modified within 60 minutes, asking the user whether they meant to run `specflow:complete` instead — informational only, never blocking.
- Failure modes are deterministic: file missing → create with the standard preamble + new entry; file malformed (truncated last entry, missing trailing separator) → refuse to write and point at `specflow:doctor` + manual repair; write error → preserve the draft to `admin/scratch/decision-{timestamp}.md` and surface the path.
- Verification is two-stage: post-write read-back confirms the new entry's title verbatim, all five fields present in order, today's date, and a `---` separator preceding (or the file's preamble if this is the first entry); chat confirmation echoes title + file path + date + related list back to the user.

## Non-goals

- **Capturing decisions tied to specific tasks.** Those go through `specflow:complete`'s significant-pattern path. The two skills cooperate by intent-source, never duplicate.
- **Editing or rewriting prior entries.** The file's preamble declares entries are append-only. Corrections happen via supersede (a new entry that links back) or by-hand markdown edits — never via this skill.
- **Linear or external-system sync.** `specflow:decision` writes the markdown file, full stop. If a project wants Linear cross-links, that's a `specflow:linear` enhancement.
- **Auto-detection of decision-worthy moments.** The skill is user-invoked; ambient detection is `/insights` (Phase 3 monthly cadence).
- **Phase 3 self-learning consumption.** This skill produces entries; consumption (pattern mining, rule-promotion suggestions) belongs to `/insights` and `/prune`.
- **Schema extension beyond the documented six fields.** Adding `**Tags:**`, `**Severity:**`, or any other field is out of scope for v1. If a project wants schema extension, that's an enhancement PRD; the skill warns on detected drift but does not adopt it.

## Users

- **Power User (per `admin/profiles.json`)** — engineers running specflow in their repos who hit a decision-worthy moment mid-flow. They invoke the skill in seconds, walk the prompts, and continue what they were doing. They need the prompts to be terse, the related-files validation to be soft (so they can reference paths they're about to create), and the chat-line echo to confirm the entry without opening the file.
- **Future readers** — the same engineers months later, or a new teammate reading the project's decision history. They consume `decision-log.md` in their editor or in PR diffs. They benefit from schema consistency: every entry has the same six fields in the same order, every date in the same format, every supersede chain readable as a `**Related:**` link.
- **Phase 3 self-learning consumers (`/insights`, `/prune`)** — automated readers running on monthly / quarterly cadence. They benefit from the schema-canonical writes this skill produces. Their failure mode (pattern mining sabotaged by drift) is the secondary failure mode this skill's existence prevents.

## Requirements

- **R1.** Two invocation modes. `/specflow:decision` runs the full interactive flow with six prompts: title, context, decision, rationale, related (date is auto-populated, never prompted). `specflow:decision {title-as-string}` pre-fills the title from the argument and runs the remaining five prompts interactively. No other invocation modes (no `--all-fields-as-args`, no `--from-clipboard`, no `--scratch-file`) in v1.
  - Trace: interview Round 1 — *two invocation modes for v1 — `/specflow:decision` (full interactive) and `specflow:decision {title}` (title pre-filled, remaining fields interactive); date always auto-populated from today; no other flags in v1*.
  - Serves goal: Outcome (users log decisions the moment they make them — terse invocation matches the mid-flow context).

- **R2.** Date auto-population. The skill auto-populates the entry's `**Date:**` field with today's date in `YYYY-MM-DD` format. The skill never prompts the user for a date and never accepts an override flag for the date. Backdating is explicitly out of scope for v1; if the user wants to log a decision dated to the past, they edit the file by hand.
  - Trace: interview Round 1 — *date prompt is always skipped (auto-populated)*.
  - Serves goal: Outcome (skill respects the canonical schema; date format consistent across entries).

- **R3.** Related-files-and-tasks soft validation. The Related prompt accepts a comma-separated or newline-separated list of references. Each reference is classified: entries containing `/` or ending with a recognised file extension are treated as file paths and checked against disk; entries matching the `T-NNNN` or `T{N}` pattern are treated as task IDs and resolved against `admin/task-history.json`; everything else passes through as free-text. Unresolvable file paths and task IDs surface a one-line warning naming each unresolvable reference (e.g. *"path `src/foo.ts` not found; task `T-0042` not in task-history.json — keep both anyway, edit, or drop?"*) and prompt the user to pick keep / edit / drop. Free-text references never warn. The skill never blocks on validation failure.
  - Trace: interview Round 1 — *related-files-or-tasks prompt accepts a comma-separated or newline-separated list and validates each entry exists on disk (file paths) or resolves in `admin/task-history.json` (task IDs); unresolvable entries surface a soft warning but never block*.
  - Serves goal: Outcome (sensible inferences where possible — proposed-from-recent-context is achieved by validating user input, not by autocomplete).

- **R4.** Canonical schema match for new entries. The skill writes new entries byte-for-byte against the canonical schema: H2 title (`## {title}`); blank line; `**Date:** {YYYY-MM-DD}`; blank line; `**Context:** {context paragraph}`; blank line; `**Decision:** {decision paragraph}`; blank line; `**Rationale:** {rationale paragraph}`; blank line; `**Related:** {comma-separated list, or the literal text "none"}`; blank line; `---`; blank line. New entries are appended at the end of the file. The skill never reorders, removes, or modifies prior entries.
  - Trace: interview Round 2 — *skill writes new entries byte-for-byte against the canonical schema (H2 title; blank line; five bold-prefixed paragraphs in fixed order Date → Context → Decision → Rationale → Related; blank line; `---`; blank line); skill does NOT normalise prior entries*.
  - Serves goal: Driving value (the skill keeps the format consistent so Phase 3 self-learning can read the file for patterns).

- **R5.** Schema-drift detection on the most-recently-written entry. Before writing, the skill identifies the most-recently-written existing entry — defined as the **last entry in file order** (i.e. the entry immediately preceding the file's final `---` separator, or the only entry in the file). The skill does NOT use date-based ordering for this check; file order is the canonical reading order and matches what a future Phase 3 consumer will see. The skill verifies the entry contains exactly the five canonical bold-prefixed fields (`**Date:**`, `**Context:**`, `**Decision:**`, `**Rationale:**`, `**Related:**`) in the canonical order. If the entry has additional fields (e.g. `**Tags:**`), missing fields, or fields out of order, the skill surfaces a one-line warning naming both (i) the entry's H2 title AND (ii) the entry's start line number in the file (e.g. *"Last entry in file order ('Slack removed from the stack', line 36) contains a non-canonical `**Tags:**` field — continuing with canonical schema"*) and proceeds with the write. The skill never blocks on detected drift; it warns and proceeds.
  - Trace: interview Round 2 (edited) — *on schema drift in the LAST existing entry, warn with title + line number of the drifting entry, then proceed with canonical schema; never blocks*. Refined at Gate 2 per tbc-r1-f1: the unstated "what counts as last" assumption is now stated — file order, not date order; the warning text shape includes both title AND line number per the user's Round 2 edit.
  - Serves goal: Driving value (schema-canonical writes preserve Phase 3 self-learning consumption even when prior entries have drifted).

- **R6.** Duplicate-title detection. Before writing, the skill compares the user's proposed title (case-insensitive, whitespace-trimmed) against every existing entry's H2 title (same normalisation). On exact match, the skill surfaces the existing entry's date and a one-line summary, then prompts the user to pick: (a) **supersede** — write a new entry; the new entry's `**Related:**` field automatically prepends a link to the original entry by title (e.g. `Supersedes: "{original title}" (YYYY-MM-DD)`); the original entry stays untouched; (b) **abort** — exit without writing; no scratch file. Edit-in-place is explicitly rejected; if the user asks for edit-in-place, the skill responds: *"Existing entries are append-only by file preamble. Supersede instead? The new entry can link back to the original."* The skill never auto-supersedes — it always prompts.
  - Trace: interview Round 3 — *duplicate-title detection uses exact-match (case-insensitive, whitespace-trimmed); options are supersede or abort; edit-in-place is explicitly rejected; never auto-supersedes*.
  - Serves goal: Outcome (re-running on a duplicate title surfaces the existing entry and asks the user how to proceed; never silently appending).

- **R7.** `specflow:complete` boundary soft-prompt. Before writing, the skill checks `admin/task-history.json`'s `mtime`. If the file's `mtime` is within the last 60 minutes (3600 seconds), the skill surfaces a soft prompt: *"You closed a task recently (`task-history.json` written {N} minutes ago). If this decision is task-related, consider running `specflow:complete` instead — it will link the decision to the task. Continue with out-of-band entry, or abort?"*. The user picks continue or abort; the skill proceeds only on explicit continue. **File-missing path:** when `admin/task-history.json` does not exist (fresh project, or `specflow:complete` has never written), the soft prompt does not fire — the skill proceeds directly to the write step. The boundary check is informational only and exists to make the `specflow:complete` lane visible at the user's mid-flow moment, never to block.
  - Trace: interview Round 4 (edited) — *safety net is the duplicate-title check (Round 3) plus a soft prompt when the most-recent `task-history.json` entry's `completedAt` is within the last 60 minutes; the prompt is informational only and the user can confirm-and-proceed*. Extended at Gate 2 per da-r1-f1: file-missing path follows the goal's "never blocks" principle — no `task-history.json` means no boundary to check, skill proceeds directly.
  - Serves goal: Out-of-scope-at-goal-level (capturing decisions tied to specific tasks belongs to `specflow:complete`; the soft prompt makes the lane visible without coupling the two skills).

- **R8.** File-missing creation path. When `admin/decision-log.md` does not exist, the skill creates the file with the standard preamble copied verbatim from the worked-example file's preamble (file purpose statement + format-per-entry list + `---` separator), then appends the new entry per R4. The standard preamble is part of the skill's prompt body — the skill carries the canonical preamble text and writes it on first creation, so projects without an existing file get the same schema framing as projects with one. **First-entry detection:** when the skill is writing the first entry into a freshly-created file, the new entry is preceded by the preamble's trailing `---` separator (not by another entry's trailing separator).
  - Trace: interview Round 5 — *file-missing → skill creates with standard preamble + new entry*.
  - Serves goal: Driving value (the skill keeps the format consistent — the preamble itself is part of the format).

- **R9.** File-malformed refusal path. Before writing, the skill performs a minimal parse: read the file; verify the file ends with either (a) the file's preamble alone followed by `---` (no entries yet) or (b) a complete entry — H2 title, all five canonical fields in order, trailing `---` separator. If the parse detects any other shape (truncated entry, missing trailing separator, dangling preamble without `---`), the skill refuses to write and surfaces the failure: *"`admin/decision-log.md` appears truncated or malformed at end-of-file — last shape detected: {description}. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` to validate, or fix the file by hand and re-run."* The skill never auto-repairs a malformed file. **Scope of the parse:** the parse looks only at the file's tail (preamble-only OR last entry + trailing separator); drift detected mid-file is handled by R5's warn-and-proceed path, not by this refusal path. R9 is for tail-corruption only.
  - Trace: interview Round 5 — *file-malformed (truncated last entry, missing trailing separator) → skill refuses to write and surfaces a clear error pointing at `specflow:doctor` and manual repair*.
  - Serves goal: Driving value (the decision log is the project's narrative memory; corrupting that file silently is the worst possible outcome).

- **R10.** Write-failure preservation path. When the file write fails (disk full, permission denied, filesystem error), the skill catches the error, writes the prepared entry content to `admin/scratch/decision-{timestamp}.md` (where `{timestamp}` is `YYYYMMDD-HHMMSS` in UTC), and surfaces the failure with both the underlying error and the scratch path: *"Could not write `docs/specflow/admin/decision-log.md`: {error}. Your draft is preserved at `docs/specflow/admin/scratch/decision-{timestamp}.md` — copy it into the file by hand once the underlying issue is resolved."* The scratch directory is created if missing. The skill exits non-zero (or returns a failure marker to the parent harness) so callers can detect the failure programmatically.
  - Trace: interview Round 5 — *write-failure → skill preserves the draft to `admin/scratch/decision-{timestamp}.md` and surfaces the path*.
  - Serves goal: Driving value (the decision log is the project's narrative memory — preserving the user's draft on filesystem failure preserves the user's effort).

- **R11.** Two-stage verification (post-write read-back + chat confirmation). After the file write succeeds, the skill (Stage 1) re-reads the file's last entry and confirms (i) the H2 title matches the user's input verbatim, (ii) all five bold-prefixed fields are present in the canonical order, (iii) the date matches today's `YYYY-MM-DD`, (iv) the entry is preceded by a `---` separator (or by the file's preamble if this was the first entry into a freshly-created file). Any Stage-1 failure aborts the run with an error pointing at the scratch path (R10's scratch preservation applies). Then (Stage 2) the skill returns one chat line to the user: *"Logged decision `{title}` to `docs/specflow/admin/decision-log.md`. Date: {YYYY-MM-DD}. Related: {comma-separated list, or the literal text "none"}."* The chat line is the user-facing confirmation surface; it always fires after a successful Stage-1 verification. Stage 1 is the binary verify step; Stage 2 is the binary user-surface contract.
  - Trace: interview Round 6 — *two-stage verification — (1) post-write read-back confirms title verbatim, five fields present in order, today's date, separator preceding; (2) chat confirmation echoes title + file path + date + related list*. Refined at Gate 2 per goal-r1-f1: the chat-line shape is now an R-level contract (not just a verify step), so AC-9's chat-line check has an R to verify against.
  - Serves goal: Success-looks-like (returns one chat line confirming the entry's title and the file path).

## Acceptance criteria

- **AC-1.** Running `/specflow:decision` (no argument) prompts for title first, then context, decision, rationale, related — in that order. Running `specflow:decision "{title-string}"` skips the title prompt and starts with the context prompt. Neither flow prompts for a date. Neither flow accepts other flags (e.g. `--from-clipboard`); unrecognised flags produce an error message naming the two supported invocation shapes. (Verifies R1, R2.)

- **AC-2.** When the user enters a comma-separated or newline-separated list at the related prompt, every entry containing `/` or ending with a recognised file extension (`.ts`, `.tsx`, `.js`, `.jsx`, `.py`, `.go`, `.rs`, `.md`, `.json`, `.yml`, `.yaml`, `.html`, `.css`, etc.) is checked against disk; every entry matching the pattern `T-?\d+` is resolved against `admin/task-history.json`'s `tasks[].id` field; every other entry is treated as free-text and never validated. Unresolvable file paths and task IDs surface a single warning line naming each unresolvable reference and prompt the user to pick keep / edit / drop. The skill proceeds regardless of the user's choice. (Verifies R3.)

- **AC-3.** A new entry written to `admin/decision-log.md` matches the canonical schema byte-for-byte: starts with `## {title}` exactly as the user entered it; followed by a single blank line; then `**Date:** {YYYY-MM-DD}` (today's date); then a single blank line; then `**Context:** {context paragraph}`; single blank line; `**Decision:** {decision paragraph}`; single blank line; `**Rationale:** {rationale paragraph}`; single blank line; `**Related:** {comma-separated list, or the literal text "none"}`; single blank line; `---`; single blank line. New entries are appended at end-of-file. Prior entries are byte-identical before and after the run (verified by checksum or `git diff`). (Verifies R4.)

- **AC-4.** When the most-recently-written existing entry (defined as the last entry in file order — the entry immediately preceding the file's final `---` separator, or the only entry in the file) has additional fields, missing fields, or fields out of order relative to the canonical schema, the skill emits exactly one warning line of the shape *"Last entry in file order ('{title}', line {N}) contains {description of drift} — continuing with canonical schema"* before proceeding with the write. The warning fires once and does not block. The new entry written after the warning matches the canonical schema (per AC-3) regardless of the drifting entry's shape. (Verifies R5.)

- **AC-5.** When the user-proposed title (case-insensitive, whitespace-trimmed) exact-matches an existing entry's H2 title (same normalisation), the skill surfaces the matching entry's date and the first 80 characters of its `**Decision:**` field, then prompts for supersede / abort. On supersede, the new entry's `**Related:**` field has the literal prefix `Supersedes: "{original title}" ({original date})` followed by any user-provided related references separated by `; `. On abort, no file is written and no scratch file is created. When the user asks for edit-in-place, the skill returns the literal response *"Existing entries are append-only by file preamble. Supersede instead? The new entry can link back to the original."* and re-prompts for supersede / abort. (Verifies R6.)

- **AC-6.** When `admin/task-history.json` exists AND its `mtime` is within the last 3600 seconds (60 minutes), the skill surfaces exactly one prompt of the shape *"You closed a task recently (`task-history.json` written {N} minutes ago). If this decision is task-related, consider running `specflow:complete` instead — it will link the decision to the task. Continue with out-of-band entry, or abort?"* before any other prompt fires. The user must explicitly pick continue or abort. When `admin/task-history.json` does not exist OR its `mtime` is older than 3600 seconds, this prompt does not fire and the skill proceeds directly. (Verifies R7.)

- **AC-7.** When `admin/decision-log.md` does not exist at the start of the run, the skill creates the file containing (i) the canonical preamble (file purpose statement + format-per-entry bullet list, copied verbatim from the skill's prompt body) followed by (ii) a `---` separator on its own line followed by (iii) a blank line followed by (iv) the new entry per AC-3. The created file is well-formed against R9's parse rules — a subsequent `specflow:decision` invocation does not trigger R9's refusal path on the file the skill just created. (Verifies R8.)

- **AC-8.** When `admin/decision-log.md` exists but its tail does not match either (a) the canonical preamble alone followed by `---` (no entries) or (b) a complete entry with H2 title + all five canonical fields in order + trailing `---` separator, the skill refuses to write and emits the literal error *"`admin/decision-log.md` appears truncated or malformed at end-of-file — last shape detected: {description}. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` to validate, or fix the file by hand and re-run."* No new entry is written; no scratch file is created (the user has not yet entered any content because the parse runs before the field prompts). The R9 parse looks only at the file's tail; drift detected mid-file is handled by R5's warn-and-proceed path (per AC-4) and does not trigger R9 refusal. (Verifies R9.)

- **AC-9.** When the file write step raises an error (filesystem failure, permission denied, disk full, etc.), the skill writes the prepared entry content to `docs/specflow/admin/scratch/decision-{YYYYMMDD-HHMMSS-UTC}.md` (creating the `scratch/` directory if missing) and emits the literal error *"Could not write `docs/specflow/admin/decision-log.md`: {underlying error message}. Your draft is preserved at `docs/specflow/admin/scratch/decision-{timestamp}.md` — copy it into the file by hand once the underlying issue is resolved."* The skill exits with a non-zero status (or returns a structured failure marker to the parent harness). (Verifies R10.)

- **AC-10.** After a successful file write, the skill (Stage 1) re-reads the file and confirms the last entry's H2 title matches the user's input verbatim, all five canonical fields are present in canonical order, the `**Date:**` field equals today's `YYYY-MM-DD`, and the entry is preceded by either a `---` separator (existing-file path) or the file's preamble + `---` (file-missing path). If any Stage-1 check fails, the skill aborts and falls through to AC-9's scratch preservation. After a successful Stage-1 pass, the skill (Stage 2) emits exactly one chat line of the shape *"Logged decision `{title}` to `docs/specflow/admin/decision-log.md`. Date: {YYYY-MM-DD}. Related: {comma-separated list, or the literal text "none"}."* The chat line is the only output line returned to the parent context on success. (Verifies R11.)

## Open questions

- **`specflow:decision` invocation while another specflow skill is mid-flow.** If the user invokes `/specflow:decision` while `specflow:develop` (Phase 2) is paused on a Verifier rejection, does the decision-log entry land cleanly, or does the in-flight orchestration's `admin/scratch/{orchestration-id}/` state interfere? The interview did not surface this. Recommend: the skill is independent — it never touches `admin/scratch/{orchestration-id}/` — so the two flows do not interfere. Confirm at implementation.
- **Preamble drift over time.** R8 carries the canonical preamble in the skill's prompt body; if a project has hand-edited the existing file's preamble (added a sentence, reformatted the bullet list), the skill does not touch the existing preamble — it only writes the canonical preamble on file-missing. But subsequent `/insights` consumers reading the file will see a non-canonical preamble. The interview did not cover preamble drift specifically. Recommend: leave the existing preamble alone; if Phase 3 self-learning surfaces preamble drift as a friction point, address via a `specflow:doctor` schema check. Defer to implementation.
- **Internationalisation of the date format.** `YYYY-MM-DD` is the canonical format per the file's existing entries. The interview did not surface any user need for alternate date formats. Recommend: hard-code `YYYY-MM-DD`; surface as a v2 enhancement if a project asks for it. Defer.
