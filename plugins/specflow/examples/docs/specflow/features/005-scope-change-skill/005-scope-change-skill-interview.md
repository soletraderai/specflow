# PRD interview — features/005-scope-change-skill

## Original request

> Write the spec for `specflow:scope-change`, the Phase 3 skill that captures mid-development scope changes — *why* the intent changed, what the PRD now needs to say, which tasks regenerate, and what in-flight work is impacted. The architectural shape is locked in by `docs/PRD.md` Phase 3 scope item 4 (and referenced from Verifier-rejection option 3 in `specflow:develop`); this PRD synthesises the implementation contract at the SKILL.md level. The skill is the place specflow keeps mid-development drift honest instead of silent.

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `docs/PRD.md` § "Phase 3 — Memory and self-learning" scope item 4 (lines 217-218) names `specflow:scope-change` end-to-end: capture the *why*, update PRD, regenerate affected tasks, flag impacts on in-flight work. Phase 3 self-learning relies on the PRD/task/decision triad staying in sync; this skill is what keeps it honest. Re-litigating the architectural decision is out of scope per `docs/SESSION-HANDOFF.md` § "Architectural decisions — locked in".
- **Stub SKILL.md exists.** `skills/scope-change/SKILL.md` is a description-level stub with the v2 contract: `requires:` includes the active feature's PRD + tasks + interview; `produces:` includes the updated PRD + HTML re-render + regenerated tasks + updated interview + `decision-log.md` entry. The stub names the five-step behaviour (capture *why*, update PRD, regenerate tasks, flag in-flight, log decision) and the four verify steps, but does not yet have the operational prompt body.
- **Auto-suggestion handoff from `specflow:develop` Phase F.** `skills/develop/SKILL.md` Phase F.3 option 3 ("abort the task and surface to `specflow:scope-change`") and the Phase A resume prompt ("`specflow:scope-change` if the PRD itself needs revision") both name this skill as the destination when a Verifier rejection or end-of-feature inspection points at the PRD itself rather than the implementation. The integration is one-directional: `specflow:develop` directs the user to invoke `specflow:scope-change`; `specflow:scope-change` does not auto-fire from `specflow:develop` without the user's election.
- **Sister Phase 1 orchestrators are operational.** `skills/prd/SKILL.md` (5 phases, Gate 2) and `skills/task/SKILL.md` (5 phases, Gate 3) both exhibit the orchestrator pattern this skill must reuse — the PRD-update step delegates to `specflow:prd` Phase C synthesis re-fired against the revised inputs, and the task-regeneration step delegates to `specflow:task` Phase B re-fired against the revised PRD. Calibration anchor: `templates/orchestrator-pattern.md` for fork / file handoff / command substitution conventions.
- **Decision-log entry shape locked in.** `skills/decision/SKILL.md` (Phase 3 sister skill) defines the canonical `decision-log.md` entry shape — title, context, decision, rationale, date, references. `specflow:scope-change` writes one decision-log entry per scope change event using that schema, with the *why* landing in the rationale field.
- **Interview file is the audit trail.** Per `docs/PRD.md` § "Resolved decisions" line on PRD interview file, every PRD has a sibling `NNN-{slug}-interview.md` capturing original request, codebase findings, grilling Q&A, and resolved assumptions. Scope changes that mutate the PRD must preserve the interview's resolved-line trace — silently invalidating a Resolved line breaks the PRD-to-interview audit chain. Append-only edits to the interview (a new "Scope change" section) are the surgical path.
- **Standard agents already operational.** Lifecycle agents (Orchestrator, Devil's Advocate, Verifier) and the four principle reviewers ship with the plugin and copy to `admin/agents/standard/` at setup. Scope-change re-uses Gate 2 (PRD vs interview) when the PRD revision crosses a significant boundary, so the standard reviewer set is consumed via the re-fired `specflow:prd` Phase E rather than opening a new gate type.
- **`task-history.json` already populated.** `specflow:task` Phase D writes user overrides; `specflow:develop` Phase F appends development-time fields. A task that gets regenerated by `specflow:scope-change` retains its prior history but gains a `regenerated_at` + `superseded_by_scope_change: {decision-log-id}` field — history is preserved, not erased.
- **`specflow:render` is a sub-skill.** PRD HTML render fires automatically after every `specflow:prd` PRD write. `specflow:scope-change`'s PRD-update step re-fires render at the end of the update, so the HTML stays in sync with the markdown.
- **`specflow:linear` exists for in-flight cross-reference.** When Linear MCP is available, the in-flight impact list cross-references each task's Linear status; tasks in `In Progress` or `In Review` are surfaced as load-bearing impacts. Open PRs (via `gh pr list` or equivalent) are surfaced separately. Without Linear MCP, the impact list falls back to `task-history.json` status-field reads — the contract degrades gracefully.
- **Calibration anchor: 002-develop-skill.** The hand-iterated Phase 2 dogfood example for what a healthy interview + PRD + Gate 2 manifest looks like. This Phase 3 dogfood pass aims to match its shape — neither rubber-stamping nor bikeshedding, with at least one defensible push-back in Round 2.

## Goal (confirmed before grilling)

- **Outcome:** `specflow:scope-change` makes mid-development scope changes first-class instead of silent rewrites. Every scope change leaves an audit trail (the *why*, what was impacted), the PRD/tasks update mechanically rather than by manual rewrite, and in-flight work gets a concrete impact list rather than implicit invalidation. The skill is the place specflow keeps the PRD/task/decision triad honest when intent changes mid-flight.
- **Audience:** Power Users (frontend / backend engineers with specflow installed) who hit a scope-change moment during `specflow:develop` execution — a Verifier rejection that points at a wrong AC, a discovery during implementation that invalidates a requirement, a stakeholder ask that shifts the feature mid-flight. Secondary: the orchestrator agents (`specflow:develop`, `specflow:test`) that consume the updated PRD/tasks downstream and need a stable contract. Tertiary: stakeholders reading the `decision-log.md` retrospectively to understand why a feature shifted.
- **Success looks like:** invoking `/specflow:scope-change {NNN-slug}` (manually, or after the user accepts the auto-suggestion from `specflow:develop` Phase F option 3) on a feature with an existing PRD + tasks produces (a) a captured *why* recorded as an append-only block in the interview file, (b) an updated PRD whose diff is reviewable (only the requirements/ACs that the scope change touches are modified — the rest is byte-stable), (c) an updated `prd.html` re-render, (d) regenerated tasks for the affected scope only (a delta regeneration, not a full re-task), (e) a concrete impact list cataloguing every in-flight artefact (open PR, in-progress task, draft test plan, Linear ticket in `In Progress` or `In Review`) the scope change touches, (f) a `decision-log.md` entry with title + context + decision + rationale (the *why*) + date + references. Every artefact is co-located in `features/NNN-{slug}/` so a downstream agent can read the scope-change chain without cross-folder chase.
- **Driving value:** removes the failure mode where mid-development scope changes happen silently — the PRD goes stale, tasks drift from intent, and decisions are lost; removes the failure mode where regenerating tasks means burning the whole task list and re-running Gate 3 from scratch when only a subset is affected; removes the failure mode where in-flight work (open PRs, in-progress branches) gets implicitly invalidated by a PRD edit without anyone surfacing the impact. Phase 3 self-learning relies on the PRD/task/decision triad staying in sync; without `scope-change` the triad rots silently.
- **Out of scope at the goal level:** (1) building the decision-log writer itself — that's `specflow:decision`'s job; `specflow:scope-change` invokes it as a sub-skill, never embeds the writer logic; (2) re-running the full grilling phase from scratch — `specflow:scope-change` extends the existing interview rather than re-creating it (the original *why* landed in the original rounds; the new *why* lands as a new "Scope change" section); (3) auto-resolving in-flight artefacts (closing PRs, transitioning Linear tickets, force-pushing branches) — the skill surfaces the impact list and waits for the user to triage; the user owns the merge / abort / rebase decision; (4) cross-feature scope changes (a scope change that affects multiple features simultaneously) — v1 scopes to one feature per invocation; multi-feature scope changes are a Phase 3+ concern when consumers report friction; (5) replacing `specflow:prd` for new-feature creation — `specflow:scope-change` is for mid-development revisions of an existing PRD, never for creating a PRD from scratch.

## Rounds

### Round 1 — Drift detection: what triggers the auto-suggestion from `specflow:develop`?

- **Q:** `specflow:develop` Phase F option 3 ("abort the task and surface to `specflow:scope-change`") names this skill as the destination when a Verifier rejection points at the AC itself being wrong. But the wider `SKILLS.md` entry says the skill is "auto-suggested by `specflow:develop` on detected drift" — broader than just Verifier rejection. What concretely counts as "detected drift" — a Verifier reject only, or also things like a Gate 4 reviewer-driven re-lane that changes scope, a rule-violation auto-flag that surfaces a missing requirement, a 30/40/30 lane distribution suggesting the PRD needs re-cutting? And does the auto-suggestion actually fire (skill auto-invokes on drift), or does the user always elect?
- **AI's recommended answer:** Auto-suggestion is a chat-line prompt, never auto-invocation — the user always elects. Three drift triggers in v1: (a) Verifier rejection where the user picks option 3 (`specflow:develop` Phase F.3) — the skill prompts *"Run `specflow:scope-change {NNN-slug}` now? (y/n)"* and lands at the scope-change skill if the user says yes; (b) end-of-feature inspection in `specflow:develop` Phase A's resume prompt when the user picks option 3 — same chat-line shape; (c) a `specflow:develop` lane distribution that comes out 30/40/30 instead of the target 60/30/10 (per `docs/PRD.md` Phase 2 scope item 1) surfaces a chat-line note suggesting `specflow:scope-change` may be needed to re-cut the PRD into smaller tasks. Gate 4 reviewer-driven re-lane (R5/R5.1) does NOT fire `specflow:scope-change` — re-lane is a within-skill recovery, not a PRD-level revision. Rule-violation auto-flag (`specflow:misc --auto`) does NOT fire `specflow:scope-change` — that's a quality concern logged out-of-band, not a scope shift. — *Reasoning: the goal's Driving value field calls out preventing silent scope changes, but the goal's Out-of-scope-at-goal-level rules out auto-resolving artefacts; the user always electing matches that constraint. Only PRD-level revisions count as "drift" — within-skill recoveries (re-lane, agent-teams fallback, machine-check upgrades) are recovered locally without a scope change. The 30/40/30 lane signal is a documented pattern in `docs/PRD.md` already — surfacing it as a scope-change suggestion connects the architectural learning signal to the operational skill.*
- **User's answer:** confirmed, with one edit — the chat-line prompt for trigger (c) (lane distribution) should be a soft note, not a y/n prompt, because the user typically wants to ship the current task before re-cutting. Use *"[scope-change suggestion: lane distribution {G/Y/R} suggests the PRD may need re-cutting; run `specflow:scope-change {NNN-slug}` when ready]"* — informational, not blocking.
- **Resolved:** drift = three triggers (Verifier-reject option 3, end-of-feature inspection option 3, 30/40/30 lane distribution); auto-suggestion is chat-line only, user always elects; triggers (a) + (b) are y/n prompts at decision points, trigger (c) is an informational note; Gate 4 re-lane and rule-violation auto-flag do NOT count as drift. — flows into §Requirements R1, R2; AC AC-1, AC-2.

### Round 2 — PRD update mechanism: manual edit or re-invoke `/grill`?

- **Q:** The skill produces "an updated PRD whose diff is reviewable" — but how does the update happen? Does `specflow:scope-change` re-invoke `/grill` for the affected scope (full grilling on the new requirements), re-fire `specflow:prd` Phase C synthesis against the extended interview, or perform a direct AI-edit of the PRD body with reviewer Gate 2 closure? And does the original interview's resolved-line trace get preserved or invalidated?
- **AI's recommended answer:** Two-step update mechanism: (i) extend the interview with a new "Scope change — {date}" section appended after Topics not discussed, capturing the *why*, the new questions + recommended answers + user answers, and a fresh sign-off line — this re-uses `/grill` as a sub-skill in "extend mode" (per `/grill` SKILL.md's "manual `/grill {feature-id}` to extend an existing interview file with new rounds" trigger); (ii) re-fire `specflow:prd` Phase C synthesis against the extended interview, but with a surgical-changes constraint — only the requirements/ACs whose Trace lines reference the new scope-change rounds are modified; existing requirements whose Trace lines reference the original rounds are byte-stable in the diff. The original interview's Resolved lines are preserved (append-only); the only edits to existing rounds are if a scope change explicitly invalidates a prior round, in which case the prior round's Resolved line gets a strikethrough + a `superseded by Scope change {date}` note (NOT deletion — the audit trail must remain readable). Gate 2 re-fires after the surgical PRD edit to validate the diff. — *Reasoning: the goal's Outcome calls out "PRD updates mechanically rather than by manual rewrite" — that means re-using the `/grill` + Phase C synthesis machinery rather than asking the user to edit the PRD by hand. The goal's Out-of-scope-at-goal-level rules out re-running the full grilling from scratch; "extend mode" matches that. Surgical Changes principle: every modification traces to a stated drift; preserving Resolved-line trace is the audit-chain corollary. Gate 2 re-fires because the PRD is a different artefact post-edit, even if surgical.*
- **User's answer:** confirmed, with one nuance — the strikethrough for superseded Resolved lines should use markdown's `~~text~~` syntax inline rather than rewriting the line, so a diff viewer shows exactly which characters were marked superseded vs which were deleted. And the "Scope change — {date}" section should reference the `decision-log.md` entry id (e.g. *"See `admin/decision-log.md` entry SC-{NNN}"*) so the audit trail closes both ways.
- **Resolved:** PRD update = (i) extend interview via `/grill` extend-mode with new "Scope change — {date}" section (append-only); (ii) re-fire `specflow:prd` Phase C synthesis with surgical-changes constraint (only scope-change-touched R/ACs modify; rest is byte-stable); superseded Resolved lines use `~~text~~` strikethrough inline + `superseded by Scope change {date}` note; "Scope change" section references the `decision-log.md` entry id; Gate 2 re-fires post-edit for validation. — flows into §Requirements R3, R4, R5; AC AC-3, AC-4, AC-5.

### Round 3 — Task regeneration: full re-task or delta only?

- **Q:** The skill produces "regenerated affected tasks" — but does that mean re-running `specflow:task` from scratch (which would invalidate every prior `task-history.json` entry, lose the development-time fields populated by `specflow:develop` Phase F, and re-fire Gate 3), or surgically re-task only the affected scope (preserving the unchanged tasks' history and their Gate 3 closure)? And when a task is partially complete (some sub-steps shipped, some not), what counts as "affected" — the whole task or only the un-shipped portion?
- **AI's recommended answer:** Surgical delta regeneration, never full re-task. The mechanism: (a) read the PRD diff between the pre-scope-change and post-scope-change versions; (b) compute the set of changed R-IDs (added, modified, deleted, superseded); (c) for each changed R-ID, locate the tasks whose Anchor field references it via the coverage matrix in `tasks.md`; (d) re-run `specflow:task` Phase B (task synthesis) ONLY against the changed R-IDs, generating new/modified tasks — unchanged tasks are byte-stable; (e) every regenerated task gets a `regenerated_at: {timestamp}` + `superseded_by_scope_change: {decision-log-id}` + `prior_task_id: {original T-id}` triple in `task-history.json`; the prior entry is NOT deleted (preserves the development-time fields if any), it gains a `superseded_by: {new T-id}` field; (f) Gate 3 re-fires ONLY against the regenerated subset (the manifest's "Reviewers" line is unchanged but the "Artefact under review" cites the delta). Partial-completion handling: if a task is `in_progress` (`task-history.json.status`) AND its R-ID changed, the task is surfaced in the in-flight impact list (Round 4) for user triage rather than auto-regenerated — the skill surfaces, the user decides whether to abort the in-flight work and regenerate, or finish-then-revisit. — *Reasoning: the goal's Outcome calls out "regenerated affected tasks have updated coverage" — that's a statement about the regenerated subset, not the full list. The goal's Out-of-scope-at-goal-level rules out auto-resolving in-flight work; partial-completion → impact list surfacing matches that. Preserving prior `task-history.json` entries is the Phase 3 self-learning corollary — the development-time fields are evidence corpus for `/insights`; deleting them on regeneration loses Phase 3 signal. Surgical delta regeneration is the same shape as the surgical PRD-update mechanism (Round 2) — pattern consistency.*
- **User's answer:** confirmed.
- **Resolved:** task regeneration = surgical delta only (compute PRD diff → changed R-IDs → re-run `specflow:task` Phase B against changed R-IDs only); unchanged tasks byte-stable; regenerated tasks gain `regenerated_at` + `superseded_by_scope_change` + `prior_task_id` triple; prior entries retained with `superseded_by` field; Gate 3 re-fires against the delta only; partial-completion (`status: in_progress`) tasks surface to in-flight impact list rather than auto-regenerate. — flows into §Requirements R6, R7; AC AC-6, AC-7.

### Round 4 — In-flight impact list: what counts as "in-flight"?

- **Q:** The skill produces "an impact list for in-flight work" — what concretely counts as "in-flight"? Open PRs only? Linear tickets in specific statuses? Branches with uncommitted changes? Tasks with `status: in_progress` in `task-history.json`? And how exhaustive must the list be — every artefact across the whole repo, or only artefacts the scope change directly touches?
- **AI's recommended answer:** Four sources cross-referenced; only artefacts touching the scope-change-affected R-IDs count. (a) `task-history.json` — every entry where `feature == {NNN-slug}` AND `status` ∈ {`planned`, `in_progress`, `review`} AND the entry's Anchor R-ID is in the changed-R-ID set. (b) Linear (when MCP available) — every issue where the issue's `feature` field == `{NNN-slug}` AND `status` ∈ {`In Progress`, `In Review`, `Backlog` if the user explicitly opts in via `--include-backlog` flag} AND the issue's Anchor R-ID is in the changed-R-ID set. Backlog excluded by default to avoid surfacing every queued task. Without Linear MCP, this source contributes nothing — chat-line note logs the degraded coverage. (c) Open PRs (via `gh pr list --state open --label feature/{NNN-slug}` or equivalent) — every PR labelled or branch-named to the feature whose touched files overlap with the changed R-IDs' scope-listed files. Without `gh` CLI, falls back to `git branch --list 'feature/{NNN-slug}-*'` for branch presence with chat-line note logging the degraded coverage. (d) Draft test plans (`features/{NNN-slug}/{NNN-slug}-test.md` with `status: draft` frontmatter) — surfaced as a single line if present. The list is **scoped** to the affected R-IDs; an open PR for a different feature, or an in-progress task whose R-ID didn't change, is NOT in the list. The skill writes the impact list to `features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` AND surfaces it inline in chat for user triage. The user owns merge / abort / rebase decisions per the goal's Out-of-scope-at-goal-level. — *Reasoning: the goal's Driving value field calls out preventing implicit invalidation of in-flight work — that means the list must be concrete and exhaustive across the four sources, but scoped to the affected R-IDs (otherwise the list explodes into noise). Backlog default-exclusion is the noise-reduction corollary. The four-sources cross-reference matches the soft-dependency pattern from Phase 2 (each source degrades gracefully if its tool is absent). Writing the list to a dated file under the feature folder matches the co-located-artefacts goal.*
- **User's answer:** confirmed, with one addition — the impact list file should also include a "What you should consider" section that, for each in-flight artefact, names a recommended action (e.g. *"open PR #123 touches files now removed from R3 scope — consider rebasing or closing"*). Surfacing without recommendation puts the diagnostic burden entirely on the user; one-line recommendations leave the decision but reduce friction.
- **Resolved:** in-flight = four sources (task-history.json status ∈ {planned, in_progress, review}; Linear when MCP available with status ∈ {In Progress, In Review} default + Backlog opt-in via flag; open PRs via `gh` CLI with branch-name fallback; draft test plans); list scoped to affected R-IDs; written to `features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` AND surfaced inline; includes a "What you should consider" section with one-line recommended action per artefact; user owns triage decisions. — flows into §Requirements R8, R9; AC AC-8, AC-9.

### Round 5 — Decision-log entry: who writes it, what shape?

- **Q:** The skill produces "a `decision-log.md` entry" — does `specflow:scope-change` write the entry directly, or invoke `specflow:decision` as a sub-skill? And what's the entry's exact shape — title + context + decision + rationale + date + references per the standard schema, or extended with scope-change-specific fields like `affected_r_ids`, `superseded_resolved_lines`, `impact_list_path`?
- **AI's recommended answer:** Invoke `specflow:decision` as a sub-skill — never embed the writer logic, per the goal's Out-of-scope-at-goal-level. The payload passed to `specflow:decision` uses the standard schema (title, context, decision, rationale, date, references) PLUS three scope-change-specific fields embedded in the references block (not as new top-level fields, to keep the decision-log schema stable for `/insights` Phase 3 cross-feature queries): (a) `affected_r_ids: [R1, R3, R7]` — the changed R-ID set; (b) `superseded_resolved_lines: [round-2.line-78, round-4.line-15]` — the interview rounds whose Resolved lines were strikethrough'd; (c) `impact_list_path: features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` — pointer to the in-flight impact list. The entry's `id` follows the convention `SC-{NNN}` where NNN is monotonically incremented per scope-change event (separate counter from `specflow:decision`'s default counter, so scope-change entries are filterable). The *why* lands in the rationale field verbatim — the rationale is the load-bearing field, captured during the `/grill` extend-mode rounds (Round 2's mechanism). — *Reasoning: the goal's Out-of-scope-at-goal-level rules out embedding the writer logic; invoking `specflow:decision` matches that. Keeping the decision-log schema stable matters for Phase 3 `/insights` self-learning — adding scope-change-specific top-level fields would fragment the schema; embedding them inside references preserves backward compatibility. Separate `SC-` id counter is the filterability win for `/insights`. The *why* in rationale is the architectural decision from `docs/PRD.md` Phase 3 scope item 4 ("the *why* is the most important field — it justifies the change to future readers").*
- **User's answer:** confirmed.
- **Resolved:** invoke `specflow:decision` as sub-skill (no embedded writer logic); payload = standard schema + three scope-change fields embedded in references block (`affected_r_ids`, `superseded_resolved_lines`, `impact_list_path`); id convention `SC-{NNN}` (separate counter); *why* lands verbatim in rationale field. — flows into §Requirements R10, R11; AC AC-10, AC-11.

### Round 6 — Failure modes: scope-change on a feature without PRD; partial-completion mid-scope-change

- **Q:** Two failure modes worth nailing down: (1) scope-change invoked on a feature that doesn't have a PRD or has a PRD that hasn't closed Gate 2 yet — refuse, fall through to `specflow:prd`, or open a stub? (2) scope-change itself fails partway through (e.g. `/grill` extend-mode succeeds but Phase C synthesis crashes; or PRD updates but `specflow:decision` invocation fails) — how does the skill recover, and is the partial state safe to resume from?
- **AI's recommended answer:** (1) Refuse with sentinel. If the feature folder doesn't exist, refuse: *"Feature `{NNN-slug}` does not exist. Run `specflow:prd` first to create it; `specflow:scope-change` is for revising an existing PRD, not creating one."* If the PRD exists but Gate 2 closing decision is `failed` or missing, refuse: *"PRD has not closed Gate 2 (status: `{status|missing}`). Resolve Gate 2 first via `specflow:prd {NNN-slug}` before running scope-change — scope-change preserves Gate 2 closure as a pre-condition for the surgical-edit pattern."* No fall-through to `specflow:prd` (different intent — new vs revise; smuggling is what the failure-mode-design rules out). No stub creation (the goal field's Audience names existing-feature consumers, not new-feature consumers). (2) Idempotent-resume via scratch directory. The skill writes intermediate state to `admin/scratch/{NNN-slug}-scope-change/` — interview extension, PRD diff, computed changed-R-IDs, regenerated task list, impact list draft — each step writes a status file. Resume logic on re-invocation: read scratch dir → detect last completed step → resume at the next step. Steps:  (i) interview extension; (ii) PRD synthesis; (iii) Gate 2 re-fire; (iv) task delta regeneration; (v) Gate 3 re-fire on delta; (vi) impact list compilation; (vii) `specflow:decision` invocation; (viii) cleanup scratch. Mid-step failures: any step that crashes leaves its status file as `failed` with an error trace; the user can re-invoke and the skill resumes from the failed step (after the user resolves the underlying error). The decision-log entry only writes after step (vii) — partial scope changes never write to `decision-log.md` (which would corrupt the audit trail). The PRD itself is updated in step (ii) but Gate 2 hasn't re-fired yet — if step (iii) fails, the PRD on disk has the surgical edit but no Gate 2 closure; re-invoke resumes at (iii). The strikethrough Resolved lines in the interview are written in step (i) and persist across the failure; the audit trail tolerates the partial state because it's append-only. — *Reasoning: the goal's Outcome promises a complete chain of artefacts; partial-state recovery is the corollary that promise is robust under failure. Refusing on missing/failed Gate 2 matches the Phase 1 `specflow:task` pre-condition pattern (Gate 2 closure required before tasking) — pattern consistency. Idempotent-resume matches the Phase 2 `specflow:develop` resume logic; copying that pattern is surgical. The decision-log being the last write is the audit-trail integrity corollary — a corrupted scope change must not leave an entry that promises something the artefacts didn't deliver.*
- **User's answer:** confirmed.
- **Resolved:** failure modes = (1) refuse on missing/failed-Gate-2 with literal sentinels (no fall-through to `specflow:prd`, no stub creation); (2) idempotent-resume via `admin/scratch/{NNN-slug}-scope-change/` with per-step status files; eight steps (interview extension → PRD synthesis → Gate 2 re-fire → task delta regen → Gate 3 re-fire → impact list → `specflow:decision` → cleanup); decision-log entry only writes after step (vii) (audit-trail integrity); strikethrough interview edits persist across failures (append-only audit trail tolerates partial state). — flows into §Requirements R12; AC AC-12.

## Topics not discussed

- *Cross-feature scope changes (one scope change affecting multiple features simultaneously).* Out of scope per goal's "Out of scope at the goal level". v1 scopes to one feature per invocation. If a scope change affects feature A and feature B, the user runs `specflow:scope-change A` then `specflow:scope-change B` separately, each producing its own decision-log entry. Multi-feature batched scope changes are a Phase 3+ concern when consumers report friction with the per-feature pattern.
- *Auto-resolving in-flight artefacts (closing PRs, transitioning Linear tickets, force-pushing branches when a scope change invalidates them).* Out of scope per goal's "Out of scope at the goal level". The skill surfaces the impact list with recommended actions; the user owns the merge / abort / rebase decisions. Auto-resolution would cross the autonomous-mutation line that Phase 2's `specflow:develop` Verifier-rejection design also explicitly rules out — pattern consistency.
- *Rollback of a scope change.* Not covered in this PRD. If a user wants to undo a scope change (the new *why* turned out to be wrong, the original PRD was right), v1 directs them to invoke another `specflow:scope-change` reversing the prior one — every change is forward, every change leaves a decision-log entry, no in-place rollback. `panic` (Phase 1 trust-ladder primitive) is the reversibility surface for catastrophic mistakes; routine reversals go through another scope-change cycle. Native rollback support is deferred to v2 if consumers report friction with the forward-only pattern.
