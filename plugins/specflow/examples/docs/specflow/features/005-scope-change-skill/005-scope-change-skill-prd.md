# specflow:scope-change — mid-development scope change orchestrator

## Vision

`specflow:scope-change` makes mid-development scope changes first-class instead of silent rewrites. Power Users running `specflow:develop` who hit a scope-change moment — a Verifier rejection that points at a wrong AC, a discovery during implementation that invalidates a requirement, a stakeholder ask that shifts the feature mid-flight — get a single skill that captures the *why*, updates the PRD/tasks mechanically rather than by manual rewrite, and surfaces a concrete impact list cataloguing every in-flight artefact the change touches. Every scope change leaves an audit trail (the *why*, what was impacted), the PRD/tasks update mechanically rather than by manual rewrite, and in-flight work gets a concrete impact list rather than implicit invalidation. The skill is the place specflow keeps the PRD/task/decision triad honest when intent changes mid-flight — and the surgical-edit discipline + preserved interview audit chain + delta task regeneration are the three legs that make mid-development scope changes auditable instead of silent.

## Problem

Phase 1 of specflow ships `specflow:prd` for new-feature PRD creation and `specflow:task` for task generation, and Phase 2's `specflow:develop` runs implementation against a frozen PRD/task contract. But the gap between "PRD signed off + tasks closed Gate 3" and "feature shipped" is where mid-development scope changes happen: a Verifier rejection surfaces an AC that's actually wrong, a discovery during implementation reveals a requirement that wasn't grounded, a stakeholder shifts the feature's intent. Without a dedicated skill to handle these moments, the failure modes that result are well-known: (a) the PRD goes stale because the user edits it by hand without re-firing Gate 2, breaking the audit chain back to the interview's Resolved lines; (b) tasks drift from intent because regenerating them means re-running `specflow:task` from scratch, which discards the prior `task-history.json` development-time fields that Phase 3 self-learning depends on; (c) in-flight work (open PRs, in-progress tasks, draft test plans) gets implicitly invalidated by a PRD edit without anyone surfacing the impact, leading to silent rebases and lost decisions; (d) the *why* of the scope change is lost — there's no `decision-log.md` entry, so future readers see the new PRD but cannot reconstruct what changed or why.

The fix is structural: a single skill that owns mid-development scope-change orchestration end-to-end with append-only interview extension (preserves the original Resolved-line audit trail), surgical PRD synthesis (only the requirements/ACs that the scope change touches are modified), delta task regeneration (preserves prior `task-history.json` history), a concrete impact list cataloguing every in-flight artefact the change touches, and a `decision-log.md` entry capturing the *why* with the standard schema. The skill consumes `specflow:prd`, `specflow:task`, `specflow:render`, and `specflow:decision` as sub-skills — never embeds their writer logic — and degrades gracefully when soft dependencies (Linear MCP, `gh` CLI) are absent.

## Goals

- Drift-detection auto-suggestion from `specflow:develop` — three triggers (Verifier-rejection option 3, end-of-feature inspection option 3, 30/40/30 lane distribution) surface as chat-line prompts; the user always elects, the skill never auto-invokes.
- Append-only interview extension via `/grill` extend-mode — a new "Scope change — {date}" section captures the new *why* + new rounds + sign-off; superseded Resolved lines from prior rounds use `~~text~~` strikethrough inline (NOT deletion) with a `superseded by Scope change {date}` note.
- Surgical PRD synthesis via re-fired `specflow:prd` Phase C — only the requirements/ACs whose Trace lines reference the new scope-change rounds are modified; existing R/ACs whose Trace lines reference the original rounds are byte-stable in the diff.
- Gate 2 re-fires post-edit on the surgically updated PRD; the standard five-reviewer set runs the same way it does for new PRDs, with closing decision recorded against the post-scope-change manifest.
- Delta task regeneration via re-fired `specflow:task` Phase B — only tasks whose Anchor R-ID is in the changed-R-ID set are regenerated; unchanged tasks are byte-stable; prior `task-history.json` entries are retained with `superseded_by: {new T-id}` field; Gate 3 re-fires against the delta only.
- In-flight impact list cross-references four sources (`task-history.json` status field, Linear when MCP available, open PRs via `gh` CLI, draft test plans), scoped to the affected R-IDs only — the user owns merge / abort / rebase decisions, the skill never auto-resolves.
- `decision-log.md` entry written via `specflow:decision` sub-skill invocation — standard schema (title, context, decision, rationale, date, references) with three scope-change-specific fields embedded inside the references block (`affected_r_ids`, `superseded_resolved_lines`, `impact_list_path`) and a separate `SC-{NNN}` id counter for `/insights` filterability.
- Idempotent resume via `admin/scratch/{NNN-slug}-scope-change/` — eight-step flow with per-step status files; mid-step failures resume cleanly; the `decision-log.md` entry only writes after the penultimate step so a corrupted scope change never leaves a dangling audit entry.
- Co-located artefacts: every scope-change-extended interview block, updated PRD, regenerated tasks file, impact list, and orchestration scratch file lives under `features/NNN-{slug}/` (or `admin/scratch/{orchestration-id}/`), so a downstream skill can read the full scope-change chain without cross-folder chase.

## Non-goals

- **Building the decision-log writer.** That's `specflow:decision`'s job. `specflow:scope-change` invokes it as a sub-skill with a payload, never embeds the writer logic. Pattern consistency with `specflow:develop`'s "consumes plugins, never re-implements them" stance.
- **Re-running the full grilling phase from scratch.** `specflow:scope-change` extends the existing interview rather than re-creating it — the original *why* landed in the original rounds; the new *why* lands in a new "Scope change" section. Discarding the prior interview would lose the resolved-line trace that downstream skills (`specflow:test`, `/insights`) depend on.
- **Auto-resolving in-flight artefacts.** Closing PRs, transitioning Linear tickets, force-pushing branches, aborting `specflow:develop` runs — all out of scope. The skill surfaces the impact list with recommended actions; the user owns the triage. Auto-resolution would cross the autonomous-mutation line that Phase 2's Verifier-rejection design also explicitly rules out.
- **Cross-feature scope changes.** v1 scopes to one feature per invocation. A scope change affecting feature A and feature B requires two separate invocations, each producing its own decision-log entry. Multi-feature batching is a Phase 3+ concern gated on real consumer friction.
- **Replacing `specflow:prd` for new-feature creation.** `specflow:scope-change` is for mid-development revisions of an existing PRD only. Invoked on a feature that doesn't exist or hasn't closed Gate 2, the skill refuses with a literal sentinel pointing the user at `specflow:prd`.
- **Native rollback of a scope change.** v1 is forward-only — every change leaves a decision-log entry; reversing a scope change means running another `specflow:scope-change` against the new state. `panic` (Phase 1 trust-ladder primitive) is the catastrophic-mistake recovery surface; routine reversals go through another scope-change cycle. Native rollback is deferred to v2 if consumers report friction.

## Users

- **Power User (per `admin/profiles.json`)** — frontend / backend engineers running implementation in their own repos who hit a scope-change moment during `specflow:develop`. They invoke `specflow:scope-change` manually after picking option 3 on a Verifier rejection, or after the end-of-feature resume prompt suggests it, or proactively when they realise mid-flight that the PRD needs revision. They need the interview-extension to be append-only (no silent edits to the audit trail), the PRD diff to be reviewable (only the affected R/ACs change), and the impact list to be concrete with recommended actions.
- **Orchestrator agents (`specflow:develop`, `specflow:test`)** — the downstream consumers of the updated PRD/tasks. They need a stable contract — the post-scope-change PRD passes Gate 2, the post-scope-change tasks pass Gate 3 against the delta, the `decision-log.md` entry exists. The Phase F resume prompt in `specflow:develop` is the integration surface; this skill produces the artefacts that resume reads.
- **Secondary: stakeholders reading `decision-log.md` retrospectively** — product managers, reviewers, future engineers. They consume the decision-log entry to understand why a feature shifted. They benefit from the standard schema (title, context, decision, rationale, date, references) being preserved across `specflow:decision`-written and `specflow:scope-change`-written entries — `/insights` Phase 3 cross-feature queries depend on schema stability.

## Requirements

- **R1.** Pre-flight chain check. `specflow:scope-change {NNN-slug}` reads `features/NNN-{slug}/{NNN-slug}-prd.md`, `{NNN-slug}-tasks.md`, `{NNN-slug}-interview.md`, and `debate-log/prd-gate2/manifest.md`. The skill refuses to run if any artefact is missing OR if the Gate 2 manifest's closing decision is `failed` (or missing). Refusal sentinels are literal: *"Feature `{NNN-slug}` does not exist. Run `specflow:prd` first to create it; `specflow:scope-change` is for revising an existing PRD, not creating one."* and *"PRD has not closed Gate 2 (status: `{status|missing}`). Resolve Gate 2 first via `specflow:prd {NNN-slug}` before running scope-change — scope-change preserves Gate 2 closure as a pre-condition for the surgical-edit pattern."*
  - Trace: codebase context (pre-grilling) bullet — *Stub SKILL.md exists; requires existing feature with PRD/tasks*. Pattern inherited from `specflow:task` Phase A's Gate 2 pre-condition rule.
  - Serves goal: Outcome (skill operates on a feature with closed Gate 2; never creates new features).

- **R2.** Drift-detection auto-suggestion from `specflow:develop`. Three triggers surface as chat-line prompts in `specflow:develop`: (a) Verifier rejection where the user picks option 3 (`specflow:develop` Phase F.3) prompts *"Run `specflow:scope-change {NNN-slug}` now? (y/n)"*; (b) end-of-feature inspection in `specflow:develop` Phase A's resume prompt option 3 prompts the same y/n line; (c) `specflow:develop` lane distribution skewing 30/40/30 instead of the target 60/30/10 surfaces an informational note: *"[scope-change suggestion: lane distribution {G/Y/R} suggests the PRD may need re-cutting; run `specflow:scope-change {NNN-slug}` when ready]"* — informational only, not blocking. The user always elects; the skill never auto-invokes. Gate 4 reviewer-driven re-lane (R5/R5.1 in `specflow:develop`) and rule-violation auto-flags (`specflow:misc --auto`) do NOT count as drift triggers — those are within-skill recoveries, not PRD-level revisions.
  - Trace: interview Round 1 (edited) — *drift = three triggers; auto-suggestion is chat-line only, user always elects; triggers (a) + (b) are y/n prompts at decision points, trigger (c) is an informational note*. Schema dependency: AC-2's verification of trigger (c) depends on `specflow:develop` Phase B emitting the lane-distribution chat-line note when the ratio crosses the threshold; that emission landed in `specflow:develop`'s Phase B.5 ("If the distribution looks pathological…"). Confirmed against `skills/develop/SKILL.md:171`.
  - Serves goal: Outcome (drift detection is a chat-line prompt — user always elects).

- **R3.** Append-only interview extension via `/grill` extend-mode. The skill invokes `/grill {NNN-slug}` in extend-mode (per `/grill` SKILL.md's "manual `/grill {feature-id}` to extend an existing interview file with new rounds" trigger). `/grill` appends a new "Scope change — {date}" section to the interview file after the "Topics not discussed" section. The new section captures: (a) the *why* of the scope change as a preamble paragraph; (b) the new rounds (typically 1-3 — narrower than a full PRD interview); (c) a fresh sign-off line dated to the scope-change event; (d) an explicit reference to the resulting `decision-log.md` entry id (e.g. *"See `admin/decision-log.md` entry SC-{NNN}"*). The original Goal section, Original Request, Codebase context, and prior Rounds are NEVER edited — append-only.
  - Trace: interview Round 2 (edited) — *PRD update = (i) extend interview via `/grill` extend-mode with new "Scope change — {date}" section (append-only)*; user nuance — *"Scope change" section should reference the `decision-log.md` entry id*.
  - Serves goal: Driving value (audit trail preserved; the original *why* and new *why* both land in the interview, never overwritten).

- **R4.** Superseded Resolved-line markup. When a scope-change round explicitly invalidates a prior round's Resolved line (e.g. Round 2's Resolved said "the foo flag defaults to true"; the scope change resolves "the foo flag is removed entirely"), the prior Resolved line is marked with markdown's `~~text~~` strikethrough inline AND a parenthetical note appended: *"(superseded by Scope change {date})"*. The line is NEVER deleted — strikethrough preserves the audit trail, deletion would erase it. The strikethrough markup must wrap only the affected text, not the whole line, so a diff viewer shows exactly which characters were superseded.
  - Trace: interview Round 2 (edited) — *superseded Resolved lines use `~~text~~` strikethrough inline + `superseded by Scope change {date}` note*.
  - Serves goal: Driving value (silent rewrites are the failure mode this skill removes; strikethrough makes supersession visible).

- **R5.** Surgical PRD synthesis via re-fired `specflow:prd` Phase C. After interview extension, the skill re-fires `specflow:prd` Phase C (synthesis) against the extended interview with a surgical-changes constraint: only the requirements/ACs whose Trace lines reference the new scope-change rounds (or whose original Trace line is now strikethrough-superseded) are modified; existing R/ACs whose Trace lines reference unchanged original rounds are byte-stable in the diff. The Vision, Problem, Goals, Non-goals, Users, Open questions, and See-also sections are byte-stable unless the scope change explicitly mandates a change to those sections (rare; surfaced in the new round's Resolved line if so). The PRD's frontmatter `status` field stays `draft`; a separate `last_scope_change: {SC-NNN}` line is appended to the frontmatter so downstream skills can detect the most recent revision. After PRD synthesis, the skill re-invokes `specflow:render` to refresh the sibling `prd.html`.
  - Trace: interview Round 2 — *re-fire `specflow:prd` Phase C synthesis with surgical-changes constraint (only scope-change-touched R/ACs modify; rest is byte-stable)*. Sub-skill delegation pattern inherited from `specflow:develop` consumes-plugins-never-re-implements stance.
  - Serves goal: Outcome (PRD diff is reviewable — only affected R/ACs change; the rest is byte-stable).

- **R6.** Gate 2 re-fires post-edit. After the surgical PRD synthesis lands on disk, the skill re-fires `specflow:prd` Phase E (Gate 2 multi-agent debate manifest) against the post-scope-change PRD. The standard five reviewers (Devil's Advocate + Simplicity + Surgical + Think-Before-Coding + Goal-Driven) fire the same way they do for a new-feature PRD; Codex joins as a sixth reviewer when `admin/environment.json.cli.codex.available` is true. The Gate 2 manifest is written to a NEW path inside the same debate-log subfolder: `features/{NNN-slug}/debate-log/prd-gate2/manifest-scope-change-{SC-NNN}.md`. The original Gate 2 manifest at `manifest.md` is NEVER modified — append-only across scope-change events. The closing decision of the new manifest determines whether the scope change can proceed to task regeneration; `failed` halts the flow with the same surface that `specflow:prd` Phase E.7 uses for new PRDs.
  - Trace: interview Round 2 — *Gate 2 re-fires post-edit for validation*. Manifest path convention preserves the original closing decision per the surgical-changes principle.
  - Serves goal: Outcome (post-scope-change PRD passes the same adversarial-review bar as a new PRD).

- **R7.** Delta task regeneration via re-fired `specflow:task` Phase B. After Gate 2 closes on the post-scope-change PRD, the skill computes the changed-R-ID set by diffing the pre- and post-scope-change PRDs (added, modified, deleted, superseded R-IDs). For each changed R-ID, the skill locates affected tasks via the existing coverage matrix in `tasks.md` and re-fires `specflow:task` Phase B (synthesis) ONLY against the changed R-IDs. Unchanged tasks are byte-stable in the resulting `tasks.md`. Each regenerated task gets a `regenerated_at: {timestamp}` + `superseded_by_scope_change: {SC-NNN}` + `prior_task_id: {original T-id}` triple in `task-history.json`. Each prior `task-history.json` entry whose task was regenerated is RETAINED (not deleted) and gains a `superseded_by: {new T-id}` field — the development-time fields populated by `specflow:develop` Phase F are preserved as Phase 3 self-learning corpus.
  - Trace: interview Round 3 — *task regeneration = surgical delta only; unchanged tasks byte-stable; regenerated tasks gain `regenerated_at` + `superseded_by_scope_change` + `prior_task_id` triple; prior entries retained with `superseded_by` field*.
  - Serves goal: Driving value (regenerating tasks preserves prior development-time fields; Phase 3 self-learning corpus is not erased on scope change).

- **R7.1.** Partial-completion handling for in-flight tasks. If a task whose R-ID is in the changed-R-ID set has `task-history.json.status` of `in_progress` (i.e. `specflow:develop` is mid-run on it), the task is NOT auto-regenerated. Instead, the task is surfaced in the in-flight impact list (R8) for user triage. The user decides whether to abort the in-flight `specflow:develop` run (via `panic` or manual abort) and then resume `specflow:scope-change` to regenerate, or finish the in-flight run against the pre-scope-change task definition and revisit. R7.1 is the catch-all for tasks where auto-regeneration would race against active development work.
  - Trace: interview Round 3 — *partial-completion (`status: in_progress`) tasks surface to in-flight impact list rather than auto-regenerate*.
  - Serves goal: Driving value (in-flight work is never silently invalidated; user triage required for active tasks).

- **R8.** In-flight impact list across four sources, scoped to affected R-IDs. The skill writes `features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` cross-referencing four sources: (a) `task-history.json` — every entry where `feature == {NNN-slug}` AND `status` ∈ {`planned`, `in_progress`, `review`} AND the entry's Anchor R-ID is in the changed-R-ID set; (b) Linear (when `admin/environment.json.mcp.linear.available` is true) — every issue where the issue's `feature` field == `{NNN-slug}` AND `status` ∈ {`In Progress`, `In Review`} AND the issue's Anchor R-ID is in the changed-R-ID set (Backlog excluded by default to avoid surfacing every queued ticket; user can opt in via `--include-backlog` flag); (c) open PRs via `gh pr list --state open --label feature/{NNN-slug}` (or branch-name fallback `git branch --list 'feature/{NNN-slug}-*'` when `gh` CLI is absent) — every PR labelled or branch-named to the feature whose touched files overlap with the changed R-IDs' scope-listed files; (d) draft test plans (`features/{NNN-slug}/{NNN-slug}-test.md` with `status: draft` frontmatter) — surfaced as a single line if present. The list is **scoped** to the affected R-IDs; an open PR for a different feature, or an in-progress task whose R-ID didn't change, is NOT in the list. Each source degrades gracefully when its tool is absent — chat-line note logs the degraded coverage; the section in the impact file records the absence as `(source unavailable: {reason})`.
  - Trace: interview Round 4 — *in-flight = four sources; list scoped to affected R-IDs; written to `features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` AND surfaced inline*.
  - Serves goal: Outcome (impact list cites every in-flight artefact the change touches; never silently invalidates).

- **R9.** Recommended actions per impact-list entry. The impact-list file includes a "What you should consider" section that, for each in-flight artefact, names a one-line recommended action (e.g. *"open PR #123 touches files now removed from R3 scope — consider rebasing or closing"*; *"task T4 with `status: in_progress` anchored to R7 (now superseded) — consider aborting current run and resuming after scope-change completes"*). The recommendations leave the decision to the user — the skill never auto-resolves — but reduce the diagnostic burden of figuring out what each artefact's relationship to the scope change is.
  - Trace: interview Round 4 (edited) — user addition: *"What you should consider" section that, for each in-flight artefact, names a recommended action*.
  - Serves goal: Outcome (impact list is actionable, not just informational).

- **R10.** Decision-log entry via `specflow:decision` sub-skill invocation. The skill invokes `specflow:decision` as a sub-skill (never embeds the writer logic). The payload uses the standard schema: `title` (e.g. *"Scope change — {feature title} — {one-line summary of the change}"*), `context` (the pre-scope-change state in 1-2 sentences), `decision` (the post-scope-change state in 1-2 sentences), `rationale` (the *why* verbatim from the interview's new "Scope change" section preamble — the load-bearing field per `docs/PRD.md` Phase 3 scope item 4), `date` (the scope-change date), `references` (the references block, see R10.1).
  - Trace: interview Round 5 — *invoke `specflow:decision` as sub-skill (no embedded writer logic); payload = standard schema*. *Why* in rationale per the architectural decision from `docs/PRD.md` Phase 3 scope item 4.
  - Serves goal: Outcome (decision-log entry exists for every scope change; the *why* is the rationale).

- **R10.1.** Scope-change-specific fields embedded in references block. The decision-log entry's `references` field includes three scope-change-specific keys EMBEDDED inside the references block (not as new top-level fields, to keep the decision-log schema stable for `/insights` Phase 3 cross-feature queries): `affected_r_ids: [R1, R3, R7]` (the changed R-ID set); `superseded_resolved_lines: [round-2.line-78, round-4.line-15]` (interview rounds whose Resolved lines were strikethrough'd); `impact_list_path: features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` (pointer to the in-flight impact list). The entry's `id` follows the convention `SC-{NNN}` where NNN is monotonically incremented per scope-change event (separate counter from `specflow:decision`'s default counter, so scope-change entries are filterable by id-prefix in `/insights` queries). **Schema dependency:** R10.1 depends on `specflow:decision` accepting an arbitrary keyed-block within `references` AND accepting an `id_prefix: "SC"` parameter on invocation. If the current Phase 3 `specflow:decision` schema (per `skills/decision/SKILL.md`) does not accept these, ship them via a `specflow:decision` enhancement PRD before `specflow:scope-change` v1 lands.
  - Trace: interview Round 5 — *payload = standard schema + three scope-change fields embedded in references block; id convention `SC-{NNN}` (separate counter)*. Schema dependency surfaced at Gate 2 per surgical-r1-f1 — cross-skill schema requirements must be loud, not buried.
  - Serves goal: Outcome (decision-log schema stable for `/insights`; scope-change entries are filterable; cross-skill dependency named, not smuggled).

- **R11.** Idempotent resume via `admin/scratch/{NNN-slug}-scope-change/`. The skill writes intermediate state to `admin/scratch/{NNN-slug}-scope-change/` per the orchestrator pattern. Eight steps fire sequentially: (i) interview extension via `/grill` extend-mode; (ii) PRD synthesis via `specflow:prd` Phase C; (iii) Gate 2 re-fire via `specflow:prd` Phase E; (iv) task delta regeneration via `specflow:task` Phase B; (v) Gate 3 re-fire on delta via `specflow:task` Phase E; (vi) impact list compilation; (vii) `specflow:decision` invocation; (viii) cleanup of scratch directory. Each step writes a status file (`step-{N}-status.json` with `state: pending|in_progress|done|failed`). Resume logic on re-invocation: read scratch dir → detect last `done` step → resume at the next step. Mid-step failures leave the step's status file as `failed` with an error trace; the user resolves the underlying error and re-invokes. The decision-log entry only writes after step (vii) — partial scope changes never write to `decision-log.md` (which would corrupt the audit trail). The PRD is updated in step (ii) but Gate 2 hasn't re-fired yet — if step (iii) fails, the PRD on disk has the surgical edit but no Gate 2 closure; re-invoke resumes at (iii). The strikethrough Resolved lines in the interview are written in step (i) and persist across failures — the audit trail tolerates the partial state because it's append-only.
  - Trace: interview Round 6 — *idempotent-resume via `admin/scratch/{NNN-slug}-scope-change/` with per-step status files; eight steps*. Pattern inherited from `specflow:develop` resume logic; copying the pattern is the surgical-changes-compliant move.
  - Serves goal: Driving value (mid-step failures recover cleanly; the audit-trail integrity is preserved under failure).

- **R12.** Orchestrator pattern compliance. Every sub-skill invocation (`/grill`, `specflow:prd` Phase C, `specflow:prd` Phase E, `specflow:task` Phase B, `specflow:task` Phase E, `specflow:render`, `specflow:decision`) runs in a forked sub-agent context per `templates/orchestrator-pattern.md`. Verbatim file content is injected via command substitution; intermediate artefacts land in `admin/scratch/{NNN-slug}-scope-change/`; only file paths return to the parent context. The four-source impact list compilation in step (vi) is the only step that runs in the parent context (it's a small read-aggregate operation, not a sub-skill invocation).
  - Trace: codebase context (pre-grilling) bullet — *Sister Phase 1 orchestrators are operational; orchestrator pattern is the must-read*. Pattern inherited from `templates/orchestrator-pattern.md` and pre-confirmed at the architectural level.
  - Serves goal: Outcome (artefacts co-located in `features/NNN-{slug}/`; downstream skills read the full chain without cross-folder chase).

## Acceptance criteria

- **AC-1.** Running `specflow:scope-change {NNN-slug}` on a feature whose Gate 2 manifest closing decision is `passed`, `passed-with-revisions`, or `passed-with-escalations` proceeds to step (i) interview extension. Running on a non-existent feature OR on a feature with `failed`/missing Gate 2 closing decision refuses with the exact sentinel from R1, with no fall-through to `specflow:prd`. (Verifies R1.)

- **AC-2.** When `specflow:develop` Verifier rejection occurs (per `specflow:develop` Phase F.3) and the user picks option 3, `specflow:develop` emits the chat-line *"Run `specflow:scope-change {NNN-slug}` now? (y/n)"* and on `y` invokes `specflow:scope-change`. When `specflow:develop` Phase A's resume prompt fires for a complete feature and the user picks option 3, the same y/n prompt is emitted. When `specflow:develop` Phase B.5 detects a 30/40/30 lane distribution skew, the chat-line *"[scope-change suggestion: lane distribution {G/Y/R} suggests the PRD may need re-cutting; run `specflow:scope-change {NNN-slug}` when ready]"* is emitted as informational only (no y/n prompt; no auto-invocation). Gate 4 re-lane (R5/R5.1 in `specflow:develop`) and `specflow:misc --auto` rule-violation flags do NOT trigger this chat-line. **Schema dependency:** AC-2 depends on `specflow:develop` Phase B.5 emitting the lane-distribution chat-line note as documented in `skills/develop/SKILL.md:171`. Already in place per the existing skill body; no `specflow:develop` enhancement PRD needed. (Verifies R2.)

- **AC-3.** After step (i), the interview file `features/{NNN-slug}/{NNN-slug}-interview.md` contains a new top-level section `## Scope change — {YYYY-MM-DD}` appended after `## Topics not discussed`. The new section has a `*why*` preamble paragraph, ≥1 round (Q + AI's recommended answer + user's answer + Resolved line), a sign-off line dated to today, and an explicit reference to the `decision-log.md` entry id (e.g. *"See `admin/decision-log.md` entry SC-{NNN}"*). The original Goal section, Original Request, Codebase context, and prior Rounds are byte-identical to their pre-scope-change content (verified by file-content comparison against the pre-scope-change snapshot saved to scratch). (Verifies R3.)

- **AC-4.** When a scope-change round explicitly invalidates a prior Resolved line, the prior line in the interview file has `~~{affected text}~~` strikethrough markup applied AND a parenthetical `(superseded by Scope change {YYYY-MM-DD})` note appended. The strikethrough wraps only the affected text, not the whole line — a diff viewer renders the strikethrough'd characters distinct from preserved characters. NO Resolved line is deleted; deletion of a prior Resolved line is a failed step (i). (Verifies R4.)

- **AC-5.** After step (ii), the PRD diff between pre-scope-change and post-scope-change shows changes ONLY to: (a) requirements/ACs whose Trace line references a scope-change round OR a strikethrough'd prior Resolved line; (b) the frontmatter's new `last_scope_change: {SC-NNN}` line. The Vision, Problem, Goals, Non-goals, Users, Open questions, and See-also sections are byte-identical UNLESS the scope-change round's Resolved line explicitly mandated a change to those sections. R/ACs whose Trace line references unchanged original rounds are byte-identical. After step (ii), `specflow:render` is invoked and `prd.html` is byte-stable except for the regions corresponding to the changed R/ACs (and the frontmatter line). (Verifies R5.)

- **AC-6.** After step (iii), a new Gate 2 manifest exists at `features/{NNN-slug}/debate-log/prd-gate2/manifest-scope-change-{SC-NNN}.md` with closing decision `passed`, `passed-with-revisions`, `passed-with-escalations`, or `failed`. The original `manifest.md` at the same folder is byte-identical to its pre-scope-change content (verified by file-content comparison). If the new manifest's closing decision is `failed`, step (iv) does NOT fire — the skill halts and surfaces the blocking findings the same way `specflow:prd` Phase E.7 does. (Verifies R6.)

- **AC-7.** After step (iv), `tasks.md` shows changes ONLY to tasks whose Anchor R-ID is in the changed-R-ID set (or to the coverage matrix entries for those R-IDs). Each regenerated task has a `regenerated_at`, `superseded_by_scope_change`, and `prior_task_id` field in its `task-history.json` entry. Each prior `task-history.json` entry for a regenerated task is retained (NOT deleted) and gains a `superseded_by: {new T-id}` field — the development-time fields (`lane_assigned`, `ai_assistance_level`, `elapsed_minutes`, `what_worked`, `what_didnt_work`, `blast_radius_outcome`) populated by prior `specflow:develop` runs are preserved verbatim. After step (iv) Gate 3 re-fires (step (v)) — a new manifest at `features/{NNN-slug}/debate-log/tasks-gate3/manifest-scope-change-{SC-NNN}.md` records the closing decision; the original `manifest.md` is byte-stable. **Partial-completion sub-clause (R7.1):** if a task whose R-ID is in the changed-R-ID set has `task-history.json.status == "in_progress"`, the task is NOT regenerated in step (iv) — instead it is added to the in-flight impact list (AC-8). (Verifies R7, R7.1.)

- **AC-8.** After step (vi), `features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md` exists with four sections corresponding to the four sources: `## task-history.json`, `## Linear`, `## Open PRs`, `## Draft test plans`. Each section either lists matching artefacts (one bullet per artefact, with the artefact's id, R-ID anchor, and current status) OR records `(source unavailable: {reason})` when the source's tool is absent (Linear MCP not detected; `gh` CLI not detected). The list is scoped — every listed artefact's R-ID anchor is in the changed-R-ID set; artefacts outside the affected R-IDs are NOT listed. The user is shown the impact list inline in chat. When `--include-backlog` flag is set, the Linear section additionally surfaces tickets with `status: Backlog` whose Anchor R-ID is in the changed set; without the flag, Backlog tickets are excluded. (Verifies R8.)

- **AC-9.** The impact-list file contains a `## What you should consider` section AFTER the four source sections. For each artefact listed in the source sections, this section has a corresponding bullet with a one-line recommended action (e.g. *"PR #123 (T2 anchor R3) — files now removed from R3 scope; consider rebasing or closing"*; *"T4 in_progress (anchor R7 now superseded) — consider aborting current `specflow:develop` run and resuming after scope-change completes"*). Every artefact in the source sections has exactly one corresponding "What you should consider" entry; an artefact without a recommendation is a failed step (vi). (Verifies R9.)

- **AC-10.** After step (vii), `admin/decision-log.md` has a new entry with `id: SC-{NNN}` and the standard schema fields (`title`, `context`, `decision`, `rationale`, `date`, `references`). The `rationale` field contains the *why* verbatim from the interview's new "Scope change" section preamble. The `references` field is a block containing the standard reference shape PLUS three scope-change-specific keys: `affected_r_ids: [R{N}, R{M}, ...]`; `superseded_resolved_lines: [round-{N}.line-{N}, ...]`; `impact_list_path: features/{NNN-slug}/{NNN-slug}-scope-change-{date}-impact.md`. The entry's `id` prefix is `SC-` (separate counter from `specflow:decision`'s default). The skill does NOT write `decision-log.md` directly — the file is written via `specflow:decision` invocation only. **Schema dependency:** AC-10 depends on `specflow:decision` accepting an arbitrary keyed-block within `references` AND accepting an `id_prefix: "SC"` parameter on invocation. If the current Phase 3 `specflow:decision` schema (per `skills/decision/SKILL.md`) does not include these, ship them via a separate `specflow:decision` enhancement PRD before `specflow:scope-change` v1 lands. (Verifies R10, R10.1.)

- **AC-11.** Step (vii) runs ONLY after steps (i) through (vi) have all completed with `state: done` in their respective scratch status files. If any prior step has `state: failed` or `state: pending`, step (vii) does NOT run — the skill halts and surfaces the failed step's error trace to the user. `decision-log.md` therefore never contains a `SC-{NNN}` entry for a partial scope change. (Verifies R11 audit-trail-integrity sub-clause.)

- **AC-12.** On re-invocation of `specflow:scope-change {NNN-slug}` while `admin/scratch/{NNN-slug}-scope-change/` exists, the skill reads the per-step status files and resumes at the first step whose state is NOT `done`. Steps with `state: done` are NOT re-run. Steps with `state: failed` are re-run from the same step (after the user resolves the underlying error). On successful step (viii), the scratch directory is removed and a fresh re-invocation starts at step (i). (Verifies R11.)

- **AC-13.** End-to-end on a feature with 8 PRD requirements and 12 tasks where a scope change affects 2 R-IDs (and therefore ~3 tasks via the coverage matrix), parent-context token consumption stays under 25K tokens (per the orchestrator-pattern target, slightly tighter than `specflow:develop`'s 30K because scope-change has fewer sub-skill steps). Per-sub-skill-invocation growth stays under 2K tokens. `specflow:budget --skill specflow:scope-change` confirms both bounds. (Verifies R12.)

## Open questions

- **Scope change invoked while `specflow:develop` is mid-run on a different task in the same feature.** R7.1 covers the case where the affected task itself is `in_progress`; the unsettled case is when the scope change affects R3 but `specflow:develop` is currently mid-run on a task anchored to R5 (an unaffected R-ID). Does the scope change proceed in parallel, or block until the in-flight `specflow:develop` run completes? Recommend: proceed in parallel (the in-flight task is anchored to an unchanged R-ID; surgical-changes principle says don't touch what's not affected). Confirm at implementation; surface in the impact list as an informational entry.
- **Scope change that adds a new R-ID without changing any prior R-IDs.** R7's delta-regeneration mechanism handles modified/deleted R-IDs cleanly, but the case "scope change introduces R9 (a new requirement) without touching R1-R8" needs explicit handling. Recommend: treat the new R-ID as the changed-R-ID set, run `specflow:task` Phase B against the new R-ID only, generate a new task whose `prior_task_id` is null. Confirm at implementation; document in `tasks.md` schema.
- **Multi-scope-change in one invocation (e.g. user wants to change R3 AND remove R7 in one session).** v1 implicitly supports this — the `/grill` extend-mode can capture multiple new rounds in one section, and the changed-R-ID set is the union. But the impact list and decision-log entry need to handle the multi-change case cleanly. Recommend: one decision-log entry per `specflow:scope-change` invocation regardless of how many R-IDs change; impact list aggregates across all changes. Confirm at implementation.
