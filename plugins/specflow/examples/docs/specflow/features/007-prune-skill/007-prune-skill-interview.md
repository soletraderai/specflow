# PRD interview — features/007-prune-skill

## Original request

> Write the spec for `/prune`, the Phase 3 quarterly-cadence skill that prunes stale rules, decisions, and snapshots — keeping the project memory's signal-to-noise ratio healthy as the corpus grows. Architectural shape is locked in by `v2/docs/PRD.md` § "Phase 3" scope item 10 and the SKILLS.md `/prune` entry: archive of pruned items at `admin/archive/{YYYY-Q}-prune.md`; updated registry (rules / decision-log / agents/index — only after user sign-off per item); pruning is reversible (archive retained); user signs off before delete. This PRD synthesises the implementation contract at the SKILL.md level. Sister Phase 3 cadence skills are `/insights` (monthly) and `specflow:complete` / `specflow:decision` (the writers `/prune` reads).

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `v2/docs/PRD.md` § "Phase 3 — Memory and self-learning" scope item 10 (line 223) names `/prune` as the quarterly cadence sister of `/insights` ("`/insights` (monthly) + `/prune` (quarterly). Surface recurring patterns from `task-history.json`; prune stale rules and decisions."). `SKILLS.md` line 185-190 documents the v2 contract: triggers `/prune` + scheduled cron; produces `admin/archive/{YYYY-Q}-prune.md` + updated registry; requires registry with at-least-one-quarter age (refuse on fresh project); eval — pruning is reversible (archive retained); user signs off before delete.
- **No SKILL.md stub exists yet.** `plugins/specflow/skills/` has no `prune/` directory; `/prune` will be the first skill in the prune surface. The interview + PRD + Gate 2 manifest establish the contract before the SKILL body is written.
- **Surfaces `/prune` operates on are populated and stable.** Four registries: (1) `admin/decision-log.md` — narrative entries written by `specflow:complete` (task-derived) and `specflow:decision` (out-of-band), append-only by file preamble; (2) `admin/rules/non-negotiable.md` and `admin/rules/guidelines.md` — rules registry, two tiers, populated at setup and self-evolving via observation→guideline→non-negotiable promotions; (3) `admin/agents/index.json` + `admin/agents/specialised/` — agent snapshots, pinned, refreshed via `/specflow:agent refresh`. The skill reads each surface's existing schema and proposes prune candidates per surface.
- **Sister skill `/insights` (monthly) is the pattern-surfacer; `/prune` is the cleanup-cadence.** Per SKILLS.md line 178-184, `/insights` reads `task-history.json` for recurring patterns and suggests rule registry promotions. `/prune` is the inverse-cadence — it reads the same registries `/insights` promotes into and proposes demotions / archival when entries have aged out of relevance. The two skills are complementary; never collide on the same write surface (insights writes promotions, prune writes archival + demotions).
- **`agent refresh` already surfaces drift on specialised snapshots.** `skills/agent/SKILL.md` Verb `refresh` (line 159-189) writes a drift report to `admin/scratch/agent-refresh-{timestamp}.md` flagging orphans (source plugin uninstalled), drifted (upstream body changed), clean. `/prune` is the cadence layer that escalates persistent drift — an agent flagged drifted across two consecutive `/prune` runs is a prune candidate.
- **`specflow:complete` writes task-history retention shape.** `skills/complete/SKILL.md` writes append-only entries to `task-history.json` with `superseded_by_retro` and `addenda` semantics. Pruning policy must respect the append-only contract — `/prune` archives the entry, never edits in place, and updates `task-history.json` only after user sign-off per item.
- **Calibration anchors for sibling Phase 3 skill PRDs.** `features/004-decision-skill/` is the small-skill anchor (interview Q&A flow with 6 rounds; PRD with R1-R11 and AC-1 to AC-10; Gate 2 manifest with 6 findings, 1 push-back, status passed-with-revisions). `/prune` is similar scope — smaller than `/insights`, larger than `/specflow:decision` because of the four-surface span, but tightly bounded by the "user signs off before delete" eval. Aim for 8-11 R + 8-11 AC.
- **Worked example: 003-complete-skill.** Calibration anchor for what a Phase 3 multi-surface skill looks like (writes to two surfaces, schema-discipline, structured failure on every refused exit). `/prune` shares the multi-surface property but in read-mostly form — it surfaces candidates, does not auto-mutate.

## Goal (confirmed before grilling)

- **Outcome:** `/prune` keeps the project memory's signal-to-noise ratio healthy as the corpus grows. Quarterly review surfaces stale rules, decisions, and snapshots; user-confirmed prunes are archived for reversibility; the registry stays sharp.
- **Audience:** Power Users (engineers running specflow in their repos) running `/prune` quarterly — either manually at retro time or via scheduled cron. They want a fast review pass that surfaces high-confidence prune candidates with evidence (last-referenced date, age-since-creation, drift status), confirms each one before mutating any registry, and leaves a reversible audit trail. Secondary: future readers reading `admin/archive/` to understand which entries dropped out of the live registry and why.
- **Success looks like:** invoking `/prune` (or scheduled-cron-fire) reads the four target surfaces (rules, decision-log, agent snapshots, task-history), classifies each entry against the staleness boundary, and surfaces a per-surface prune-candidate list with a one-line *why* per candidate. The user signs off per item (keep / archive / defer). Archived items land in `admin/archive/{YYYY-Q}-prune.md` byte-for-byte; the source registry is updated only for archived items. Reversibility: every archived item retains enough context in the archive (full original entry, source surface, prune date, *why*) that a future user can paste it back into the live registry. The skill exits with a chat-line summary: `{N} candidates surfaced; {K} archived; {M} kept; {P} deferred. Archive at admin/archive/{YYYY-Q}-prune.md.`
- **Driving value:** removes the failure mode where the project's narrative memory (`decision-log.md`) and rule registry (`admin/rules/`) accumulate stale entries faster than they age out, eroding the signal Phase 3 self-learning consumers (`/insights`, `specflow:prd`, `specflow:task`) read for. Without quarterly pruning, a six-month-old project has a registry where 30% of rules cite incidents nobody on the current team remembers, three rules contradict more recent decisions, and the decision-log carries entries about tools the project no longer uses. The `/prune` skill is the cadence that keeps the registry trustworthy — entries that earn their slot stay, entries that have aged out of relevance get archived (not deleted) so future readers can recover them. Removes the secondary failure mode where engineers DO try to prune by hand, drift from the schema, and accidentally delete entries that should have been archived.
- **Out of scope at the goal level:** (1) automatic deletion without user sign-off — the eval names "user signs off before delete" as non-negotiable; the skill never auto-prunes; (2) writing to surfaces other than the four named (rules, decision-log, agent snapshots, task-history); cross-skill `pages.json`, `profiles.json`, `environment.json` are out of scope — those are setup/upgrade-managed; (3) pattern-mining or rule-promotion suggestions — that's `/insights`' lane (monthly cadence); `/prune` only proposes archival/demotion; (4) editing or rewriting prior entries in any registry — pruning is archive-then-remove, never in-place edit; (5) running on a fresh project (registry less than one quarter old) — the skill refuses with a clear message; the cadence cannot meaningfully fire before there is a quarter of history to evaluate.

## Rounds

### Round 1 — Staleness boundary: what makes a rule, decision, or snapshot stale?

- **Q:** The goal's Outcome names "stale rules, decisions, and snapshots" but does not define stale. Reading the surfaces — `decision-log.md` entries have `**Date:**` fields; rules in `admin/rules/` have implicit creation dates from git but no explicit field; agent snapshots have `snapshot_date` in `index.json`; `task-history.json` entries have `completed_at`. The staleness boundary could be (a) age-since-creation (>1 quarter), (b) last-referenced date (no entry in `task-history.json` cited this rule/decision in the last quarter), (c) drift signal (agent's upstream body changed; rule's cited decision-log entry was superseded), (d) cross-contradiction (a newer decision-log entry contradicts an older one). The four are distinct and produce different candidate sets. Which boundary does the skill apply, and is it the same boundary across all four surfaces?
- **AI's recommended answer:** Per-surface boundaries, each binary, named explicitly so a fresh agent implementing the skill has one canonical interpretation per surface — the Goal-Driven binary test bites if "stale" stays under-defined. (1) **Decision-log entries:** stale = age-since-creation older than 4 quarters AND no `task-history.json` entry's `prd_anchor` or `Related` substring cites the decision-log entry's title in the last 2 quarters. Pure age-only would over-fire on still-relevant foundational decisions; last-referenced-only would under-fire on entries that are old AND irrelevant. The conjunction is the calibration. (2) **Rules (non-negotiable + guidelines):** stale = the rule's cited decision-log entry has been superseded (the supersede-link is the deterministic signal) OR the rule has zero `task-history.json` violations AND zero `misc-task` references in the last 4 quarters. The two-condition disjunction matches the file's preamble — rules cite decision-log entries; superseded citations are the strongest staleness signal, dormancy is the secondary signal. (3) **Agent snapshots:** stale = the snapshot has been flagged `orphan` (source plugin uninstalled) by `/specflow:agent refresh` for two consecutive `/prune` runs, OR has been flagged `drifted` and not re-snapshotted by the user across two consecutive runs. The two-run threshold avoids over-firing on a one-off install hiccup; persistent drift across a quarter is the calibration. (4) **Task-history entries:** stale = `completed_at` older than 4 quarters AND `superseded_by_retro: true` AND no addenda in the last 2 quarters. Task-history is the most append-heavy surface; conservative pruning preserves the corpus `/insights` reads. — *Reasoning: the goal's Outcome names "the registry stays sharp" — sharp requires per-surface calibration because each surface has a different shape (narrative vs structured-rule vs snapshot vs append-log). Naming each boundary at R-level makes the AC-level binary check possible. The 4-quarter age + 2-quarter dormancy thresholds are calibrated to "quarterly cadence" — by the time `/prune` fires its 4th run on a project, an entry that's seen no reference is genuinely cold.*
- **User's answer:** edit — the dormancy threshold for rules is too aggressive for non-negotiable rules. Non-negotiable rules can be silently observed (no violations BECAUSE the rule is working) — that's the success state, not the staleness state. For non-negotiable rules, drop the dormancy clause and rely solely on superseded-citation. Guidelines keep both clauses (they are softer; dormancy is meaningful signal). Also: thresholds should be configurable in `admin/config.json` under `prune.thresholds` so projects on different cadences can tune; defaults match the AI's numbers.
- **Resolved:** per-surface staleness boundaries, each binary; four surfaces (decision-log, rules, agent snapshots, task-history); decision-log = age >4Q AND no reference in 2Q; non-negotiable rules = superseded-citation only (no dormancy clause — non-violation is success); guidelines = superseded-citation OR zero references in 4Q; agent snapshots = persistent orphan/drift across two runs; task-history = age >4Q AND superseded AND no addenda in 2Q. Thresholds default as named, configurable in `admin/config.json` under `prune.thresholds`. — flows into §Requirements R2, R3, R4, R5; AC AC-2, AC-3, AC-4, AC-5.

### Round 2 — Per-surface vs batch prune flow: one big review or one section at a time?

- **Q:** The skill operates on four surfaces (decision-log, rules, agent snapshots, task-history). The goal's Success-looks-like names "per-surface prune-candidate list" — but the user-flow shape is open: does the skill present all four surfaces as one batch list (user reviews everything in one pass), or one surface at a time (rules first → user signs off → decision-log next → user signs off, etc.)? And does the user see all candidates per surface and pick across them, or is each candidate prompted individually?
- **AI's recommended answer:** Per-surface phases, sequential, each surface its own user-facing review pass. The skill orchestrates four sub-phases (rules → decision-log → agent snapshots → task-history); within each sub-phase, all candidates from that surface are surfaced as a single numbered list with one-line *why* per candidate; the user picks per-item: keep / archive / defer. **Surgical Changes** binds this — batching across surfaces would mean a single user sign-off touches multiple registries simultaneously, which makes a partial failure (e.g. archive write to `decision-log.md` succeeds, write-back to `rules/non-negotiable.md` fails) ambiguous about what the registry now contains. Per-surface sub-phases keep each registry's mutation atomic from the user's perspective: the user signs off on rules → skill writes archive entries for rules → skill demotes/removes from `rules/` → skill verifies → moves to decision-log sub-phase. Within a sub-phase, all-candidates-as-one-list (rather than one-by-one) lets the user see relative weights ("these three rules all cite the same superseded decision-log entry; archive all three together"). Order: rules → decision-log → agent snapshots → task-history. Rules first because rule changes have the largest blast radius (every skill loads the registry); task-history last because it's the most conservative pruner (the corpus `/insights` reads). User can skip any sub-phase via `skip` keyword (defers all candidates from that surface to the next run). — *Reasoning: the goal's "user signs off before delete" eval is per-item, not per-batch; per-surface sub-phases preserve atomicity at the registry-write level. The "all-candidates-per-surface as one list" shape matches the user's review cognitive model — see five rules at once, decide together. The `skip` keyword is the user-elected escape hatch when they don't have time to review a surface this quarter.*
- **User's answer:** confirmed.
- **Resolved:** per-surface sub-phases, sequential (rules → decision-log → agent snapshots → task-history); each sub-phase surfaces all candidates from that surface as one numbered list; user picks keep / archive / defer per item; user can `skip` any sub-phase to defer all candidates to the next run; registry mutations are atomic per sub-phase (write archive entries → update source registry → verify → next sub-phase). — flows into §Requirements R6; AC AC-6.

### Round 3 — Archive retention policy: how long do archived entries stay in `admin/archive/`?

- **Q:** The goal's Success-looks-like names "Reversibility: every archived item retains enough context in the archive (full original entry, source surface, prune date, why) that a future user can paste it back into the live registry." Archive files live at `admin/archive/{YYYY-Q}-prune.md`. Open question: how long do those archive files stay? Until the next prune run? Forever? Configurable? And does `/prune` itself ever prune the archive (meta-cleanup)?
- **AI's recommended answer:** Archive files are retained **forever by default** (no expiry, no auto-cleanup). Three reasons: (1) the goal's Outcome explicitly names reversibility — pruning is reversible — and reversibility with an expiry is conditional reversibility, which defeats the eval; (2) archive files are small markdown (each `{YYYY-Q}-prune.md` is dozens-of-entries scale, KB not MB) and disk cost is not the bottleneck; (3) archive files are the audit trail Phase 3 self-learning consumers may read in future (e.g. a future skill that detects pattern *"this rule was archived 2 quarters ago, then a similar pattern emerged again"* — meta-signal). The skill never prunes its own archive; meta-cleanup is explicitly out of scope. Users who want to delete old archives do so by hand (or via a future `archive` command, not in v1). One-quarter-per-file is the partition shape (`2026-Q2-prune.md`, `2026-Q3-prune.md`); each file is append-only within its quarter (multiple `/prune` runs in the same quarter append to the same file). Cross-quarter retention is therefore implicit in the partition: each quarter's file lives indefinitely. Configuration knob: `admin/config.json` `prune.archiveRetention` defaults to `"forever"`; v1 accepts only `"forever"` (any other value is rejected with a message naming the v1 contract). The knob exists so the v2 conversation has a slot but cannot fire today — speculative configurability prevented by the validation. — *Reasoning: the goal's Outcome makes reversibility the non-negotiable surface. Archive-retention shorter than the project's lifetime weakens reversibility silently. The "forever" default with a stub config knob is the Surgical compromise — the v1 contract is unambiguous; the v2 enhancement path is named without firing.*
- **User's answer:** confirmed.
- **Resolved:** archive retention is **forever by default**; archive files are append-only per quarter (`{YYYY-Q}-prune.md`); the skill never prunes its own archive (meta-cleanup out of scope); `admin/config.json` `prune.archiveRetention` slot exists but v1 accepts only `"forever"` (any other value rejected); cross-quarter retention is implicit in the partition. — flows into §Requirements R7; AC AC-7.

### Round 4 — Cron + manual concurrency: what happens if scheduled cron fires while a manual `/prune` is in progress?

- **Q:** Triggers per SKILLS.md are `/prune` (manual) + scheduled cron. The two paths can fire concurrently — the user kicks off `/prune` manually at 14:00; the cron fires at 14:30 while the manual run is still mid-review (waiting for user sign-off on the decision-log sub-phase). Does the cron path detect the in-flight manual run and skip, queue, or proceed independently? And how does the skill detect concurrency without a coordination layer the harness doesn't expose?
- **AI's recommended answer:** Lock-file concurrency control, mirroring `specflow:complete`'s pattern (per `skills/complete/SKILL.md` Phase A.3). On entry, the skill creates `admin/scratch/prune-{YYYY-Q}.lock` atomically (write-with-O_EXCL). The lock body is a single line: ISO-8601 timestamp + invocation source (`manual` | `cron`). Three cases: **(a) no lock present** → create the lock, proceed. **(b) lock present, age < 90 minutes** → refuse with the literal sentinel: *"`/prune` is already in flight (started `{timestamp}` via `{source}`). Wait for it to complete, or run `/prune --force-unlock` if the prior run crashed."* Exit without touching any registry. The 90-minute threshold is calibrated for typical multi-surface review duration (rules + decision-log + snapshots + task-history can be 30-60 minutes of human review; 90 covers a tabbed-away user with margin). **(c) lock present, age ≥ 90 minutes** → treat as stale (covers crashed-run cleanup); overwrite the lock with a fresh timestamp + source; surface chat-line *"[stale lock detected for prune-{YYYY-Q} — proceeding]"*; proceed. Cron-fire on existing manual lock = path (b); manual-fire on existing cron lock = path (b). The first path (whichever started) holds the lock until end-of-run; the second path always defers via the sentinel. The lock is released atomically at end-of-run on every exit path (success, refusal, cancellation). `--force-unlock` is the user-elected escape hatch when a prior run crashed and the user knows it; never auto-clears. The 90-minute threshold is hard-coded for v1; promotable to `admin/config.json` `prune.staleLockMinutes` in v2 if a project's reviews routinely exceed 90. — *Reasoning: the goal's "user signs off before delete" implies the user owns each prune decision; concurrency would split that decision authority across two contexts (manual user vs cron silent run) and produce a registry whose state nobody knows. Lock-based concurrency control is the Goal-Driven binary check (locked-or-not is unambiguous); 90-minute stale-lock threshold matches the cadence; `--force-unlock` is the documented escape hatch.*
- **User's answer:** confirmed.
- **Resolved:** lock-file concurrency control at `admin/scratch/prune-{YYYY-Q}.lock`; lock body = ISO-8601 timestamp + invocation source (`manual` | `cron`); fresh-lock proceeds, fresh existing lock (<90min) refuses with sentinel, stale lock (≥90min) overwrites and proceeds; lock released atomically on every exit path; `--force-unlock` is the user-elected escape hatch; never auto-clears; thresholds hard-coded for v1, promotable to `admin/config.json` `prune.staleLockMinutes` in v2. — flows into §Requirements R8; AC AC-8.

### Round 5 — Refusal modes: fresh project, registry corrupt, archive-write failed — what's the path?

- **Q:** SKILLS.md `requires:` names "registry with at-least-one-quarter age (refuse on fresh project)." That's one explicit refusal path. Other failure modes worth naming: (a) one of the source registries is corrupt or malformed (e.g. `decision-log.md` truncated mid-entry, `agents/index.json` doesn't parse); (b) the archive write fails mid-sub-phase (disk full, permission denied) — does the skill roll back the registry update, or leave the registry in a partial state? (c) the user's sign-off is ambiguous (typed `archvie` not `archive`) — does the skill re-prompt or default? What's the contract for each?
- **AI's recommended answer:** Four explicit refusal-or-recovery paths, each binary, each emits a sentinel chat line so the user always knows what happened. **(a) Fresh project (registry < 1 quarter old):** detect by reading the oldest entry across all four surfaces; if the oldest entry's date is less than 1 quarter (~91 days) before today, refuse with: *"`/prune` requires at least one quarter of registry history. Oldest entry is `{date}` (`{N}` days). Re-run after `{date + 91 days}`."* Exit without touching any registry. The threshold matches SKILLS.md's "at-least-one-quarter age" requires line. **(b) Source registry corrupt:** before opening any sub-phase, parse each source registry. For `decision-log.md` use the same tail-only parse `specflow:decision` uses (R9 of features/004); for `rules/non-negotiable.md` and `rules/guidelines.md` validate every rule has a frontmatter block + body sections; for `agents/index.json` validate against the schema in `skills/agent/SKILL.md`; for `task-history.json` validate the `tasks` array shape. If any registry fails parse, refuse with: *"`{registry}` failed parse: `{description}`. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` to validate, or fix by hand and re-run."* The skill never auto-repairs. **(c) Archive write fails mid-sub-phase:** use a transaction shape — compose the archive entry first (in working memory), then write the archive file, then write the source registry update only if archive write succeeded; if archive write fails, do NOT touch the source registry, surface: *"Archive write to `admin/archive/{YYYY-Q}-prune.md` failed: `{error}`. Source registry NOT modified — your prune decisions for this sub-phase are not yet applied. Resolve the underlying issue and re-run; the candidate list is regenerated each run."* Atomic per sub-phase — partial-archive + partial-registry-update is a forbidden state. **(d) Ambiguous sign-off:** every per-item prompt accepts only `keep` | `archive` | `defer` (or single-letter shortcuts `k` | `a` | `d`); any other input re-prompts with the literal *"Choose `keep` (k), `archive` (a), or `defer` (d)."*; never auto-defaults; empty input also re-prompts. — *Reasoning: the goal's "user signs off before delete" requires every refusal to be visible (silent-skip would defeat the eval); the goal's "pruning is reversible" requires archive-before-mutate semantics (write archive first, mutate registry only on archive-write success). Auto-default on ambiguous input is the path that produces silent wrong outcomes; re-prompting is the binary surface.*
- **User's answer:** confirmed.
- **Resolved:** four refusal-or-recovery paths — (a) fresh project (<1Q registry age) → refuse with date-arithmetic message; (b) source registry corrupt → refuse with parse-failure message + route to `specflow:doctor`; (c) archive-write fails → archive-before-mutate transaction shape, source registry untouched on archive failure; (d) ambiguous user input → re-prompt with literal options, never auto-default. — flows into §Requirements R1, R9, R10, R11; AC AC-1, AC-9, AC-10.

### Round 6 — Verify discipline: how does the skill confirm each archived item round-trips to original state if restored?

- **Q:** Goal-Driven Execution requires inline verify steps. The goal names "every archived item retains enough context that a future user can paste it back" — but how does the skill confirm that round-trip property at write time? Does it re-read the archive entry and validate the original-entry text matches byte-for-byte? Compute a checksum? And what about post-archive verification — does the skill confirm the source registry no longer contains the archived entry's identifier?
- **AI's recommended answer:** Two-stage verification per archived item, both binary, mirroring `specflow:decision`'s post-write read-back pattern. **Stage 1 (round-trip integrity):** after composing the archive entry but before writing, the skill captures the original entry's bytes from the source registry verbatim; the archive entry's `Original entry` field carries those bytes byte-for-byte. After writing the archive file, the skill re-reads the archive entry and confirms (i) the H2 title matches the candidate's title; (ii) the `**Source surface:**` field names the source registry path; (iii) the `**Prune date:**` field equals today's `YYYY-MM-DD`; (iv) the `**Why:**` field is non-empty; (v) the `Original entry` block is byte-identical to the captured original. Any Stage-1 failure aborts the per-item write with a structured error; the source registry is NOT modified (per R10's archive-before-mutate). **Stage 2 (source-registry mutation):** after Stage 1 passes, the skill updates the source registry — for `decision-log.md`, this is *not* a delete (the file is append-only by preamble) but an annotation: append a line `<!-- archived YYYY-Q-prune -->` immediately after the entry's `---` separator (the original entry stays in the file, but Phase 3 consumers' staleness-readers skip annotated entries). For `rules/`, demote a rule by removing it from the live file (add a stub line `<!-- {rule-id} archived YYYY-Q-prune -->` at end of file). For `agents/index.json`, drop the entry; the snapshot file at `admin/agents/specialised/{name}.md` moves to `admin/archive/agents/{YYYY-Q}/{name}.md`. For `task-history.json`, set the entry's `archived_at: YYYY-MM-DD` field; the entry stays in the array. After mutation, Stage 2 re-reads the source registry and confirms the annotation/demotion landed. — *Reasoning: the goal's "pruning is reversible" eval demands the round-trip property hold mechanically, not by inspection. Byte-identical capture + post-write read-back is the binary check the LLM can run independently. The decision-log annotation rather than delete is the surgical move — append-only contract preserved + future-reader skip-signal preserved.*
- **User's answer:** edit — for `rules/`, removing the rule from the live file is the right move, but the stub line at end of file is noise; instead, write the demoted rule's `id` to `admin/archive/{YYYY-Q}-prune.md` with the full body (per Stage 1 already), and leave the live `rules/{tier}.md` clean. The archive file IS the audit trail; we don't also need stub lines in the source. Same for `decision-log.md`: instead of an annotation comment in-file, the staleness-readers in Phase 3 (e.g. `/insights`) read the archive file directly to know which entries were pruned. Single source of truth for archive state = the archive file.
- **Resolved:** two-stage verification per archived item — Stage 1 round-trip integrity (byte-identical original-entry capture + post-write read-back of five archive fields); Stage 2 source-registry mutation (decision-log entry stays in file unmarked — Phase 3 consumers cross-reference the archive file; rules removed from live file; agent snapshot moved to `admin/archive/agents/{YYYY-Q}/{name}.md` and dropped from `index.json`; task-history entry sets `archived_at` field). Single source of truth for archive state is the archive file; no in-source stub lines or annotation comments. — flows into §Requirements R12; AC AC-11.
