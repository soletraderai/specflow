# /prune — quarterly registry-pruning cadence

## Vision

`/prune` keeps the project memory's signal-to-noise ratio healthy as the corpus grows. The user invokes it (or scheduled cron fires it) once a quarter; the skill reads the four target surfaces — rules (`admin/rules/non-negotiable.md`, `admin/rules/guidelines.md`), decisions (`admin/decision-log.md`), agent snapshots (`admin/agents/index.json` + `admin/agents/specialised/`), and task-history (`admin/task-history.json`) — classifies each entry against an explicit per-surface staleness boundary, and surfaces a per-surface prune-candidate list with a one-line *why* per candidate. The user signs off per item — keep, archive, or defer. Archived items land byte-for-byte in `admin/archive/{YYYY-Q}-prune.md`; the source registry is updated only for archived items; the live registry stays sharp. Pruning is reversible: every archive entry retains the original entry's bytes plus the source surface, prune date, and *why*, so a future user can paste it back into the live registry. The skill exits with a chat-line summary: `{N} candidates surfaced; {K} archived; {M} kept; {P} deferred. Archive at admin/archive/{YYYY-Q}-prune.md.` Re-running on a project less than one quarter old refuses with a clear date-arithmetic message; re-running while another `/prune` run is in flight refuses via lock-file sentinel.

## Problem

Phase 3 of specflow closes the self-learning loop: every completed task feeds memory; every new task reads from it. `specflow:complete` writes append-only entries to `task-history.json` and (on significant patterns) to `decision-log.md`. `specflow:decision` writes user-driven out-of-band decision-log entries. `/specflow:agent refresh` snapshots agents and surfaces drift. Rules accumulate at setup and self-evolve via observation→guideline→non-negotiable promotions. Without a counter-cadence, the registry grows monotonically — entries accumulate faster than they age out, and within two or three quarters a project has a registry where 30% of rules cite incidents nobody on the current team remembers, three rules contradict more recent decisions, and the decision-log carries entries about tools the project no longer uses. Phase 3 self-learning consumers (`/insights`, `specflow:prd`, `specflow:task`) read the same registries for context; signal-to-noise erosion silently degrades every downstream skill.

The fix is a skill that runs once a quarter, surfaces stale entries against an explicit per-surface boundary, confirms each one with the user, and archives confirmed prunes for reversibility. Two invocation modes: `/prune` (manual interactive) and scheduled cron (same flow, refuses on user-prompt branches that require interactive input — cron deferrals are written to the run report). Per-surface sub-phases preserve atomicity at the registry-write level. Lock-file concurrency control prevents cron-and-manual collision. Archive-before-mutate transaction shape preserves reversibility on failure. Every refusal exits with a sentinel chat line so the user always knows what happened. Twelve requirements; eleven acceptance criteria; the cadence layer that keeps the registry trustworthy.

## Goals

- Two invocation modes — `/prune` (interactive manual) and scheduled cron (same orchestration; cron-mode refuses on user-prompt branches that require interactive sign-off and writes deferrals to the run report). Refuses on a fresh project (registry less than one quarter old) with a date-arithmetic message.
- Per-surface staleness boundaries, each binary, configurable with project-tunable thresholds (per Round 1 user-ask). Decision-log: age-since-creation older than 4 quarters AND no `task-history.json` reference in 2 quarters. Non-negotiable rules: superseded-citation only (no dormancy clause — non-violation is success). Guidelines: superseded-citation OR zero references in 4 quarters. Agent snapshots: persistent orphan/drift across two consecutive `/prune` runs. Task-history: age >4Q AND `superseded_by_retro: true` AND no addenda in 2Q. Thresholds default as named, configurable in `admin/config.json` under `prune.thresholds` per the user's Round 1 edit.
- Per-surface sub-phases, sequential — rules → decision-log → agent snapshots → task-history. Each sub-phase surfaces all candidates from that surface as a single numbered list with one-line *why* per candidate; the user picks `keep` / `archive` / `defer` per item. Registry mutations are atomic per sub-phase: write archive entries for that surface → update source registry → verify → next sub-phase. User can `skip` a sub-phase to defer all candidates from that surface to the next run.
- Archive retention is forever by default. Archive files at `admin/archive/{YYYY-Q}-prune.md` are append-only per quarter (multiple `/prune` runs in the same quarter append to the same file). The skill never prunes its own archive; meta-cleanup is out of scope. No `admin/config.json` knob in v1 — the v1 contract is forever-by-default with no configuration surface. The retention-knob v2 enhancement path is named in Open Questions.
- Lock-file concurrency control at `admin/scratch/prune-{YYYY-Q}.lock`. Lock body = ISO-8601 timestamp + invocation source (`manual` | `cron`). Fresh-lock proceeds; existing lock <90 minutes old refuses with a sentinel; stale lock ≥90 minutes is overwritten (covers crashed-run cleanup) with a chat-line note. `--force-unlock` is the user-elected escape hatch when a prior run crashed; never auto-clears. Lock released atomically on every exit path.
- Refusal modes are deterministic: fresh project → refuse with date-arithmetic message; source registry corrupt (any of the four parsers fails) → refuse with structured error pointing at `specflow:doctor`; archive-write failure mid-sub-phase → archive-before-mutate transaction shape, source registry untouched on archive failure; ambiguous user input → re-prompt with literal options, never auto-default.
- Two-stage verification per archived item. Stage 1 (round-trip integrity): byte-identical capture of the original entry's source-registry bytes; post-write read-back confirms five archive fields (H2 title, `**Source surface:**`, `**Prune date:**`, `**Why:**` non-empty, `Original entry` block byte-identical). Stage 2 (read-only on three surfaces + bespoke on agent snapshots): for decision-log, rules, and task-history, Stage 2 is read-only — the live source registry stays unmodified; the archive file is the single source of truth for archive state; Phase 3 consumers cross-reference the archive file. For agent snapshots only, Stage 2 mutates the live registry — moves `admin/agents/specialised/{name}.md` to `admin/archive/agents/{YYYY-Q}/{name}.md` and drops the index entry — because the live agent registry is the runtime surface (a read-only Stage 2 here would mean a 'pruned' agent stays active at runtime, defeating the prune). Round-trip restoration is the R-level contract Stage 1's byte-identical capture establishes — pasting an archive block's `Original entry` content back into the source surface reproduces the pre-archive state byte-for-byte.

## Non-goals

- **Automatic deletion without user sign-off.** The eval names "user signs off before delete" as non-negotiable; the skill never auto-prunes. Cron-mode deferrals are written to the run report, not silently archived.
- **Writing to surfaces other than the four named** (rules, decision-log, agent snapshots, task-history). `pages.json`, `profiles.json`, `environment.json` are setup/upgrade-managed; pruning policy for them belongs to those skills.
- **Pattern-mining or rule-promotion suggestions.** That's `/insights`' lane (monthly cadence). `/prune` only proposes archival/demotion.
- **Editing or rewriting prior entries in any registry.** Pruning is archive-then-remove (or archive-then-annotate-via-archive-file), never in-place edit.
- **Running on a fresh project (registry less than one quarter old).** The skill refuses with a clear message; the cadence cannot meaningfully fire before there is a quarter of history to evaluate.
- **Pruning the archive itself.** Archive retention is forever; meta-cleanup is explicitly out of scope. Users who want to delete old archives do so by hand.
- **Cross-project prune patterns.** The skill operates on one project's `admin/` registry. Cross-project corpus updates would require a registry shape that doesn't exist yet.

## Users

- **Power User (per `admin/profiles.json`)** — engineers running specflow in their repos, invoking `/prune` quarterly at retro time or via scheduled cron. They want a fast review pass that surfaces high-confidence prune candidates with concrete *why* per candidate, confirms each one, and leaves a reversible audit trail. They need the per-surface phases to be skippable (some quarters they only have time to review one surface) and the prompts to be terse (single-letter shortcuts on every per-item prompt).
- **Future readers** — the same engineers months later, or a new teammate reviewing the project's `admin/archive/` to understand which entries dropped out of the live registry and why. They benefit from the byte-identical archive capture: pasting an archived entry back into the live registry reproduces the original state exactly.
- **Phase 3 self-learning consumers (`/insights`, `specflow:prd`, `specflow:task`)** — automated readers running on monthly / quarterly cadence. They benefit from the live registry staying sharp (signal-to-noise high). They also read the archive file as a meta-signal — "this rule was archived 2 quarters ago" is data a future pattern-detector can use.

## Requirements

- **R1.** Two invocation modes + fresh-project refusal. `/prune` runs the full interactive flow (manual mode); scheduled cron runs the same orchestration but in `cron` mode (deferrals on any branch requiring interactive user input are written to the run report, never auto-defaulted). Before any other check, the skill identifies the oldest entry across the four source registries (oldest of: oldest decision-log entry's `**Date:**`, oldest rule's git-history creation date, oldest agent snapshot's `snapshot_date`, oldest task-history entry's `completed_at`). If the oldest entry is less than 91 days before today, refuse with the literal sentinel: *"`/prune` requires at least one quarter of registry history. Oldest entry is `{date}` (`{N}` days). Re-run after `{date + 91 days}`."* Exit without touching any registry.
  - Trace: interview Round 5 — *fresh project (<1Q registry age) → refuse with date-arithmetic message*.
  - Serves goal: Out-of-scope-at-goal-level (the cadence cannot meaningfully fire before there is a quarter of history to evaluate).

- **R2.** Decision-log staleness boundary. A `decision-log.md` entry is a prune candidate iff (a) the entry's `**Date:**` field is older than 4 quarters (~365 days) before today, AND (b) no `task-history.json` entry's `prd_anchor` field, no `task-history.json` entry's `decision_log_links[].title`, AND no other `decision-log.md` entry's `**Related:**` field, contains the candidate entry's H2 title as a substring within the last 2 quarters (~182 days). The conjunction is binary; pure-age would over-fire on still-relevant foundational decisions; pure-dormancy would under-fire on entries that are old AND irrelevant. Threshold defaults configurable in `admin/config.json` under `prune.thresholds.decisionLog.{ageDays, dormancyDays}` (defaults: 365, 182).
  - Trace: interview Round 1 — *decision-log = age >4Q AND no reference in 2Q*.
  - Serves goal: Driving value (the live registry stays sharp because the boundary is binary and per-surface).

- **R3.** Rules staleness boundary (two-tier). A rule's body's *Why* section may cite a `decision-log.md` entry by **title** (a quoted string matching an entry's H2 title) OR by **date** (a `YYYY-MM-DD` substring matching an entry's `**Date:**` field). The skill's citation-resolution helper extracts both forms — for title citations, the rule cites the decision-log entry whose H2 title matches the quoted string; for date citations, the rule cites the decision-log entry whose `**Date:**` field matches the date. The two existing rules in the worked example (`PREFER_LOCAL_TESTS` cites `2026-02-14`; `PREFER_COMPOSITION_OVER_INHERITANCE` cites `2026-01-08`) use the date form, so date-citation tolerance is non-optional. Once a citation is resolved to a decision-log entry's title, supersession detection is title-based per `specflow:decision`'s R6 + AC-5: a rule cites a superseded decision-log entry iff a later `decision-log.md` entry's `**Related:**` field carries the literal prefix `Supersedes: "{resolved title}"`. **Non-negotiable rules:** prune candidate iff the rule's *Why* section cites (by title or date) a superseded decision-log entry. No dormancy clause for non-negotiable rules — non-violation is the success state, not the staleness state (per Round 1 user-edit). **Guidelines:** prune candidate iff (a) the rule cites a superseded decision-log entry (title or date), OR (b) zero `task-history.json` `addenda[].description` entries and zero `misc-task` entries cite the rule's `id` (frontmatter field) within the last 4 quarters. Threshold defaults configurable in `admin/config.json` under `prune.thresholds.guidelines.dormancyDays` (default: 365).
  - Trace: interview Round 1 (edited) — *non-negotiable rules = superseded-citation only (no dormancy clause — non-violation is success); guidelines = superseded-citation OR zero references in 4Q*. Refined at Gate 2 per tbc-r1-f1: citation-resolution helper extracts both title and date forms; the existing rules in the worked example cite by date, so date-citation tolerance is non-optional.
  - Serves goal: Driving value (the rules registry is the most blast-radius surface; the conservative non-negotiable boundary preserves rules whose silent observance is success).

- **R4.** Agent snapshot staleness boundary. An agent snapshot in `admin/agents/specialised/` is a prune candidate iff `/specflow:agent refresh` has flagged the snapshot as `orphan` (source plugin uninstalled) OR `drifted` (upstream body differs from snapshot) on two consecutive prior `/prune` runs. The two-run threshold avoids over-firing on a one-off install hiccup. Persistence is determined by reading the prior `/prune` run's report (held at `admin/scratch/prune-history.json`, an append-only ledger of `{run_date, surface, candidate_id, status}` records each `/prune` invocation writes at the close of every sub-phase). On the first-ever `/prune` run for a project, no agent snapshots are candidates (the two-run history does not yet exist) — the skill emits a chat-line *"Agent sub-phase: no candidates this run; persistence threshold not yet met. Drift will be evaluated next run."* and proceeds to the next sub-phase.
  - Trace: interview Round 1 — *agent snapshots = persistent orphan/drift across two runs*.
  - Serves goal: Driving value (the goal explicitly names "persistent drift" as the calibration; one-off drift is not signal).

- **R5.** Task-history staleness boundary. A `task-history.json` entry is a prune candidate iff `completed_at` is older than 4 quarters (~365 days) before today AND `superseded_by_retro: true` AND the entry's `addenda` array has zero entries with `date` within the last 2 quarters (~182 days). Task-history is the most append-heavy surface and the most conservative pruner — the corpus `/insights` reads. Threshold defaults configurable in `admin/config.json` under `prune.thresholds.taskHistory.{ageDays, dormancyDays}` (defaults: 365, 182).
  - Trace: interview Round 1 — *task-history = age >4Q AND superseded AND no addenda in 2Q*.
  - Serves goal: Driving value (preserves the corpus `/insights` reads while still aging out genuinely cold entries).

- **R6.** Per-surface sub-phase orchestration with strict input contracts. The skill runs four sequential sub-phases in fixed order: (i) rules, (ii) decision-log, (iii) agent snapshots, (iv) task-history. Within each sub-phase, the skill computes the candidate set per the corresponding R (R3 / R2 / R4 / R5), surfaces all candidates as a single numbered list with one-line *why* per candidate, then prompts per-item: the per-item prompt accepts only the literal values `keep` | `archive` | `defer` (or single-letter shortcuts `k` | `a` | `d`); any other input (including empty) re-prompts with the literal *"Choose `keep` (k), `archive` (a), or `defer` (d)."*; the skill never auto-defaults. After all per-item picks for the surface, the skill enters the per-surface write phase: compose archive entries for archived items, write the archive file (per R10), update the source registry (per R11 Stage 2). Verify (per R11 Stage 1 + Stage 2). Then next sub-phase. The per-sub-phase entry prompt accepts only `proceed` | `skip` (or `p` | `s`); the user can type `skip` at the start of any sub-phase to defer all candidates from that surface to the next run. The `--force-unlock` confirm-prompt (per R8) accepts only `y` | `N` (default N on empty input). Cron-mode treats any prompt that would re-fire after re-prompt as a `skip` (the candidate is deferred to the next run; the run report records the deferral with reason `cron-mode-cannot-prompt`). Order is fixed (rules first because rule changes have the largest blast radius; task-history last because it is the most conservative).
  - Trace: interview Round 2 — *per-surface sub-phases, sequential (rules → decision-log → agent snapshots → task-history); each sub-phase surfaces all candidates as one numbered list; user picks keep / archive / defer per item; user can `skip` any sub-phase*. Combined with interview Round 5 — *ambiguous user input → re-prompt with literal options, never auto-default* (the input-contract clause).
  - Serves goal: Outcome (per-surface prune-candidate list with a one-line *why* per candidate; user signs off per item — silent default would defeat the eval).

- **R7.** Archive file shape and retention. Archived items land in `admin/archive/{YYYY-Q}-prune.md` (e.g. `admin/archive/2026-Q2-prune.md`). The file is append-only within its quarter (multiple `/prune` runs in the same quarter append to the same file). Each archived item is a markdown block with five fields in fixed order: `## {original entry title}`; blank line; `**Source surface:** {registry path — one of admin/rules/non-negotiable.md, admin/rules/guidelines.md, admin/decision-log.md, admin/agents/index.json, admin/task-history.json}`; blank line; `**Prune date:** {YYYY-MM-DD}`; blank line; `**Why:** {one-line description carrying the staleness signal that fired — e.g. "Cited decision-log entry 'Slack removed from the stack' was superseded on 2026-04-12"}`; blank line; ` ```` ` block labelled `Original entry` containing the original entry's bytes verbatim; blank line; `---`; blank line. Retention is forever by default. There is no `admin/config.json` knob for archive retention in v1 — the v1 contract is forever-by-default with no configuration surface. The skill never prunes its own archive. The retention-knob v2 enhancement path is named in Open Questions; until a project documents real disk-pressure or audit-policy reasons for retention shorter than forever, the v1 default holds.
  - Trace: interview Round 3 — *archive retention is forever by default; archive files are append-only per quarter; the skill never prunes its own archive*. Refined at Gate 2 per simplicity-r1-f1 concession: the `prune.archiveRetention` config knob is dropped from v1 entirely; v2 enhancement path moved to Open Questions.
  - Serves goal: Outcome (every archived item retains enough context that a future user can paste it back into the live registry — full original entry, source surface, prune date, why).

- **R8.** Lock-file concurrency control. On entry, the skill creates `admin/scratch/prune-{YYYY-Q}.lock` atomically (write-with-O_EXCL). Lock body is one line: ISO-8601 timestamp of acquisition + invocation source (`manual` | `cron`), space-separated. **Implausible-timestamp refusal:** before any of the three cases below fires, the skill compares the lock-body timestamp against the current time. If the lock-body timestamp is more than 24 hours in the past (older than any real run could have started) OR more than 1 hour in the future (no real lock acquisition is in the future), refuse with the literal sentinel: *"Lock file at `admin/scratch/prune-{YYYY-Q}.lock` has implausible timestamp `{ts}` (compared to current time `{now}`). Inspect the lock file by hand and use `--force-unlock` if appropriate."* Exit without touching any registry. The 24-hour-past bound covers battery-failed-clock cases; the 1-hour-future bound covers misconfigured-timezone-offset cases. Three nominal cases (after the implausible-timestamp gate passes): **(a) no lock present** → create the lock, proceed to R1's fresh-project check. **(b) lock present, age <90 minutes** (compare lock timestamp to now using filesystem `mtime` as the primary clock and the lock body's timestamp as the cross-check; if the two disagree by more than 60 seconds, prefer the lock-body value as authoritative — the cron host's clock skew should not silently invalidate a manual user's lock) → refuse with the literal sentinel: *"`/prune` is already in flight (started `{timestamp}` via `{source}`). Wait for it to complete, or run `/prune --force-unlock` if the prior run crashed."* Exit without touching any registry. **(c) lock present, age ≥90 minutes** → treat as stale; overwrite the lock with a fresh timestamp + source; surface chat-line *"[stale lock detected for prune-{YYYY-Q} — proceeding]"*; proceed. The 90-minute threshold is hard-coded for v1 (calibrated for typical multi-surface review duration, 30-60 minutes of human review with margin); promotable to `admin/config.json` `prune.staleLockMinutes` in v2 if a project's reviews routinely exceed 90. **`--force-unlock` and the unlock-marker priority window:** `--force-unlock` is the user-elected escape hatch — refuses if no lock present with *"`/prune --force-unlock` invoked but no lock present at `admin/scratch/prune-{YYYY-Q}.lock`. No-op."*; otherwise removes the lock after a confirm prompt *"Force-unlock will discard the in-flight run's state. Confirm? (y/N)"* (default N on empty input). After a successful force-unlock, the skill writes a one-line marker file at `admin/scratch/prune-{YYYY-Q}.unlock-marker` containing the unlock timestamp AND emits the chat-line *"[lock cleared at {timestamp}; re-invoke /prune within 5 minutes to start a fresh run]"*. The next `/prune` invocation reads the marker; if the marker's timestamp is within 5 minutes of now AND the invocation is `manual`, the manual invocation has priority — any concurrent `cron` path that would otherwise create a lock between unlock and re-invoke must defer (refuse with *"`/prune --force-unlock` was invoked at `{ts}`; awaiting manual re-invoke. Cron deferred."*). The marker is consumed (deleted) by the next manual `/prune` invocation OR auto-expires after 5 minutes (whichever first). The lock is released atomically at end-of-run on every exit path.
  - Trace: interview Round 4 — *lock-file concurrency control at `admin/scratch/prune-{YYYY-Q}.lock`; fresh-lock proceeds, fresh existing lock (<90min) refuses with sentinel, stale lock (≥90min) overwrites and proceeds; lock released atomically; `--force-unlock` is the user-elected escape hatch*. Extended at Gate 2 per da-r1-f1: implausible-timestamp refusal (24h-past / 1h-future bounds for hours-scale clock-skew); `--force-unlock` unlock-marker priority window (5-minute manual-priority window after force-unlock); clock-skew tolerance via lock-body timestamp cross-check; `--force-unlock` confirm-prompt and no-lock-present safety.
  - Serves goal: Out-of-scope-at-goal-level (concurrency would split decision authority across two contexts; lock-based control preserves the "user signs off before delete" eval).

- **R9.** Source registry corruption refusal. Before opening any sub-phase, the skill parses each source registry. **For `decision-log.md`:** the same tail-only parse `specflow:decision`'s R9 uses (file ends with either canonical preamble + `---` (no entries) OR a complete entry with five canonical bold-prefixed fields + trailing `---`). **For `admin/rules/non-negotiable.md` and `admin/rules/guidelines.md`:** every rule must have a YAML frontmatter block (with `id`, `tier`, `paths` fields) followed by *Rule*, *Why*, *On violation*, *Exceptions* sections; missing any of those is a parse failure. **For `admin/agents/index.json`:** validate against the schema in `skills/agent/SKILL.md` (top-level `schema_version: 1`, `agents` array, each entry with `name`, `category`, `source`, `version`, `path`, `snapshot_date` populated). **For `admin/task-history.json`:** top-level `tasks` array; every entry has `id`, `feature_id` (or `feature`), `task_id`, `completed_at`. Any parse failure refuses with the literal sentinel: *"`{registry-path}` failed parse: `{description}`. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` to validate, or fix by hand and re-run."* The skill never auto-repairs. Lock is released on the refused exit per R8's release-on-every-exit-path contract.
  - Trace: interview Round 5 — *source registry corrupt → refuse with parse-failure message + route to `specflow:doctor`*.
  - Serves goal: Driving value (the registry is the project's narrative memory; pruning a corrupt registry would compound corruption silently).

- **R10.** Archive-before-mutate transaction shape. For every archive operation within a sub-phase: (i) compose the archive entry in working memory per R7's five-field shape; (ii) append to `admin/archive/{YYYY-Q}-prune.md` (creating the directory and file if missing); (iii) verify the archive write per R11 Stage 1; (iv) only then mutate the source registry per R11 Stage 2. If step (ii) or (iii) fails, the source registry is NOT touched; the skill surfaces *"Archive write to `admin/archive/{YYYY-Q}-prune.md` failed: `{error}`. Source registry NOT modified — your prune decisions for this sub-phase are not yet applied. Resolve the underlying issue and re-run; the candidate list is regenerated each run."* and exits the sub-phase. Already-archived items earlier in the sub-phase whose source registry has been mutated stay mutated; the failure is per-item, not per-sub-phase. The skill writes per-item status to `admin/scratch/prune-history.json` (per R4's persistence ledger) so the next run can recompute the candidate set against the updated registry state. Lock is released on the refused exit.
  - Trace: interview Round 5 — *archive-write fails → archive-before-mutate transaction shape, source registry untouched on archive failure*.
  - Serves goal: Outcome (pruning is reversible — the archive is written first; the live registry is mutated only after archive success).

- **R11.** Two-stage verification per archived item. **Stage 1 (round-trip integrity):** before composing the archive entry, the skill captures the original entry's bytes from the source registry verbatim — for `decision-log.md`, the H2 line through the entry's trailing `---` (exclusive) is the captured slice; for `rules/{tier}.md`, the YAML frontmatter through the *Exceptions* section's terminating `---` is the slice; for `admin/agents/index.json`, the JSON object for the entry plus the file body of `admin/agents/specialised/{name}.md` is the slice; for `task-history.json`, the JSON object for the entry is the slice. After writing the archive file, the skill re-reads the appended archive block and confirms (i) the H2 title matches the candidate's title; (ii) the `**Source surface:**` field names the source registry path; (iii) the `**Prune date:**` field equals today's `YYYY-MM-DD`; (iv) the `**Why:**` field is non-empty; (v) the `Original entry` block's bytes are byte-identical to the captured slice. Any Stage-1 failure aborts the per-item write with a structured error; the source registry is NOT modified (per R10). **Stage 2 (source-registry mutation, three-surface uniform read-only + agent-snapshot exception):** after Stage 1 passes, the Stage-2 treatment differs by whether the live registry is a runtime surface or a read-by-Phase-3-consumers surface. **Read-only at Stage 2 (decision-log, rules, task-history):** the source registry stays unmodified at Stage 2. The archive file is the single source of truth for archive state across these three surfaces; Phase 3 consumers (`/insights`, `specflow:prd`, `specflow:task`) cross-reference the archive file to identify pruned entries when reading these surfaces. The skill never mutates the live `decision-log.md`, never edits `rules/{tier}.md`, and never sets an `archived_at` field on `task-history.json`. **Bespoke Stage 2 (agent snapshots):** the agent snapshot file at `admin/agents/specialised/{name}.md` is referenced by `agents/index.json` and loaded by every skill that uses the agent at runtime; a read-only Stage 2 here would mean a 'pruned' agent is still active at runtime, which defeats the purpose of pruning. So agent snapshots specifically need Stage-2 mutation: move `admin/agents/specialised/{name}.md` to `admin/archive/agents/{YYYY-Q}/{name}.md`; remove the entry from `admin/agents/index.json`. The asymmetry is structural (the live agent registry IS the runtime surface), not bespoke per surface; it is documented here once and called out at every consumer integration point. After mutation, Stage 2 re-reads the source registry and confirms the agent-index entry is no longer present + the archive-agents file exists. For the three read-only surfaces, Stage 2 re-reads the source registry to confirm it is byte-identical to its pre-Stage-2 state (no accidental mutation). **Round-trip restoration:** a future user pasting a single archive block's `Original entry` content back into the source surface MUST reproduce the source registry's pre-archive state byte-for-byte for that entry. For decision-log, rules, and task-history — restoration is paste-the-archive-block-Original-entry into the source position; since Stage 2 was read-only, the restoration is purely additive into a registry that never lost the entry from the on-disk source (the archive marked it as pruned for Phase 3 consumers, but the live source bytes are unchanged). For agent snapshots, restoration is two-step: copy the file from `admin/archive/agents/{YYYY-Q}/{name}.md` back to `admin/agents/specialised/{name}.md` and re-add the index entry from the archive block's `Original entry` JSON. The byte-identical capture at Stage 1 is the surface that makes restoration deterministic across both treatments. Refined at Gate 2 per goal-r1-f1 (round-trip restoration named explicitly as the contract Stage 1's byte-identical capture establishes) and surgical-r1-f1 (uniform read-only Stage 2 across three surfaces; bespoke Stage 2 for agent snapshots only, with the structural rationale documented).

## Acceptance criteria

- **AC-1.** When the oldest entry across the four source registries is less than 91 days before today, the skill refuses with the literal sentinel *"`/prune` requires at least one quarter of registry history. Oldest entry is `{date}` (`{N}` days). Re-run after `{date + 91 days}`."* No registry is modified; no archive file is created; the lock is released. When the oldest entry is ≥91 days old, the skill proceeds past the fresh-project check. (Verifies R1.)

- **AC-2.** A `decision-log.md` entry is included in the rules sub-phase candidate list iff (a) its `**Date:**` value is older than the configured `prune.thresholds.decisionLog.ageDays` (default 365) days before today, AND (b) no `task-history.json` entry's `prd_anchor`, no `task-history.json` entry's `decision_log_links[].title`, and no other `decision-log.md` entry's `**Related:**` field, contains the candidate's H2 title as a substring within the configured `prune.thresholds.decisionLog.dormancyDays` (default 182) days. An entry that fails either clause is NOT a candidate. (Verifies R2.)

- **AC-3.** The skill's citation-resolution helper extracts citations from each rule's *Why* section in two forms: (i) **title citations** — quoted strings (delimited by single or double quotes) that exact-match an existing `decision-log.md` entry's H2 title; (ii) **date citations** — `YYYY-MM-DD` substrings that exact-match an existing decision-log entry's `**Date:**` field value. For each extracted citation, the helper resolves to the corresponding decision-log entry's H2 title. A non-negotiable rule is included in the rules sub-phase candidate list iff at least one resolved citation has been superseded — the skill scans every `decision-log.md` entry's `**Related:**` field for the literal substring `Supersedes: "{resolved title}"` (case-sensitive on the resolved title; the supersede-link prefix is documented in `specflow:decision`'s R6 + AC-5). Dormancy is NOT a candidacy criterion for non-negotiable rules. A guideline is included iff (a) at least one of its resolved citations has been superseded, OR (b) zero `task-history.json` `addenda[].description` entries and zero `misc-task` entries cite the rule's `id` within `prune.thresholds.guidelines.dormancyDays` (default 365) days. If a rule's *Why* section contains no extractable citations (no quoted strings AND no `YYYY-MM-DD` substrings), the rule is NOT a candidate via clause (a) — guidelines fall through to clause (b); non-negotiable rules without resolvable citations are never candidates. (Verifies R3.)

- **AC-4.** An agent snapshot is included in the agent-snapshots sub-phase candidate list iff `admin/scratch/prune-history.json` records the same agent's `surface: agents`, `status: orphan` OR `status: drifted` for two consecutive prior `/prune` runs (most-recent two entries for that agent). On the first-ever `/prune` run for a project (`prune-history.json` absent or empty), no agent snapshots are candidates and the skill emits the literal *"Agent sub-phase: no candidates this run; persistence threshold not yet met. Drift will be evaluated next run."* before proceeding to the next sub-phase. (Verifies R4.)

- **AC-5.** A `task-history.json` entry is included in the task-history sub-phase candidate list iff `completed_at` is older than `prune.thresholds.taskHistory.ageDays` (default 365) days before today, AND `superseded_by_retro: true`, AND the entry's `addenda` array has zero entries with `date` within `prune.thresholds.taskHistory.dormancyDays` (default 182) days. An entry that fails any of the three clauses is NOT a candidate. (Verifies R5.)

- **AC-6.** The skill runs four sub-phases in fixed order — rules, decision-log, agent snapshots, task-history. Within each sub-phase: (i) the candidate list is computed per the corresponding AC (AC-3 / AC-2 / AC-4 / AC-5); (ii) all candidates are surfaced as a single numbered list with a one-line *why* per candidate; (iii) the per-item prompt accepts only `keep` | `archive` | `defer` (or `k` | `a` | `d`); any other input (including empty) re-prompts with the literal *"Choose `keep` (k), `archive` (a), or `defer` (d)."*; the skill never auto-defaults; (iv) after all per-item picks, the per-surface write phase runs (archive entries written per AC-7, source registry updated, R11 verification fires per AC-11). The per-sub-phase entry prompt accepts only `proceed` | `skip` (or `p` | `s`); the user can type `skip` at the start of any sub-phase to defer all candidates; cron-mode treats `skip` as the default for any sub-phase requiring interactive input AND records the deferral with reason `cron-mode-cannot-prompt`. The `--force-unlock` confirm-prompt accepts only `y` | `N` (default N on empty input). (Verifies R6.)

- **AC-7.** Archived items land in `admin/archive/{YYYY-Q}-prune.md` matching the canonical archive shape byte-for-byte: `## {title}`; blank line; `**Source surface:** {registry path}`; blank line; `**Prune date:** {YYYY-MM-DD}`; blank line; `**Why:** {one-line description}`; blank line; ` ```` ` block labelled `Original entry` containing the source bytes verbatim; blank line; `---`; blank line. The file is append-only within its quarter; the skill never reads or modifies prior archive files for cleanup. The archive directory `admin/archive/` is created on first archive write if missing; the per-quarter file is created on the quarter's first archive write. There is no v1 configuration knob for archive retention — retention is forever by default, with no surface area for any other value. (Verifies R7.)

- **AC-8.** When `admin/scratch/prune-{YYYY-Q}.lock` does not exist, the skill creates the lock with a one-line body matching `{ISO-8601 timestamp} {manual|cron}` and proceeds. When the lock exists, the skill first checks the lock-body timestamp against the current time: if the timestamp is more than 86400 seconds (24 hours) in the past OR more than 3600 seconds (1 hour) in the future, refuse with the literal *"Lock file at `admin/scratch/prune-{YYYY-Q}.lock` has implausible timestamp `{ts}` (compared to current time `{now}`). Inspect the lock file by hand and use `--force-unlock` if appropriate."* and exit. When the lock-body timestamp passes the implausibility gate, age is computed using filesystem `mtime` as the primary clock and the lock-body timestamp as the cross-check; when the two disagree by more than 60 seconds, the lock-body timestamp is preferred. When the resulting age is within 5400 seconds (90 minutes), the skill refuses with the literal sentinel *"`/prune` is already in flight (started `{timestamp}` via `{source}`). Wait for it to complete, or run `/prune --force-unlock` if the prior run crashed."* When the resulting age is older than 5400 seconds, the skill overwrites the lock with a fresh timestamp + source, emits the chat-line *"[stale lock detected for prune-{YYYY-Q} — proceeding]"*, and proceeds. The lock is released atomically on every exit path (success, refusal, cancellation, or any sub-phase failure). **`--force-unlock` and unlock-marker priority window:** `/prune --force-unlock` refuses with *"`/prune --force-unlock` invoked but no lock present at `admin/scratch/prune-{YYYY-Q}.lock`. No-op."* if absent; otherwise prompts *"Force-unlock will discard the in-flight run's state. Confirm? (y/N)"* (default N on empty input) and, on `y`, removes the lock, writes a one-line marker file at `admin/scratch/prune-{YYYY-Q}.unlock-marker` containing the unlock timestamp, and emits *"[lock cleared at {timestamp}; re-invoke /prune within 5 minutes to start a fresh run]"*. The next `/prune` invocation reads the marker; if the marker's timestamp is within 300 seconds (5 minutes) of now AND the invocation is `manual`, the manual invocation has priority and any concurrent `cron` path that would otherwise create a lock between unlock and re-invoke must defer with *"`/prune --force-unlock` was invoked at `{ts}`; awaiting manual re-invoke. Cron deferred."* The marker is consumed (deleted) by the next manual `/prune` invocation OR auto-expires after 300 seconds (whichever first). (Verifies R8.)

- **AC-9.** When any of the four source registries fails parse — `decision-log.md` tail does not match canonical preamble-only OR complete-entry-with-trailing-separator; any rule in `rules/{tier}.md` is missing YAML frontmatter or any of the four required sections; `agents/index.json` does not validate against the schema in `skills/agent/SKILL.md`; any entry in `task-history.json`'s `tasks` array is missing `id`, `feature_id` (or `feature`), `task_id`, or `completed_at` — the skill refuses with the literal *"`{registry-path}` failed parse: `{description}`. Aborting to avoid compounding the corruption. Run `specflow:doctor --feature admin` to validate, or fix by hand and re-run."* No registry is modified; no archive file is created or appended; the lock is released. The skill never attempts auto-repair. (Verifies R9.)

- **AC-10.** When the archive-write step (R10 step ii) raises an error mid-sub-phase, the skill emits the literal *"Archive write to `admin/archive/{YYYY-Q}-prune.md` failed: `{error}`. Source registry NOT modified — your prune decisions for this sub-phase are not yet applied. Resolve the underlying issue and re-run; the candidate list is regenerated each run."* and exits the sub-phase. Already-archived items earlier in the sub-phase whose source-registry mutation succeeded stay mutated; the failure is per-item, not per-sub-phase. A diff of the source registry before vs after the failed item shows the failed item's pre-archive state preserved (no partial mutation). The lock is released on the exit path. Per-item status (success / archive-write-failed / mutation-failed) is appended to `admin/scratch/prune-history.json`. (Verifies R10.)

- **AC-11.** For every archive operation, Stage 1 confirms (i) H2 title matches the candidate's title; (ii) `**Source surface:**` names the source registry path; (iii) `**Prune date:**` equals today's `YYYY-MM-DD`; (iv) `**Why:**` is non-empty; (v) the `Original entry` block's bytes are byte-identical to the captured source-registry slice for the entry. Any Stage-1 failure aborts the per-item write with a structured error and the source registry is NOT modified. **Stage-2 treatment differs by surface.** For three surfaces (decision-log, rules, task-history), Stage 2 is read-only — the source registry stays unmodified at Stage 2. Stage 2 re-reads the source registry and confirms it is byte-identical to its pre-Stage-2 state (no accidental mutation). The archive file is the single source of truth for archive state on these three surfaces. For agent snapshots, Stage 2 moves `admin/agents/specialised/{name}.md` to `admin/archive/agents/{YYYY-Q}/{name}.md` and removes the entry from `admin/agents/index.json`; Stage 2 re-reads `agents/index.json` and confirms the entry is no longer present, AND confirms the file at `admin/archive/agents/{YYYY-Q}/{name}.md` exists with non-empty body. **Round-trip restoration property:** for any archive block, restoring the entry to the source surface reproduces the source registry's pre-archive state byte-for-byte for that entry. For decision-log, rules, and task-history, restoration is paste-the-archive-block-Original-entry-content into the source position; since Stage 2 was read-only, the live source bytes are unchanged from pre-archive (the archive file marked the entry as pruned for Phase 3 consumers, but the on-disk source never lost the entry). For agent snapshots, restoration is two-step: copy the file from `admin/archive/agents/{YYYY-Q}/{name}.md` back to `admin/agents/specialised/{name}.md`, AND re-add the index entry from the archive block's `Original entry` JSON. The byte-identical capture at Stage 1 is the surface that makes restoration deterministic across both treatments. The round-trip restoration property is testable by capturing pre-archive source bytes, running the prune, running the restoration, and diffing — the diff against pre-archive bytes is empty for the restored entry on every surface. (Verifies R11.)

## Open questions

- **Cross-quarter rolling-archive partition.** R7 partitions one archive file per quarter (`{YYYY-Q}-prune.md`). Open question: what happens at the boundary between two `/prune` runs in different quarters but the second run is itself the first of the new quarter — does the cron-fire trigger create the new quarter's file before the user has actually closed the prior quarter's run? The lock-file naming `prune-{YYYY-Q}.lock` makes the boundary explicit (per-quarter lock), but the interaction across boundaries was not surfaced in the interview. Recommend: file-naming follows the run-fire date (the cron-fire's calendar date determines the `{YYYY-Q}` of both lock and archive); cross-boundary collisions are a non-issue because each quarter has its own lock. Confirm at implementation.
- **Persistence ledger schema stability.** R4 and R10 use `admin/scratch/prune-history.json` as the persistence surface. The schema is documented inline in the requirements but the ledger has no separate skill that owns it (unlike `task-history.json`, which `specflow:complete` owns). Open question: does `prune-history.json` get its own schema validator (separate from `specflow:doctor`) or live in `admin/scratch/` long enough that schema drift across quarters is a real concern? Recommend: ledger lives in `admin/scratch/` (not promoted to `admin/`), v1 validates the ledger inline at every read, v2 promotion to `admin/` happens if a future skill needs to read it. Defer to implementation.
- **Misc-task surface inclusion.** The interview Round 1 left `admin/misc-task/` out of scope (the goal explicitly named four surfaces). But misc-tasks accumulate too; long-resolved misc-tasks could be archive candidates. Recommend: defer to v2 — adding misc-task as a fifth surface is additive, the skill's per-surface sub-phase architecture supports it, but v1's surface set is the four named. A future enhancement PRD can extend.
- **Archive retention v2 enhancement path.** v1 hard-codes archive retention as forever; no `admin/config.json` knob exists for retention. A v2 enhancement could surface `prune.archiveRetention` with values like `"forever"` (default), `"4q"` (drop archives older than four quarters), `"on-demand"` (require explicit `/prune --archive-cleanup` invocation). Gated on real consumer ask — until a project documents disk pressure or audit-policy reasons for retention shorter than forever, the v1 forever-default holds. `prune.staleLockMinutes` (R8) is the other v2 knob in the same shape; both wait for documented friction before promotion.
