# /optimize — autoresearch loop across the verifiable-skill set

## Vision

`/optimize` generalises `simplify`'s discipline-installer pattern across the verifiable-skill set. Outcome — every skill with a binary `eval:` field gets sequential prompt-variant generation, machine-evaluated against its own eval surface, surfaced as a single-skill PR for human review. The *pattern* (branch-per-run, no LLM-as-judge inside the loop, human merge owns taste) is what we're industrialising, not the immediate optimisations any one run produces. One target per run; ~6 runs covers the initial verifiable-skill set; the cron schedule re-runs the loop monthly so improvements compound without humans re-triggering. Maintainers running specflow in their own repos benefit from prompt improvements landing without invoking the skill, reviewers approving the auto-generated PRs get a structured eval-results table they can spot-check, and Phase 3 self-learning consumers (`/insights`, `/prune`) mine the resulting `optimize-runs.jsonl` corpus for which targets converge, which keep failing variants, which the human always rejects (a signal the eval is missing something). The skill is the place specflow's discipline-installer pattern compounds — and the binary-eval eligibility criterion + frontmatter-immutability rule + auto-merge structural lock are the three guardrails that make autoresearch trustworthy at the catalog level instead of the one-skill level.

## Problem

Phase 1 of specflow shipped `simplify` as a discipline-installer — branch-per-run, sequential variant generation, read-only machine eval, human merge owns taste — and proved the pattern works on a single target. But the *deliverable that mattered most* was the pattern itself, not the optimisations of any one scope; without a Phase 3 mechanism to extend the pattern across the verifiable-skill catalog, the discipline is left as a one-off and never compounds. The failure modes that result are well-known: (a) prompt improvements stay gated on human attention — the maintainer notices a skill is under-performing, hand-edits the prompt, ships, and the next under-performance goes unnoticed for months; (b) prompts drift away from their eval surface over time without any feedback signal; (c) `simplify`'s discipline tenets (no LLM-as-judge, branch-per-run, sequential variants, human merge) get re-invented poorly by hand-iteration on each new prompt rather than industrialised once and applied uniformly; (d) the corpus signal `simplify`'s `simplify-runs.jsonl` produces is a single skill's signal, not a catalog signal — Phase 3 mining can't detect "this operator works on three targets but not the others" without a wider corpus.

The fix is structural: a single skill that owns prompt optimisation across the verifiable-skill set with mechanical target-eligibility (binary-eval criterion, judgement-word rejection), structured variant-generation operators (six operators, frontmatter-immutable, sequential), per-target weekly budget caps, branch-per-run isolation matching `simplify`, read-only eval surface enforced via per-variant scratch redirection, structural auto-merge lockout, and a corpus-mining feedback loop that backs off operators the human declined and surfaces a chat-line warning when a target gets three consecutive declines. The skill is the *generalisation* of `simplify`, not a replacement — `simplify` continues to ship as the Phase 1 discipline-installer, and `/optimize` can target `simplify` itself for prompt-level improvements without superseding it.

## Goals

- Mechanical target-eligibility check on every invocation — binary-eval criterion (no judgement words from a default + project-extensible list) refuses targets whose eval surface would Goodhart the loop, even when those targets are nominally on the architectural allow-list.
- Sequential prompt-variant generation with six structured mutation operators (tighten, consolidate, clarify, deduplicate, reorder, split-by-phase) — one operator per variant; frontmatter is immutable; variants that mutate `requires:` / `produces:` / `eval:` are rejected pre-eval.
- Per-target weekly budget cap (default $10/target/week, configurable) so one chatty target can't starve the budget for the others; aggregate envelope ($60/week across six targets) is implicit; override via `--override-budget {reason}` extends only that target.
- Branch-per-run isolation matching `simplify` exactly — `optimize/{target-slug}-{ts}` with a single commit (winning variant applied), variant-level history in `admin/scratch/optimize-{ts}/`, declined PRs retain the branch for ≥30 days for Phase 3 corpus mining.
- Read-only eval surface enforced via per-variant scratch redirection — running the target skill is allowed inside a forked sub-agent with output redirected to `admin/scratch/optimize-{ts}/variant-{N}/run-output/`; only the winning variant's SKILL.md diff is applied to the working tree.
- Structural auto-merge lockout — PR description includes a literal `<!-- optimize: human-merge-required -->` comment, no auto-merge label is applied, a separate pre-merge GH Action blocks merge on `optimize/*` branches until a `human-approved` label is applied by a real user (automation cannot apply the label).
- Corpus-mining decline feedback — operator that produced a declined variant is avoided for 7 days on that target; 3 consecutive declines on a target → skip the target for 30 days and surface a chat-line warning at next manual invocation (Goodharting-detection signal).
- Single `/optimize` process per repo at a time enforced by lockfile; single open PR per target enforced at pre-flight; refuse rather than queue when concurrent invocation is detected.
- Co-located artefacts: every variant patch, eval result, and run record lives under `admin/scratch/optimize-{ts}/` (per orchestration) or `admin/optimize-runs.jsonl` (the persistent corpus), so Phase 3 self-learning can read the full chain without cross-folder chase.

## Non-goals

- **Optimising taste-driven skills (grill, plan, design, QA-with-judgment).** Per the locked-in architectural exclusion (`v2/docs/PRD.md` Phase 3 scope item 7), autoresearch on these would reward-hack the LLM judge. The eligibility criterion (R1) refuses them mechanically; this is non-negotiable.
- **Running an LLM-as-judge inside the loop.** The eval is binary and machine-checkable. Adding "is this prompt cleaner?" as an LLM call inside the loop is exactly the Goodharting failure mode `simplify` was designed to prevent. `/optimize` inherits the rule — full stop.
- **Auto-merging the resulting PR.** Human merge owns taste. The skill never auto-merges, even when CI passes; the structural lockout (R12) is non-skippable.
- **Cross-skill co-evolution.** A `/optimize` run on `simplify` simultaneously editing `feedback-loop-audit` because they share a contract surface is deferred to a future version if the corpus shows real benefit. v1 ships with one target per run.
- **Auto-promoting a `/optimize` run's outcome into `admin/rules/guidelines.md`.** That's the Phase 3 rules-registry-self-evolution flow's responsibility (`v2/docs/PRD.md` Phase 3 scope item 8), not `/optimize`'s. `/optimize` produces a PR; the rules registry consumes its own corpus.
- **Replacing `simplify`.** `/optimize` is the *generalisation* of `simplify`, not a replacement. `simplify` continues to ship as the Phase 1 discipline-installer; `/optimize` can target `simplify` itself for prompt-level improvements without superseding it.
- **Mid-run budget caps below the per-target weekly cap.** The variant-count cap (max 10) gives a known per-run upper bound; per-run sub-budget aborting is deferred to v2 if consumers report runaway costs.
- **Stale-branch housekeeping.** Out of scope for `/optimize` v1 — the branch retention contract (≥30 days, R8) is the lower bound; the upper bound is left to a separate housekeeping skill (deferred). Maintainers running `/optimize` long-term may need to manually prune `optimize/*` branches periodically. Added at Gate 2 per da-r1-f1.

## Users

- **Plugin maintainer (primary)** — the human who owns the specflow plugin. They benefit from prompt improvements landing without manual attention, supervise the cron's choices via `optimize-runs.jsonl`, review the auto-generated PRs as the merge gate, and tighten target eval clauses when a target accumulates 3 consecutive declines (the eval-is-missing-what-the-human-values signal). They need the chat-line warning to be loud, the auto-merge lockout to be structural, and the corpus to be auditable.
- **Power User (per `admin/profiles.json`)** — frontend / backend engineers running specflow in their own repos. They benefit indirectly: when prompts improve in the upstream plugin, their installs pick the changes up at the next `specflow:upgrade` invocation. They typically do not run `/optimize` themselves on their own copy of the plugin (the cron handles that for the canonical plugin), but the skill is invocable in their repo if they want to experiment with the discipline locally.
- **Reviewers approving auto-generated PRs (secondary)** — the maintainer + occasional collaborators who review the PR. They consume the PR description's eval-results table + variants-tried table (same shape as `simplify` PRs) so they can spot-check rather than re-derive every variant. They need the operator that produced the winning variant named in the PR description so they can decide whether the operator's mutation matches their judgement of "this is a real improvement."
- **Phase 3 self-learning consumers (tertiary)** — `/insights` (monthly cadence, scope item 10) and `/prune` (quarterly cadence, scope item 10). They mine `optimize-runs.jsonl` for which targets converge, which keep failing variants, which the human always rejects. They consume the corpus; they don't invoke `/optimize` directly.

## Requirements

- **R1.** Mechanical target-eligibility pre-flight check. `/optimize {target}` (or cron-selected target) reads the target's SKILL.md frontmatter `eval:` field and applies a structured check: (a) `eval:` field exists and is non-empty; (b) every clause in the field can be evaluated to true/false from produced files (path exists, JSON field present, count ≤ N, exit-code 0); (c) no clause uses a judgement word from `config.json.optimize.judgementWords` (default list: `appropriately`, `adequately`, `cleanly`, `concrete signals`, `coverage`, `idiomatic`, `well`, `properly`, `correctly`). Targets failing any sub-check are refused with a structured message naming the specific clause and the offending word (or "missing eval field" for clause (a)). The default list is hard-coded; `config.json.optimize.judgementWords` extends it (project-specific judgement words can be added without forking the skill).
  - Trace: interview Round 1 — *eligibility = mechanical pre-flight check on the target's SKILL.md eval field; clause (a) eval exists, (b) every clause evaluates to true/false from produced files, (c) no clause uses judgement words from the configurable list*.
  - Serves goal: Driving value (the metric is a signal, not a goal — the binary-eval criterion is the load-bearing Goodharting protection at the eligibility level).

- **R2.** Pre-flight gate chain. Before entering the variant-generation loop, `/optimize` runs a chain of gates analogous to `simplify`'s Pre.1-Pre.4: (a) **lockfile gate** — refuse if `admin/scratch/optimize.lock` exists with a start timestamp < 4 hours old; reclaim the lock if the timestamp is ≥4 hours old (treat as stale); (b) **single-PR-per-target gate** — refuse if `gh pr list --head 'optimize/{target}-*'` returns ≥1 open PR; (c) **target-eligibility gate** — apply R1; (d) **budget gate** — refuse if the target's weekly spend ≥ `config.json.optimize.targetCapUsd` (default $10), unless `--override-budget {reason}` is passed; (e) **baseline-eval gate** — run the target skill at its current SKILL.md (no variants applied) inside a forked sub-agent, run the eval, refuse the run if baseline eval is not green. Refusal messages are structured (named gate + specific failure detail).
  - Trace: interview Rounds 1, 3, 7, 8 — *eligibility check, budget cap, lockfile + single-PR concurrency, baseline-eval gate*.
  - Serves goal: Outcome (refusing rather than queueing is the simpler primitive; refuse-on-broken-baseline matches `simplify`'s discipline transposed to prompt-eval).

- **R3.** Variant-generation operator set. Each variant picks exactly one of six structured mutation operators applied to the target SKILL.md body (everything below the frontmatter delimiter): (1) **tighten** — remove qualifiers and hedge-words; (2) **consolidate** — fold two adjacent instructions into one; (3) **clarify** — replace vague phrasing with concrete pass/fail language; (4) **deduplicate** — drop a redundant instruction the prompt repeats; (5) **reorder** — move a load-bearing instruction earlier; (6) **split-by-phase** — when the target prompt has multi-phase orchestration sections (Phase A, Phase B, etc.), rewrite ONE phase while leaving the others byte-identical. Variant generation runs inside a forked sub-agent context whose inputs are: (a) the target SKILL.md body, (b) the target's `eval:` field as the binary contract the variant must still satisfy, (c) the operator instruction, (d) the hard rule that the variant MUST NOT change the frontmatter. Each variant writes its proposed SKILL.md to `admin/scratch/optimize-{ts}/variant-{N}.md` and its diff to `variant-{N}.patch`.
  - Trace: interview Round 2 — *six operators; LLM-driven sequential variants with one mutation operator per variant*.
  - Serves goal: Driving value (operators force the variant to narrow rather than expand; comparable across runs for Phase 3 corpus mining).

- **R4.** Frontmatter immutability. Before evaluating a variant, the skill mechanically diffs the variant's SKILL.md frontmatter against the original's frontmatter (everything between the first `---` and the second `---`). If the frontmatter has changed in any way (`requires:`, `produces:`, `eval:`, `name`, `description`, `phase`, etc.), the variant is rejected pre-eval and recorded as `passes_all_gates: false, reason: "frontmatter mutated"`. The frontmatter is the contract; the body is the prompt. Variants that violate this rule are not eligible to win the loop, regardless of their eval score.
  - Trace: interview Round 2 — *frontmatter is immutable; variants that mutate frontmatter are rejected pre-eval*.
  - Serves goal: Outcome (the contract surface stays stable; only the prompt body is being optimised).

- **R5.** Sequential variants, default 5, max 10. Variants run sequentially (not in parallel), default count 5, hard cap 10 — exactly matching `simplify`'s primitive. The sequential discipline is non-negotiable: parallel attempts would explode the budget and create merge headaches. Variant count is configurable via `--variants {N}` flag (clamped to [1, 10]).
  - Trace: interview Round 2 — *default 5 variants per run, max 10*.
  - Serves goal: Driving value (matches `simplify` exactly — the discipline-installer's primitive transposed cleanly).

- **R6.** Per-variant eval execution. After each variant lands its SKILL.md to scratch, the skill: (a) creates a per-variant scratch directory `admin/scratch/optimize-{ts}/variant-{N}/run-output/`; (b) invokes the target skill inside a forked sub-agent with output redirected to that directory (the project's working tree is NOT mutated — see R10 for the read-only eval surface contract); (c) runs the target's `eval:` field clauses against the per-variant output; (d) records the per-variant eval result to `admin/scratch/optimize-{ts}/eval-{N}.json` with fields `variant`, `operator`, `eval_clauses_passed`, `eval_clauses_failed`, `score` (the primary numeric signal, target-specific — e.g. lines deleted for `simplify`, CONTEXT.md line count for `feedback-loop-audit`), `passes_all_gates` (true iff all clauses pass), `approach` (one-line description of what the operator did to the prompt body).
  - Trace: interview Rounds 2, 5 — *per-variant eval; score = primary signal; per-variant scratch isolation*.
  - Serves goal: Outcome (every variant's eval recorded — that's the corpus Phase 3 mines).

- **R7.** Per-target weekly budget cap. `config.json.optimize.targetCapUsd` defaults to $10/target/week. The weekly spend per target is read from `admin/budget/per-skill-tokens.json` (the existing Phase 1 budget surface, see `skills/budget/SKILL.md`) filtered to the target's invocations within the rolling 7-day window. Pre-flight gate (R2.d) refuses the run if `weekly_spend >= targetCapUsd`. Override path: `--override-budget {reason}` extends only that target's cap for the current run; the override reason is recorded to `admin/optimize-runs.jsonl`. Aggregate envelope is implicit ($10 × 6 targets = $60/week, matching the architectural envelope); no aggregate cap is enforced — the per-target caps are the only hard cap.
  - Trace: interview Round 3 — *per-target weekly cap, default $10/target/week, configurable; aggregate envelope is implicit*.
  - Serves goal: Outcome (one chatty target can't starve the budget for the others).

- **R8.** Branch-per-run isolation. The skill creates a branch named `optimize/{target-slug}-{ts}` from the current `main` (or default) branch. The branch holds a single commit at the end: the winning variant applied. Variant-level history lives in `admin/scratch/optimize-{ts}/variant-{N}.patch` + `eval-{N}.json` (both files are part of the PR's audit trail referenced from the PR description). The skill captures a SHA of the target SKILL.md at run-start (`admin/scratch/optimize-{ts}/baseline-skill-sha.txt`) and verifies the SHA matches before opening the PR — if the target SKILL.md was modified mid-run, the run is discarded with a structured message and the scratch is retained for inspection.
  - Trace: interview Rounds 4, 8 — *single commit per branch; baseline SHA captured + verified before PR open*.
  - Serves goal: Outcome (branch holds one reviewable commit; mid-run edit protection is mechanical).

- **R9.** Mechanical pre-PR cross-skill-contamination check. Before opening the PR (Phase D), the skill runs `git diff HEAD~1 HEAD --name-only` on the branch and verifies the file list matches exactly: the target's `SKILL.md` plus `admin/optimize-runs.jsonl` (and optionally a single test file if the target's eval surface requires it, declared in the run config). Any unrelated file modification fails the pre-PR check and the run is aborted with: *"Optimize run modified unexpected files: `{list}`. Expected: `{target}/SKILL.md`, `admin/optimize-runs.jsonl`. Aborting — Surgical discipline broken."* This is the structural defence against `/optimize` smuggling unrelated edits ("while I was here, I should also tweak SKILLS.md's entry for this skill").
  - Trace: interview Round 4 — *mechanical pre-PR file-diff check fails the run if unrelated files are modified*.
  - Serves goal: Driving value (the discipline includes "Surgical changes — touch only what you must"; `/optimize` modifies cross-skill prompts by definition, so the discipline must be that the modification is bounded mechanically).

- **R10.** Read-only eval surface contract. "Read-only" means the eval check itself does not mutate state beyond the per-run scratch directory. Running the target skill to produce its output is allowed (and necessary for many targets), but constrained: (a) the target skill must be invoked inside a forked sub-agent context with its output redirected to `admin/scratch/optimize-{ts}/variant-{N}/run-output/` — NOT the project's actual working tree; (b) the eval check reads files from the per-variant scratch directory without modifying the project's actual state; (c) when the variant is selected (Phase C), only the SKILL.md diff is applied to the working tree — nothing the variant produced as side-effect (e.g. an updated `CONTEXT.md`) is preserved. **Eligibility precondition (`eval_reads ⊂ produces:` contract):** every file the target's `eval:` field clauses read MUST be enumerated in the target's `produces:` field. Targets whose `eval:` reads files outside `produces:` (e.g. project-level lint output, working-tree state) are not eligible until the `produces:` field is extended to enumerate them. The check is performed at pre-flight by parsing the `eval:` field for file references and verifying each appears in `produces:`.
  - Trace: interview Round 5 — *"read-only eval surface" = the eval check does not mutate state beyond the per-run scratch directory; running the target skill is allowed inside a forked sub-agent with output redirected*. Revised at Gate 2 per tbc-r1-f2: the `eval_reads ⊂ produces:` mapping was an unstated assumption; now stated explicitly with a structured pre-flight check.
  - Serves goal: Outcome (the project's state is not at risk while the loop iterates; the assumption mapping eval-reads to produces is named, not silent).

- **R11.** Pick + apply. From the variants where `passes_all_gates: true`, pick the variant with the best `score` according to the direction declared per R17 (highest score for `direction: maximize`, lowest for `direction: minimize`). If two variants tie on score, pick the one with fewer side-effects (smaller `variant-{N}.patch`); if still tied, pick the lower variant number (the one generated first). If no variants pass all gates, the run fails — surface explicitly to the user, skip Phase D, and record `winner_variant: null, all_gates_passed: false` to `optimize-runs.jsonl`.
  - Trace: interview Round 2 (variant pick rules inherited from `simplify` Phase C.1).
  - Serves goal: Outcome (winner-pick rule is mechanical; direction-handling is delegated to R17 so the same loop works for both maximize and minimize surfaces).

- **R12.** Auto-merge structural lockout. Three independent guardrails prevent auto-merge on `/optimize` PRs: (a) the PR description includes a literal `<!-- optimize: human-merge-required -->` HTML comment that any auto-merge wrapper can detect and refuse on; (b) the skill explicitly does NOT call `gh pr merge --auto` and never applies an `auto-merge` label even if one exists in the project; (c) a separate pre-merge GH Action (shipped with `/optimize`) blocks merge on PRs whose head branch matches `optimize/*` until a `human-approved` label is applied by a real user — the GH Action verifies the label applier is a human (not a bot or GH Action) and blocks the merge if not. Automation cannot apply the `human-approved` label. **Workflow file ownership:** the pre-merge GH Action workflow file is shipped at `.github/workflows/optimize-merge-gate.yml`. `/optimize` writes this file on first run if missing (idempotent — re-runs do not modify an existing file). The workflow file is part of `/optimize`'s `produces:` surface (declared in `skills/optimize/SKILL.md` frontmatter).
  - Trace: interview Round 6 — *auto-merge prevention via HTML comment + no auto-merge label + separate GH Action blocking auto-merge on `optimize/*` branches*. Revised at Gate 2 per surgical-r1-f1: workflow file ownership made explicit (single-skill responsibility) rather than smuggled.
  - Serves goal: Driving value (human merge owns taste, full stop — the auto-merge surface area is structurally locked, not just configured-off; the workflow-file owner is named, not implicit).

- **R13.** Decline feedback + Goodharting-detection signal. When the human closes a `/optimize` PR without merge: (a) `optimize-runs.jsonl` is updated with `merge_decision: "closed-without-merge"` and the operator that produced the winning variant is recorded; (b) the next overnight cron run on the same target avoids that operator until at least 7 days have passed; (c) after 3 consecutive declines on the same target (any operator), the cron skips the target for 30 days AND a chat-line warning is surfaced when the maintainer next invokes `/optimize` manually: *"Target `{target}` has had 3 consecutive PRs closed without merge. The eval is producing improvements the human keeps rejecting — likely the eval is missing what the human values. Inspect `optimize-runs.jsonl` for the rejected variants and consider tightening the eval before the next run."* This is the corpus-mining feedback loop the discipline relies on — the skill doesn't blacklist the target; it surfaces the signal so the human can decide. **Explicit state semantics:** a "consecutive decline" means the immediately-prior `optimize-runs.jsonl` record for this target has `merge_decision: "closed-without-merge"`. Refused runs (`merge_decision: "null-failed-run"`) do NOT reset the streak and do NOT count toward it — the decline counter walks the most recent N records filtered to `merge_decision IN (closed-without-merge, merged)`. "7 days have passed" means `now() - ended_at(prior_decline) >= 7 * 24 * 60 * 60 seconds`. "30-day skip" is the same comparison with a 30-day window applied at cron-target-selection time. **Manual-override clause:** manual invocation of `/optimize {target}` on a target in the 30-day-skip state proceeds with the chat-line warning surfaced (not refused). On manual invocation that lands a `merged` decision (the human accepted the variant), the 30-day skip is cleared — the cron resumes targeting the skill on its next nightly run. On manual invocation that lands `closed-without-merge`, the skip window is NOT extended (the prior streak's skip continues to expire on its original schedule).
  - Trace: interview Round 6 — *3-decline-then-back-off policy + chat-line warning at next manual invocation*. Revised at Gate 2 per tbc-r1-f1 (block): explicit semantics for "consecutive decline" and "7 days have passed" added to make the mechanism implementable without invented comparison logic. Revised at Gate 2 per da-r1-f1: manual-override clause added to resolve the cron-vs-manual interaction the binary present/absent framing missed.
  - Serves goal: Driving value ("which ones humans always reject — signal that the eval is missing something" per `simplify` SKILL.md Phase E; the corpus-mining feedback loop now fires reliably with stated semantics).

- **R14.** Concurrency policy. Single `/optimize` process per repo at a time, enforced by `admin/scratch/optimize.lock` (acquired in Phase A, released in Phase E or on failure). Lockfile contains the orchestration ID + start timestamp. Pre-flight gate (R2.a) refuses the new invocation if the lockfile is < 4 hours old. The 4-hour staleness threshold is generous enough to recover from a real hang; a stale lockfile is reclaimed automatically. The GH Actions cron workflow uses GH's `concurrency:` group (`group: optimize-cron, cancel-in-progress: false`) to ensure only one cron run is active. Cron-vs-manual races are resolved by both paths acquiring the same lockfile (manual paths refuse if cron has the lock, and vice-versa). Single open PR per target enforced separately at R2.b.
  - Trace: interview Round 7 — *single `/optimize` process per repo via lockfile (stale threshold 4 hours); GH Actions cron uses concurrency group; single open PR per target enforced at pre-flight*.
  - Serves goal: Outcome (refuse rather than queue is the simpler primitive; queueing introduces ordering concerns v1 doesn't need).

- **R15.** Variant compile-failure handling. Before evaluating a variant, the skill mechanically validates the variant's SKILL.md: (a) YAML frontmatter parses (the skill attempts to parse the frontmatter block; failure produces `passes_all_gates: false, reason: "frontmatter parse error: {detail}"`); (b) the body has at least one heading; (c) the frontmatter is unchanged per R4 (already enforced; this is the second validation pass for defence-in-depth); (d) markdown lints pass when the project's markdown linter is detected via `admin/environment.json.lint.markdown`. Validation failures mark the variant `passes_all_gates: false` with a `reason:` field; the loop continues to the next variant — does NOT abort the run. A run where every variant fails validation surfaces explicitly: `winner_variant: null, all_gates_passed: false, reason: "all variants failed validation"`.
  - Trace: interview Round 8 — *variant compile-failure → mark variant `passes_all_gates: false`, continue loop*.
  - Serves goal: Driving value (one failed variant doesn't kill the run; the loop's eval surface stays binary even when the LLM produces garbage).

- **R16.** Run record + corpus append. After Phase D (PR opens) OR after a refused/failed run, `/optimize` appends to `admin/optimize-runs.jsonl` a structured record: `{id: "optimize-{ts}", target: "{target-slug}", branch: "{branch|null}", variants_tried: N, winner_variant: M|null, winner_operator: "{operator|null}", winner_score: X|null, all_gates_passed: bool, pr_url: "{url|null}", spend_usd: Y, started_at: "{iso}", ended_at: "{iso}", merge_decision: "pending|closed-without-merge|merged|null-failed-run", refuse_reason: "{string|null}"}`. The `merge_decision` starts `pending` for runs that opened a PR; the human (or the Phase 3 retro skill) updates it to `merged` or `closed-without-merge` after the review lands. Refused runs (eligibility, budget, baseline-eval) record `merge_decision: null-failed-run` with the refuse reason. The corpus is append-only (matching `simplify-runs.jsonl`'s shape).
  - Trace: interview Rounds 1, 3, 6, 7, 8 — *corpus shape mirrors `simplify-runs.jsonl`; refused runs are logged for Phase 3 mining*.
  - Serves goal: Outcome (Phase 3 self-learning consumers — `/insights`, `/prune` — read this corpus; refused runs are part of the signal).

- **R17.** Score-direction declaration (cross-skill schema dependency). The target SKILL.md's `eval:` field is augmented with a structured score declaration of the form `score: { signal: "{description}", direction: "maximize|minimize" }` placed alongside the existing free-form eval prose. Targets without the structured score block default to `direction: maximize` (matches `simplify`'s lines-deleted shape). R17 requires extending every initial-six target skill's SKILL.md with the structured score block before `/optimize` v1 can run on them; this is a cross-skill schema dependency and ships via separate per-target enhancement PRDs (one per target) before `/optimize` v1 lands. The pre-flight eligibility check (R1) is extended to verify the structured score block exists OR the target's eval surface has a self-evident maximize-direction shape (lines deleted, count of passing tests, etc.); ambiguous score directions refuse with: *"Target `{target}` has no structured `score:` block in its `eval:` field and the score-direction is not self-evident. Refusing — `/optimize` requires a declared score direction. Add `score: { signal: \"{description}\", direction: \"maximize|minimize\" }` to the target's `eval:` field."*
  - Trace: interview Round 2 (variant pick rules need direction-handling for non-`simplify`-shaped targets) + Gate 2 review goal-r1-f1 (block) — *winner-pick rule needs explicit score-direction handling AND the cross-skill schema dependency must be named (rather than burying the eval-frontmatter shape change inside R11)*. Added at Gate 2 to close the orphan-AC gap on AC-10.
  - Serves goal: Outcome (the same loop works for both maximize and minimize surfaces; the cross-skill schema dependency is named, not buried).

## Acceptance criteria

- **AC-1.** Running `/optimize {target}` on a target whose SKILL.md `eval:` field uses no judgement words (per the default + `config.json.optimize.judgementWords` extension) AND every clause is binary AND the field is non-empty proceeds past R2.c. Running on a target whose `eval:` field contains a judgement word (e.g. "concrete signals" in `feedback-loop-audit`'s current eval) refuses with the structured message: *"Target `{target}` eval clause `{N}` ('{clause text}') uses judgement word `{word}`. Refusing — `/optimize` requires a fully binary eval surface."* Running on a target with no `eval:` field refuses with: *"Target `{target}` has no `eval:` field. Refusing — `/optimize` requires an eval surface."* (Verifies R1.)

- **AC-2.** A project-extended judgement-word list works: setting `config.json.optimize.judgementWords` to `["publishable"]` AND running `/optimize {target}` on a target whose eval contains "the published artefact is publishable" refuses on the project-extension word, not the default list. The default list is preserved (the project list extends, does not replace). (Verifies R1.)

- **AC-3.** Each generated variant's `eval-{N}.json` records exactly one operator from the six-operator set in R3. Variants whose body is byte-identical to the baseline (no actual mutation occurred) record `passes_all_gates: false, reason: "no-op variant"`. The split-by-phase operator only fires on targets whose SKILL.md body contains at least one section heading matching `^## Phase [A-Z]` (heuristic for multi-phase orchestrators) — for targets without phase sections, split-by-phase is skipped during operator selection. (Verifies R3.)

- **AC-4.** Frontmatter-immutability check fires correctly. A variant whose generated SKILL.md has any frontmatter difference from the baseline (any `requires:` line added/removed/modified, any `produces:` line, any `eval:` line, any other frontmatter key) is rejected pre-eval with `passes_all_gates: false, reason: "frontmatter mutated: {specific diff}"`. A variant whose frontmatter is byte-identical to the baseline proceeds to eval. (Verifies R4.)

- **AC-5.** A run with `--variants 5` (default) generates exactly 5 variant files (`variant-1.md` through `variant-5.md`) and 5 eval-result files (`eval-1.json` through `eval-5.json`) in `admin/scratch/optimize-{ts}/`. A run with `--variants 12` clamps to 10 with a chat-line warning: *"Variant count clamped to 10 (max). Sequential variants per `simplify` discipline."* A run with `--variants 0` refuses with: *"Variant count must be ≥1."* (Verifies R5.)

- **AC-6.** Pre-flight budget gate fires when the target's weekly spend ≥ `targetCapUsd` (default $10). With `targetCapUsd: 10` and the target's rolling 7-day spend already at $10.50 in `admin/budget/per-skill-tokens.json`, `/optimize {target}` refuses: *"Target `{target}` is at $10.50 of the $10.00 weekly cap. Refusing to run. Override via `--override-budget {reason}`."* `/optimize {target} --override-budget "release deadline pressure"` proceeds, AND `admin/optimize-runs.jsonl` records the run with `override_reason: "release deadline pressure"`. (Verifies R7.)

- **AC-7.** Branch creation and naming. A successful run produces a branch named `optimize/{target-slug}-{YYYYMMDD-HHMMSS}` where `{target-slug}` is the target name (with non-alphanumerics replaced by `-`). The branch contains exactly one commit at the end whose tree differs from the base only in: (a) the target's SKILL.md, (b) `admin/optimize-runs.jsonl`, (c) optionally one test file declared in the run config. (Verifies R8.)

- **AC-8.** Mechanical pre-PR cross-skill-contamination check fails the run when `git diff HEAD~1 HEAD --name-only` returns any file outside the allowed set. Test scenario: a variant whose generated SKILL.md somehow modifies `SKILLS.md` (the glossary file) → pre-PR check captures the unexpected file in the diff → run aborts with the structured message and `optimize-runs.jsonl` records `refuse_reason: "cross-skill contamination: {list}"`. The branch is retained for inspection; the PR is NOT opened. (Verifies R9.)

- **AC-9.** Read-only eval surface contract. For every variant, the per-variant scratch directory `admin/scratch/optimize-{ts}/variant-{N}/run-output/` exists and contains the files the target's eval reads. After the run completes (success or failure), the project's working tree state outside `admin/scratch/optimize-{ts}/` and `optimize-runs.jsonl` is unchanged for non-winning variants — only the winning variant's SKILL.md diff is applied. Targets whose `produces:` field doesn't enumerate any files refuse at pre-flight with: *"Target `{target}` has no enumerable `produces:` field. Refusing — `/optimize` requires a redirectable eval surface."* **`eval_reads ⊂ produces:` sub-clause:** pre-flight verifies every file reference in the target's `eval:` field appears in the target's `produces:` field; targets with eval reads outside `produces:` refuse with a structured message naming the offending file. (Verifies R10.)

- **AC-10.** Score-direction handling. For a target whose `eval:` field declares (per R17) a structured `score: { signal: "...", direction: "maximize" }` block (or no direction field, defaulting to maximize), the winner-pick rule selects the highest-score variant. For a target whose `eval:` declares `direction: minimize` (e.g. CONTEXT.md line count for `feedback-loop-audit`), the winner-pick rule selects the lowest-score variant. Tie-breaks (smaller patch, then lower variant number) apply identically for both directions. Test scenario: two variants of `feedback-loop-audit` produce CONTEXT.md files of 480 and 510 lines respectively, both `passes_all_gates: true` — winner is the 480-line variant (lower is better when direction is minimize). Targets without a structured score block AND no self-evident direction refuse at pre-flight per R17. (Verifies R11, R17.)

- **AC-11.** Auto-merge structural lockout — all three guardrails fire. (a) The PR body includes the literal HTML comment `<!-- optimize: human-merge-required -->`. (b) The PR has no `auto-merge` label applied by the skill (verified by `gh pr view --json labels`). (c) The pre-merge GH Action (shipped at `.github/workflows/optimize-merge-gate.yml`) is configured to block merge on `optimize/*` branches without the `human-approved` label, AND verifies the label applier is a human (not a bot/GH Action) by checking the `actor.type` of the label-applied event. Automation attempts to apply `human-approved` are blocked. **Workflow file install sub-clause:** on first invocation in a project, the file `.github/workflows/optimize-merge-gate.yml` is created with the merge-gate workflow content. On subsequent invocations, the file is left unchanged (idempotent). (Verifies R12.)

- **AC-12.** Decline feedback fires correctly. When the human closes a `/optimize` PR without merging, `optimize-runs.jsonl` is updated with `merge_decision: "closed-without-merge"` and `winner_operator` is preserved in the record. The next cron run on the same target reads the previous record and excludes the same operator from the operator-selection pool for 7 days (timestamp comparison against `ended_at`). After 3 consecutive `closed-without-merge` records on the same target (any operator), the cron skips the target for 30 days AND the next manual `/optimize {target}` invocation prints the chat-line warning: *"Target `{target}` has had 3 consecutive PRs closed without merge..."* before proceeding (or refusing if budget/eligibility/etc. fails). **Streak-state sub-clauses:** (a) a refused-run record (`merge_decision: "null-failed-run"`) between two declines does NOT reset the streak (counter walks `merge_decision IN (closed-without-merge, merged)` records only); (b) a `merged` record between two declines DOES reset the streak. (Verifies R13.)

- **AC-13.** Concurrency lockout. With an `admin/scratch/optimize.lock` file containing a timestamp 1 hour old, a second `/optimize` invocation refuses with: *"Another `/optimize` run is in progress (id: `{id}`, started: `{ts}`). Wait or remove the lockfile."* With the same lockfile 5 hours old, the second invocation reclaims the lock and proceeds. The GH Actions workflow file at `.github/workflows/optimize-cron.yml` declares `concurrency: { group: optimize-cron, cancel-in-progress: false }`. With an open PR matching `optimize/{target}-*`, `/optimize {target}` refuses at R2.b regardless of lockfile state. (Verifies R14.)

- **AC-14.** Variant compile-failure handling. A variant whose generated SKILL.md has malformed YAML frontmatter (e.g. unclosed quote) records `passes_all_gates: false, reason: "frontmatter parse error: {parser detail}"` and the loop continues. A variant whose body has no headings records `passes_all_gates: false, reason: "body has no headings"`. A run where all 5 variants fail validation produces `winner_variant: null, all_gates_passed: false, reason: "all variants failed validation"` in the run record AND surfaces explicitly in chat (no PR opened). (Verifies R15.)

- **AC-15.** Run record schema + corpus integrity. Every `/optimize` invocation appends exactly one line to `admin/optimize-runs.jsonl` whose JSON has the fields specified in R16 (id, target, branch, variants_tried, winner_variant, winner_operator, winner_score, all_gates_passed, pr_url, spend_usd, started_at, ended_at, merge_decision, refuse_reason). Refused runs (eligibility, budget, baseline-eval, lockfile, single-PR, cross-skill-contamination) record `merge_decision: "null-failed-run"` and a populated `refuse_reason`; successful runs that opened a PR record `merge_decision: "pending"` initially and a populated `pr_url`. The file is append-only (existing lines are never rewritten by the skill; `merge_decision` updates land on a fresh line per existing record? — clarification deferred to implementation; per Round 8, follow `simplify-runs.jsonl`'s shape exactly). **Corpus-integrity sub-clauses:** (a) across all records in `admin/optimize-runs.jsonl`, the `id` field is unique (no two records share the same `id`); (b) records with `merge_decision: "closed-without-merge"` have a non-null `winner_operator`; (c) records with `merge_decision: "null-failed-run"` have a non-null `target` AND a non-null `refuse_reason`; (d) the file is valid JSONL — every line parses as JSON in isolation, no partial writes (the lockfile in R14 is the load-bearing mechanism preventing concurrent writes). (Verifies R16; closes goal Outcome surface for Phase 3 corpus-mining.)

- **AC-16.** 30-day-skip manual-override path. With a target in the 30-day-skip state (the most recent 3 corpus records for the target all have `merge_decision: "closed-without-merge"` AND the third decline's `ended_at` is < 30 days old), manual invocation of `/optimize {target}` proceeds AND the chat-line warning is surfaced before pre-flight gates fire. A subsequent `merged` decision (the user reviewed and merged the manual-run PR) clears the skip — the next cron run targets the skill normally (no 30-day-skip filter applied). A subsequent `closed-without-merge` decision does NOT extend the skip — the prior streak's skip continues to expire on its original schedule (computed from the third decline's `ended_at`, not the new one's). The cron's target-selection logic reads the corpus and applies the 30-day-skip filter to skip eligible targets; manual invocation bypasses the filter with the warning surfaced. (Verifies R13 manual-override clause.)

## Open questions

- **Append-only vs in-place update for `merge_decision`.** `simplify-runs.jsonl` is described as append-only in `simplify/SKILL.md` Phase E, but the example schema shows `merge_decision` starting as `pending` and being updated to `merged | closed-without-merge | open-with-feedback`. Two possibilities: (a) the file is genuinely append-only and `merge_decision` updates land as fresh lines with the same `id`, requiring readers to dedupe by latest `ended_at` per `id`; (b) the file is append-only-on-creation but in-place-update for `merge_decision` only. The interview did not resolve this for `optimize-runs.jsonl`; cleanest default is to mirror `simplify-runs.jsonl`'s actual implementation when it lands. Defer to implementation; document the chosen mechanic in `skills/optimize/SKILL.md` Phase E.
- **Self-targeting `/optimize {optimize}`.** Per "Topics not discussed," v1 does not block self-targeting if `/optimize`'s own `eval:` field passes the binary-eval criterion. The recursive case is left to surface naturally in the corpus. If problems emerge (e.g. the optimised `/optimize` prompt itself fails the eligibility check), the user can disable via `config.json.optimize.allowSelfTarget: false`. Confirm at implementation; flag if the recursive run produces a degenerate variant pattern.
- **Markdown lint detection key.** R15.d references `admin/environment.json.lint.markdown`. The Phase 1 `feedback-loop-audit` skill writes `admin/environment.json` but does not currently populate a `lint.markdown` key explicitly (it captures lint commands per detected stack). If the key is not present, R15.d's clause (d) is treated as N/A and the variant proceeds past validation. Confirm the environment-detection contract at implementation; consider opening a `specflow:misc` for `feedback-loop-audit` to add the key explicitly.
