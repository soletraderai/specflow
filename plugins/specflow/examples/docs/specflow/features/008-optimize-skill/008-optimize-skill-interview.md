# PRD interview — features/008-optimize-skill

## Original request

> Write the spec for `/optimize`, the Phase 3 autoresearch loop that generalises `simplify`'s discipline-installer pattern across the verifiable-skill set (~6 initial targets: `release-version-check`, `simplify`, `format`, `tdd-cadence`, `init`, `feedback-loop-audit`). The skill walks one target per run, generates prompt variants, runs each variant against a binary eval, and opens a single-skill PR for human merge review. The architectural shape is locked in by `v2/docs/PRD.md` Phase 3 scope item 7; this PRD synthesises the implementation contract at the SKILL.md level. The skill is the most architecturally significant piece of Phase 3 — it is recursive in two senses: it dogfoods `simplify`'s loop pattern, and it can target `simplify` itself.

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `v2/docs/PRD.md` § "Phase 3 — Memory and self-learning" scope item 7 names the six initial targets and the budget envelope (~$60 total via overnight GH Actions); scope item 7 also locks in the exclusion criterion ("Skills with taste-driven output (grill, plan, design, QA-with-judgment) explicitly excluded — autoresearch would reward-hack the LLM judge"). Phase 3 scope item 7's hard cap on the eligible target set is the main locked-in decision. Re-litigating which six skills are eligible is out of scope for this interview; the *binary-eval criterion* that defines eligibility for new targets is in scope.
- **Discipline-installer precedent already shipped.** `skills/simplify/SKILL.md` is operational and has produced runs in `admin/simplify-runs.jsonl` (the corpus this skill mines for pattern signals). The four discipline tenets `simplify` installed are load-bearing for `/optimize`: (1) branch-per-run, (2) sequential variant generation (no parallel), (3) read-only machine eval (no LLM-as-judge inside the loop), (4) human merge owns taste. `/optimize` is the *generalisation*, not a replacement — it MUST match these four tenets, not invent new ones.
- **Stub SKILL.md exists.** `skills/optimize/SKILL.md` is currently a description-level entry only (per `SKILLS.md` Phase 3 § entry). No operational prompt body yet. The frontmatter shape needs to declare `requires:` (target SKILL.md, target's eval surface, budget summary, simplify-runs.jsonl as corpus reference) and `produces:` (PR on optimize/{target}-{ts} branch, optimize-runs.jsonl entry, eval results table).
- **Sister Phase 3 skills are also stubs.** `specflow:complete`, `specflow:decision`, `specflow:scope-change`, `/insights`, `/prune` all live in Phase 3. None have shipped yet. `/optimize` is the most architecturally novel of the set because it is the only Phase 3 skill that *modifies other skills' prompts*. The cross-skill modification surface is the single most-load-bearing concern this interview must resolve.
- **Verifiable-skill set defined by binary eval.** Per `v2/docs/PRD.md` Phase 3 scope item 7, the six initial targets all have machine-checkable `eval:` fields in their SKILL.md frontmatter. `/optimize` reads each target's `eval:` field to determine whether the target is eligible — refuses on skills lacking a binary `eval:` (the "taste-driven output" exclusion the architectural spec calls out). The tightness of the binary-eval criterion is the *first* failure mode this interview must surface (vague eval fields would let taste-driven skills sneak into the eligible set).
- **Budget-cap precedent in `simplify`.** `simplify` has a $20/week hard cap, override only via `--override-budget {reason}`. `/optimize` runs ~$60 across six targets per the architectural envelope, so the budget mechanics are different in shape — per-skill weekly cap, shared monthly cap, or one-cap-per-target-per-run? This interview must resolve.
- **GH Actions overnight cron.** The architectural spec names the cron as the primary trigger ("overnight GH Actions"). Manual `/optimize` invocation is the secondary trigger. The race condition (cron and manual invocation overlapping; two GH Actions firing for two different targets in parallel) is unresolved at the architectural level and must be resolved here.
- **Standard agents already operational.** Lifecycle agents (Orchestrator, Devil's Advocate, Verifier) and the four principle reviewers ship with the plugin. `/optimize` does NOT introduce a Gate-6 reviewer set — variants are evaluated *only* by the target skill's binary eval (no LLM judge in the loop, per `simplify`'s discipline). Reviewers fire only at the meta level (this PRD's Gate 2, not at runtime).
- **Cross-skill modification = Surgical concern.** `/optimize` modifies `SKILL.md` content for the *target* skill. That is, by definition, a non-Surgical operation — the change touches files outside the immediate task scope. The discipline this PRD must establish: (a) the change is reviewable as a PR with eval evidence, (b) the human-merge step is non-skippable, (c) the change is reverted automatically if the human declines. The Surgical Reviewer will (and should) bite at Gate 2 if the discipline is loose.
- **Goodharting risk is the existential threat.** Karpathy's autoresearch insight (per `simplify` SKILL.md's "Why this matters" section) is the single load-bearing principle: *the metric is a signal, not a goal*. When the eval is narrow and machine-checkable, the loop produces genuine improvement OR nothing. When the eval is fuzzy (or worse, an LLM judge), the loop reward-hacks. `/optimize`'s eligibility criterion (binary eval required) and runtime discipline (no LLM-as-judge inside the loop) both exist to keep Goodharting at bay. Any drift in this PRD that softens either is the failure the dogfood discipline must surface.
- **Worked example: 002-develop-skill.** Calibration anchor for what a complex first-pass dogfood PRD looks like — `develop` had 18 R + 15 AC, two `block` findings at Gate 2, both resolved with PRD revisions, one push-back partially defended. This dogfood pass aims to match its shape for an architecturally-novel Phase 3 skill.

## Goal (confirmed before grilling)

- **Outcome:** `/optimize` generalises `simplify`'s discipline-installer pattern across the verifiable-skill set. Every skill with a binary `eval:` field gets sequential prompt-variant generation, machine-evaluated against its own eval surface, surfaced as a single-skill PR for human review. The *pattern* (branch-per-run, no LLM-as-judge inside the loop, human merge owns taste) is what we're industrialising, not the immediate optimisations any one run produces. One target per run; ~6 runs covers the initial verifiable-skill set; the cron schedule re-runs the loop monthly so improvements compound without humans re-triggering.
- **Audience:** primary — the plugin maintainer + power users running specflow in their own repos, both of whom benefit from prompt improvements landing without invoking the skill. Secondary — reviewers approving the auto-generated PRs, who get a structured eval-results table + variants-tried table per PR (same shape as `simplify` PRs) so they can spot-check rather than re-derive the result. Tertiary — Phase 3 self-learning consumers (`/insights`, `/prune`) which mine `optimize-runs.jsonl` for which targets converge, which keep failing variants, which the human always rejects (a signal the eval is missing something).
- **Success looks like:** invoking `/optimize {target-skill}` (or letting the overnight cron pick a target) on a skill whose `eval:` field is binary produces (a) a branch `optimize/{target}-{ts}`, (b) N prompt variants generated sequentially against the target's SKILL.md prompt body (default 5, configurable), (c) per-variant eval-result file recording the eval's binary outcome + the score the eval surfaces (e.g. lines deleted for `simplify`, CONTEXT.md length for `feedback-loop-audit`), (d) a single PR with eval-results table + variants-tried table, (e) `optimize-runs.jsonl` updated with the run's structured record (pending merge_decision), (f) `panic` safety — if the human declines, the branch is closed and the next run picks a different target so we don't loop on the same failed prompt. Every artefact is co-located in `admin/scratch/optimize-{ts}/` (per orchestration) and the run record lives in `admin/optimize-runs.jsonl` so Phase 3 can mine the corpus.
- **Driving value:** removes the failure mode where prompt improvements are gated on human attention (the maintainer notices a skill is under-performing, hand-edits the prompt, ships); removes the failure mode where prompts drift away from their eval surface over time without a feedback signal; removes the failure mode where the discipline `simplify` installed is left as a one-off, never compounded across the catalog. The discipline tenets (branch-per-run, sequential variants, no LLM-as-judge, human merge owns taste) are what we're industrialising — `/optimize` is the *mechanism* that proves the discipline scales.
- **Out of scope at the goal level:** (1) optimising taste-driven skills (grill, plan, design, QA-with-judgment) — autoresearch would reward-hack the LLM judge per the locked-in architectural exclusion; this is non-negotiable; (2) running an LLM-as-judge inside the loop — that defeats the entire discipline `simplify` installed and is the single most load-bearing exclusion; (3) auto-merging the resulting PR — human merge owns taste, full stop; the skill never auto-merges, even when CI passes; (4) cross-skill co-evolution (e.g. a `/optimize` run on `simplify` simultaneously editing `feedback-loop-audit` because they share a contract surface) — one target per run is hard, deferred to a future version if the corpus shows real benefit; (5) auto-promoting a `/optimize` run's outcome into `admin/rules/guidelines.md` — that's the Phase 3 rules-registry-self-evolution flow's responsibility (scope item 8), not `/optimize`'s; (6) replacing `simplify` — `/optimize` is the *generalisation*, not a replacement; `simplify` continues to ship as the Phase 1 discipline-installer, and `/optimize` can target `simplify` itself for prompt-level improvements without superseding it.

User confirmed: 2026-05-06.

## Rounds

### Round 1 — Target eligibility: how tight is the binary-eval criterion?

- **Q:** Per the architectural spec, `/optimize` runs only against skills with a binary `eval:` field. The six initial targets are named (`release-version-check`, `simplify`, `format`, `tdd-cadence`, `init`, `feedback-loop-audit`). What happens when a new skill is added in the future — what's the precise criterion that lets `/optimize` decide it's eligible? And what's the failure mode when a target's `eval:` field *says* it's binary but actually needs judgement (e.g. "audit report covers all five dimensions with concrete signals")?
- **AI's recommended answer:** Eligibility is determined by a *structured pre-flight check on the target's SKILL.md eval field*, not by an allow-list. The criterion is mechanical: (a) the target's `eval:` field exists; (b) every clause in the field can be evaluated to true/false by reading produced files (path exists, JSON field present, count ≤ N, exit-code 0); (c) no clause uses judgement words (`appropriately`, `adequately`, `cleanly`, `concrete signals`, `coverage`, `idiomatic`). If clause (c) trips, refuse the run with a structured message naming the offending clause: *"Target `{skill}` eval clause `{N}` ('audit report covers all five dimensions with concrete signals') uses judgement word `concrete signals`. Refusing — `/optimize` requires a fully binary eval surface. Either tighten the clause or exclude the skill from `/optimize`'s target set."* The six initial targets are pre-vetted (the architectural spec says so), but the pre-flight check still runs on every invocation so the criterion stays tight as the catalog grows. Failure mode case: `feedback-loop-audit`'s current eval includes "audit report covers all five dimensions with concrete signals" — that's NOT binary by clause (c). Either tighten the eval clause (e.g. "audit report's `dimensions` array has length ≥ 5 and every element has a non-empty `signal` field") or `feedback-loop-audit` is not eligible for `/optimize` until the eval is tightened. — *Reasoning: the goal's Driving value field calls out "the metric is a signal, not a goal" and Phase 3 scope item 7 names the exclusion criterion architecturally; making the criterion mechanical (rather than allow-list) keeps the eligibility check at parity with `simplify`'s pre-flight gates pattern. The judgement-word check is the operational instance of the binary test from `templates/agents/standard/principles/goal-driven-reviewer.md`.*
- **User's answer:** confirmed, with one edit — the judgement-word list is project-extensible via `config.json.optimize.judgementWords` (default list as recommended), so if a project's eval surface uses domain-specific judgement words (e.g. "publishable" in a publishing-stack project), they can add them without forking the skill. Default list stays as recommended; configurability lets teams whose stack-specific judgement words aren't in the default still reject them.
- **Resolved:** target eligibility = mechanical pre-flight check on the target's SKILL.md eval field; clause (a) eval exists, (b) every clause evaluates to true/false from produced files, (c) no clause uses judgement words from the configurable list. Default judgement-word list is hard-coded; `config.json.optimize.judgementWords` extends it. `feedback-loop-audit` is provisionally ineligible until its eval is tightened — flagged as an open question for the implementation phase. — flows into §Requirements R1, R2; AC AC-1, AC-2.

### Round 2 — Variant generation strategy: LLM-driven, template substitution, or hand-curated seed?

- **Q:** `simplify` generates variants by re-reading the scope and applying a different simplification strategy each iteration (extract no helper, inline a helper, drop a comment block, etc.) — that's *content* variants on the source code being simplified. `/optimize` generates *prompt* variants on the target's SKILL.md body, which is a different shape entirely. What's the variant-generation strategy? LLM-driven with a "rewrite this prompt to be tighter" instruction? Template substitution against a fixed set of mutation operators? Hand-curated seed prompts plus mutation? And how do we keep variants from drifting outside the target's actual contract (frontmatter `requires:` / `produces:` / `eval:` are the contract — variants that change them are out of scope by construction)?
- **AI's recommended answer:** LLM-driven variant generation, but with structured *mutation operators* applied per variant rather than free-form rewriting. The operators are: (1) tighten — remove qualifiers and hedge-words from the prompt body; (2) consolidate — fold two adjacent instructions into one tighter instruction; (3) clarify — replace vague phrasing with concrete pass/fail language; (4) deduplicate — drop a redundant instruction the prompt repeats; (5) reorder — move a load-bearing instruction earlier in the prompt so the LLM sees it first. Each variant picks one operator (sequential, not parallel — same as `simplify`). The LLM that generates the variant is given a forked sub-agent context with: (a) the target SKILL.md body (everything below the `---` after frontmatter), (b) the target's `eval:` field as the binary contract the variant must still satisfy, (c) the operator instruction, (d) a hard rule that the variant MUST NOT change the frontmatter (`requires:`, `produces:`, `eval:` are the immutable contract). The variant is then applied to the target's SKILL.md body, the eval is run, and the result is recorded. **Drift protection:** before evaluating the variant, the skill mechanically diffs the variant's frontmatter against the original — if the frontmatter changed, the variant is rejected pre-eval and recorded as `passes_all_gates: false, reason: "frontmatter mutated"`. The frontmatter is the contract; the body is the prompt. **Why operators not free-form:** free-form "rewrite this prompt" runs into the LLM's bias toward verbosity (the model adds qualifiers it thinks are helpful but that soften the prompt's signal). Operators force the variant to *narrow*, not expand. Operator (1) — tighten — is the most common simplify-equivalent operation; operators (2)-(5) cover the structural variants the body can have. — *Reasoning: matches `simplify`'s "different strategy per variant" shape (`simplify` SKILL.md Phase B.1 lists strategies); using operators rather than free-form rewriting keeps the variants comparable across runs, which is what the corpus mining in Phase 3 needs to detect drift. The frontmatter-immutability rule maps directly to the Surgical principle — the variant touches only the prompt body, not the contract.*
- **User's answer:** confirmed, with two edits — (a) add a sixth operator: *split-by-phase* — when the target prompt has multi-phase orchestration sections (Phase A, Phase B, etc.) the variant can rewrite ONE phase while leaving the others byte-identical. This is the most surgical operator and is likely to be the highest-converging operator on long prompts (`develop`, `complete`). (b) The default variant count should be 5 (matches `simplify`); cap at 10 (also matches). Each operator has equal probability of being picked unless the operator-selection field in the run config overrides; configurability deferred to v2 unless the corpus shows operators have systematically different convergence rates.
- **Resolved:** variant generation = LLM-driven sequential variants with one mutation operator per variant; six operators (tighten, consolidate, clarify, deduplicate, reorder, split-by-phase); frontmatter is immutable — variants that mutate frontmatter are rejected pre-eval; default 5 variants per run, max 10. — flows into §Requirements R3, R4, R5; AC AC-3, AC-4, AC-5.

### Round 3 — Budget cap mechanics: shared cap, per-skill cap, or per-run cap?

- **Q:** `simplify` has a $20/week hard cap with `--override-budget {reason}` for the rare exception. `/optimize`'s architectural envelope is ~$60 total for the six initial targets (per Phase 3 scope item 7). What's the cap shape — one shared cap for `/optimize` across all targets per week (e.g. $60/week, all six targets share)? A per-skill cap so each target runs independently (e.g. $10/target/week × 6 targets = $60/week)? A per-run cap (each invocation gets $X, regardless of how many runs land that week)? And how does the cap interact with the overnight cron — does the cron skip a target if the per-skill budget is exhausted, or does the cron always pick a target with remaining budget?
- **AI's recommended answer:** Per-target weekly cap, default $10/target/week, configurable via `config.json.optimize.targetCapUsd` (default 10). The shared `/optimize`-level cap is implicit: $10 × 6 targets = $60/week, matching the architectural envelope. Per-target rather than shared because: (a) one chatty target (e.g. `develop` if it ever became eligible) shouldn't starve the budget for the other five; (b) Phase 3 corpus mining can then per-target-detect convergence rates, which is a stronger signal than aggregate cost; (c) per-target caps make the per-run override cleanly bounded — `--override-budget {reason}` extends only the target being run, not the whole `/optimize` envelope. The overnight cron's target selection: always pick a target with `weekly_spend < targetCapUsd` AND that hasn't been run yet this week; if no targets are eligible (all under-cap and already-run), the cron is a no-op for that night and logs the no-op to the run record. Manual `/optimize {target}` runs the named target; if its weekly cap is exhausted, refuse with the same shape as `simplify`'s budget gate. The override is logged with reason to `admin/optimize-runs.jsonl`. — *Reasoning: the goal's Outcome names "~6 runs covers the initial verifiable-skill set; the cron schedule re-runs the loop monthly," which implies each target gets a known weekly slot; per-target cap matches that mental model. Shared cap would make the budget interactions opaque — if `simplify`'s `/optimize` run ate $40 because it generated 10 variants, the other five targets would queue up unhappily. Per-run cap doesn't make sense because the cap is a forcing function on per-run cost (variant count + LLM-call cost) — `/optimize`'s cost per run is bounded by the variant-count cap (max 10) which gives a known per-run upper bound, so the weekly cap is the more useful cadence-anchored cap.*
- **User's answer:** confirmed.
- **Resolved:** budget cap = per-target weekly cap, default $10/target/week (configurable via `config.json.optimize.targetCapUsd`); aggregate envelope is implicit ($10 × 6 = $60/week); cron skips targets with exhausted weekly cap; manual run on exhausted target refuses; override via `--override-budget {reason}` extends only that target's cap. — flows into §Requirements R6, R7; AC AC-6.

### Round 4 — Branch-per-run isolation: how is cross-skill contamination prevented?

- **Q:** `simplify` runs in a `simplify/{scope}-{ts}` branch — the branch holds exactly the simplification of one scope. `/optimize` modifies `SKILL.md` for the target skill, which is a file shared across the whole plugin (and ultimately consumed by every project that installs the plugin). What's the branch isolation contract? One branch per run per target is obvious; but does the branch have a single commit (the winning variant applied) or multiple (one per variant)? And what's the contract when the human declines the PR — does the branch get deleted, or kept for audit?
- **AI's recommended answer:** Branch named `optimize/{target-slug}-{ts}` exactly mirroring `simplify/{scope-slug}-{ts}`. Each variant is generated and evaluated in a *forked sub-agent context* whose working tree state is a stash, NOT a commit on the optimize branch — same primitive `simplify` uses (Phase B.2: `git stash` between variants). The optimize branch holds *one* commit at the end: the winning variant applied. Variant-level history lives in `admin/scratch/optimize-{ts}/variant-{N}.patch` (the diff each variant produced) and `eval-{N}.json` (the eval outcome) — both are part of the PR's audit trail. **Decline path:** when the human closes the PR without merging, `/optimize` updates `optimize-runs.jsonl` setting `merge_decision: "closed-without-merge"` and *the branch is retained* (NOT deleted). Retention is for two reasons: (1) Phase 3 corpus mining needs the variant patches available to spot patterns in declined variants; (2) the human may want to revisit the rejected variants later. A weekly housekeeping script (separate skill, not `/optimize`'s job) prunes branches whose `merge_decision` has been `closed-without-merge` for ≥30 days. The retention policy is documented but the housekeeping skill is deferred — `/optimize` only ensures the `merge_decision` is recorded. **Cross-skill contamination protection:** the branch only contains a diff to *one* SKILL.md (the target's) plus run-record updates to `admin/optimize-runs.jsonl`. The mechanical pre-PR check verifies: (a) `git diff HEAD~1 HEAD --name-only` matches exactly `{target-skill}/SKILL.md` plus `admin/optimize-runs.jsonl` (and optionally a single test file if the target's eval requires it); (b) any unrelated file modification fails the pre-PR check and the run is aborted with a structured failure message. This is the Surgical-discipline-installer for `/optimize` — no "while I was here" edits leak into a `/optimize` PR. — *Reasoning: the branch-per-run primitive is locked in from `simplify`; the open questions were single-vs-multi-commit (single is cleaner for review and matches `simplify`) and decline-path (retain because the corpus value > the disk-space cost). The mechanical pre-PR file-diff check is the Surgical Reviewer's defence against `/optimize` smuggling unrelated edits — without it, the AI variant generation could decide "while I'm here, I should also tweak `SKILLS.md`'s entry for this skill" and the discipline would be silently broken.*
- **User's answer:** confirmed.
- **Resolved:** branch-per-run = `optimize/{target-slug}-{ts}` with a single commit (winning variant applied); variant-level history in `admin/scratch/optimize-{ts}/`; declined PRs retain the branch for ≥30 days for Phase 3 corpus mining; mechanical pre-PR file-diff check fails the run if unrelated files are modified. — flows into §Requirements R8, R9; AC AC-7, AC-8.

### Round 5 — Eval surface: what does "read-only eval surface" mean operationally?

- **Q:** The architectural spec says `/optimize` requires a *read-only eval surface*. `simplify`'s eval is genuinely read-only: it runs `git diff --stat`, the test command, the typecheck, and the lint — all of which read the working tree without modifying it. But for some targets, the eval might require *running* the target skill itself (e.g. `feedback-loop-audit`'s eval reads the produced `CONTEXT.md` — which the audit run *writes*). Is "read-only" violated when the eval requires running the skill (which is by definition not read-only)? What's the boundary?
- **AI's recommended answer:** "Read-only eval surface" means *the eval check itself does not mutate state beyond the per-run scratch directory*. Running the target skill to produce its output is allowed (and necessary for many targets), but: (a) the target skill must be invoked inside a forked sub-agent context with its working tree scoped to a per-variant scratch directory (`admin/scratch/optimize-{ts}/variant-{N}/run-output/`), NOT the project's actual working tree; (b) the eval check then reads files from the per-variant scratch directory without modifying the project's actual state; (c) when the variant is selected (Phase C), only the `SKILL.md` diff is applied to the working tree — nothing the variant produced as side-effect (e.g. an updated `CONTEXT.md`) is preserved. **Concrete instance:** for `feedback-loop-audit`, each variant of the prompt is applied to the target SKILL.md, then the target skill is invoked in a forked sub-agent with output redirected to `admin/scratch/optimize-{ts}/variant-{N}/run-output/CONTEXT.md`. The eval reads the produced CONTEXT.md, checks its length is within target/cap, checks every reference resolves, etc. — all read-only against the per-variant scratch path. The project's actual `admin/CONTEXT.md` is never touched. **Implication:** the eval-surface gate (analogous to `simplify`'s Pre.4 eval-surface gate) checks that the target skill's `produces:` field lists the files the eval reads — without that mapping, the eval can't be redirected to the per-variant scratch directory. Targets whose `produces:` field doesn't enumerate files (or that produce side-effects outside the working tree) are not eligible. — *Reasoning: the goal's Driving value field names "removes the failure mode where prompts drift away from their eval surface over time" — that's only true if the eval can run safely against the variant-being-evaluated. Per-variant scratch isolation is the operational meaning of "read-only" — the project's state is not at risk while the loop iterates. The `produces:` field as the redirection mapping is the contract surface that already exists in every skill's frontmatter, so we're not introducing a new convention.*
- **User's answer:** confirmed.
- **Resolved:** "read-only eval surface" = the eval check does not mutate state beyond the per-run scratch directory; running the target skill is allowed inside a forked sub-agent with output redirected to `admin/scratch/optimize-{ts}/variant-{N}/run-output/`; only the winning variant's SKILL.md diff is applied to the working tree; targets whose `produces:` field doesn't enumerate files are not eligible. — flows into §Requirements R10, R11; AC AC-9, AC-10.

### Round 6 — Merge governance: human-only, with what guardrails?

- **Q:** Per the goal: "auto-merging the resulting PR is out of scope; human merge owns taste, full stop." Operationally, what guardrails are in place to make sure auto-merge can't happen accidentally — e.g. a CI rule that auto-merges PRs with all green checks, or a `gh pr merge --auto` left in a script somewhere? And what's the contract when the human declines: does the skill record the decline, propose a different operator next run, or back off the target entirely?
- **AI's recommended answer:** **Auto-merge prevention guardrails:** (1) the PR description includes a literal `<!-- optimize: human-merge-required -->` HTML comment that any auto-merge wrapper can detect and refuse; (2) the PR is opened with no auto-merge label and the skill explicitly does NOT call `gh pr merge --auto` — even if a label like `auto-merge` exists in the project, the skill never applies it; (3) a separate pre-merge GH Action (shipped with `/optimize`) blocks merge on PRs whose head branch matches `optimize/*` until a `human-approved` label is applied by a real user — automation cannot apply the label. **Decline path:** the human closing the PR without merge → `/optimize` updates `optimize-runs.jsonl` with `merge_decision: "closed-without-merge"`, the *operator that produced the winning variant* is recorded, and the next overnight cron run on the same target *avoids that operator* until at least 7 days have passed. This is the simplest "back off without giving up" policy — the skill doesn't blacklist the target, it just doesn't repeat the operator that just got rejected. After three consecutive declines on the same target (any operator), the cron skips the target for 30 days and surfaces a chat-line warning when the maintainer next invokes `/optimize` manually: *"Target `{target}` has had 3 consecutive PRs closed without merge. The eval is producing improvements the human keeps rejecting — likely the eval is missing what the human values. Inspect `optimize-runs.jsonl` for the rejected variants and consider tightening the eval before the next run."* This is the Goodharting-detection signal — if the human keeps declining, the metric is wrong. — *Reasoning: the goal names "removes the failure mode where the discipline is left as a one-off" — the discipline includes "human merge owns taste," and operationally that means the auto-merge surface area is structurally locked, not just configured-off. The 3-decline-then-back-off policy is the corpus-mining signal `simplify`'s discipline named: "which scopes converged, which kept failing variants, which ones humans always reject (signal that the eval is missing something)." Surfacing the signal at the meta level (chat warning) is the only place the human notices without mining the corpus by hand.*
- **User's answer:** confirmed.
- **Resolved:** auto-merge prevention via HTML comment + no auto-merge label + separate GH Action blocking auto-merge on `optimize/*` branches; on decline, the operator that produced the winning variant is avoided for 7 days; 3 consecutive declines on a target → skip for 30 days and surface chat-line warning at next manual invocation. — flows into §Requirements R12, R13; AC AC-11, AC-12.

### Round 7 — Concurrency policy: cron + manual race conditions.

- **Q:** The overnight cron and manual `/optimize` invocation are both valid triggers. What happens when (a) the cron is mid-run and the user manually invokes `/optimize {target}` for the same target, (b) the cron picks Target A while the user is running Target B manually (different targets), (c) two GH Actions cron jobs accidentally fire concurrently because of a re-run? Single-skill PR per run is the architectural rule — does that mean single-`/optimize`-process per repo, or single-PR-per-target, or both?
- **AI's recommended answer:** Concurrency policy = **single `/optimize` process per repo at a time**, enforced by a lockfile at `admin/scratch/optimize.lock` containing the in-flight orchestration ID and start timestamp. Pre-flight gate: if `optimize.lock` exists AND the start timestamp is < 4 hours old, refuse the new invocation with: *"Another `/optimize` run is in progress (id: `{id}`, started: `{ts}`). ## Topics not discussed

- *Cross-skill optimisation co-evolution.* Per the goal's Out-of-scope-at-goal-level, one target per run is hard. A future version may run `/optimize` on a *contract surface* (e.g. the frontmatter `requires:`/`produces:` schema) across all skills simultaneously, but that's a Phase 3+ concern gated on the corpus showing the same pattern emerge across multiple targets independently. v1 ships with one target per run.
- *LLM-as-judge experiments outside the loop.* The discipline forbids LLM-as-judge *inside* the loop (it's the load-bearing Goodharting protection). A future experiment might run an LLM-as-judge as a post-hoc analysis tool — e.g. reading the corpus of declined PRs and summarising what the human appeared to value — but that sits outside the optimisation loop and outside `/optimize`'s contract. Out of scope for v1.
- *Self-targeting `/optimize`.* The architectural spec lists `simplify` (and by implication `/optimize` itself, recursively) as an eligible target. v1 does not block self-targeting — `/optimize {optimize}` is allowed if `/optimize`'s own `eval:` field passes the binary-eval criterion — but the recursive case is left to surface naturally in the corpus rather than be specified up front. If the recursive run starts producing problems (e.g. the optimised `/optimize` prompt fails the binary-eval criterion for itself), the user can disable self-targeting via `config.json.optimize.allowSelfTarget: false`. Configurability deferred until the recursive case actually surfaces.
