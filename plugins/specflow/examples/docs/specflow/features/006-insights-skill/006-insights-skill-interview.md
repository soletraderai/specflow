# PRD interview — features/006-insights-skill

## Original request

> Write the spec for `/insights`, the Phase 3 self-evolution skill. The skill mines `admin/task-history.json` (the corpus `specflow:complete` writes) for cross-task recurring patterns at a monthly cadence, surfaces a markdown report at `admin/insights/{YYYY-MM}-report.md`, and proposes rule-registry promotions (observation → guideline → non-negotiable) that the user accepts/rejects in chat. The architectural shape is locked in by `docs/PRD.md` Phase 3 scope item 10 ("`/insights` (monthly) + `/prune` (quarterly)") + Appendix I's self-learning memory loop; this PRD synthesises the implementation contract at the SKILL.md level.

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `docs/PRD.md` § "Phase 3 — Memory and self-learning" (lines 204-225) names `/insights` as scope item 10: "Surface recurring patterns from `task-history.json`; prune stale rules and decisions." Appendix I (lines 501-565) documents the `admin/` folder, `task-history.json` schema (I3), the feedback loop (I4), and explicitly names the auto-research vision as out-of-scope-for-current-phases (I6) — `/insights` v1 is a deterministic pattern miner over the corpus, not an LLM-driven research loop. SKILLS.md `/insights` entry locks the contract: surfaces recurring patterns; suggests promotions; suggestions cite ≥3 observations per promotion. Re-litigating those decisions is out of scope for this PRD.
- **Producer skill ships in `003-complete-skill`.** `skills/complete/SKILL.md` (PRD `003-complete-skill-prd.md`) is the producer; it writes the corpus this skill consumes. The Schema Appendix (lines 137-176 of `003-complete-skill-prd.md`) is the v1 contract — 25 fields per entry including `lane_assigned`, `ai_assistance_level`, `escaped_issues`, `regressions_caught`, `blast_radius_outcome`, `addenda`, `accepted_with_failure`, `elevation_fired_by`. `/insights` reads these fields by name; schema additions to the producer require a coordinated `/insights` PRD revision so the consumer keeps pace. The 003 PRD's `See also` (line 188) explicitly names `/insights` as the downstream consumer.
- **`task-history.json` real-world entries.** `examples/docs/specflow/admin/task-history.json` has five existing entries at 2026-05-06 (T-2026-01-T1 BaseService refactor, T-2026-02-T1 tests-colocation, T-2026-04-T1 specflow-adoption, T-001-design-skill-T1, T-2026-04-T2 orders-list-bulk-actions). The corpus is *small* — five entries is below the meaningful-pattern threshold this skill needs to enforce. The first round of grilling has to surface that threshold and the no-fire path on a fresh project.
- **Rules registry shape.** `examples/docs/specflow/admin/rules/{non-negotiable.md, guidelines.md, glossary.md}` is the registry `/insights` proposes promotions for. Existing guidelines (e.g. `PREFER_COMPOSITION_OVER_INHERITANCE`, `PREFER_LOCAL_TESTS`) cite their decision-log entry; non-negotiable rules have a tighter frontmatter contract (`id`, `tier`, `paths`) plus body (`Rule:`, `Why:`, `On violation:`, `Exceptions:`). The glossary expects a one-line entry per rule. Promotion-proposal output must compose the full frontmatter + body shape so the user can accept-and-write in one step; partial proposals would push the user back into manual rule authoring.
- **`decision-log.md` interaction.** Per `complete`'s elevation rule (R6 in 003-PRD), per-task significant patterns already elevate to `decision-log.md` at retro time. `/insights` reads `decision-log.md` as a secondary signal — clusters of decision-log entries citing the same pattern are themselves a promotion signal. The skill does NOT write to `decision-log.md` directly (that's `specflow:decision`'s contract). When `/insights` recommends a guideline promotion, the report cites the corpus observations; the user accepting writes only to `admin/rules/{guidelines,non-negotiable}.md` + `admin/rules/glossary.md`.
- **Sister Phase 3 skills.** `/prune` (Phase 3 scope item 10) is the quarterly counterpart — `/insights` adds; `/prune` removes. `/insights` v1 does NOT ship `/prune` integration; the two skills run on independent cadences and consume the same corpus. `specflow:complete` is upstream; `specflow:decision` and `specflow:scope-change` write to `decision-log.md` which `/insights` reads. The skill's I/O surface is read-mostly: reads `task-history.json` + `decision-log.md` + current `admin/rules/*`, writes `admin/insights/{YYYY-MM}-report.md` + (on user accept) appends to `admin/rules/*`.
- **Cron cadence convention.** PRD scope item 10 names "monthly" for `/insights` and "quarterly" for `/prune`. The cadence is suggested, not enforced — the skill must support manual `/insights` invocation any time AND a scheduled (cron / GH Actions) auto-invocation. The cron payload would be the same as manual invocation; the cadence is a config knob (`config.json.insights.cadence`) defaulted to monthly. Question for grilling: does v1 ship the cron wiring or just the skill body that a future cron job invokes?
- **Threshold-for-meaningful-patterns convention.** The SKILLS.md eval line says "suggestions cite at least three observations per promotion." The PRD scope item 10 says "surface recurring patterns" without naming the threshold. The 3-observation rule for promotion is locked. But there's a separate threshold for *running at all*: a corpus with 2 entries can't surface patterns reliably. That refusal threshold is a grilling round — what's the minimum corpus size before the skill produces a meaningful report?
- **No-fire path on fresh projects.** A project that just ran `specflow:setup` has zero `task-history.json` entries. Running `/insights` against an empty corpus must NOT silently produce an empty report — it must surface a structured refusal explaining the threshold, naming the current entry count, and recommending the user run more tasks before invoking the skill. This is the goal-driven "no silent failures" surface; refused exits are loud.
- **Cluster-detection algorithm.** The PRD does not specify *how* to detect patterns. Candidate algorithms: (a) tag-based grouping (the I3 schema's `tags` field — lightweight but depends on consistent tagging); (b) field-shape grouping (cluster by `lane_assigned`, `ai_assistance_level`, `blast_radius_outcome`, common substrings in `what_didnt_work`); (c) embedding-based clustering (semantic similarity over `what_worked` / `what_didnt_work` / `scope` text fields). Embedding clustering needs an LLM call surface and a vector store — heavyweight for v1. The grilling round must pick a v1 algorithm that is deterministic, debuggable, and ships without infrastructure dependencies.
- **Idempotency on re-run.** Running `/insights` twice in the same month must not produce two distinct reports of the same shape — but the corpus may have grown between invocations. Idempotency convention from sister skills: append-only execution log + replace-the-active-report. The grilling round must lock this in.
- **Standard agents, no debate manifest.** Like `specflow:complete`, `/insights` is a Phase 3 retro-cadence skill. It does NOT run an adversarial debate manifest — the only "gate" is the schema-parse + threshold-check + binary "every promotion proposal cites ≥3 observations." Consistent with `specflow:decision`, `specflow:misc`, `specflow:complete`. A debate manifest on monthly insights would be over-instrumentation for a deterministic pattern miner.
- **Worked examples 003-complete-skill, 004-decision-skill, 005-scope-change-skill.** Calibration anchors. 003 is the closest match — Phase 3, no debate manifest, 14R/15AC, two block findings + two push-backs at Gate 2. This dogfood pass aims for a similar realistic shape.

## Goal (confirmed before grilling)

- **Outcome:** `/insights` closes the self-learning loop by mining structured retro entries for cross-task patterns. Outcome — recurring observations get surfaced as candidate rule promotions; the rules registry self-evolves with human sign-off at every step. Without `/insights`, the corpus `specflow:complete` writes never gets read for its compounding signal — the lessons are captured but never aggregated, and the `task-history.json` corpus becomes a write-only audit trail rather than a feedback loop.
- **Audience:** Power Users (frontend / backend engineers with specflow installed) running `/insights` manually mid-month or accepting/rejecting promotions surfaced by the monthly auto-fire. Secondary: Developer / API Consumer profiles whose teams ingest the report through chat or PR-review surfaces — they read the report, the team lead acts on it. Tertiary: future-readers (the same team six months later, an auditor looking at why a guideline got promoted, the next `/insights` cadence reading prior reports for trend signals) who consume the markdown reports as the human-readable narrative of the self-learning loop's evolution.
- **Success looks like:** invoking `/insights` (manual or scheduled) on a project with ≥10 corpus entries produces (a) a markdown report at `admin/insights/{YYYY-MM}-report.md` listing every pattern cluster above the observation threshold, citing each cluster's contributing `task-history.json` entry ids, with the cluster's shape (lane, blast-radius, common terms in `what_didnt_work`); (b) zero or more rule-promotion proposals in chat, each citing ≥3 corpus observations and rendered with the full target frontmatter + body shape so the user can accept-and-write in one step; (c) explicit user accept/reject per proposal — never auto-promotion; the rules registry only mutates on explicit accept; (d) zero silent failures (refused invocation on under-threshold corpus, schema-gap, or duplicate-month-rerun surfaces explicitly with a structured reason).
- **Driving value:** removes the failure mode where `task-history.json` becomes a write-only audit trail with no compounding feedback; removes the failure mode where rule-registry evolution depends on a human remembering to scan retros and propose promotions (which never happens consistently because retros aren't read in aggregate); removes the failure mode where significant patterns surface only as one-off `decision-log.md` entries without ever being abstracted into reusable rules; removes the failure mode where the rules registry stays static while the codebase's actual conventions shift under it. Mining the corpus + proposing promotions + binding human sign-off at every promotion are the three surfaces the self-evolution loop depends on for output value.
- **Out of scope at the goal level:** (1) Auto-promotion to the rules registry — every promotion is human-confirmed, full stop; (2) cross-project pattern mining — `/insights` reads only the local repo's `task-history.json`, never aggregates across repos, never ships findings to a central service; (3) embedding-based or LLM-judge clustering — v1 ships deterministic field-shape + token-frequency clustering, no embedding store, no LLM call inside the cluster loop (per Karpathy autoresearch discipline: read-only machine eval inside the loop, human merge owns taste); (4) `/prune` integration — `/prune` is the quarterly counterpart skill (Phase 3 scope item 10), shipped separately, never invoked from `/insights`; (5) writing to `decision-log.md` — `/insights` reports patterns and proposes rule promotions; significant per-task patterns elevate via `specflow:complete` at retro time, not via this skill; (6) trend dashboards or per-month metrics rollups — the report is markdown for human reading, not a structured metrics surface; (7) editing or removing existing rules — promotion is additive (observation → guideline → non-negotiable); demotion or removal is `/prune`'s contract.

User confirmed: 2026-05-06.

## Rounds

### Round 1 — Cluster-detection algorithm: deterministic field-shape vs token-frequency vs embedding?

- **Q:** The PRD scope item 10 says "surface recurring patterns" but doesn't specify the algorithm. Three candidates: (a) field-shape grouping — cluster entries by exact-match buckets across `lane_assigned`, `ai_assistance_level`, `blast_radius_outcome`, plus tag intersection from the `tags` field if present (deterministic, debuggable, no infrastructure); (b) token-frequency on free-text retro fields — n-gram extraction over `what_worked`, `what_didnt_work`, `scope` text, surface n-grams appearing across ≥3 entries (deterministic, debuggable, no LLM); (c) embedding-based semantic clustering — vectorise free-text fields, cluster, surface cluster centroids (heavyweight, needs vector store, surfaces semantic-not-lexical patterns). Which algorithm does v1 ship, and how does it compose with the Phase 3 PRD scope item 10's "monthly cadence + ≥3-observations-per-promotion" eval?
- **AI's recommended answer:** Ship (a) + (b) combined; explicitly defer (c) to v2. v1's cluster-detection has two passes: pass 1 = field-shape exact-match grouping (e.g. all entries where `lane_assigned: green` AND `ai_assistance_level: full` AND `blast_radius_outcome` in {medium, high} cluster together — surfaces lane-vs-outcome divergence patterns); pass 2 = token-frequency n-gram extraction over `what_didnt_work` + `escaped_issues.descriptions` + `regressions_caught.descriptions`, with n=2..4 (bigrams through quadgrams), surfacing n-grams that appear across ≥3 distinct entries (the SKILLS.md eval threshold). Both passes are deterministic, run in seconds, debuggable (the report cites which entries contributed to each cluster), and ship without infrastructure. Stop-words filtered via a small fixed list (~40 common English tokens — `the`, `and`, `was`, etc.); no stemming (preserves the audit trail's lexical fidelity). Embedding-based (c) is explicitly v2 — the v1 schema and report shape leave room for an additional cluster source labelled `semantic` when (c) lands. — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly defers embedding-based / LLM-judge clustering per Karpathy autoresearch discipline (read-only machine eval inside the loop). Field-shape pass surfaces the patterns the schema's structured fields make obvious; token-frequency pass surfaces the lexical patterns the free-text fields hold. Together they cover the bulk of cross-task pattern signals without speculative complexity. The pattern matches `simplify`'s read-only-eval-inside-the-loop discipline: deterministic input, deterministic output, no model judgement in the cluster step, human owns the promotion call.*
- **User's answer:** confirmed, with one edit — make the n-gram pass explicitly case-insensitive and Unicode-normalised (NFC) before frequency counting. The retro fields are written by humans typing prose; "BaseService" and "baseservice" and "Base service" should cluster together. Without normalisation the token-frequency pass will fragment real patterns into near-duplicates that miss the ≥3 threshold.
- **Resolved:** v1 cluster-detection has two passes: field-shape exact-match grouping (lane_assigned × ai_assistance_level × blast_radius_outcome buckets, plus tag intersection) and token-frequency n-grams (n=2..4) over free-text retro fields after case-folding + NFC normalisation; stop-words filtered via a fixed ~40-token list; no stemming; embedding-based clustering deferred to v2 with a `semantic` cluster-source label reserved in the report schema. — flows into §Requirements R1, R2, R3; AC AC-1, AC-2, AC-3.

### Round 2 — Promotion threshold: how strict is "at least three observations per promotion"?

- **Q:** SKILLS.md eval: "suggestions cite at least three observations per promotion." The 3-observation rule is locked at the eval level. But what counts as an "observation" — three distinct `task-history.json` entries citing the same pattern, three distinct *features* (groups of tasks), or three distinct *causes* (three different reasons the pattern surfaced)? And does the same pattern recurring within a single task (e.g. a task with 3 escaped_issues all citing the same root cause) count as 1 observation or 3?
- **AI's recommended answer:** Three distinct `task-history.json` entries (i.e. three distinct task-ids), each contributing the pattern at least once. A single task with 3 escaped_issues citing the same root cause counts as 1 observation toward the threshold (the task is the unit of work; the corpus's atomic record is one entry per task). Three distinct features is a stronger signal but not required — the threshold is task-id-level, not feature-id-level, because Phase 3's compounding signal is per-task work. The cluster-detection algorithm tracks contributing entries by `id` field (the `{NNN-slug}-T{N}` shape from 003-PRD's Schema Appendix); duplicate ids in a cluster's contribution list are deduplicated before threshold check; the threshold check is `len(unique_contributing_ids) >= 3`. Promotion proposals in the report cite the contributing ids verbatim so the user can audit the cluster's basis. — *Reasoning: the goal's Outcome requires "each citing ≥3 corpus observations" — task-id-level is the most surgical interpretation of "observation" because the corpus's atomic unit is the entry. Counting within-entry repetitions inflates the count without adding signal (the same root cause showing up 3 times in one task is still one task's lesson). Counting at feature-id level would gate against legitimate cross-task patterns within a single feature (e.g. T1 + T2 + T3 of the same feature all hitting the same gotcha — three observations of one signal, even though it's one feature). Task-id is the right granularity.*
- **User's answer:** confirmed, with one addendum — the report's promotion proposal must list the unique contributing ids inline AND must show at least one short verbatim excerpt from each contributing entry's relevant field (e.g. the `what_didnt_work` snippet, or the `escaped_issues.descriptions[i]` snippet). Listing only ids is auditable but the verbatim excerpt is what makes the proposal reviewable in one read — without it the user has to open three files to evaluate the proposal.
- **Resolved:** "observation" = distinct `task-history.json` entry (task-id-level, deduplicated by `id` field); within-entry repetitions count as 1; threshold check is `len(unique_contributing_ids) >= 3`; promotion proposals list the unique contributing ids verbatim AND include at least one short excerpt (≤140 chars) from each contributing entry's relevant field, so the proposal is reviewable in one read without opening source files. — flows into §Requirements R4, R5; AC AC-4, AC-5.

### Round 3 — Cron cadence: does v1 ship the scheduler wiring or only the skill body?

- **Q:** PRD scope item 10 says "monthly cadence" and SKILLS.md says "Triggers: `/insights` (manual), scheduled cron." Does v1 ship (a) the cron / GH Actions wiring inside the skill (skill auto-installs a workflow file, registers a system cron, etc.); (b) only the skill body, with the cadence being a `config.json.insights.cadence` knob the user wires to their own scheduler; (c) both — wiring is opt-in per project, the knob defaults to "manual-only" with a documented opt-in path?
- **AI's recommended answer:** Ship (b) — only the skill body. The cadence is a `config.json.insights.cadence` knob with default value `"monthly"` (informational, not enforced — the skill itself doesn't run a scheduler). The skill emits a chat-line on every successful run noting the next-suggested-run date (computed as completed_at + cadence-interval); users wire their own scheduler (GH Actions cron, system cron, Linear automation) to invoke `/insights {feature}` at the suggested cadence. v1 ships zero scheduler installation; v2 may ship a `/specflow:schedule install` helper if real consumers report scheduler-friction. The knob's existence (a) keeps the cadence surface visible in `config.json` for users to tune, and (b) lets the skill compute the next-suggested-run date deterministically. — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly defers cross-project automation infrastructure; auto-installing schedulers is exactly that surface. Simplicity First sub-clause: "Do not introduce config knobs without a concrete second consumer demanding them" applies to the *scheduler installation* (no documented consumer ask for that) but NOT to the cadence knob itself (the SKILLS.md trigger contract names "scheduled cron" — the cadence knob is the documented surface). Cleanest split: the knob ships, the auto-install does not.*
- **User's answer:** confirmed.
- **Resolved:** v1 ships only the skill body; cadence is a `config.json.insights.cadence` knob (default `"monthly"`, accepts `"weekly" | "monthly" | "quarterly" | "manual-only"`); the skill itself never installs a scheduler; on every successful run, a chat-line names the next-suggested-run date computed from the previous successful run's date plus the cadence interval; v2 may ship a scheduler-install helper when a documented consumer surfaces. — flows into §Requirements R6, R7; AC AC-6, AC-7.

### Round 4 — Promotion-proposal format: full-frontmatter pre-rendered or one-line summary with edit-mode?

- **Q:** When the skill proposes a promotion (observation → guideline OR guideline → non-negotiable), what shape does the proposal take in chat? Options: (a) one-line summary ("Pattern X seen in 3 entries; promote to guideline?"); (b) full frontmatter + body pre-rendered so the user can accept-and-write in one step; (c) one-line summary with an edit-mode option that opens the full frontmatter + body for review-and-edit. The full-frontmatter shape is the most surgical write surface; one-line summary is shortest-prompt; edit-mode is the middle ground.
- **AI's recommended answer:** Ship (b) — full frontmatter + body pre-rendered, with explicit accept-edit-reject options (mirrors `specflow:complete`'s elevation-write surface, R7 / AC-7 of 003-PRD). Each proposal in the report renders the full target rule (frontmatter `id`, `tier`, `paths`; body `Rule:`, `Why:`, `On violation:`, `Exceptions:` for non-negotiable; same shape minus the `On violation` strictness for guideline) so the user can accept-and-write in one step. The `Why:` is auto-composed from the cluster's contributing ids' verbatim excerpts (per Round 2 resolution); the `paths:` is auto-suggested from the union of `scope` arrays across contributing ids (de-duplicated, common-prefix folded — e.g. five entries with `scope: ["src/services/orders/...", "src/services/billing/..."]` proposes `paths: ["src/services/**/*.ts"]`); the `id:` is auto-suggested as a SCREAMING_SNAKE_CASE form of the cluster's dominant n-gram (user can edit). The user has three options per proposal: accept-and-write (skill appends to the target rules file + glossary); edit-and-write (user edits any field, skill re-validates frontmatter shape, writes); reject (no write; cluster recorded in the report as `proposed-rejected` for trend-signal). — *Reasoning: the goal's Outcome requires "each citing ≥3 corpus observations and rendered with the full target frontmatter + body shape so the user can accept-and-write in one step" — the verbatim Goal language pre-locks (b). The path-suggestion + id-suggestion logic is bounded auto-composition, not LLM judgement; the user always reviews. Edit-mode (c) is implicit in the accept-edit-reject triple; one-line summary (a) would force the user back into manual rule authoring at the moment of acceptance, defeating the goal's "accept-and-write in one step" surface.*
- **User's answer:** confirmed, with one edit — the auto-suggested `paths:` glob folding must be conservative (default to the longest common prefix that covers all contributing scopes, not an aggressive `**/*.ts`-style generalisation). A guideline that accidentally widens its path glob beyond the contributing entries' actual surface would fire on unrelated code and degrade the registry's signal. Default to specific; let the user widen at edit time if appropriate.
- **Resolved:** promotions render as full frontmatter + body in the report; user has three options per proposal (accept-and-write, edit-and-write, reject); auto-suggested `paths:` uses the longest common prefix across contributing entries' `scope` arrays (conservative — never generalises to a broader glob unless the user widens at edit-time); auto-suggested `id:` is SCREAMING_SNAKE_CASE of the dominant n-gram (user can edit); rejected proposals recorded in the report's `proposed-rejected` section for trend-signal in subsequent runs. — flows into §Requirements R8, R9; AC AC-8, AC-9.

### Round 5 — Failure modes: what happens when the corpus is below the meaningful-pattern threshold?

- **Q:** SKILLS.md eval names "≥3 observations per promotion" but doesn't name a corpus-size threshold for *running at all*. A project with 0 entries can't surface anything; a project with 2 entries can technically surface zero patterns but the report would be near-empty. Does v1 ship a hard refusal threshold (e.g. <10 entries refuses with a structured chat line), a soft threshold (produces a report but flags it as "low-corpus"), or no threshold (always produce a report, even empty)?
- **AI's recommended answer:** Hard refusal at <10 entries with a structured chat line: *"Corpus too small for meaningful pattern detection (`{N}` entries; threshold 10). Run more tasks through `specflow:complete` and re-invoke `/insights` when the corpus has grown."* The 10-entry threshold is calibrated for the smallest corpus where the ≥3-observations-per-promotion rule has any chance of firing AND where the field-shape buckets are likely to have multiple entries (a 5-entry corpus with 3 lanes and 3 ai_assistance levels has at most 1-2 entries per bucket on average — no clusters surface). The threshold is a `config.json.insights.minCorpusSize` knob defaulted to 10; users can lower it if they want low-signal reports for early calibration. The refusal is loud (sentinel chat line, no silent skip) and exits without writing the report file. Manual mode and cron mode both refuse identically. — *Reasoning: the goal's surface (d) (zero silent failures) requires the under-threshold case to surface explicitly. The 10-entry default is small enough to be reachable by month 2-3 of a normal team's specflow usage but large enough that the cluster passes have material to work with. The knob's existence honours Simplicity First's "config knobs only when a documented consumer surfaces" — the consumer here is the early-adopter team that wants to tune the threshold downward to see what the skill does on a small corpus. Hard refusal beats soft refusal because the report file's existence is itself a signal — a "low-corpus" report would be read by future-readers as "we tried but couldn't find anything," which is misleading; better to have no file at all and a chat-line saying "wait."*
- **User's answer:** confirmed, with one addition — the refusal chat line should also name the `minCorpusSize` config knob so the user knows the threshold is tunable. Plain "threshold 10" without naming the knob makes it look hard-coded.
- **Resolved:** hard refusal at corpus size below `config.json.insights.minCorpusSize` (default 10) with a structured chat line naming the current count, the threshold value, and the knob name; refusal exits without writing the report file; manual and cron modes refuse identically. — flows into §Requirements R10; AC AC-10.

### Round 6 — Idempotency: re-running `/insights` within the same month — append, replace, or refuse?

- **Q:** `specflow:misc` is append-only; `specflow:test`'s execution log is append-only; `specflow:complete` refuses re-invocation in plain mode and uses `--amend` for follow-ups. What happens when `/insights` runs twice in the same month — append a fresh report (corpus has two reports for the same month), replace the existing report (loses the audit trail of mid-month runs), or refuse the second invocation (forces user to wait for next cadence)?
- **AI's recommended answer:** Replace-the-active-report-in-place; preserve prior runs in an append-only execution log at `admin/insights/{YYYY-MM}-runs.jsonl`. The active report file at `admin/insights/{YYYY-MM}-report.md` is overwritten on each within-month re-run (the report is the *current* state of the month's pattern detection — a stale mid-month report has no value); each run's metadata (run-id, timestamp, contributing-ids count, promotions-proposed count, promotions-accepted count, promotions-rejected count) appends to `admin/insights/{YYYY-MM}-runs.jsonl` for trend-signal. When the month rolls over (`{YYYY-MM}` changes), the new month's report is a fresh file; the prior month's report is archived in place. User-accepted promotions (writes to `admin/rules/*`) are NOT reverted on re-run — those writes are independent and committed to the repo on each acceptance. The replace-in-place + execution-log pattern matches `specflow:test`'s precedent (test plan replaces, execution log appends). — *Reasoning: the goal's Outcome requires "a markdown report at `admin/insights/{YYYY-MM}-report.md` listing every pattern cluster" — singular "the report" implies one report per month, not a history. The execution log captures the audit trail (run-times, run-counts, promotion-acceptance rate over the month) without bloating the report file with repeated content. Refusing the second invocation would gate against legitimate mid-month re-runs (e.g. user accepted some promotions and wants to re-check whether the remaining cluster signal changes). Append-mode would produce confusing duplicate-content reports.*
- **User's answer:** confirmed.
- **Resolved:** active report at `admin/insights/{YYYY-MM}-report.md` is replaced-in-place on within-month re-runs; per-run metadata appends to `admin/insights/{YYYY-MM}-runs.jsonl` (run-id, timestamp, contributing-ids count, promotions-proposed/accepted/rejected counts); user-accepted promotion writes to `admin/rules/*` are independent and never reverted; cross-month rollover produces fresh files (prior month's report archived in place). — flows into §Requirements R11, R12; AC AC-11, AC-12.

### Round 7 — `decision-log.md` interaction: read-only signal vs proposed-write surface?

- **Q:** Per `specflow:complete` R6 (003-PRD), per-task significant patterns elevate to `decision-log.md` at retro time. The `/insights` skill reads `decision-log.md` as a secondary signal (clusters of decision-log entries citing the same pattern strengthen a promotion proposal). Does v1 also propose *new* `decision-log.md` entries for cross-task patterns the skill detects, or does it stay read-only on the decision log and only propose rule promotions?
- **AI's recommended answer:** Stay read-only on `decision-log.md` — `/insights` v1 reads but does not propose decision-log entries. Decision-log entries are the per-task narrative `specflow:complete` writes; cross-task abstractions are *rules*, not decisions, and surface as rule-promotion proposals not decision-log proposals. If the user wants a cross-task pattern captured in `decision-log.md` (e.g. "we're seeing this pattern across the codebase, let's record the meta-decision to address it"), they invoke `/specflow:decision` manually with the pattern as context — that's `specflow:decision`'s contract, not `/insights`'s.
