# /insights — self-evolution skill that closes the loop on the rules registry

## Vision

`/insights` closes the self-learning loop by mining structured retro entries for cross-task patterns. Outcome — recurring observations get surfaced as candidate rule promotions; the rules registry self-evolves with human sign-off at every step. The skill turns the corpus `specflow:complete` writes into compounding feedback: `task-history.json` becomes a *read* surface, not just a write-only audit trail. Power Users running `/insights` mid-month or accepting/rejecting promotions surfaced by the monthly auto-fire; Developer / API Consumer profiles whose teams ingest the report through chat or PR-review surfaces; future-readers (the same team six months later, an auditor looking at why a guideline got promoted, the next `/insights` cadence reading prior runs for trend signals) consume the markdown reports as the human-readable narrative of the self-learning loop's evolution. Two trigger paths — manual `/insights` and user-wired scheduled cron — and a hard refusal threshold below 10 corpus entries keep the skill honest. Append-only execution log + replace-in-place active report keeps the audit trail intact while the active report stays current.

## Problem

`specflow:complete` (Phase 3, shipped in `003-complete-skill`) writes structured retro entries to `admin/task-history.json`; `specflow:decision` and `specflow:scope-change` write to `admin/decision-log.md`; the rules registry at `admin/rules/{non-negotiable.md, guidelines.md, glossary.md}` is the project's living conventions surface. But the corpus has been *write-only* up to this point — five entries land at 2026-05-06 (T-2026-01-T1 through T-2026-04-T2) and no skill reads them in aggregate for cross-task patterns. The failure modes that result are well-known: (a) `task-history.json` becomes a write-only audit trail with no compounding feedback — six months of retros accumulate, the lessons are captured but never aggregated, and the next time the same gotcha surfaces nobody connects it to the prior occurrences; (b) rule-registry evolution depends on a human remembering to scan retros and propose promotions, which never happens consistently because retros aren't read in aggregate; (c) significant patterns surface only as one-off `decision-log.md` entries without ever being abstracted into reusable rules — the pattern is named once per task at retro time but never gets the registry treatment that would prevent recurrence; (d) the rules registry stays static while the codebase's actual conventions shift under it, drifting toward the failure mode the registry was built to prevent.

The fix is structural: a single skill that owns the read-mostly cross-task pattern detection surface, runs deterministically (no LLM judgement inside the cluster loop), proposes promotions in chat with full frontmatter + body pre-rendered for one-step accept-and-write, never auto-promotes (every promotion is human-confirmed), refuses on under-threshold corpora with a structured chat line (zero silent failures), and replaces-the-active-report on within-month re-runs while preserving the execution log of every prior run. Two trigger paths — manual `/insights` and scheduled cron the user wires to their own scheduler — plus a `config.json.insights.cadence` informational knob keep the surface visible without auto-installing infrastructure.

## Goals

- Run on two trigger paths only: manual `/insights` (CLI) and scheduled cron the user wires (the skill never installs a scheduler). The cadence knob `config.json.insights.cadence` (default `"monthly"`, accepts `"weekly" | "monthly" | "quarterly" | "manual-only"`) is informational — the skill emits a chat-line on every successful run naming the next-suggested-run date computed from previous-successful-run + cadence-interval; users wire their own scheduler.
- Two-pass deterministic cluster detection: pass 1 = field-shape exact-match grouping (lane_assigned × ai_assistance_level × blast_radius_outcome buckets, plus tag intersection from the I3 `tags` field if present); pass 2 = token-frequency n-grams (n=2..4) over `what_didnt_work` + `escaped_issues.descriptions` + `regressions_caught.descriptions` after case-folding + Unicode NFC normalisation, with a fixed ~40-token English stop-word list and no stemming. Both passes surface clusters where `len(unique_contributing_ids) >= 3`. Embedding-based clustering deferred to v2 with a `semantic` cluster-source label reserved.
- "Observation" = distinct `task-history.json` entry (task-id-level; deduplicated by `id` field). Within-entry repetitions count as 1. Threshold check is `len(unique_contributing_ids) >= 3` per cluster.
- Promotion proposals render in chat AND in the report with full target-rule frontmatter + body pre-rendered (frontmatter `id`, `tier`, `paths`; body `Rule:`, `Why:`, `On violation:`, `Exceptions:` for non-negotiable; same shape minus `On violation` strictness for guideline). The `Why:` is auto-composed from the cluster's contributing entries' verbatim excerpts (one short excerpt per contributing id, ≤140 chars each); the `paths:` is auto-suggested as the conservative longest-common-prefix across contributing entries' `scope` arrays (never aggressively generalised); the `id:` is auto-suggested as SCREAMING_SNAKE_CASE of the cluster's dominant n-gram. User can edit any field at acceptance time.
- Three-option user prompt per proposal: accept-and-write (skill appends to `admin/rules/{guidelines,non-negotiable}.md` + adds the matching one-line glossary entry); edit-and-write (user edits any field, skill re-validates frontmatter shape, writes); reject (no write; cluster recorded in the report's `proposed-rejected` section for trend-signal in subsequent runs). Never auto-promote — every promotion is human-confirmed.
- Hard refusal at `corpus_size < config.json.insights.minCorpusSize` (default 10) with a structured chat line naming current count, threshold, and knob name; refusal exits without writing the report file. Manual and cron modes refuse identically.
- Idempotency on within-month re-run: replace-the-active-report at `admin/insights/{YYYY-MM}-report.md`; append per-run metadata to `admin/insights/{YYYY-MM}-runs.jsonl` (run-id, timestamp, contributing-ids count, promotions-proposed/accepted/rejected counts). User-accepted writes to `admin/rules/*` are independent and never reverted on re-run. Cross-month rollover produces fresh files; prior month's report stays archived in place.
- `decision-log.md` read-only — the skill reads it as a secondary signal (decision-log entries cited by date/title in the report's observation list when relevant); the skill NEVER proposes or writes new decision-log entries. Cross-task abstractions are *rules*, not decisions; per-task decision-log writes belong to `specflow:complete` and `specflow:decision`.
- Zero silent failures: refused invocation on under-threshold corpus, schema-gap (e.g. `task-history.json` schema drift from the v1 contract this PRD reads), or duplicate-month-rerun-without-replace surfaces explicitly to the user with a structured reason. Every artefact lives at `admin/insights/` so the corpus stays per-repo and committed.

## Non-goals

- **Auto-promotion to the rules registry.** Out of scope per goal's Out-of-scope-at-goal-level (item 1). Every promotion is human-confirmed; the skill never writes to `admin/rules/*` without the user's explicit accept-and-write or edit-and-write choice.
- **Cross-project pattern mining.** Out of scope per goal's Out-of-scope-at-goal-level (item 2). `/insights` reads only the local repo's `task-history.json`; never aggregates across repos; never ships findings to a central service.
- **Embedding-based or LLM-judge clustering.** Out of scope per goal's Out-of-scope-at-goal-level (item 3). v1 ships deterministic field-shape + token-frequency clustering; no embedding store; no LLM call inside the cluster loop. Karpathy autoresearch discipline: read-only machine eval inside the loop, human merge owns taste. v2 may add a `semantic` cluster source when a documented consumer surfaces.
- **`/prune` integration.** Out of scope per goal's Out-of-scope-at-goal-level (item 4). `/prune` is the quarterly counterpart skill (Phase 3 scope item 10), shipped separately. v1 of `/insights` does not invoke `/prune`; the two skills consume the same corpus on independent cadences.
- **Writing to `decision-log.md`.** Out of scope per goal's Out-of-scope-at-goal-level (item 5). `/insights` reports patterns and proposes rule promotions; per-task significant patterns elevate via `specflow:complete` at retro time; manual decision-log entries land via `specflow:decision`; never via this skill.
- **Trend dashboards or per-month metrics rollups.** Out of scope per goal's Out-of-scope-at-goal-level (item 6). The report is markdown for human reading, not a structured metrics surface. The execution log per R12 captures data that would feed multi-month rollups in v2.
- **Editing or removing existing rules.** Out of scope per goal's Out-of-scope-at-goal-level (item 7). Promotion is additive (observation → guideline → non-negotiable); demotion or removal is `/prune`'s contract.
- **Auto-installing schedulers.** v1 ships zero scheduler installation. The cadence knob is informational; users wire their own GH Actions cron, system cron, or Linear automation to invoke `/insights` at the suggested cadence.
- **Adversarial review gating (multi-agent debate manifest).** Phase 3 retro-cadence skills do not gate at adversarial review — the only "gate" is the schema-parse + threshold-check + binary "every promotion proposal cites ≥3 unique contributing ids." Consistent with sister skills `specflow:complete` (no manifest), `specflow:decision` (no manifest), `specflow:misc` (no manifest).

## Users

- **Power User (per `admin/profiles.json`)** — frontend / backend engineers running implementation in their own repos. They invoke `/insights` manually mid-month when they want to check the pattern surface (e.g. "we've shipped a lot recently — what's the corpus saying?") AND accept/reject promotions surfaced by the monthly auto-fire. They need promotions rendered in full frontmatter + body so accepting is one step (no manual rule authoring at the moment of acceptance), refusals to be loud (chat line, not silent skip), and the auto-suggested `paths:` glob to be conservative (specific by default, widening only at edit-time).
- **Developer / API Consumer (per `admin/profiles.json`)** — engineers whose teams ingest the report through chat or PR-review surfaces. They never invoke `/insights` directly — the report file is committed by the team lead after the monthly cadence run, and they read it during PR review or sprint planning. They need the report's promotion proposals to be reviewable in one read (verbatim excerpts inline, no need to open contributing entry files) and the proposed-rejected section to carry the trend-signal so the next month's run can pattern-match on rejections.
- **Secondary: future-readers** — the same team six months later, an auditor looking at why a guideline got promoted, the next `/insights` cadence reading prior runs for trend signals. They consume `admin/insights/{YYYY-MM}-report.md` files and the `admin/insights/{YYYY-MM}-runs.jsonl` execution log without ever invoking the skill. They benefit from append-only execution-log discipline (run history stays trustworthy as audit trail), schema consistency (the `runs.jsonl` shape is the v1 contract documented in this PRD's Schema Appendix), and the conservative `paths:` glob convention (the registry stays high-signal because broad globs route to edit-time review instead of auto-acceptance).

## Requirements

- **R1.** Two-pass deterministic cluster detection. The skill runs two cluster passes over the corpus: pass 1 = field-shape exact-match grouping over `(lane_assigned, ai_assistance_level, blast_radius_outcome)` tuples, plus tag-intersection grouping from the I3 `tags` field where present; pass 2 = token-frequency n-grams (n=2..4) over the concatenation of `what_didnt_work` + `escaped_issues.descriptions[]` + `regressions_caught.descriptions[]`, after case-folding (lowercase) + Unicode NFC normalisation, with a fixed English stop-word list (~40 tokens — `the`, `and`, `was`, `for`, etc.; the full list lives in the SKILL body at implementation time) and no stemming. Both passes are deterministic — same corpus produces same clusters byte-for-byte; same input → same output is the contract.
  - Trace: interview Round 1 — *v1 cluster-detection has two passes: field-shape exact-match grouping and token-frequency n-grams (n=2..4) ... after case-folding + NFC normalisation; stop-words filtered via a fixed ~40-token list; no stemming*.
  - Serves goal: Driving value (no compounding feedback failure mode — deterministic clusters that produce the same result on the same corpus, debuggable, ship without infrastructure).

- **R2.** Cluster contribution tracking. Each cluster surfaces a list of contributing entry ids (the `id` field from `task-history.json`); the list is deduplicated before threshold check; `len(unique_contributing_ids) >= 3` is the threshold for the cluster to appear in the report. Within-entry repetitions count as 1 (a single task with three escaped_issues all citing the same root cause contributes 1 observation toward the threshold; the task-id is the unit). Sub-cluster tracking — when n-gram pass 2 surfaces a sub-cluster of pass 1's tuple bucket, the report nests them (e.g. "Lane=green ∧ AI=full ∧ blast=high (4 entries) → token cluster `service worker race` (3 of 4 entries)").
  - Trace: interview Round 2 — *"observation" = distinct `task-history.json` entry (task-id-level, deduplicated by `id` field); within-entry repetitions count as 1; threshold check is `len(unique_contributing_ids) >= 3`*.
  - Serves goal: Driving value (compounding signal preserved — the threshold rule guards against single-task noise being abstracted to a rule; sub-cluster nesting preserves the field-shape × token-shape signal hierarchy).

- **R3.** Embedding-based clustering deferred. v1 does NOT ship embedding-based clustering. The report schema reserves a `semantic` cluster-source label (alongside `field-shape` and `token-ngram`) so a v2 embedding pass can land additively without breaking the v1 report shape. v1 reports use only the two-pass deterministic clusters; the `semantic` label appears in the schema but never in v1 output.
  - Trace: interview Round 1 — *embedding-based (c) is explicitly v2 — the v1 schema and report shape leave room for an additional cluster source labelled `semantic` when (c) lands*. Defended at Gate 2 against simplicity-r1-f1's drop-the-reservation proposal: the reservation is interview-grounded (Round 1 user-confirmed), and the runs.jsonl `semantic_clusters` counter is the additivity surface — without it, the v2 PR adding embedding clustering becomes a breaking schema revision (every prior month's runs.jsonl needs migration). Round 3 simplicity-reviewer accepted the defence on the same grounds the 003-complete-skill simplicity-r1-f1 push-back held: documented user-stated decision + downstream consumer evidence (v2 embedding-based clustering named in goal Out-of-scope item 3).
  - Serves goal: Out-of-scope-at-goal-level (item 3 — embedding-based / LLM-judge clustering deferred); Simplicity First (no speculative configurability — but the v2 hook exists in the schema so the additive-not-breaking path is preserved).

- **R4.** Promotion proposals render full frontmatter + body. Each proposal in the report (and at the chat-line surface during interactive accept-edit-reject) renders the full target rule shape: frontmatter (`id`, `tier`, `paths`); body (`Rule:`, `Why:`, `On violation:`, `Exceptions:` for non-negotiable; the same shape minus the `On violation` strictness for guideline). The `Why:` field is auto-composed from the cluster's contributing entries' verbatim excerpts — one short excerpt per contributing id, each excerpt ≤140 chars, drawn from the field that contributed the cluster (e.g. for a token-cluster surfaced from `what_didnt_work`, the excerpt is from each contributing entry's `what_didnt_work`; for an `escaped_issues`-driven cluster, the excerpt is the offending `escaped_issues.descriptions[i]`).
  - Trace: interview Round 4 — *promotions render as full frontmatter + body in the report ... The `Why:` is auto-composed from the cluster's contributing ids' verbatim excerpts*.
  - Serves goal: Outcome ("rendered with the full target frontmatter + body shape so the user can accept-and-write in one step" — verbatim from goal); Driving value (the rules registry self-evolves with human sign-off — the full-frontmatter rendering is what makes one-step accept-and-write possible).

- **R5.** Conservative `paths:` glob auto-suggestion. The auto-suggested `paths:` array on each promotion proposal uses the longest common prefix across contributing entries' `scope` arrays (de-duplicated, common-prefix folded — e.g. five entries with `scope: ["src/services/orders/file1.ts", "src/services/billing/file2.ts"]` proposes `paths: ["src/services/**/*.ts"]` only when the common prefix is `src/services/`; if the prefix is more specific like `src/services/orders/`, the proposal is `paths: ["src/services/orders/**/*.ts"]`). Never aggressively generalise to a broader glob (e.g. `**/*.ts`) unless the user widens at edit-time. The auto-suggested `id:` is SCREAMING_SNAKE_CASE of the cluster's dominant n-gram (the n-gram with highest cross-entry frequency in the cluster); user can edit any field at acceptance time.
  - Trace: interview Round 4 — *auto-suggested `paths:` uses the longest common prefix across contributing entries' `scope` arrays (conservative — never generalises to a broader glob unless the user widens at edit-time)*.
  - Serves goal: Driving value (registry stays high-signal — broad globs route to edit-time review instead of auto-acceptance, preventing accidental rule fire on unrelated code).

- **R6.** Two trigger paths only. The skill runs on (1) manual CLI `/insights [--feature {NNN-slug}]` and (2) user-wired scheduled cron — the skill itself NEVER installs a scheduler. The cadence is read from `config.json.insights.cadence` (default `"monthly"`, accepts `"weekly" | "monthly" | "quarterly" | "manual-only"`); the value is informational — the skill computes the next-suggested-run date and emits it on every successful run, but does not enforce or schedule. v2 may ship a scheduler-install helper (`/specflow:schedule install insights`) when a documented consumer surfaces.
  - Trace: interview Round 3 — *v1 ships only the skill body; cadence is a `config.json.insights.cadence` knob (default `"monthly"`, accepts `"weekly" | "monthly" | "quarterly" | "manual-only"`); the skill itself never installs a scheduler*.
  - Serves goal: Out-of-scope-at-goal-level (item 8 — auto-installing schedulers); Simplicity First (no speculative configurability — the cadence knob ships because SKILLS.md trigger contract names "scheduled cron" but the auto-install does not).

- **R7.** Next-suggested-run date emission. On every successful run, the skill emits a chat-line naming the next-suggested-run date computed from `last_successful_run_at + cadence_interval` (where `cadence_interval` ∈ {7d, 30d, 90d, never} matching the four cadence enum values; `manual-only` emits "no scheduled cadence — invoke manually"). The previous-successful-run timestamp is read from the most recent record in the active month's `runs.jsonl` (or any prior month if the active month has no records); the chat-line is informational only — the skill never blocks on "too soon" re-runs (the user's scheduler owns cadence enforcement). **Note (Gate 2 tbc-r1-f1):** the cadence knob is purely informational inside this skill. It changes only this chat-line; cluster detection and refusal logic are cadence-independent — running with `cadence=weekly` produces the same cluster output as `cadence=manual-only` on the same corpus. v2 enhancements adding cadence enforcement (refuse-too-soon, etc.) would be breaking changes against this v1 contract.
  - Trace: interview Round 3 — *on every successful run, a chat-line names the next-suggested-run date computed from the previous successful run's date plus the cadence interval*. Extended at Gate 2 per tbc-r1-f1: load-bearing-assumption Note articulates the cadence knob's purely-informational status as a v1 contract.
  - Serves goal: Outcome (per-run summary chat-line); Audience (Power Users running mid-month invocations need to know when the next cadence run lands).

- **R8.** Three-option user prompt per proposal. Each promotion proposal surfaces in chat with three explicit options: (1) accept-and-write — skill appends the rule frontmatter + body to the target file (`admin/rules/guidelines.md` for observation-to-guideline; `admin/rules/non-negotiable.md` for guideline-to-non-negotiable) AND adds the matching one-line entry to `admin/rules/glossary.md` under the appropriate section; (2) edit-and-write — accepts an edited version of any of the four rule fields (`id`, `paths`, `Rule:`, `Why:`), re-validates the frontmatter shape (id matches `^[A-Z][A-Z0-9_]*$`; paths is a non-empty array of glob strings; tier matches the destination file), writes to the target rule file + glossary; (3) reject — no write to `admin/rules/*`; the cluster is recorded in the report's `proposed-rejected` section with the rejection timestamp and the proposal's auto-suggested `id`. The skill MUST NOT proceed without an explicit user choice per proposal — empty input or any input not matching `1|2|3` re-prompts. Auto-default is a failed run.
  - Trace: interview Round 4 — *user has three options per proposal (accept-and-write, edit-and-write, reject); rejected proposals recorded in the report's `proposed-rejected` section for trend-signal in subsequent runs*.
  - Serves goal: Outcome ("explicit user accept/reject per proposal — never auto-promotion; the rules registry only mutates on explicit accept" — verbatim from goal); Driving value (registry self-evolves with human sign-off at every step).

- **R9.** Promotion-tier routing. The skill detects which tier a promotion targets based on the cluster's source: clusters where contributing entries cite a pattern that has NO existing guideline (cross-checked against the current `admin/rules/glossary.md`) propose observation→guideline (target file `admin/rules/guidelines.md`); clusters where contributing entries cite a pattern that DOES have an existing guideline AND surface ≥3 distinct guideline-flagged violations propose guideline→non-negotiable (target file `admin/rules/non-negotiable.md`). The skill reads `admin/rules/glossary.md` to determine existing-rule coverage; the matching is by the dominant-n-gram-derived `id` AND by `paths:` glob overlap. Each proposal in the report names the tier transition explicitly (e.g. `proposes: observation→guideline` or `proposes: guideline→non-negotiable`). **Tradeoff (Gate 2 tbc-r1-f2):** R9 detects guideline-flagged violations via substring-match on the rule's id in contributing entries' free-text retro fields (`escaped_issues.descriptions[i]`, `what_didnt_work`). Substring matching is implementation-cheap and works against the existing `task-history.json` schema, but has known false-positive risks (rule id mentioned in unrelated context) and false-negative risks (user describes violation in prose without naming the rule). Decision: v1 ships substring matching to avoid a cross-skill `task-history.json` schema change; v2 may add a structured `rule_violations: ["RULE_ID", ...]` field on entries (a `specflow:complete` schema enhancement) for higher-fidelity detection. The v1 false-positive risk is mitigated by R8's three-option human-confirmed prompt — a substring false-positive surfaces a proposal the user rejects rather than auto-promoting noise. The v1 false-negative risk is the cost of substring matching's lexical-not-semantic limit; embedding-based matching (R3) would address it but is out-of-scope for v1.
  - Trace: interview Round 2 — *promotion proposals list the unique contributing ids verbatim AND include at least one short excerpt (≤140 chars) from each contributing entry's relevant field*; SKILLS.md eval — *Suggested rule registry promotions (observation → guideline → non-negotiable)*. Extended at Gate 2 per tbc-r1-f2: substring-match tradeoff articulated; v2 structured-field path named.
  - Serves goal: Outcome ("recurring observations get surfaced as candidate rule promotions; the rules registry self-evolves" — verbatim from goal); Driving value (rule-registry evolution failure mode — the tier-routing logic ensures the right promotion target file is selected without forcing the user to remember tier semantics).

- **R10.** Hard refusal below corpus-size threshold. When the corpus has fewer than `config.json.insights.minCorpusSize` entries (default 10), the skill refuses with the literal sentinel chat line: *"Corpus too small for meaningful pattern detection (`{N}` entries; threshold `{threshold}`, configurable via `config.json.insights.minCorpusSize`). Run more tasks through `specflow:complete` and re-invoke `/insights` when the corpus has grown."* — where `{N}` is the actual entry count and `{threshold}` is the configured value. Refusal exits without writing the report file or appending to the runs.jsonl. Manual mode and cron-invoked mode refuse identically.
  - Trace: interview Round 5 — *hard refusal at corpus size below `config.json.insights.minCorpusSize` (default 10) with a structured chat line naming the current count, the threshold value, and the knob name; refusal exits without writing the report file*.
  - Serves goal: Outcome ("zero silent failures (refused invocation on under-threshold corpus ... surfaces explicitly with a structured reason)" — verbatim from goal); Driving value (avoids the failure mode where a low-signal report gets read by future-readers as evidence of "we tried but couldn't find anything").

- **R11.** Active report replace-in-place; execution log append-only. The active monthly report at `admin/insights/{YYYY-MM}-report.md` is overwritten on each within-month re-run (the report represents the *current* state of the month's pattern detection — a stale mid-month report has no value). Per-run metadata appends to `admin/insights/{YYYY-MM}-runs.jsonl` as one JSON object per line: `{run_id, started_at, completed_at, corpus_size, clusters_surfaced, promotions_proposed, promotions_accepted, promotions_rejected, next_suggested_run_at}`. The runs.jsonl file is never overwritten or edited; only appended.
  - Trace: interview Round 6 — *active report at `admin/insights/{YYYY-MM}-report.md` is replaced-in-place on within-month re-runs; per-run metadata appends to `admin/insights/{YYYY-MM}-runs.jsonl`*.
  - Serves goal: Audience (future-readers consume both the active report AND the execution log; replace-in-place keeps the report current; append-only keeps the audit trail intact).

- **R12.** Cross-month rollover. When the current month (`{YYYY-MM}` from system date) differs from the most recent month with a report file in `admin/insights/`, the skill writes a fresh `{YYYY-MM}-report.md` and a fresh `{YYYY-MM}-runs.jsonl`; the prior month's files stay archived in place (never deleted by this skill — `/prune`'s contract handles registry pruning, not insights pruning, but `/insights` itself never deletes). User-accepted promotion writes to `admin/rules/*` are independent of the monthly rollover and never reverted by this skill on any cadence.
  - Trace: interview Round 6 — *cross-month rollover produces fresh files (prior month's report archived in place); user-accepted promotion writes to `admin/rules/*` are independent and never reverted*.
  - Serves goal: Audience (future-readers can read prior months' reports as the historical narrative); Out-of-scope-at-goal-level (item 7 — editing or removing existing rules; the skill is additive only, never reverts).

- **R13.** `decision-log.md` read-only. The skill reads `admin/decision-log.md` as a secondary signal — when a cluster's contributing entries are also cited in `decision-log.md` entries' `Related` fields, the report's observation list cites those decision-log entries by date + title (read-only reference) so the user can audit the cross-link. The skill NEVER writes to `decision-log.md`. Per-task significant patterns elevate to `decision-log.md` via `specflow:complete`'s R6 (003-PRD); manual decision entries land via `specflow:decision`; cross-task abstractions are *rules*, not decisions.
  - Trace: interview Round 7 — *`/insights` reads `decision-log.md` as a secondary signal ... `/insights` NEVER proposes or writes new decision-log entries*.
  - Serves goal: Out-of-scope-at-goal-level (item 5 — writing to `decision-log.md`); Surgical Changes (don't touch `decision-log.md` from this skill because no R requires it).

- **R14.** Schema-stability check on read. Before running cluster detection, the skill validates that every `task-history.json` entry has the v1 contract field-set (per 003-complete-skill-prd Schema Appendix's 25 documented fields). If any entry is missing required fields (`id`, `lane_assigned`, `ai_assistance_level`, `blast_radius_outcome`, `what_didnt_work`, `regressions_caught`, `escaped_issues`, `addenda`, `superseded_by_retro`) the skill refuses with the structured chat line: *"Schema drift detected: `task-history.json` entry `{id}` missing required field `{name}`. The corpus must match the v1 contract documented in `003-complete-skill-prd.md`'s Schema Appendix before `/insights` can run. Re-fire `specflow:complete` for the affected entry."* Refusal exits without writing. **Cross-skill dependency:** R14 depends on `specflow:complete`'s Schema Appendix being the authoritative contract; if that schema evolves, this PRD's R14 + the v1 contract field-set list must be revised in lockstep. The dependency is explicit, not buried.
  - Trace: Gate 2 surgical-r1-f1 (concern) — *cross-skill schema dependency on `specflow:complete`'s 25-field v1 contract; reading the corpus without a schema check is implicit cross-skill creep*. Resolved at Gate 2 by adding the explicit dependency clause to R14.
  - Serves goal: Outcome ("zero silent failures (refused invocation on ... schema-gap ... surfaces explicitly with a structured reason)" — verbatim from goal).

- **R15.** Concurrent-trigger guard between manual and cron paths. When a scheduled cron invocation is in flight AND the user concurrently invokes `/insights` manually (or vice versa) for the same calendar month, the second invocation detects the in-flight run via a per-month lock file at `admin/scratch/insights-{YYYY-MM}.lock` (created by whichever path starts first; removed atomically on every exit path — successful write, refused exit, schema drift exit, threshold exit). The second invocation refuses with the literal sentinel chat line: *"`/insights` for `{YYYY-MM}` is in flight (started `{timestamp}`). Wait for it to complete, then re-invoke if you have additions."* Lock files older than 60 minutes are considered stale and ignored (cluster detection is fast; user-interactive accept-edit-reject prompts can extend a run's duration; 60 minutes covers a typical interactive monthly run with margin). Stale-lock-detected paths overwrite the lock and proceed.
  - Trace: Gate 2 review da-r1-f1 (concern) — *concurrent-trigger ambiguity: manual `/insights` and scheduled cron could race on the same monthly run; replace-in-place semantics make the race more dangerous than `specflow:complete`'s because both paths could produce divergent reports interleavingly*. Resolved at Gate 2 by adding R15 + AC-15.
  - Serves goal: Driving value (zero silent failures — the race surfaces explicitly via the in-flight lock-file check rather than producing a divergent report or duplicate runs.jsonl entries).

## Acceptance criteria

- **AC-1.** Running `/insights` on a corpus of ≥10 entries produces a report at `admin/insights/{YYYY-MM}-report.md`. The report's body contains a `## Field-shape clusters` section AND a `## Token-frequency clusters` section. Each section lists every cluster with `len(unique_contributing_ids) >= 3`; when zero clusters meet the threshold for a section, the section's body contains the literal sentinel: *"No clusters above the 3-observation threshold this run."* Sections are always present (even when empty); a report missing either section header is a failed render. Each cluster lists its contributing ids verbatim (the `id` field from `task-history.json`). Two consecutive runs on the same corpus produce byte-identical report bodies (deterministic clustering). (Verifies R1; empty-cluster handling extended at Gate 2 per goal-r1-f2.)

- **AC-2.** Each cluster in the report includes a `Contributing entries` field listing the unique `id` values from `task-history.json`; the list length is ≥3; within-entry repetitions of the cluster's pattern do NOT inflate the count (a single task whose `escaped_issues.descriptions` array contains the same n-gram three times contributes 1 to the cluster's contributing-ids count, not 3). When a token cluster nests inside a field-shape cluster, the report renders both: e.g. `Lane=green ∧ AI=full ∧ blast=high (4 entries) → token cluster "service worker race" (3 of 4 entries)`. (Verifies R2.)

- **AC-3.** No `semantic` cluster source appears in any v1 report. The report's schema (per the Schema Appendix below) reserves the `semantic` label as a documented future-reserved value, but every cluster object emitted by v1 has `cluster_source ∈ {"field-shape", "token-ngram"}`. A v1 run that emits a cluster with `cluster_source: "semantic"` is a failed run. (Verifies R3.)

- **AC-4.** Every promotion proposal in the report renders a full frontmatter + body block (matching the existing `admin/rules/{guidelines, non-negotiable}.md` format): triple-dashed frontmatter with `id`, `tier`, `paths`; body sections `**Rule:**`, `**Why:**`, `**On violation:**` (for non-negotiable; absent for guideline tier), `**Exceptions:**`. The `Why:` section contains one verbatim excerpt per contributing id, each excerpt is ≤140 characters, and each excerpt is drawn from the field that contributed the cluster (e.g. a token cluster on `what_didnt_work` quotes from `what_didnt_work`; an `escaped_issues`-driven cluster quotes from `escaped_issues.descriptions[i]`). A proposal whose `Why:` section is missing any contributing id's excerpt is a failed render. (Verifies R4.)

- **AC-5.** Each promotion proposal's auto-suggested `paths:` is the longest common prefix across the contributing entries' `scope` arrays, never broader. For a cluster with contributing scopes `["src/services/orders/file1.ts", "src/services/billing/file2.ts"]`, the proposed `paths:` is `["src/services/**/*.ts"]` (common prefix `src/services/` → `src/services/**/{ext}` glob); for a cluster with contributing scopes `["src/services/orders/file1.ts", "src/services/orders/file2.ts", "src/services/orders/file3.ts"]`, the proposed `paths:` is `["src/services/orders/**/*.ts"]`. The proposed `id:` is SCREAMING_SNAKE_CASE of the cluster's dominant n-gram (e.g. n-gram `service worker race` → `id: SERVICE_WORKER_RACE`). The user CAN widen the path at edit-time; the auto-suggestion never widens beyond the contributing scopes' common prefix on its own. (Verifies R5.)

- **AC-6.** The skill runs on two trigger paths: (a) manual `/insights [--feature {NNN-slug}]` from the CLI; (b) cron-invoked via the user's own scheduler passing the same arguments. No path inside the skill installs a scheduler, registers a cron, or writes to a system scheduler config. The skill reads `config.json.insights.cadence` and accepts only the four documented values (`weekly`, `monthly`, `quarterly`, `manual-only`); any other value refuses with a structured chat line: *"`config.json.insights.cadence` value `{value}` is not one of the documented values (`weekly | monthly | quarterly | manual-only`). Update the config and re-fire."* (Verifies R6.)

- **AC-7.** On every successful run, the skill emits a chat-line in the form: *"Next suggested `/insights` run: `{date}` (cadence `{cadence}`)."* — where `{date}` is `last_successful_run_at + cadence_interval` (cadence intervals: weekly = 7 days, monthly = 30 days, quarterly = 90 days; `manual-only` emits *"Next suggested `/insights` run: no scheduled cadence — invoke manually."*). The `last_successful_run_at` is read from the most recent record in any `admin/insights/*-runs.jsonl` file. The chat-line is informational only — the skill never blocks subsequent invocations on "too soon" or "too late" relative to the suggested date. (Verifies R7.)

- **AC-8.** Each promotion proposal surfaces three options to the user: `1` (accept-and-write), `2` (edit-and-write), `3` (reject). On option 1: the rule's frontmatter + body is appended to the target file (`admin/rules/guidelines.md` for guideline-tier proposals; `admin/rules/non-negotiable.md` for non-negotiable-tier proposals); a one-line entry is added to `admin/rules/glossary.md` under the matching section header. On option 2: the user edits any of `id`, `paths`, the `Rule:` body, or the `Why:` body; the skill re-validates frontmatter shape (id matches `^[A-Z][A-Z0-9_]*$`; paths is a non-empty array of glob strings); on validation pass, writes to the target rule file + glossary as in option 1. On option 3: no write to `admin/rules/*`; the proposal is recorded in the report's `## Proposed-rejected` section with `{rejection_timestamp, auto_suggested_id, contributing_ids[]}`. Empty input or any input not matching `1|2|3` re-prompts. The skill exits with a failed run if it auto-defaults (no human choice captured for any proposal). (Verifies R8.)

- **AC-9.** The skill cross-checks each proposal's auto-suggested `id` AND `paths` glob against `admin/rules/glossary.md`. When NO existing glossary entry matches the auto-suggested id OR the paths glob, the proposal targets `observation→guideline` (target file `admin/rules/guidelines.md`); when an existing guideline matches AND the cluster's contributing entries include ≥3 distinct entries citing post-promotion violations of that guideline (signalled by the contributing entries' `escaped_issues.descriptions[i]` or `what_didnt_work` substrings naming the existing rule's `id`), the proposal targets `guideline→non-negotiable` (target file `admin/rules/non-negotiable.md`). The proposal renders the tier transition explicitly in the report (e.g. `proposes: observation→guideline` or `proposes: guideline→non-negotiable`). A proposal whose tier line is absent or doesn't match one of the two transitions is a failed render. (Verifies R9.)

- **AC-10.** Running `/insights` on a corpus with fewer than `config.json.insights.minCorpusSize` entries (default 10) refuses with the literal sentinel chat line: *"Corpus too small for meaningful pattern detection (`{N}` entries; threshold `{threshold}`, configurable via `config.json.insights.minCorpusSize`). Run more tasks through `specflow:complete` and re-invoke `/insights` when the corpus has grown."* The skill exits without writing to `admin/insights/*-report.md` or `admin/insights/*-runs.jsonl`. Manual and cron-invoked modes produce identical refusal output. The threshold is read fresh from `config.json` on every invocation (no caching). (Verifies R10.)

- **AC-11.** Within-month re-runs replace `admin/insights/{YYYY-MM}-report.md` in place; the file's content reflects the most recent run only. The execution log at `admin/insights/{YYYY-MM}-runs.jsonl` is append-only — every successful run appends one JSON object per line: `{run_id, started_at, completed_at, corpus_size, clusters_surfaced, promotions_proposed, promotions_accepted, promotions_rejected, next_suggested_run_at}`. A run that overwrites or edits any line in the runs.jsonl is a failed run; a run that fails to append a record on successful completion is a failed run. The diff of `runs.jsonl` before vs after a successful run shows exactly one line added; the diff of `*-report.md` before vs after a within-month re-run shows the file replaced in full. (Verifies R11.)

- **AC-12.** When the system date's `YYYY-MM` differs from the most recent `*-report.md`'s `YYYY-MM` in `admin/insights/`, the skill writes a fresh `{YYYY-MM}-report.md` AND a fresh `{YYYY-MM}-runs.jsonl`. The prior month's files are NOT touched (no read, no write, no delete). User-accepted promotion writes to `admin/rules/*` from prior months remain in place; the skill never reverts a previously accepted promotion as part of cadence rollover. (Verifies R12.)

- **AC-13.** The skill reads `admin/decision-log.md` and, for each cluster, lists any decision-log entries whose `Related` field cites a contributing-id (substring match on the `id` field, accepting both `{NNN-slug}-T{N}` literal and prose mentions like `task T{N} of feature {NNN-slug}`). The cited entries appear in the report under a `Related decision-log entries` sub-section per cluster, with `{date, title}` per entry. The skill NEVER writes to `admin/decision-log.md`; a run that writes to `decision-log.md` (any append, edit, or new entry) is a failed run. (Verifies R13.)

- **AC-14.** Before cluster detection, the skill validates every `task-history.json` entry against the v1 contract field-set: required fields are `id`, `lane_assigned`, `ai_assistance_level`, `blast_radius_outcome`, `what_didnt_work`, `regressions_caught`, `escaped_issues`, `addenda`, `superseded_by_retro` (the 9 load-bearing fields for cluster detection per R1 + R2 + R4). When any entry is missing any required field, the skill refuses with the literal sentinel chat line: *"Schema drift detected: `task-history.json` entry `{id}` missing required field `{name}`. The corpus must match the v1 contract documented in `003-complete-skill-prd.md`'s Schema Appendix before `/insights` can run. Re-fire `specflow:complete` for the affected entry."* Exit without writing. **Schema dependency:** AC-14 depends on `003-complete-skill-prd.md`'s Schema Appendix being the authoritative contract; if that schema evolves, the v1 contract field-set list in R14 and this AC must be revised in lockstep. (Verifies R14.)

- **AC-15.** When a manual `/insights` invocation and a scheduled cron-invoked path race on the same calendar month, the second-to-start path detects the lock file at `admin/scratch/insights-{YYYY-MM}.lock` and refuses with the literal sentinel chat line: *"`/insights` for `{YYYY-MM}` is in flight (started `{timestamp}`). Wait for it to complete, then re-invoke if you have additions."* The lock file is created atomically by whichever path starts first AND removed atomically when that path exits (every exit path — successful write, schema drift refusal, threshold refusal, concurrent-trigger refusal). Lock files older than 60 minutes are ignored as stale (covers crashed-run cleanup AND extended interactive accept-edit-reject sessions); a path detecting a stale lock overwrites and proceeds. (Verifies R15.)

- **AC-16.** On every successful run, the skill emits a chat-line summary: *"`/insights` `{YYYY-MM}` run complete. Corpus `{N}` entries → `{C}` clusters → `{P}` promotions proposed (`{A}` accepted, `{R}` rejected). Report: `admin/insights/{YYYY-MM}-report.md`."* The five resolved tokens (N corpus size, C clusters surfaced, P proposals, A accepted count, R rejected count) carry the load-bearing signals for trend-analysis in subsequent runs. Failed runs (refusal exits) emit one of the five sentinel failure lines from R10 / R14 / R15 / R6 (config-value invalid) / R8 (auto-default detected); no silent exits. (Verifies the goal Outcome surface — every successful run produces an auditable summary; goal surface (d) — zero silent failures. Deferred-state token dropped at Gate 2 per goal-r1-f1: R8's three-option prompt forbids deferral; the orphan-AC counter was removed.)

```json
  "run_id": "{ULID or timestamp-shaped unique id}",
  "started_at": "{ISO-8601 UTC}",
  "completed_at": "{ISO-8601 UTC}",
  "trigger": "manual | cron",

  "minCorpusSize_used": 10,
  "cadence_used": "weekly | monthly | quarterly | manual-only",
  "clusters_surfaced": 0,
  "field_shape_clusters": 0,
  "token_ngram_clusters": 0,
  "semantic_clusters": 0,
  "promotions_proposed": 0,
  "promotions_accepted": 0,
  "promotions_rejected": 0,
  "next_suggested_run_at": "{ISO-8601 UTC | null when cadence=manual-only}",

}
```

## Schema appendix — report cluster object shape (v1)

Clusters in the report's body render with this minimum field-set (the report is markdown for human reading, but the cluster objects map 1:1 to the runs.jsonl counters):

```yaml
cluster_source: "field-shape" | "token-ngram" | "semantic"  # semantic reserved for v2
field_shape_tuple: {lane_assigned, ai_assistance_level, blast_radius_outcome}  # null for token-ngram clusters
token_ngram: "service worker race"  # null for field-shape clusters
contributing_ids: ["003-complete-skill-T1", "001-design-skill-T2", ...]  # length >= 3
contributing_excerpts: [{id: "...", excerpt: "...", source_field: "what_didnt_work"}]  # one per contributing id
proposes: "observation→guideline" | "guideline→non-negotiable" | null  # null when no promotion warranted
proposed_rule:  # null when proposes is null
  id: "SERVICE_WORKER_RACE"
  tier: "guideline" | "non-negotiable"
  paths: ["src/services/**/*.ts"]
  rule_body: "..."
  why_body: "..."  # composed from contributing_excerpts
  on_violation_body: "..."  # non-negotiable only
  exceptions_body: "..."
related_decision_log_entries: [{date, title}]  # may be empty
```

## Open questions

- **Stop-word list maintainability.** R1's fixed ~40-token stop-word list is hard-coded for v1. Open question: does the list ship as a SKILL-body constant (current plan) or as `admin/insights/stop-words.txt` so projects with non-English retro fields can extend it? Recommend SKILL-body constant for v1; surface `admin/insights/stop-words.txt` as a v2 enhancement when a non-English-corpus consumer surfaces. Confirm at implementation.
- **Stale-lock threshold for interactive runs.** R15's 60-minute stale-lock heuristic is calibrated for typical interactive accept-edit-reject sessions. Open question: should the threshold be a `config.json.insights.staleLockMinutes` knob? Recommend hard-coded 60 minutes for v1 (consistent with `specflow:complete`'s 30-minute hard-coded threshold pattern); surface as a knob if real consumers report stale-lock false-positives on long deliberation sessions.
- **Multi-month aggregation in v2.** v1 emits one report per month; v2 may aggregate across months for stronger trend signals (e.g. "the same pattern surfaced in three consecutive months — auto-promote the proposal to the top of the next month's report"). Open question: does v2 need a separate `/insights --rollup` invocation or extend the existing skill body? Defer to v2 PRD.
