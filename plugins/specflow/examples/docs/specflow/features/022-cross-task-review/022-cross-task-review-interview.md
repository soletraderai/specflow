## Original request

## Codebase context (pre-grilling)

- `plugins/specflow/skills/task/SKILL.md` Phase E (Gate 3 multi-agent debate, lines 320-444) currently runs the standard reviewer set (Simplicity / Surgical / Think-Before-Coding / Goal-Driven / Devil's Advocate / Codex when available) against the *individual tasks*. Per E.3 lens documentation: the reviewers fire per-task — Goal-Driven verifies forward coverage; Surgical verifies reverse traceability; Simplicity flags over-decomposition; Think-Before-Coding flags unstated assumptions; Devil's Advocate flags Gate-2-to-Gate-3 drift. **There is no whole-set lens** today.
- The whole-set lenses 022 introduces are **(1) coherence** (do tasks work together; flow correctly; not overlap; all trace back to PRD requirements + goal) and **(2) better arrangement** (could two tasks merge; could one split; is there a different ordering reducing dependency tangles; is there a missing task the per-task lens couldn't see). Both apply to the entire task list as a single artefact.
- 027-reviewer-context-isolation (Sprint 3, target v2.6.0) mandates fresh-context discipline for every reviewer. 022 explicitly cross-cuts 027: the cross-task reviewer **must not see the writer's chat** — it runs in a fresh context window with only the artefact (tasks.md + PRD + interview + Gate 2 manifest) as input. Per FEATURES.md § 022 trace: *"reviewer-never-sees-writer's-chat — pairs with 027"*. The manifest's `writer_id` ≠ `cross_task_reviewer_id` is the auditable signal.
- 029-single-context-task (shipped, commit b2e4ee9) § Implications #2 explicitly anticipates 022's "better arrangement" lens: *"are any tasks oversized? Should two tasks merge to share context? Should one split because its budget overflows?"* The cross-task reviewer reads each task's `context-budget-estimate` and surfaces budget-driven merge/split recommendations.
- 025-sprint-task-flagging (Sprint 2 — being landed alongside 022) writes `sprint-bucket: N` per task at synthesis time. 022's "better arrangement" lens may suggest re-bucketing — but per 025's R10 the field is read-only / re-synthesis is the legitimate edit path. 022's recommendations route through `specflow:scope-change`, not in-place edits.
- `knowledge/pocock-real-feature-build.md` § issue-sizing heuristic (the merging-too-small + PRD-to-issues judgment) is the load-bearing doctrine. Pocock's pattern: the reviewer reads the *whole task list* and asks "is this the right granularity?" — not "is each task internally consistent?" That's the gap 022 closes.
- `knowledge/medin-piv-loop.md` § drift detection (comparing PR back to ticket) is the analogy for 022's coherence lens: just as Medin's loop validates that the implementation traced back to the spec, 022 validates that the task-set traces back to the PRD as a whole, not just task-by-task.
- `knowledge/medin-parallel-agentic-playbook.md` § reviewer-never-sees-writer's-chat is the explicit framing for the 027 cross-cut — Medin's quote frames the discipline directly.
- The cross-task reviewer's findings live in the existing Gate 3 manifest (`debate-log/tasks-gate3/manifest.md`) alongside per-task findings. Schema needs to accommodate two finding types: per-task (existing) and whole-set (new). The orchestrator's pass/fail rules apply identically.
- 022's "Done when" criterion (per FEATURES.md): *"Gate 3 produces a whole-set finding (coherence + improvement) alongside per-task findings; the reviewer ran in a fresh context (manifest's `writer_id` ≠ `cross_task_reviewer_id`); worked example shows both a coherence issue AND a better-arrangement suggestion surfaced + resolved."*

## Goal (confirmed before grilling)

- **Outcome:** `specflow:task` Gate 3 (Phase E) gains a **whole-set cross-task review** alongside the existing per-task review. The cross-task reviewer applies two lenses to the entire task list as a single artefact: (1) **coherence** — tasks flow correctly, don't overlap, all trace back to PRD requirements + goal; (2) **better arrangement** — could two tasks merge, could one split, is the dependency ordering optimal, is there a missing task the per-task lens couldn't see. The reviewer runs in a fresh context window (per 027), with no exposure to the writer's chat that produced the task list.
- **Audience:** Engineer using the task skill (direct user — sees the cross-task finding alongside per-task findings in the Gate 3 manifest); admin reading the manifest for retro / audit; downstream skills consuming the manifest (sprint-skill 020, develop, test).
- **Success looks like:** A fresh feature run produces a Gate 3 manifest containing both per-task findings (existing shape) AND a whole-set cross-task finding section. The cross-task finding section names: (a) coherence-axis observations (or `findings: []`); (b) better-arrangement suggestions (or `findings: []`). The manifest's `writer_id` differs from the `cross_task_reviewer_id` (auditable fresh-context signal). A worked example fixture demonstrates both a surfaced coherence issue AND a better-arrangement suggestion being resolved.
- **Driving value:** Pocock's issue-sizing-heuristic and Medin's reviewer-isolation discipline both point to the same gap: the per-task lens can't see the *task-set as a whole*. Without a fresh-context whole-set pass, oversized tasks ship undetected, parallelism opportunities are missed, and the task-set drifts from the PRD's overall shape. 022 closes that gap with a single new reviewer slot inside the existing Gate 3 manifold.
- **Out of scope at the goal level:** Building 027-reviewer-context-isolation itself (it's a Sprint 3 dependency 022 *uses* — the fresh-context contract is consumed, not constructed); changing the per-task review behaviour; auto-applying cross-task suggestions (suggestions go to the manifest; the human decides whether to re-run synthesis or scope-change); cross-feature task batching (R5 of 025 keeps that out-of-scope).

## Rounds

### Round 1 — Reviewer composition
- **Q:** Is the cross-task review (a) a single new reviewer agent (e.g. `cross-task-reviewer`) added to the Gate 3 standard reviewer set, (b) the existing five reviewers re-applied with whole-set lenses alongside their per-task lenses, OR (c) a separate adversarial pass entirely (e.g. a Gate 3.5 between per-task review and tasks-Gate-3-close)?
- **AI's recommended answer:** (a) — a single new principle reviewer slot. — *Reasoning: existing five reviewers are sharp on per-task principles; re-tasking them with whole-set lenses dilutes their per-task sharpness and doubles dispatch surface. A dedicated cross-task reviewer is the chain-don't-absorb shape and mirrors the 028-edge-case-reviewer pattern (FEATURES.md § 028 — new reviewer, not re-tasked existing ones). Cited: skill-size-ceiling memory feedback; task/SKILL.md:343-359 (existing reviewers each carry one principle); FEATURES.md § 028 (precedent).*
- **User's answer:** confirmed (a).
- **Resolved:** cross-task review is implemented as a single new reviewer agent added to Gate 3's standard reviewer set, not as a re-application of existing reviewers and not as a separate gate. — flows into §Requirements (TBD ItemRef — agent role-def + Gate 3 dispatch list extension).

### Round 2 — Dispatch timing
- **Q:** When in Gate 3 does the cross-task reviewer fire? (a) Round 1 alongside per-task reviewers; (b) dedicated Round 0 BEFORE per-task reviewers; (c) dedicated Round 2.5 AFTER orchestrator response to per-task findings (reviews the post-revision tasks.md).
- **AI's recommended answer:** (a) — same Round 1 dispatch alongside per-task reviewers. — *Reasoning: existing E.3 already dispatches reviewers in parallel forked contexts; the per-task-vs-whole-set split is just about input shape, not dispatch ordering. Forked sub-agent discipline already gives fresh-context for free. Cited: task/SKILL.md:343-352; templates/orchestrator-pattern.md.*
- **User's answer:** rejected (a) — chose (c) Round 2.5 AFTER orchestrator response to per-task findings.
- **Resolved:** cross-task reviewer fires as a dedicated Round 2.5 AFTER the orchestrator's Round 2 response to per-task findings, reviewing the post-revision tasks.md. The clean-up sequence is: Round 1 (per-task fan-out) → Round 2 (orchestrator response + per-task revisions) → **Round 2.5 (cross-task reviewer)** → Round 3 (per-task sharpen on the final tasks.md). Coherence and arrangement issues are easier to spot once per-task issues aren't muddying the water. — flows into §Requirements (TBD ItemRef — Gate 3 phase ordering).

### Round 3 — Cross-task reviewer's own debate cycle
- **Q:** Does the cross-task reviewer get a three-round flow of its own (R1 fire → R2 orchestrator response + revisions → R3 sharpen), OR is it single-shot at Round 2.5 (one fire, orchestrator either accepts revisions or escalates, no sharpen pass)?
- **AI's recommended answer:** single-shot at Round 2.5. — *Reasoning: a three-round flow per reviewer is justified when reviewer and writer need to converge on a contested principle. Cross-task findings are arrangement-level suggestions — they're either taken (and per-task Round 3 catches downstream issues) or escalated. Cited: task/SKILL.md:382-386; skill-size-ceiling memory feedback.*
- **User's answer:** rejected — three rounds. After thinking through the benchmark/convergence question, decided to keep the standard three-round flow so that "after three rounds, a decision has to be made" applies uniformly. Single-shot risks decisions feeling rushed when reviewers and writer have differences of opinion that warrant a sharpen pass.
- **Resolved:** cross-task reviewer gets its own three-round mini-debate inside the Round 2.5 slot — cross-task R1 fire → orchestrator R2 response + revisions → cross-task R3 sharpen. After three cross-task rounds the existing Gate 3 convergence rules apply (passed / passed-with-revisions / passed-with-escalations). Overall Gate 3 sequence: Round 1 (per-task fire) → Round 2 (per-task orchestrator response) → Round 2.5 (cross-task three-round mini-debate) → Round 3 (per-task sharpen on the final tasks.md). — flows into §Requirements (TBD ItemRef — debate-cycle structure).

### Round 4 — Manifest schema

- **AI's recommended answer:** (b) dedicated section in the existing manifest. — *Reasoning: keeps Gate 3 manifest as the single readable artefact downstream skills already read; two-section structure makes per-task vs whole-set distinction visible without a second file. Cited: task/SKILL.md:328; specflow:brief one-file compose; 019 one-canonical-artefact pattern.*

Single manifest file, two parallel sections, one closing-decision footer covering both lenses. — flows into §Requirements (TBD ItemRef — manifest schema extension).

### Round 5 — Resolution mechanics
- **Q:** When the cross-task reviewer surfaces a finding (merge / split / reorder / add / drop), how does Round 2.5.2 (orchestrator response) apply revisions? (a) auto-apply all inline; (b) tiered (structural-only inline, coverage-changing requires user approval); (c) all require user approval; (d) feedback only, never auto-applied.
- **AI's recommended answer:** (b) tiered. — *Reasoning: matches existing per-task Round 2 mechanics; non-coverage-changing edits auto-apply, coverage-shifting routes to scope-change. Cited: task/SKILL.md:283-318 Phase D override-capture; skill-size-ceiling memory.*
- **User's answer:** rejected (a)/(b)/(c) — closer to (d) but with a twist. Cross-task review produces FEEDBACK ONLY. The feedback then goes to a separate fresh-context agent ("fresh set of eyes") that reads just the feedback, decides which pieces are necessary, and implements the changes if it judges the feedback warrants action. The original writer/orchestrator does NOT respond to or auto-apply cross-task findings.
- **Resolved:** cross-task review is **feedback-only**. Round 2.5 produces a feedback artefact (findings JSONs from the cross-task reviewer's three-round mini-debate). After Round 2.5 closes, a separate fresh-context **applier agent** reads the feedback in isolation, decides which findings are necessary on their own merits, and applies the accepted changes to tasks.md. The applier records its accept/reject decisions in the manifest's "Cross-task findings" section. The original writer never responds to cross-task findings; the applier replaces the orchestrator's role for the cross-task lens. This pairs with 027's reviewer-context-isolation discipline (the applier is also fresh-context — never sees the writer's chat AND never sees the cross-task reviewer's deliberation, only its written findings). — flows into §Requirements (TBD ItemRef — applier role + feedback-only contract).

### Round 6 — Applier identity
- **Q:** What kind of agent is the applier? (a) new dedicated agent type with its own role-def; (b) re-invocation of `specflow:task` in a fresh context; (c) orchestrator role re-played in a fresh forked context with applier prompt embedded; (d) generic forked sub-agent with applier prompt.
- **AI's recommended answer:** (a) dedicated agent type. — *Reasoning: applier has unique semantics; role-def captures auditably. Cited: existing admin/agents/standard pattern; 028-edge-case-reviewer's own role-def.*
- **User's answer:** rejected (a) — leaning (b) but with a twist. Re-invoke `specflow:task` in a fresh context window because the skill already knows how tasks are generated (synthesis schema, verify steps, coverage-matrix logic). But give it explicit context about what has taken place (the post-Round-2 tasks.md state) and the feedback (the cross-task findings) so it doesn't re-run Phase A/B/C/D from scratch — it enters a targeted "apply cross-task feedback" mode.
- **Resolved:** the applier is **`specflow:task` re-invoked in a fresh context window**, gated through a new mode/flag (e.g. `specflow:task --apply-cross-task-feedback {NNN-slug}`). When invoked this way, the skill skips Phases A/B/C/D and enters a new Phase (call it Phase F — "Cross-task feedback application") that takes three inputs: (1) the post-Round-2 `{NNN-slug}-tasks.md`; (2) the cross-task findings JSON from Round 2.5.1; (3) the PRD + interview for coverage-matrix validation. The applier reads the feedback, decides which findings to implement on their own merits, applies accepted changes to tasks.md, and records accept/reject decisions in the manifest's "Cross-task findings" section. Reusing `specflow:task` means the applier inherits the synthesis/verify logic for free; the fresh context window enforces the "no writer's chat" discipline (027). — flows into §Requirements (TBD ItemRef — `specflow:task --apply-cross-task-feedback` mode + Phase F contract).

### Round 7 — Applier's response surface + Round 2.5.3 sharpen interaction
- **Q:** When the applier disagrees with a cross-task finding, what's its response surface, and does that rejection survive the cross-task reviewer's Round 2.5.3 sharpen pass? (a) full three-round flow — applier records rejection with rationale, R3 sharpen may push back with new evidence, applier gets one more pass, unresolved escalate; (b) applier's accept/reject is final — no R3 sharpen; (c) sharpen fires but only as audit trail — applier's rejection stands.
- **AI's recommended answer:** (a) — full three-round flow with the applier playing the orchestrator's role. — *Reasoning: matches Round 3's resolution; sharpens are how reviewer and writer converge or escalate. Without (a), Round 3's "forced decision after three rounds" loses its teeth. Cited: Round 3 resolution; task/SKILL.md:382-386.*
- **User's answer:** confirmed (a). The more eyes we get on it the better; pass it off and then sharpen.
- **Resolved:** the applier records `rejected: <rationale>` per cross-task finding it declines. Round 2.5.3 cross-task reviewer reads (i) the post-applier tasks.md and (ii) the applier's accept/reject record, and may sharpen any rejection with new evidence or escalated severity. If the reviewer sharpens, the applier gets one more pass to either accept-with-revision or stand on the rejection. After that, unresolved cross-task findings escalate to the user via the manifest's Cross-task Escalations sub-section. The full Round 2.5 mini-debate is: 2.5.1 reviewer R1 fire → 2.5.2 applier responds + applies accepted → 2.5.3 reviewer sharpens → 2.5.4 applier final pass on sharpened findings → close. — flows into §Requirements (TBD ItemRef — applier response surface + sharpen mechanics).

Chain-don't-absorb: 022's interim becomes 027's foundation, not a parallel mechanism. — flows into §Requirements (TBD ItemRef — manifest schema agent_id fields + dispatch convention).

### Round 9 — Scope-change boundary
- **Q:** Some cross-task findings cross Gate 3's boundary into PRD-coverage territory (missing R coverage, merge-with-coverage-ambiguity, drop-with-coverage-hole). What does the applier do? (a) auto-route to `specflow:scope-change` and halt cross-task application; (b) auto-apply with PRD-side delta recorded; (c) escalate, no auto-routing; (d) tiered — pure-coverage-shift escalates, coverage-preserving auto-applies.
- **AI's recommended answer:** (a) auto-route to `specflow:scope-change`. — *Reasoning: PRD-coverage changes are scope-change territory by existing convention; the applier's job is to recognise out-of-Gate-3 scope and route correctly. (b) crosses Gate 2/3 boundary; (c) leaves user with manual-action manifest; (d) collapses to (a). Cited: existing scope-change skill; 029 Phase B.4 oversize-task routing.*
- **User's answer:** confirmed (a).
- **Resolved:** when the applier identifies a cross-task finding as PRD-coverage-changing (adds a missing task with a new R/AC anchor; merge-with-coverage-ambiguity; drop-with-coverage-hole), it flags the finding `scope-change-required` in the manifest, halts further cross-task application for that finding, and the gate closes with a manifest entry directing the user to run `specflow:scope-change`. The user resolves the PRD-coverage gap via scope-change, which then re-runs `specflow:task` from Phase A — at which point the new task list flows into Gate 3 fresh. Coverage-preserving cross-task findings (merge of two tasks both anchoring R5; split of a task into two sub-tasks both still anchoring R3; reorder within preserved dependency edges) auto-apply normally without scope-change routing. — flows into §Requirements (TBD ItemRef — applier scope-change routing + coverage-preserving auto-apply).

### Round 10 — 029 budget integration
- **Q:** Per FEATURES.md § 029 Implications #2, the better-arrangement lens explicitly checks oversize/merge/split. 029 R4 already auto-flags oversize tasks at synthesis. Does cross-task add real signal? (a) within-budget budget-awareness for merge/split signal; (b) ignore budget entirely; (c) defence-in-depth re-check; (d) budget-as-primary signal for merge/split.
- **AI's recommended answer:** (a) — within-budget budget-awareness. — *Reasoning: 029 R4 is the hard cap; cross-task is the soft signal for "could this be arranged better given the budgets?". Cited: 029 § Implications #2; FEATURES.md § 022.*
- **User's answer:** confirmed (a).
- **Resolved:** the cross-task reviewer reads each task's `context-budget-estimate` field (added by 029) and surfaces merge/split findings as a soft signal — e.g. "T3 (60K) and T4 (65K) are both within the 80K cap but operationally similar; consider whether they're really one concept" or "T7 is at 75K with weak coherence in its scope; consider whether it should split". 029 R4's hard-cap auto-flag continues to fire at synthesis time and never reaches Gate 3. Cross-task budget signal is one input among several (coherence and arrangement remain the load-bearing lenses); budget is not the primary driver. — flows into §Requirements (TBD ItemRef — cross-task reviewer reads budget; surfaces within-cap merge/split signal).

### Round 11 — Applicability threshold (when to skip)
- **Q:** Cross-task review adds latency to Gate 3. When does it fire? (a) always; (b) threshold-gated — skip if <3 tasks; (c) config-gated; (d) both threshold AND config-gated.
- **AI's recommended answer:** (b) threshold-gated at <3 tasks. — *Reasoning: 1-task list has nothing to compare; 2-task list is too small for coherence/arrangement signal; 3+ becomes meaningful. Skipping below threshold respects "don't add error handling for impossible scenarios" (Simplicity First). Cited: CORE_PRINCIPLES.md.*
- **User's answer:** confirmed (b). Real-world calibration: had a project with only 3 tasks; it was very small but coherence/arrangement just barely meaningful at that count.
- **Resolved:** cross-task review fires only when the synthesised task list has 3 or more tasks. Below that threshold (1 or 2 tasks), Round 2.5 is skipped entirely and Gate 3 proceeds straight from Round 2 (per-task orchestrator response) to Round 3 (per-task sharpen). The skipped case is recorded in the manifest's "Cross-task findings" section as `Cross-task review skipped: task count {N} below threshold (3)` so the audit trail shows the deliberate omission, not a silent miss. The threshold is a mechanical convention in `task/SKILL.md` Phase E.4.5 (the new sub-phase); not a config knob — keeps the surface tight per simplicity-first. — flows into §Requirements (TBD ItemRef — Phase E.4.5 threshold gate + manifest skipped-record).
