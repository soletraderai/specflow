# PRD interview — features/002-develop-skill

## Original request

> Write the spec for `specflow:develop`, the Phase 2 implementation orchestrator. The skill turns a closed-Gate-3 task list into shipped code via lane-based execution (green/yellow/red), runs Gates 4 and 5 of the adversarial review chain, and integrates the agent-teams plugin when present. The architectural shape is already locked in by `docs/PRD.md` Phase 2 + Appendix L; this PRD synthesises the implementation contract at the SKILL.md level.

## Codebase context (pre-grilling)

- **Architectural spec already exists.** `docs/PRD.md` § "Phase 2 — Development" (lines 181-202) and Appendix L (lines 653-687) document `specflow:develop` end-to-end: lane triage tuple, agent-teams as soft dep, Gates 4 + 5, dev plan ↔ PRD anchor convention, rule-violation auto-flagging. This PRD synthesis must align with that spec — re-litigating those decisions is out of scope per `docs/SESSION-HANDOFF.md` § "Architectural decisions — locked in".
- **Stub SKILL.md exists.** `skills/develop/SKILL.md` is a description-level stub with the v2 contract: `requires:` includes the tasks file + PRD + interview + agents directory + config + rules + environment; `produces:` includes Gate 4 + Gate 5 manifest paths + `task-history.json` + an orchestration scratch directory. Frontmatter shape is correct; the stub does not yet have the operational prompt body.
- **Sister Phase 1 orchestrators are operational.** `skills/prd/SKILL.md` (5 phases, Gate 2) and `skills/task/SKILL.md` (5 phases, Gate 3) both exhibit the orchestrator pattern this skill must follow: forked sub-agent contexts, file handoff via `admin/scratch/{orchestration-id}/`, command substitution for verbatim file injection. Calibration anchor: ~5K tokens of parent context across 3 sub-skill steps. `templates/orchestrator-pattern.md` is the must-read.
- **Gate 4 + Gate 5 are new debate manifests.** `docs/PRD.md` Appendix N1 names them; the multi-agent debate manifest pattern (Appendix N2) reuses the same shape as Gates 2 + 3 — five reviewers (DA + 4 principle reviewers) plus Codex when available, three rounds, Orchestrator closer.
- **Agent-teams plugin pattern.** `agent-teams` is a separate plugin (per `admin/environment.json.plugins`) that exposes `team-spawn`, `team-feature`, `team-status`, `team-review`, etc. The Phase 2 PRD treats it as a soft dependency: `specflow:develop` composes a team via the plugin when available, degrades to sequential agent invocation when absent. `config.json.teams` is the project-side composition declaration the plugin consumes.
- **Standard agents already operational.** Lifecycle agents (Orchestrator, Devil's Advocate, Verifier) and the four principle reviewers ship with the plugin and are copied to `admin/agents/standard/` at setup. `specflow:develop` reuses them for Gate 4 + Gate 5 (no new reviewer category).
- **Rules registry seeded.** `admin/rules/non-negotiable.md` and `admin/rules/guidelines.md` exist and are read by every skill's system prompt. `specflow:develop` reads the path-scoped slice for the touched files (per Appendix L1 step 1) and auto-flags out-of-scope violations as `misc-task`s (per Appendix L4).
- **`config.json.confidentialPaths`** is the rule-based confidentiality classifier — path globs decide red-lane qualification, never AI judgement. This is locked in per `docs/PRD.md` Phase 2 scope item 1 ("Confidentiality classification is rule-based ... not AI-rated").
- **`task-history.json` already populated by `specflow:task` Phase D overrides.** Phase 2's `specflow:develop` extends the schema with development-time fields (lane assigned, AI assistance level, time, what-worked, what-didn't, blast-radius outcome) per `docs/PRD.md` Phase 3 scope item 1. The schema lives at Appendix I3 (referenced from `skills/task/SKILL.md`).
- **Linear is a soft dependency.** `specflow:linear` (v1-shipped) handles Linear MCP integration. `specflow:develop` posts status updates through that surface when MCP is available; degrades to a chat-only summary when absent.
- **Worked example: 001-design-skill.** Calibration anchor for what a healthy interview + PRD + Gate 2 manifest looks like — neither rubber-stamping nor bikeshedding. This dogfood pass aims to match its shape.

## Goal (confirmed before grilling)

- **Outcome:** `specflow:develop` turns a closed-Gate-3 task list into shipped code via lane-based execution (green/yellow/red), running Gate 4 (plan vs tasks/PRD) and Gate 5 (code vs plan, with Codex when available) on the way. The skill is the implementation orchestrator that closes the gap between task creation and `specflow:test` — the place specflow gains its hands.
- **Audience:** Power Users (frontend / backend engineers with specflow installed) running implementation in their own repos. Secondary: Developer / API Consumer profiles supervising AI-led green-lane batches. Tertiary: stakeholders reviewing the PR with PRD-anchored plan commentary attached, who don't run the skill directly.
- **Success looks like:** invoking `specflow:develop {NNN-slug}` (or per-task `specflow:develop {NNN-slug} --task T3`) on a feature whose Gate 3 manifest is `passed` produces (a) a per-task plan with a PRD-requirement anchor, (b) a Gate 4 manifest closing with Orchestrator sign-off, (c) a code change set, (d) a Gate 5 manifest closing with Orchestrator sign-off (Codex finding when CLI present, Devil's Advocate fallback when absent), (e) a Verifier confirmation against the task's acceptance criteria, (f) a PR with the PRD anchor in the description, (g) a Linear status update (when MCP present), and (h) a `task-history.json` record extended with the development-time fields. Every artefact is co-located in `features/NNN-{slug}/` so a downstream agent can read the full implementation chain without cross-folder chase.
- **Driving value:** removes the failure mode where AI-led implementation drifts from the PRD intent because the implementer never re-anchored to the requirement; removes the failure mode where high-blast-radius or confidential changes ship under green-lane assumptions because lane assignment was AI-judged instead of rule-based; removes the failure mode where Codex's adversarial findings (the ones same-provider review misses) never reach the rules registry. Lane discipline + PRD anchor + cross-provider review are the three legs that make AFK-eligible green-lane execution trustworthy.
- **Out of scope at the goal level:** (1) building the agent-teams plugin itself — `specflow:develop` consumes it as a soft dependency, never embeds team-spawn logic; (2) autonomous re-planning when a task blocks (e.g. the plan was wrong, the dependency state changed mid-run) — the skill surfaces the block to the user, never silently re-plans (`specflow:scope-change` owns mid-development PRD revisions); (3) maintaining the agent index (that's `specflow:agent`'s job — Phase 2 sister skill); (4) cross-feature parallelism beyond what the agent-teams plugin's natural concurrency provides — running multiple `specflow:develop` invocations in parallel across different features is a Phase 3 concern gated on real reviewer pile-up; (5) replacing `specflow:test` — verification cadence inside the skill fires per-step, but the formal test plan + execution lives in `specflow:test`.

## Rounds

### Round 1 — Lane triage tuple: how is each axis scored?

- **Q:** Lane assignment uses a four-axis tuple (verifiability + blast radius + dependency state + confidentiality classification). Confidentiality is rule-based via `config.json.confidentialPaths` (locked in). What scores the other three axes — rule-based, AI-judged, or some mix? And what's the precedence rule when axes disagree?
- **AI's recommended answer:** Verifiability and blast radius are AI-judged from the task's `Scope` and `Acceptance` fields — but the judgement is structured (small enum: high/medium/low) and recorded in the plan with the cited evidence (which scope file, which acceptance line). Dependency state is mechanical — read from the tasks file's `Depends on:` field plus a check that all upstream tasks have `status: shipped` in `task-history.json`. Confidentiality stays rule-based per the locked-in decision. **Precedence:** ANY axis weak → at least Yellow; ANY axis Red-qualifying → Red. So lanes monotonically downgrade, never upgrade past their weakest axis. — *Reasoning: the goal's Driving value field calls out that lane assignment must not be silently AI-judged for the confidentiality axis. By analogy, the other axes can be AI-judged BUT must produce auditable evidence (the cited scope/acceptance lines), AND must downgrade-only on disagreement so a Red-qualifying axis is never overridden by a Green-qualifying one. This matches `docs/PRD.md` § Phase 2 scope item 1's "no issue escapes Red because the AI feels confident."*
- **User's answer:** confirmed, with one edit — the structured AI judgement for verifiability + blast radius must be re-checked at Gate 4 (the plan-vs-tasks reviewer reads the lane assignment and can flag a downgrade). If a reviewer flags the lane as too aggressive, the plan must re-lane and re-emit before code is written.
- **Resolved:** lane triage tuple = AI-judged verifiability + AI-judged blast radius + mechanical dependency state + rule-based confidentiality; precedence rule = monotonic downgrade (any weak axis takes the lane down); Gate 4 reviewers can flag and force a re-lane before code is written. — flows into §Requirements R3, R4, R5; AC AC-3, AC-4.

### Round 2 — Green-lane batching policy: how big is a batch, who signs off?

- **Q:** Green lane is "batched, AFK-eligible, single batched human sign-off per batch" per Appendix L2. What defines a batch — all green-qualifying tasks in a feature? A configurable size cap? And does the human sign-off happen before agents start, after the diff is ready, or both?
- **AI's recommended answer:** A batch = all green-qualifying tasks in the feature whose dependencies are all satisfied (mechanical: `Depends on:` chain resolves to either shipped tasks or other tasks in the same batch). Configurable cap via `config.json.develop.greenBatchCap` defaulting to 5 tasks per batch — projects with smaller PR-review tolerance can lower it. Human sign-off fires **once, after the full batch's diff is assembled**, not per-task — that's the AFK-eligibility win. Agents start without per-task sign-off, but every Green-lane task individually emits a plan, runs Gate 4, runs Gate 5, and runs Verifier; the batched sign-off is on the assembled PR description summarising every per-task gate outcome. If any task in the batch fails Gate 4, Gate 5, or Verifier, the batch pauses at that boundary and surfaces the failure — the user sees the partial batch and decides resume / abort / drop the failing task. — *Reasoning: the goal's Outcome calls out AFK-eligible green-lane batches; the goal's Out-of-scope-at-goal-level rules out autonomous re-planning, so the failing-task pause must surface to the user not silently retry. Default cap of 5 is conservative — `docs/PRD.md` Phase 2 scope item 1's 60/30/10 ratio target on a 10-task feature implies 6 green tasks, so 5-per-batch keeps batches small enough to review without making 10-task features two batches by default.*
- **User's answer:** edit — the cap default should be 3, not 5. PR review fatigue kicks in faster than people expect, and a 3-task batch is the size where a reviewer can still catch a pattern-level concern without skimming. Keep the configurability so projects with strong CI signal can raise it.
- **Resolved:** Green-lane batch = all green-qualifying tasks with satisfied dependencies; configurable cap via `config.json.develop.greenBatchCap` defaulting to 3 (lowered from 5); single human sign-off after the assembled PR diff; per-task gates fire individually; on per-task gate failure the batch pauses at that boundary and surfaces partial state for user decision. — flows into §Requirements R6, R7; AC AC-5.

### Round 3 — Agent-teams integration: when does the plugin get consulted, and what's the degraded path?

- **Q:** Per Phase 2 scope item 4 the agent-teams plugin is a soft dependency. When does `specflow:develop` consult it (every task, only multi-agent tasks, only when `config.json.teams` declares a team for the touched scope)? And what does "degrades to sequential agent invocation if absent" look like operationally?
- **AI's recommended answer:** Consult the plugin at lane-assignment time (Step 2 of the skill flow), once per task. The decision: if the lane is Green or Yellow AND the task's scope touches files matching a `config.json.teams[].scope` glob AND the agent-teams plugin is detected in `admin/environment.json.plugins`, invoke `team-spawn` with the matching team preset. Otherwise, pick one specialised agent from the indexed set per Step 2 of Appendix L1. Degraded path when the plugin is absent: `specflow:develop` runs each task's implementation step with one specialised agent (chosen by stack match — e.g. `frontend-developer` for `apps/web/**` files) sequentially. Red lane never spawns a team — Red is human-led, AI assists on bounded subtasks only, so multi-agent composition would defeat the safety property. Red-lane tasks always pick a single agent regardless of team config. — *Reasoning: the goal's Out-of-scope-at-goal-level forbids cross-feature parallelism beyond the plugin's natural concurrency, and Appendix L2's Red-lane semantics ("AI assists on bounded subtasks only") rule out team-spawning for Red. Consulting the plugin once at lane-assignment matches the Goal-Driven principle of structured decision points (one call site, audit-able) instead of scattering team-spawn checks throughout the implementation loop.*
- **User's answer:** confirmed.
- **Resolved:** agent-teams consulted once per task at lane-assignment time; team-spawn fires only when (lane is Green or Yellow) AND (task scope matches a `config.json.teams[].scope` glob) AND (plugin detected); degraded path = sequential single-specialist invocation chosen by stack match; Red lane never spawns a team. — flows into §Requirements R8, R9; AC AC-6.

### Round 4 — Gate 4 reviewer set: same five as Gate 2/3, or specialised?

- **Q:** Gate 4 reviews the plan against the tasks + PRD anchor. Does it use the standard five-reviewer set (DA + four principle reviewers) the same way Gates 2 and 3 do, or are some reviewers more load-bearing here, or is there a Gate-4-specific reviewer that doesn't show up at other gates?
- **AI's recommended answer:** Same five reviewers, but with explicit lens emphasis: Think-Before-Coding is load-bearing at Gate 4 (the plan is where unstated implementation assumptions surface); Goal-Driven Reviewer cross-checks the PRD anchor against the cited requirement ID; Surgical Reviewer flags scope drift between the task's `Scope` field and the plan's listed file paths; Simplicity Reviewer flags premature abstraction or speculative configurability in the plan; Devil's Advocate flags cross-artefact ambiguity (e.g. plan references a config flag the PRD doesn't mention). No Gate-4-specific reviewer — the specflow agent set is "principle-aligned reviewers" by `CORE_PRINCIPLES.md` and the set scales 1:1 with the principle list, so adding a Gate-4-specialist reviewer would break that invariant. Codex when available joins as a sixth reviewer at Gate 4 only when `admin/environment.json.cli.codex.available` AND `config.json.develop.codexAtGate4` is true (default false — Gate 4 is plan-level, Codex's strength is code-level review at Gate 5). — *Reasoning: the goal's Audience names Power Users, and the standard reviewer set is the calibration anchor those users have already learned at Gates 2 + 3 — introducing a Gate-4-specific reviewer would break consistency and force the user to relearn lens-distinctness. Reuse + lens emphasis is simpler than new reviewer types. The Codex-at-Gate-4 opt-in flag is Think-Before-Coding's "name the alternative" applied here: Gate 5 is the load-bearing Codex gate, but consumers building agentic systems may want plan-level Codex review too — name the flag, default off.*
- **User's answer:** confirmed, but add: when Gate 4 fires a `block` finding that names the lane assignment as too aggressive (per Round 1's edit), the manifest's closing decision must record the re-lane and the plan must be re-emitted before Gate 4 can close. This is the operational instance of the "Gate 4 reviewers can flag and force a re-lane" rule.
- **Resolved:** Gate 4 uses the same five-reviewer set as Gates 2 + 3 (DA + four principle reviewers); Think-Before-Coding + Goal-Driven are load-bearing at this gate; Codex joins as sixth reviewer only with explicit opt-in via `config.json.develop.codexAtGate4` (default false); `block` findings naming lane assignment force a re-lane + plan re-emission before Gate 4 can close. — flows into §Requirements R10, R11; AC AC-7, AC-8.

### Round 5 — Gate 5 Codex flow: what happens when Codex is absent?

- **Q:** Gate 5 reviews code against the plan; Codex is the load-bearing reviewer per Appendix L5 ("if Codex is in the inventory, it's the standing adversarial reviewer for Gate 5"). What's the flow when Codex isn't installed — Devil's Advocate alone, or Devil's Advocate plus the four principle reviewers, or skip Gate 5 entirely with a warning?
- **AI's recommended answer:** Gate 5 always fires — never skipped, never warning-only. When Codex is absent, the standard five-reviewer set (DA + four principle reviewers) runs Gate 5 the same way it runs Gates 2-4, with Goal-Driven Reviewer load-bearing (code-vs-plan acceptance is its lens) and Devil's Advocate covering cross-provider concerns DA can spot in same-provider review. The manifest's Codex section is replaced with a one-line note: *"Codex not detected — same-provider review only. Cross-provider findings may be missed; install Codex CLI for full Gate 5 coverage."* When Codex is present, it joins as a sixth reviewer; findings Codex catches that the five other reviewers missed get auto-promoted to `admin/rules/guidelines.md` (per Appendix L5) — that promotion lands as a `misc-task` proposing the rule, not a direct write, so the human reviews before the rule lands. — *Reasoning: the goal's Driving value field names "removes the failure mode where Codex's adversarial findings never reach the rules registry" — that means Codex IS the load-bearing reviewer when present, and the system has to behave gracefully when it's absent without falsely advertising coverage. The same-provider degraded path matches the soft-dependency pattern from Round 3. The misc-task-proposing-the-rule shape is the locked-in Phase 3 self-evolution flow (`docs/PRD.md` Phase 3 scope item 8: "Repeated misc-tasks of the same shape get promoted: observation → guideline → non-negotiable, with human sign-off at each promotion").*
- **User's answer:** confirmed.
- **Resolved:** Gate 5 always fires (never skipped); standard five-reviewer set runs when Codex absent with explicit one-line manifest note declaring degraded coverage; Codex joins as sixth reviewer when present; Codex-only findings auto-promote via `misc-task` to `admin/rules/guidelines.md` (human reviews before rule lands). — flows into §Requirements R12, R13; AC AC-9, AC-10.

### Round 6 — Linear status integration: which transitions, and who owns the timing?

- **Q:** Per Appendix L1 step 7 the skill updates Linear status; per the SKILL.md trigger list, the skill can also be auto-invoked when a Linear task moves to "In Progress". Which Linear transitions does the skill drive, and who decides the timing — the skill, the user, the Linear webhook?
- **AI's recommended answer:** The skill drives three transitions: (a) "Backlog/Todo → In Progress" when the user manually invokes `specflow:develop {NNN-slug} --task T3` on a task that isn't already In Progress (skill fires the transition before Step 1 context primer); (b) "In Progress → In Review" when the per-task PR opens (skill fires the transition after Verifier confirms acceptance and the PR is opened); (c) NO automatic "In Review → Done" — that's a human merge decision, never the skill's. Auto-invocation when the user moves a task to In Progress in Linear (the trigger list option) lands the skill at Step 1 of the same flow, just initiated from the Linear UI instead of the CLI. When the Linear MCP is absent, the skill prints the status update as a chat-only line and continues — this is the soft-dependency degraded path again. — *Reasoning: the goal's Success-looks-like names "Linear status update (when MCP present)" as one of the eight success surfaces, so the skill is responsible for driving the transitions, but the human always owns the merge decision per `docs/PRD.md` § "Resolved decisions" line on human-to-human handoffs being out-of-band. Three transitions cover the implementation lifecycle the skill is responsible for; merge-to-Done belongs to whoever reviews the PR.*
- **User's answer:** confirmed.
- **Resolved:** skill drives three Linear transitions (Backlog/Todo → In Progress on invocation, In Progress → In Review on PR open, never auto-Done); auto-invocation from Linear UI lands at Step 1 of the same flow; absent MCP → chat-only status line + continue. — flows into §Requirements R14; AC AC-11.

### Round 7 — Failure mode when verifier rejects: re-implement, escalate, or surface?

- **Q:** Verifier runs at completion vs the original task acceptance criteria (Step 6 of Appendix L1). What happens when Verifier rejects — does the skill loop back to plan emission, escalate to the user, or surface the failure with a structured payload?
- **AI's recommended answer:** Surface with structured payload. When Verifier rejects, the skill writes a structured failure payload to `admin/scratch/{orchestration-id}/verifier-failure-{task-id}.json` capturing (a) which AC failed, (b) what the verification check found, (c) the diff section the failure points to, (d) the agent that produced the diff. The skill then asks the user: *"Verifier rejected T{N} on {AC-id}. The check found {summary}. Choose: (1) re-implement (skill loops back to Step 4 implementation with the failure payload as additional context), (2) re-plan (skill loops back to Step 3 plan emission — this re-fires Gate 4), (3) abort the task and surface to scope-change (the AC may itself be wrong), (4) accept the failure and ship anyway (requires explicit confirmation, recorded as a decision-log entry)."* The skill never silently re-implements — auto-loop-on-rejection is a known failure mode where AI burns tokens on confidently-wrong fixes. — *Reasoning: the goal's Out-of-scope-at-goal-level explicitly rules out autonomous re-planning, so re-plan-on-Verifier-rejection has to be user-elected. Structured failure payload matches the orchestrator pattern (file handoff between steps, distilled not raw). Option (4) "accept and ship" exists because some AC failures are PRD-level mistakes the user will catch via the structured payload — not having an escape hatch would force scope-change for trivial AC tweaks.*
- **User's answer:** confirmed.
- **Resolved:** Verifier rejection produces structured failure payload at `admin/scratch/{orchestration-id}/verifier-failure-{task-id}.json`; user picks from four options (re-implement / re-plan / abort-to-scope-change / accept-and-ship-with-decision-log); skill never auto-loops. — flows into §Requirements R15; AC AC-12.

## Topics not discussed

- *Autonomous re-planning when blocks happen.* Out of scope per goal's "Out of scope at the goal level" line on autonomous re-planning. When a task blocks mid-implementation (e.g. dependency state changed, plan was wrong, an unstated assumption surfaces), the skill surfaces the block to the user and waits — never silently re-plans. `specflow:scope-change` (Phase 3) owns mid-development PRD revisions; `specflow:develop` is a consumer of that flow, not a competitor.
- *Cross-feature parallel batched green-lane execution beyond the agent-teams plugin's natural concurrency.* Out of scope per goal's "Out of scope at the goal level". Running multiple `specflow:develop` invocations in parallel across different features is a Phase 3 concern gated on real reviewer pile-up AND `panic` having shipped (per `docs/PRD.md` § "Items still deferred"). v1 of `specflow:develop` runs one feature's batch at a time; the agent-teams plugin's per-team concurrency is the only parallelism inside a single batch.
- *Cost / budget controls for long-running green-lane batches.* `specflow:budget` already tracks per-skill token consumption; `specflow:develop` self-reports at completion via `skill-invocations.jsonl` like every other skill. Budget caps mid-run (e.g. abort the batch when the orchestration crosses $X) are deferred — `simplify` already has the bounded-loop pattern, but porting it to `specflow:develop` is a v2 concern when consumers report runaway batches.
