# specflow:develop — lane-based implementation orchestrator

## Vision

`specflow:develop` is the implementation orchestrator that turns a closed-Gate-3 task list into shipped code via lane-based execution (green/yellow/red), running Gate 4 (plan vs tasks/PRD) and Gate 5 (code vs plan, with Codex when available) on the way. Power Users running implementation in their own repos get AFK-eligible green-lane batches they can trust, real-time HITL pairing on yellow-lane tasks, and human-led red-lane tasks where AI assists only on bounded subtasks. Every task lands a plan with a PRD-requirement anchor, every code change set lands a debate manifest with Orchestrator sign-off, and every Verifier confirmation lands against the original acceptance criteria. Stakeholders reviewing the PR see the PRD anchor in the description without ever invoking the skill, and Linear stays in sync with implementation state without a human babysitting status transitions. The skill is the place specflow gains its hands — and the lane discipline + PRD anchor + cross-provider Codex review are the three legs that make AFK-eligible green-lane execution trustworthy.

## Problem

Phase 1 of specflow ships fifteen operational skills covering brief through tasks (Gates 1-3), but the gap between a closed Gate 3 task list and a shipped change set is currently un-orchestrated — implementation runs ad-hoc, with no enforced PRD anchor on the plan, no enforced lane discipline on the change-set's blast radius, and no enforced cross-provider review on the diff. The failure modes that result are well-known: (a) AI-led implementation drifts from the PRD intent because the implementer never re-anchored to the requirement; (b) high-blast-radius or confidential changes ship under green-lane assumptions because lane assignment is AI-judged instead of rule-based; (c) Codex's adversarial findings — the ones same-provider review systematically misses — never reach the rules registry, so the system never learns from cross-provider catches; (d) Verifier rejections trigger silent retry loops where the AI burns tokens on confidently-wrong fixes instead of surfacing the failure to a human.

The fix is structural: a single skill that owns implementation orchestration end-to-end with rule-based lane assignment for the confidentiality axis, structured AI-judged + auditable lane assignment for the verifiability and blast-radius axes, mechanical dependency-state checks, two adversarial review gates with the same multi-agent debate manifest pattern Phase 1 already proved, and a hard rule that Verifier rejections surface to the user with a structured failure payload — never auto-loop. The skill consumes the agent-teams plugin as a soft dependency for team composition and degrades to sequential single-specialist invocation when the plugin is absent.

## Goals

- Per-task plan emission with a PRD-requirement anchor — every plan starts with the *"We're doing X because of PRD requirement Y. This aligns with Z."* convention before the technical plan, so reviewers and PR readers get PRD context for free.
- Lane assignment via the four-axis triage tuple (verifiability + blast radius + dependency state + confidentiality) with a monotonic-downgrade precedence rule — any weak axis takes the lane down, no axis can override another upward, and a Red-qualifying confidentiality classification is never overridden by AI judgement on the other axes.
- Green-lane batched execution with a single human sign-off after the assembled PR diff (not per-task), capped at 3 tasks per batch by default for PR-review fatigue.
- Gate 4 (plan vs tasks + PRD anchor) and Gate 5 (code vs plan) run the same five-reviewer multi-agent debate manifest pattern as Gates 2 + 3, with Codex joining as a sixth reviewer at Gate 5 when available (and at Gate 4 only with explicit opt-in).
- Verifier confirmation against the original task acceptance criteria, with structured failure payload + four user-elected options on rejection (re-implement / re-plan / abort-to-scope-change / accept-and-ship-with-decision-log) — never auto-loop.
- Linear status transitions driven by the skill (Backlog/Todo → In Progress on invocation, In Progress → In Review on PR open) with no auto-Done — the human owns the merge decision.
- Codex-only findings at Gate 5 auto-promote to `admin/rules/guidelines.md` via a `misc-task` proposing the rule (per Phase 3's observation → guideline → non-negotiable promotion flow), so the system learns from cross-provider catches without overwriting the rules file directly.
- Co-located artefacts: every plan, debate manifest, verification record, and orchestration scratch file lives under `features/NNN-{slug}/` (or `admin/scratch/{orchestration-id}/`), so a downstream skill can read the full implementation chain without cross-folder chase.

## Non-goals

- **Building the agent-teams plugin itself.** `specflow:develop` consumes it as a soft dependency, never embeds team-spawn logic. Composition logic lives in the plugin; the skill calls `team-spawn` when conditions match and falls back to sequential single-specialist invocation when the plugin is absent.
- **Autonomous re-planning when a task blocks.** When a task blocks mid-implementation, the skill surfaces the block to the user and waits — never silently re-plans. `specflow:scope-change` (Phase 3) owns mid-development PRD revisions; `specflow:develop` is a consumer of that flow.
- **Maintaining the agent index.** That's `specflow:agent`'s job (Phase 2 sister skill). `specflow:develop` reads the index from `admin/environment.json` and `admin/agents/specialised/`; it never writes them.
- **Cross-feature parallelism beyond what the agent-teams plugin's natural concurrency provides.** v1 of `specflow:develop` runs one feature's batch at a time. Multi-feature parallelism is a Phase 3 concern gated on real reviewer pile-up AND `panic` having shipped.
- **Replacing `specflow:test`.** Verification cadence inside the skill fires per-step (Verifier at Step 6, gates at Steps 4 and 5), but the formal test plan + execution lives in `specflow:test`. Downstream of `specflow:develop`, the consumer typically runs `specflow:test {NNN-slug}` to capture the test plan against the shipped change set.
- **Mid-run budget caps.** `specflow:budget` tracks per-skill token consumption via the standard `skill-invocations.jsonl` self-report, but aborting a batch when an orchestration crosses a token threshold is deferred. The bounded-loop pattern from `simplify` could be ported here in a future version if consumers report runaway batches.

## Users

- **Power User (per `admin/profiles.json`)** — frontend / backend engineers running implementation in their own repos. They invoke `specflow:develop` after Gate 3 closes, supervise green-lane batches AFK, pair with the skill on yellow-lane tasks, and lead red-lane tasks themselves with AI assisting on bounded subtasks. They need the PRD anchor in every plan, the lane assignment to be auditable, and the Verifier rejection surface to be loud not silent.
- **Developer / API Consumer (per `admin/profiles.json`)** — engineers supervising AI-led green-lane batches. They review the assembled PR diff once per batch (not per task), trusting that per-task gates fired against each component. They need the PR description's per-task gate-outcome summary so they can spot-check rather than re-derive every change.
- **Secondary: stakeholders reviewing the PR** — product managers, reviewers, ops. They consume the PR description in GitHub / equivalent. They benefit from the PRD anchor without invoking the skill: every PR description starts with the same `"We're doing X because of PRD requirement Y. This aligns with Z."` line that opens every plan, so PR review doesn't require holding the PRD in mind.

## Requirements

- **R1.** Pre-flight chain check. `specflow:develop` reads `features/NNN-{slug}/{NNN-slug}-tasks.md`, `{NNN-slug}-prd.md`, `{NNN-slug}-interview.md`, and `debate-log/tasks-gate3/manifest.md`. The skill refuses to run if Gate 3's manifest is missing or the closing decision is `failed`. Tasks not closed at Gate 3 are imported-problem candidates per the Phase 1 task skill's pre-flight rule.
  - Trace: codebase context (pre-grilling) bullet — *PRD spec already exists; Gate 3 manifest is locked-in pre-condition for `specflow:develop`*. No grilling round was needed because the chain check is inherited from the locked-in adversarial-review-chain decision (`docs/PRD.md` Appendix N1).
  - Serves goal: Outcome (skill operates on a closed-Gate-3 task list).

- **R2.** Per-task or per-feature invocation. `specflow:develop {NNN-slug}` runs every Green-qualifying task in the feature as a batch, then walks Yellow tasks one at a time, then surfaces Red tasks for human-led handling. `specflow:develop {NNN-slug} --task T{N}` runs one specific task regardless of lane.
  - Trace: codebase context (pre-grilling) bullet — *Stub SKILL.md exists with the v2 contract*. Trigger semantics inherited from the stub frontmatter and Appendix L1.
  - Serves goal: Outcome (lane-based execution with batch-per-feature default + per-task override).

- **R3.** Lane triage tuple — four axes. Lane assigned by tuple (verifiability + blast radius + dependency state + confidentiality). Verifiability and blast radius are AI-judged from the task's `Scope` and `Acceptance` fields, recorded in the plan with cited evidence (which scope file, which acceptance line). Dependency state is mechanical — read from the tasks file's `Depends on:` field plus a check that all upstream tasks have `status: shipped` in `task-history.json`. Confidentiality is rule-based via `config.json.confidentialPaths` glob match — never AI-rated.
  - Trace: interview Round 1 — *lane triage tuple = AI-judged verifiability + AI-judged blast radius + mechanical dependency state + rule-based confidentiality*.
  - Serves goal: Driving value (lane assignment must not be silently AI-judged for the confidentiality axis; auditable evidence required for the AI-judged axes).

- **R4.** Monotonic-downgrade precedence. ANY axis weak → at least Yellow; ANY axis Red-qualifying → Red. Lanes monotonically downgrade — a Red-qualifying axis is never overridden by Green-qualifying ones. Confidentiality Red qualification specifically can never be overridden, even by user request mid-run.
  - Trace: interview Round 1 — *monotonic downgrade (any weak axis takes the lane down)*.
  - Serves goal: Driving value ("no issue escapes Red because the AI feels confident", per `docs/PRD.md` Phase 2 scope item 1).

- **R5.** Gate 4 reviewer-driven lane re-check (catch-all path). The Gate 4 manifest's reviewer set may flag a `block` finding naming the lane assignment as too aggressive (e.g. a Goal-Driven or Surgical Reviewer notices a scope-vs-plan mismatch the mechanical recheck (R5.1) missed). When such a finding lands and is accepted in Round 2, the plan must be re-emitted with the corrected lane and Gate 4 must re-fire before code is written. Re-lane events are recorded in the Gate 4 manifest's closing decision. R5 is the catch-all for lane mistakes that the structured pre-Gate-4 recheck (R5.1) does not catch; reviewers do not need a dedicated lane-checking lens because R5.1 carries the load-bearing recheck mechanically.
  - Trace: interview Round 1 (edited) + Round 4 (edited) — *Gate 4 reviewers can flag and force a re-lane before code is written*. Revised at Gate 2 per tbc-r1-f1: clarified as the catch-all path on top of the new mechanical recheck R5.1.
  - Serves goal: Outcome (Gate 4 is the structural check that catches AI-judged lane mistakes before they ship).

- **R5.1.** Mechanical pre-Gate-4 lane recheck. Before the Gate 4 manifest opens, the skill mechanically re-evaluates the four-axis tuple given the plan's emitted content: (a) compare plan's actual file count against the task scope's claimed file count — if the plan touches >1.5x the scope's claimed file count, downgrade blast radius one step; (b) compare the plan's listed modules against the task's `Scope` modules — if the plan reveals new modules, downgrade blast radius one step; (c) re-run the `config.json.confidentialPaths` glob match against the plan's listed file paths — confidential-path matches in the plan that weren't in the original task scope force the lane to Red. The mechanical recheck is structured (no reviewer judgement) and runs unconditionally. If the mechanical recheck downgrades the lane, the plan is re-emitted with the corrected lane before Gate 4 opens.
  - Trace: Gate 2 review tbc-r1-f1 (block) — *missing tradeoff articulation; lane-recheck mechanism cannot rely on reviewer judgement because no reviewer's lens natively owns lane-checking*.
  - Serves goal: Driving value (lane assignment must be auditable AND mechanically enforced for the AI-judged axes; mechanical recheck catches the cases where the plan reveals more than the task scope claimed).

- **R6.** Green-lane batching policy. A Green batch = all green-qualifying tasks in the feature whose dependencies are all satisfied (mechanical: `Depends on:` chain resolves to either shipped tasks or other tasks in the same batch). The cap is configurable via `config.json.develop.greenBatchCap` defaulting to 3 tasks per batch.
  - Trace: interview Round 2 (edited) — *configurable cap via `config.json.develop.greenBatchCap` defaulting to 3*.
  - Serves goal: Outcome (AFK-eligible green-lane batches sized for review without fatigue).

- **R7.** Single batched human sign-off + per-task gate failures pause the batch. Green-lane execution fires per-task plan emission, Gate 4, agent execution, Gate 5, and Verifier individually, but the human sign-off happens once on the assembled PR diff after every per-task gate has closed. If any per-task Gate 4, Gate 5, or Verifier check fails, the batch pauses at that boundary and surfaces the partial state — the user picks resume / abort / drop the failing task.
  - Trace: interview Round 2 — *single human sign-off after the assembled PR diff; per-task gates fire individually; on per-task gate failure the batch pauses*.
  - Serves goal: Driving value (AFK-eligibility without losing per-task verification rigor).

- **R8.** Agent-teams plugin consultation at lane-assignment time. `specflow:develop` consults the agent-teams plugin once per task at lane-assignment time (Step 2 of the skill flow). If the lane is Green or Yellow AND the task's scope touches files matching a `config.json.teams[].scope` glob AND the agent-teams plugin is detected in `admin/environment.json.plugins`, the skill invokes `team-spawn` with the matching team preset. Otherwise, the skill picks one specialised agent from the indexed set per stack match. **Present-but-failing path:** when the agent-teams plugin is detected but `team-spawn` returns an error (preset name unmatched, plugin version-skew, plugin internal error), `specflow:develop` falls back to sequential single-specialist invocation per R9's stack-match logic AND surfaces the failure to the user as a chat-line warning (e.g. `[agent-teams: team-spawn failed for preset {name} — falling back to single-specialist {agent}]`). The fallback does NOT abort the task; the user can intervene if needed.
  - Trace: interview Round 3 — *agent-teams consulted once per task at lane-assignment time; team-spawn fires only when (lane is Green or Yellow) AND (task scope matches a `config.json.teams[].scope` glob) AND (plugin detected)*. Extended at Gate 2 per da-r1-f1: present-but-failing path follows the Phase 1 `specflow:design` Codex-degraded-path precedent for loud-fallback shape.
  - Serves goal: Outcome (clean integration with the agent-teams plugin without scattering team-spawn checks throughout the implementation loop).

- **R9.** Red-lane never spawns a team. Red-lane tasks always pick a single specialised agent regardless of `config.json.teams` configuration — multi-agent composition would defeat Red's "AI assists on bounded subtasks only" safety property.
  - Trace: interview Round 3 — *Red lane never spawns a team*.
  - Serves goal: Driving value (Red-lane safety properties are non-negotiable).

- **R10.** Gate 4 reviewer set. Gate 4 uses the same five-reviewer set as Gates 2 + 3 (Devil's Advocate + Simplicity, Surgical, Think-Before-Coding, Goal-Driven). Lens emphasis at Gate 4: Think-Before-Coding is load-bearing (the plan is where unstated implementation assumptions surface); Goal-Driven cross-checks the PRD anchor against the cited requirement ID; Surgical flags scope drift between the task's `Scope` field and the plan's listed file paths.
  - Trace: interview Round 4 — *Gate 4 uses the same five-reviewer set as Gates 2 + 3; Think-Before-Coding + Goal-Driven are load-bearing at this gate*.
  - Serves goal: Outcome (Gate 4 reuses Phase 1 reviewer infrastructure; consumers don't have to relearn lens-distinctness).

- **R11.** Codex is invoked at Gate 5 only, not at Gate 4. v1 ships with this hard-coded; consumers building agentic systems who want Gate-4 Codex review can request it as a v2 enhancement when the use case surfaces. Gate 4 is plan-level; Codex's strength is code-level review at Gate 5, and shipping the configurability knob in v1 without a documented consumer ask would be speculative configurability per the Simplicity First sub-clause.
  - Trace: interview Round 4 — *Codex's strength is code-level review at Gate 5*. Revised at Gate 2 per simplicity-r1-f1: dropped the proposed `config.json.develop.codexAtGate4` knob — speculative configurability without a documented consumer ask.
  - Serves goal: Outcome (Codex usage targeted at the gate where its lens is load-bearing, not scattered).

- **R12.** Gate 5 always fires; degraded path when Codex absent. Gate 5 reviews code against the plan and never skips. When Codex is present it joins as a sixth reviewer and is load-bearing for cross-provider review. When Codex is absent, the standard five-reviewer set runs Gate 5 with Goal-Driven Reviewer load-bearing (code-vs-plan acceptance is its lens). Devil's Advocate runs as part of the standard set, but cross-provider review is not available — the manifest note (below) is the authoritative framing of degraded coverage. The Gate 5 manifest's Codex section is replaced with a one-line note: *"Codex not detected — same-provider review only. Cross-provider findings may be missed; install Codex CLI for full Gate 5 coverage."*
  - Trace: interview Round 5 — *Gate 5 always fires (never skipped); standard five-reviewer set runs when Codex absent with explicit one-line manifest note declaring degraded coverage*. Rationale clarified at Gate 2 per tbc-r1-f2: same-provider DA cannot cover cross-provider concerns by definition; the manifest note is the truthful framing.
  - Serves goal: Driving value (Codex is the load-bearing reviewer when present; system behaves gracefully when absent without falsely advertising coverage).

- **R13.** Codex-only findings auto-promote via `misc-task`. Findings Codex catches at Gate 5 that the five other reviewers missed get auto-promoted to `admin/rules/guidelines.md` via a `misc-task` proposing the rule. The `misc-task` includes the finding's evidence + the proposed rule text + the Gate 5 manifest path. The human reviews and accepts the misc-task before the rule lands in `guidelines.md` — the skill never writes the rules file directly.
  - Trace: interview Round 5 — *Codex-only findings auto-promote via `misc-task` to `admin/rules/guidelines.md` (human reviews before rule lands)*.
  - Serves goal: Driving value (cross-provider catches reach the rules registry; Phase 3 self-evolution flow is honoured).

- **R14.** Linear status transitions. The skill drives three Linear transitions when Linear MCP is available: (a) Backlog/Todo → In Progress on manual invocation of a task that isn't already In Progress (fired before Step 1 context primer); (b) In Progress → In Review when the per-task PR opens (fired after Verifier confirms acceptance and the PR is opened); (c) NEVER auto-Done — that's a human merge decision. Auto-invocation from Linear UI ("In Progress" trigger) lands the skill at Step 1 of the same flow. When Linear MCP is absent, the skill prints the status update as a chat-only line and continues.
  - Trace: interview Round 6 — *skill drives three Linear transitions; never auto-Done; auto-invocation from Linear UI lands at Step 1; absent MCP → chat-only status line + continue*.
  - Serves goal: Outcome (Linear stays in sync with implementation state without a human babysitting status transitions).

- **R15.** Verifier rejection — structured failure payload + four user-elected options. When Verifier rejects a task on completion, the skill writes a structured failure payload to `admin/scratch/{orchestration-id}/verifier-failure-{task-id}.json` capturing (a) which AC failed, (b) what the verification check found, (c) the diff section the failure points to, (d) the agent that produced the diff. The skill then asks the user to pick from four options: (1) re-implement (loops back to Step 4 with the failure payload as additional context), (2) re-plan (loops back to Step 3 — re-fires Gate 4), (3) abort the task and surface to `specflow:scope-change`, (4) accept the failure and ship anyway (requires explicit confirmation, recorded as a `decision-log.md` entry). The skill never silently re-implements.
  - Trace: interview Round 7 — *Verifier rejection produces structured failure payload; user picks from four options; skill never auto-loops*.
  - Serves goal: Driving value (auto-loop-on-rejection is a known failure mode this skill exists to remove).

- **R16.** Orchestrator pattern compliance. Every sub-step (plan generation, each Gate 4 reviewer, agent execution, each Gate 5 reviewer, Verifier) runs in a forked sub-agent context. Verbatim file content is injected via command substitution (e.g. `!{cat features/NNN-{slug}/{NNN-slug}-prd.md}`) — not Read tool calls. Intermediate artefacts land in `admin/scratch/{orchestration-id}/`; only file paths return to the parent context. Target: parent context grows by ≤2K tokens per Gate manifest, ≤30K tokens for a 10-task feature end-to-end.
  - Trace: codebase context (pre-grilling) bullet — *Sister Phase 1 orchestrators are operational; orchestrator pattern is the must-read*. No grilling round was needed because the pattern is inherited from `templates/orchestrator-pattern.md` and pre-confirmed at the architectural level (`docs/PRD.md` § "Resolved decisions" line on orchestrator pattern).
  - Serves goal: Success-looks-like (artefacts co-located in `features/NNN-{slug}/`; downstream skills read the full chain without cross-folder chase).

- **R17.** Per-task plan's PRD-anchor format. Every per-task plan's first paragraph follows the format `"We're doing X because of PRD requirement Y. This aligns with Z."` where X paraphrases the task scope, Y is a literal `R{N}` from the feature's PRD, and Z paraphrases the requirement's `Serves goal:` field. Plans whose first paragraph doesn't match this format are a failed plan emission; Gate 4 must not be invoked until the format is satisfied.
  - Trace: codebase context (pre-grilling) bullet — *`docs/PRD.md` § Phase 2 scope item 7 architectural rule on dev plan ↔ PRD anchor*. Added at Gate 2 per goal-r1-f1 (block): the architectural rule needed R-level expression in this PRD body so AC-13 has a requirement to verify against (closing the orphan-AC gap).
  - Serves goal: Outcome (PRD-anchored plan commentary attached to every PR; stakeholders reviewing the PR see the PRD anchor without invoking the skill).

## Acceptance criteria

- **AC-1.** Running `specflow:develop {NNN-slug}` on a feature whose Gate 3 manifest closing decision is `passed` proceeds to Step 1 (context primer). Running on a feature with `failed` Gate 3 (or missing Gate 3 manifest) refuses with a clear message instructing the user to resolve Gate 3 first. (Verifies R1.)

- **AC-2.** Running `specflow:develop {NNN-slug}` (no `--task` flag) walks every Green-qualifying task whose dependencies are satisfied as a batch, then walks Yellow tasks one at a time, then surfaces Red tasks for human-led handling. Running `specflow:develop {NNN-slug} --task T{N}` runs exactly one task. (Verifies R2.)

- **AC-3.** Every per-task plan records the lane assignment with a four-line tuple: `verifiability: {high|medium|low} (cited: {scope file or acceptance line})`, `blast radius: {high|medium|low} (cited: {scope file or acceptance line})`, `dependency state: {satisfied|blocked} (cited: tasks file Depends-on field + task-history.json status)`, `confidentiality: {non-confidential|confidential} (cited: config.json.confidentialPaths match or no-match)`. (Verifies R3.)

- **AC-4.** When the four-axis tuple records ANY axis as Red-qualifying, the plan's lane field is `red`. When ANY axis is Red-qualifying AND another axis is Green-qualifying, the lane is still `red`. Confidentiality Red-qualification cannot be overridden — a confidential-path match always produces a Red lane regardless of other axes or user override mid-run. (Verifies R4.)

- **AC-5.** A Green batch's PR description summarises every per-task gate outcome (Gate 4 closing decision, Gate 5 closing decision, Verifier pass/fail) for every task in the batch, in task-ID order, and asks for a single human sign-off line. If any per-task gate failed, the batch is paused at that boundary, the partial PR description shows tasks completed up to and including the failing task, and the user is asked to pick from resume / abort / drop the failing task. The default green-batch cap (3) is applied unless `config.json.develop.greenBatchCap` overrides it. (Verifies R6, R7.)

- **AC-6.** When the agent-teams plugin is detected in `admin/environment.json.plugins` AND the task's lane is Green or Yellow AND the task's scope matches a `config.json.teams[].scope` glob, the implementation step's plan logs `team-spawn invoked: preset={preset-name}, members={member-list}`. When any of those conditions is false (or the lane is Red), the implementation step's plan logs `single-specialist invoked: agent={agent-name}, stack-match={glob}`. Red-lane tasks never log `team-spawn invoked` regardless of teams config. **Present-but-failing sub-clause:** when `team-spawn` returns an error, the plan logs `team-spawn failed: {error}; fell back to single-specialist invoked: agent={agent-name}` AND a chat-line warning is surfaced to the user. (Verifies R8, R9.)

- **AC-7.** Gate 4 manifest's `Reviewers:` line lists exactly the standard five (`devils-advocate, simplicity-reviewer, surgical-reviewer, think-before-coding-reviewer, goal-driven-reviewer`). Codex does not join Gate 4 in v1, regardless of `admin/environment.json.cli.codex.available`. (Verifies R10, R11.)

- **AC-8.** Lane-recheck verification — both paths fire correctly. **(a) Mechanical recheck (R5.1):** before Gate 4 opens, the skill writes a structured comparison file `admin/scratch/{orchestration-id}/lane-recheck-{task-id}.json` recording (i) plan's actual file count vs scope's claimed file count, (ii) plan's listed modules vs scope's modules, (iii) `config.json.confidentialPaths` glob match against the plan's listed file paths. If any axis downgrades, the file records the old → new lane AND the plan is re-emitted before Gate 4 opens. **(b) Reviewer-driven catch-all (R5):** when a Gate 4 round-1 finding has severity `block` AND the finding's `claim` field references the lane assignment as too aggressive AND the AI accepts in round-2, the Gate 4 manifest's closing decision records the re-lane (old → new) AND a fresh Gate 4 manifest is opened against the re-emitted plan before code is written. The first Gate 4 manifest's status is `re-lane forced`; the second manifest is the one that closes with `passed` or `failed`. (Verifies R5, R5.1.)

- **AC-9.** Gate 5 manifest exists for every task whose code change set landed (no skip path). When `admin/environment.json.cli.codex.available` is false, the Gate 5 manifest's `Codex` section contains the literal sentinel: *"Codex not detected — same-provider review only. Cross-provider findings may be missed; install Codex CLI for full Gate 5 coverage."* When Codex is available, the Codex section captures Codex's findings under a sub-heading. (Verifies R12.)

- **AC-10.** When Codex catches a Gate 5 finding that none of the standard five reviewers caught (finding ID present in Codex's round-1 file but no overlapping `claim` in any other reviewer's round-1 file), `specflow:develop` invokes `specflow:misc --auto` with a payload proposing a new rule for `admin/rules/guidelines.md`. The misc-task entry references the Gate 5 manifest path and the Codex finding ID. The skill does NOT write `guidelines.md` directly. **Schema dependency:** AC-10 depends on `specflow:misc --auto` accepting `manifest_path` and `gate_finding_id` as named fields. If the current Phase 1 schema (per `skills/misc/SKILL.md`) does not include these, ship them via a separate `specflow:misc` enhancement PRD before `specflow:develop` v1 lands. (Verifies R13.)

- **AC-11.** When Linear MCP is available per `admin/environment.json.mcp.linear.available`, the skill fires a Linear status transition to "In Progress" before Step 1 (if the task isn't already In Progress) and to "In Review" after Step 6 + PR creation. The skill never fires a transition to "Done". When Linear MCP is unavailable, the skill prints a chat line (e.g. `[linear status: T3 → In Progress (skipped — MCP not available)]`) and continues. (Verifies R14.)

- **AC-12.** When Verifier rejects a task, the skill writes `admin/scratch/{orchestration-id}/verifier-failure-{task-id}.json` with the four required fields (failed AC, verification check finding, diff section, agent name) before surfacing options to the user. The user must pick exactly one of the four options (re-implement, re-plan, abort-to-scope-change, accept-and-ship); option 4 records a `decision-log.md` entry capturing the AC, the failure summary, and the user's stated reason for shipping. The skill must not proceed without an explicit user choice. (Verifies R15.)

- **AC-13.** Every per-task plan's first paragraph follows the format `"We're doing X because of PRD requirement Y. This aligns with Z."` where X paraphrases the task scope, Y is a literal `R{N}` from the feature's PRD, and Z paraphrases the requirement's `Serves goal:` field. Plans whose first paragraph doesn't match this format are a failed plan emission; Gate 4 must not be invoked until the format is satisfied. (Verifies R17.)

- **AC-14.** End-to-end on a 10-task feature with the agent-teams plugin and Codex CLI both available, parent-context token consumption stays under 30K tokens (per the orchestrator-pattern target).
